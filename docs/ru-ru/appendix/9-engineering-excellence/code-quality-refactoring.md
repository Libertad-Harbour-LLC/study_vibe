# Качество кода и рефакторинг

::: tip Введение
**Достаточно ли, чтобы код просто работал?** Возможно, вы писали такой код: функциональность реализована, но через две недели вы сами уже не можете в нём разобраться. Или из команды уходит человек, оставляя кучу кода, который «понимают только он и Бог».

Эта глава поможет вам понять, что такое хороший код, как распознавать плохой код и как безопасно его улучшать.
:::

## 0. Общая картина: жизненный цикл кода

В разработке ПО есть часто игнорируемый факт: **код читают гораздо чаще, чем пишут**.

От рождения до вывода из эксплуатации фрагмент кода в общих чертах проходит такой путь:

::: tip Жизнь кода
- **Этап написания**: разработчик пишет первую версию реализации, функциональность заработала, тесты прошли.
- **Этап ревью**: участники команды читают код и предлагают улучшения.
- **Этап сопровождения**: исправление багов, добавление функций, адаптация под новые требования — этот этап занимает более 80% жизненного цикла кода.
- **Этап рефакторинга**: когда код становится трудно сопровождать, нужно улучшить его внутреннюю структуру, не меняя внешнего поведения.
- **Этап вывода из эксплуатации**: технологии развиваются, старый код заменяется новыми решениями.
:::

Мартин Фаулер в книге «Рефакторинг» сказал: **«Любой дурак может написать код, понятный компьютеру. Только хороший программист может написать код, понятный человеку.»**

## 1. Запахи кода: распознавание типичных проблем

### 1.1 Что такое запах кода?

Понятие «запах кода» (Code Smell) ввёл Кент Бек. Оно обозначает такие особенности кода, которые **хотя и не являются багами, но намекают на более глубокие проблемы проектирования**. Это как странный запах в комнате — он не делает вас больным сразу, но говорит о том, что где-то нужно прибраться.

### 1.2 Список распространённых запахов

| Запах | Симптом | Вред |
|-------|------|------|
| **Слишком длинная функция** | Функция превышает 50 строк | Сложно понять, тестировать и переиспользовать |
| **Магические числа** | В коде напрямую написано `86400000` | Смысл неясен, легко упустить при изменении |
| **Дублирование кода** | Похожая логика встречается в нескольких местах | При изменении нужно синхронизировать многие места, легко что-то упустить |
| **Слишком глубокая вложенность** | Более 3 уровней if/for | Логика как лабиринт, трудно проследить |
| **Слишком длинный список параметров** | У функции более 4 параметров | Сложно вызывать, легко перепутать порядок |
| **Класс-бог** | Один класс/модуль делает слишком много | Ответственность размыта, любое изменение задевает всё |

::: tip Ключевое понимание
Запах кода — это не «ошибка», а «сигнал». Он говорит вам: возможно, проектирование здесь нуждается в улучшении. Не все запахи нужно немедленно устранять, но вы должны уметь их распознавать.
:::

## 2. Приёмы рефакторинга: безопасное улучшение кода

### 2.1 Что такое рефакторинг?

Определение рефакторинга (Refactoring) очень точное: **улучшение внутренней структуры кода без изменения его внешнего поведения.**

Ключевые слова — «без изменения внешнего поведения». Рефакторинг — это не переписывание, не добавление функций, не исправление багов. Это «уборка и наведение порядка» внутри кода.

### 2.2 Распространённые приёмы рефакторинга

**Извлечение функции (Extract Function)**

Это самый часто используемый приём рефакторинга. Когда фрагмент кода можно описать одним осмысленным именем, его стоит извлечь в функцию.

```javascript
// До рефакторинга
function printReport(data) {
  // Вычисление общей суммы
  let total = 0
  for (const item of data.items) {
    total += item.price * item.qty
  }
  // Печать...
}

// После рефакторинга
function calculateTotal(items) {
  return items.reduce((sum, item) => sum + item.price * item.qty, 0)
}

function printReport(data) {
  const total = calculateTotal(data.items)
  // Печать...
}
```

**Переименование (Rename)**

Хорошее именование — это самая дешёвая и самая эффективная документация. Когда вам нужно писать комментарий, чтобы объяснить смысл переменной/функции, это значит, что её имя недостаточно хорошее.

```javascript
// До рефакторинга
const d = new Date() - startTime  // прошедшее время
const arr = users.filter(u => u.a) // активные пользователи

// После рефакторинга
const elapsedMs = new Date() - startTime
const activeUsers = users.filter(user => user.isActive)
```

**Замена вложенных условий охранными выражениями (Replace Nested Conditional with Guard Clauses)**

```javascript
// До рефакторинга
function getPayAmount(employee) {
  if (employee.isSeparated) {
    return { amount: 0 }
  } else {
    if (employee.isRetired) {
      return { amount: employee.pension }
    } else {
      return { amount: employee.salary }
    }
  }
}

// После рефакторинга
function getPayAmount(employee) {
  if (employee.isSeparated) return { amount: 0 }
  if (employee.isRetired) return { amount: employee.pension }
  return { amount: employee.salary }
}
```

::: tip Страховка при рефакторинге
Самый большой риск рефакторинга в том, что «менял-менял и доменялся до бага». Поэтому предпосылка рефакторинга — **наличие покрытия тестами**. После каждого маленького шага рефакторинга запускайте тесты, чтобы убедиться, что поведение не изменилось. Если код не покрыт тестами, сначала напишите тесты, а потом рефакторите.
:::

## 3. Code review: контроль качества в командной работе

### 3.1 Зачем нужен code review?

Code review (ревью кода) — один из самых эффективных способов контроля качества в команде. Его ценность не только в обнаружении багов, но и в следующем:

- **Обмен знаниями**: участники команды знакомятся с кодом друг друга, снижая «фактор автобуса» (если кого-то собьёт автобус, сможет ли проект продолжаться?)
- **Единый стиль**: через ревью постепенно формируются стандарты кодирования команды
- **Раннее обнаружение проблем проектирования**: плохие архитектурные решения исправить сложнее, чем баги
- **Взаимное обучение**: чтение чужого кода — короткий путь к росту навыков программирования

### 3.2 Что проверять?

| Измерение | На что обращать внимание |
|------|--------|
| **Корректность** | Правильна ли логика? Обработаны ли граничные условия? |
| **Читаемость** | Ясны ли имена? Понятна ли структура? |
| **Безопасность** | Есть ли риск инъекций? Не раскрываются ли чувствительные данные? |
| **Производительность** | Есть ли очевидные проблемы производительности? Запросы N+1? |
| **Тесты** | Есть ли соответствующие тесты? Покрыты ли ключевые пути? |

### 3.3 Этикет ревью

Хороший code review — это **обсуждение кода, а не критика человека**:

- Используйте «мы», а не «ты»: ~~«ты тут написал неправильно»~~ → «здесь мы можем рассмотреть использование guard clause»
- Задавайте вопросы, а не приказывайте: ~~«измени на const»~~ → «эта переменная будет переприсвоена позже? Если нет, безопаснее использовать const»
- Объясняйте причину: не просто «плохо», а «почему плохо» и «как лучше»

## 4. Метрики качества кода

### 4.1 Цикломатическая сложность

Цикломатическая сложность (Cyclomatic Complexity) измеряет количество независимых путей в коде. Каждый `if`, `for`, `case`, `&&`, `||` увеличивает сложность.

| Сложность | Оценка | Рекомендация |
|--------|------|------|
| 1-10 | Простой | Легко понять и тестировать |
| 11-20 | Средний | Стоит рассмотреть разделение |
| 21-50 | Сложный | Необходим рефакторинг |
| 50+ | Несопровождаемый | Срочный рефакторинг |

### 4.2 Покрытие кода

Покрытие кода измеряет, какую долю кода выполняют тесты. Распространённые показатели:

- **Покрытие строк**: доля выполненных строк кода от общего числа строк
- **Покрытие ветвей**: доля выполненных условных ветвей от общего числа ветвей

::: tip Ловушка покрытия
80% покрытия не означает, что код хорош. Покрытие может сказать вам только, «какой код не протестирован», но не может сказать, «осмысленны ли тесты». Тест, который лишь утверждает `expect(true).toBe(true)`, повышает покрытие, но не имеет никакой ценности.
:::

### 4.3 Полезные инструменты

| Инструмент | Назначение |
|------|------|
| **ESLint** | Статический анализ JavaScript/TypeScript |
| **Prettier** | Форматирование кода, единый стиль |
| **SonarQube** | Комплексная платформа качества кода |
| **Husky** | Git hooks, автоматическая проверка перед коммитом |

## 5. Помощь ИИ: повышение качества кода с помощью больших моделей

Большие модели уже очень практичны в области качества кода — они могут выступать в роли вашего «круглосуточно доступного ревьюера кода».

### 5.1 Распознавание запахов кода

> **Промпт**:
> ```
> Проверь следующий код, выяви запахи кода (Code Smell), включая, но не ограничиваясь:
> слишком длинные функции, магические числа, дублирование кода, слишком глубокая вложенность, слишком длинный список параметров.
> Для каждой проблемы укажи конкретное место, описание проблемы и рекомендацию по улучшению.
>
> [вставьте свой код]
> ```

### 5.2 Автоматический рефакторинг

> **Промпт**:
> ```
> Проведи рефакторинг следующего кода со следующими требованиями:
> 1. Не менять внешнее поведение
> 2. Использовать такие приёмы, как извлечение функции, замена вложенности охранными выражениями
> 3. Улучшить именование, устранить магические числа
> 4. Объяснить причину каждого шага рефакторинга
>
> [вставьте свой код]
> ```

### 5.3 Имитация Code Review

> **Промпт**:
> ```
> Проверь этот код с точки зрения опытного разработчика и дай обратную связь по следующим измерениям:
> - Корректность: есть ли баги в логике? Обработаны ли граничные условия?
> - Читаемость: ясны ли имена? Понятна ли структура?
> - Производительность: есть ли очевидные проблемы производительности?
> - Безопасность: есть ли риск инъекций или утечки данных?
> Используй тон «рекомендации», а не «приказа», и предложи варианты улучшения.
>
> [вставьте свой код]
> ```

::: tip Рекомендации по использованию ИИ
Рекомендации ИИ по рефакторингу нужно проверять самостоятельно — запускайте тесты, чтобы убедиться, что поведение не изменилось. Относитесь к ИИ как к «коллеге, предлагающему идеи», а не как к «безоговорочно доверяемому авторитету».
:::

## 6. Заключение

Оглядываясь на этот путь, мы прошли от распознавания проблем до их решения и выстроили целостную систему улучшения качества кода:

1. **Распознавание**: научиться чувствовать запах кода и знать, где нужно улучшение
2. **Рефакторинг**: освоить безопасные приёмы рефакторинга, улучшать маленькими шагами под защитой тестов
3. **Сотрудничество**: через code review команда сообща оберегает качество кода
4. **Измерение**: отслеживать здоровье кода объективными показателями

::: tip Финальное размышление
Качество кода — это не разовая работа, а постоянная привычка. Это как поддержание порядка в комнате — не ждать, пока станет совсем грязно, чтобы устроить генеральную уборку, а каждый день прибираться мимоходом. **Правило бойскаута** хорошо это выражает: уходя, оставь код чуть чище, чем он был, когда ты пришёл.
:::
