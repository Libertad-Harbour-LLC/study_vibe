# Паттерны проектирования

::: tip Введение
**Почему ваш код всегда «работает, но в нём бардак»?** Возможно, вы сталкивались с такой ситуацией: чуть изменилось требование — и код приходится сильно переделывать; хочется переиспользовать кусок логики, но он переплетён с другим кодом. Паттерны проектирования — это «приёмы организации кода», обобщённые предшественниками, которые помогают писать гибкий и сопровождаемый код.

Эта глава поможет вам понять самые практичные паттерны проектирования — не зубрить, а понимать, «в какой ситуации какой приём применять».
:::

**Чему вас научит эта статья?**

## 0. Общая картина: суть паттернов проектирования

Представьте, что вы учитесь готовить. Вы можете каждый раз нащупывать путь с нуля, а можете изучать классические рецепты — рецепт не ограничивает вашу креативность, а наоборот, позволяет вам встать на плечи предшественников. Паттерны проектирования — это «классические рецепты» мира программирования.

::: tip Ценность паттернов проектирования
- **Общий язык**: сказав «здесь используется паттерн наблюдатель», команда мгновенно понимает ваш замысел проектирования
- **Переиспользование опыта**: не нужно заново наступать на грабли, на которые наступали предшественники
- **Гибкое расширение**: хороший паттерн позволяет коду при изменениях требовать лишь небольших правок, а не больших переделок
:::

## 1. Порождающие паттерны: как изящно создавать объекты

### 1.1 Одиночка (Singleton)

**Сценарий**: глобально нужен только один экземпляр, например менеджер конфигурации, логгер, пул соединений с базой данных.

```javascript
class ConfigManager {
  static instance = null

  static getInstance() {
    if (!ConfigManager.instance) {
      ConfigManager.instance = new ConfigManager()
    }
    return ConfigManager.instance
  }

  constructor() {
    this.config = {}
  }
}

// Сколько бы раз ни вызывали — это один и тот же экземпляр
const a = ConfigManager.getInstance()
const b = ConfigManager.getInstance()
console.log(a === b) // true
```

### 1.2 Фабрика (Factory)

**Сценарий**: создание объектов разных типов в зависимости от различных условий, причём вызывающей стороне не нужно знать конкретных деталей создания.

```javascript
function createNotification(type, message) {
  switch (type) {
    case 'email':
      return { send: () => console.log(`Отправка письма: ${message}`) }
    case 'sms':
      return { send: () => console.log(`Отправка SMS: ${message}`) }
    case 'push':
      return { send: () => console.log(`Push-уведомление: ${message}`) }
    default:
      throw new Error(`Неизвестный тип уведомления: ${type}`)
  }
}

// Вызывающую сторону не волнует конкретная реализация
const notification = createNotification('email', 'Привет')
notification.send()
```

## 2. Структурные паттерны: как организовать структуру кода

### 2.1 Адаптер (Adapter)

**Сценарий**: два интерфейса несовместимы, нужен «переходник». Например, формат данных, возвращаемых старым API, не совпадает с форматом, ожидаемым новым компонентом.

```javascript
// Формат, возвращаемый старым API
const oldApi = {
  getUserInfo: () => ({ user_name: 'Иван', user_age: 25 })
}

// Адаптер: преобразование в новый формат
function adaptUser(oldUser) {
  return { name: oldUser.user_name, age: oldUser.user_age }
}

const user = adaptUser(oldApi.getUserInfo())
// { name: 'Иван', age: 25 }
```

### 2.2 Декоратор (Decorator)

**Сценарий**: добавление объекту новых возможностей без изменения исходного кода. Как чехол для телефона — функции телефона не меняются, но добавляется защита.

```javascript
// Базовая функция логирования
function log(message) {
  console.log(message)
}

// Декоратор: добавление временной метки
function withTimestamp(fn) {
  return (message) => fn(`[${new Date().toISOString()}] ${message}`)
}

// Декоратор: добавление уровня логирования
function withLevel(fn, level) {
  return (message) => fn(`[${level}] ${message}`)
}

const enhancedLog = withTimestamp(withLevel(log, 'INFO'))
enhancedLog('Сервис успешно запущен')
// [2025-01-15T10:30:00.000Z] [INFO] Сервис успешно запущен
```

## 3. Поведенческие паттерны: как управлять взаимодействием объектов

### 3.1 Наблюдатель (Observer)

**Сценарий**: при изменении состояния одного объекта нужно автоматически уведомить другие объекты. Например, после оформления заказа пользователем нужно одновременно отправить письмо, списать товар со склада и записать лог.

```javascript
class EventEmitter {
  constructor() {
    this.listeners = {}
  }

  on(event, callback) {
    if (!this.listeners[event]) this.listeners[event] = []
    this.listeners[event].push(callback)
  }

  emit(event, data) {
    (this.listeners[event] || []).forEach(cb => cb(data))
  }
}

const bus = new EventEmitter()
bus.on('order:created', (order) => console.log('Отправка письма-подтверждения', order.id))
bus.on('order:created', (order) => console.log('Списание со склада', order.id))
bus.emit('order:created', { id: 'ORD-001' })
```

### 3.2 Стратегия (Strategy)

**Сценарий**: у одной и той же операции есть несколько алгоритмов/стратегий, между которыми нужно переключаться во время выполнения. Например, разные способы сортировки, разные правила расчёта цены.

```javascript
const pricingStrategies = {
  normal: (price) => price,
  vip: (price) => price * 0.8,
  svip: (price) => price * 0.6
}

function calculatePrice(price, memberLevel) {
  const strategy = pricingStrategies[memberLevel] || pricingStrategies.normal
  return strategy(price)
}

calculatePrice(100, 'vip')  // 80
calculatePrice(100, 'svip') // 60
```

## 4. Как выбрать паттерн проектирования?

| Проблема, с которой вы столкнулись | Рекомендуемый паттерн | Ключевая идея |
|-------------|---------|---------|
| Глобально нужен только один экземпляр | Одиночка | Контроль количества экземпляров |
| Создание разных объектов в зависимости от условий | Фабрика | Инкапсуляция логики создания |
| Несовместимые интерфейсы, нужно преобразование | Адаптер | Обёртка-преобразователь |
| Динамическое добавление функций | Декоратор | Послойное обёртывание-усиление |
| При изменении состояния нужно уведомить многих | Наблюдатель | Развязка через публикацию-подписку |
| Несколько алгоритмов с переключением во время выполнения | Стратегия | Инкапсуляция алгоритма в объект |

::: tip Ключевой принцип
Паттернов проектирования не должно быть чем больше, тем лучше. **Избыточное проектирование** так же плохо, как и **отсутствие проектирования**. Используйте паттерны только там, где действительно нужна гибкость, а для простых задач — простые решения. Помните принцип KISS: Keep It Simple, Stupid.
:::

## 5. Помощь ИИ: изучение и применение паттернов проектирования с большими моделями

Большие модели могут помочь вам распознать в коде сценарии, подходящие для применения паттернов проектирования, и предложить конкретные варианты рефакторинга.

### 5.1 Распознавание подходящих паттернов

> **Промпт**:
> ```
> Проанализируй следующий код и определи, есть ли места, которые можно улучшить с помощью паттернов проектирования.
> Если есть, поясни:
> 1. Проблема текущего кода
> 2. Какой паттерн проектирования рекомендуется использовать
> 3. Пример кода после рефакторинга
> 4. Почему этот паттерн подходит для данного сценария
>
> [вставьте свой код]
> ```

### 5.2 Изучение паттернов на конкретных сценариях

> **Промпт**:
> ```
> На реальном сценарии «система заказа еды на доставку» продемонстрируй по отдельности применение следующих паттернов проектирования:
> - Фабрика: создание заказов разных типов
> - Наблюдатель: уведомление об изменении статуса заказа
> - Стратегия: разные правила расчёта стоимости доставки
>
> Используй примеры кода на JavaScript: для каждого паттерна сначала покажи проблему без паттерна,
> затем покажи улучшение после применения паттерна.
> ```

### 5.3 Оценка избыточного проектирования

> **Промпт**:
> ```
> Проверь следующий код и определи, есть ли проблема избыточного проектирования.
> Есть ли ненужные абстракции, неиспользуемые паттерны проектирования или преждевременная оптимизация?
> Если есть, предложи, как упростить, следуя принципу KISS.
>
> [вставьте свой код]
> ```

::: tip Рекомендации по использованию ИИ
Попросить ИИ объяснить паттерны проектирования на знакомом вам бизнес-сценарии гораздо эффективнее, чем смотреть на абстрактные UML-диаграммы. Но помните: ИИ может склоняться к рекомендации более сложных решений, и вам нужно самим оценивать, действительно ли это нужно.
:::

## 6. Заключение

1. **Порождающие паттерны**: решают проблему «как создавать объекты», делая процесс создания более гибким
2. **Структурные паттерны**: решают проблему «как организовать код», делая структуру более ясной
3. **Поведенческие паттерны**: решают проблему «как объекты взаимодействуют», делая сотрудничество более слабосвязанным
4. **Гибкое применение**: выбирайте в зависимости от реального сценария, не используйте паттерн ради паттерна

::: tip Финальное размышление
Суть паттернов проектирования — **управление изменениями**. Хорошее проектирование делает изменяемые части легко модифицируемыми, а неизменные части — стабильными. Когда вы пишете код, спросите себя: «Если требование изменится, сколько мест мне придётся менять?» — если ответ «много мест», возможно, вам нужен паттерн проектирования, чтобы помочь.
:::
