# Написание технической документации

::: tip Введение
**Кто-нибудь читает написанную вами документацию?** Многие разработчики думают: «Главное, чтобы код работал, а документацию напишем потом». В итоге: новичок при онбординге не может разобраться в проекте, интеграция API держится исключительно на устном общении, а через полгода вы и сами забываете, почему спроектировали именно так.

Эта глава поможет вам освоить ключевые методы написания технической документации, чтобы вашу документацию действительно читали, понимали и использовали.
:::

**Чему вас научит эта статья?**

| Раздел | Содержание | Ключевые понятия |
|-----|------|---------|
| **Глава 1** | Типы и структура документации | Как писать разные документы |

После изучения этой главы вы сможете писать техническую документацию с ясной структурой, точным содержанием и лёгкую в сопровождении.

## 0. Общая картина: почему техническая документация важна?

Код говорит компьютеру «как делать», документация говорит человеку «почему именно так». Проект без документации — как электроприбор без инструкции: пользоваться можно, но всё на угадай.

::: tip Ценность хорошей документации
- **Снижение затрат на коммуникацию**: новички осваиваются сами, меньше повторяющихся ответов
- **Сохранение контекста решений**: фиксирует «почему», а не только «что»
- **Повышение доверия к проекту**: хорошая документация — лицо open source-проекта
- **Ускорение совместной работы**: документация API позволяет фронтенду и бэкенду разрабатывать параллельно
:::

### 1.1 Распространённые типы документов

| Тип документа | Целевой читатель | Ключевое содержание |
|---------|---------|---------|
| **README** | Все | Что за проект, как пользоваться, как вносить вклад |
| **Документация API** | Те, кто вызывает интерфейсы | Эндпоинты, параметры, ответы, коды ошибок |
| **Архитектурная документация** | Команда разработки | Дизайн системы, выбор технологий, поток данных |
| **Журнал изменений** | Пользователи/разработчики | Изменения версий, добавления/исправления/ломающие изменения |
| **Руководство по вкладу** | Контрибьюторы | Окружение разработки, стандарты кода, процесс PR |

### 1.2 Золотая структура README

Хороший README должен содержать:

1. **Название проекта + описание в одну фразу**: чтобы за 3 секунды было понятно, что это
2. **Быстрый старт**: запуск минимальным числом шагов
3. **Возможности и особенности**: ключевые преимущества
4. **Способ установки**: подробные требования к окружению и шаги установки
5. **Примеры использования**: код, который можно скопировать
6. **Руководство по вкладу**: как участвовать
7. **Лицензия**: юридическая информация

## 2. Принципы написания

### 2.1 Ясность прежде всего

```markdown
<!-- Плохо: расплывчато -->
Эта функция обрабатывает данные.

<!-- Хорошо: конкретно и чётко -->
Преобразует исходные данные заказа в формат счёта, включая расчёт налогов и конвертацию валют.
```

### 2.2 Ориентация на читателя

Перед написанием документации спросите себя: **кто будет её читать? Какая информация им нужна?**

- Для новичков: объясняйте термины, давайте полные примеры
- Для опытных разработчиков: сразу к сути, давайте справку по API
- Для нетехнических людей: используйте аналогии, избегайте терминов

### 2.3 Примеры кода — лучшая документация

```markdown
<!-- Плохо: только текстовое описание -->
Вызовите функцию createUser, передав параметры имя пользователя и email.

<!-- Хорошо: приведён работающий пример -->
const user = await createUser({
  name: 'Иван',
  email: 'ivan@example.com'
})
// Возвращает: { id: 'u_123', name: 'Иван', createdAt: '2025-01-15' }
```

С помощью интерактивного компонента ниже сравните хорошее и плохое техническое письмо:

<TechWritingPracticeDemo />

### 3.1 Стандарты сообщения коммита

```
# Плохо
fix bug
update code

# Хорошо (Conventional Commits)
fix: исправлен белый экран на странице входа в Safari
feat: поддержка массового экспорта отчётов в формате PDF
docs: обновлены примеры кода в разделе аутентификации API
```

### 3.2 Искусство комментариев

```javascript
// Плохо: описывает «что» (код это и так говорит)
// перебор массива
for (const item of items) { ... }

// Хорошо: объясняет «почему»
// обход в обратном порядке, потому что при удалении элемента прямой порядок пропускает следующий
for (let i = items.length - 1; i >= 0; i--) { ... }
```

## 4. Сопровождение документации

### 4.1 Документация как код

Храните документацию и код в одном репозитории и управляйте ими одним и тем же рабочим процессом:

- Изменения документации отправляются в PR вместе с кодом
- CI проверяет формат документации и валидность ссылок
- При выпуске версии документация обновляется синхронно

### 4.2 Как избежать гниения документации

| Проблема | Решение |
|------|---------|
| Документация устарела | Принудительно обновлять документацию при изменении кода (проверка в PR) |
| Никто не сопровождает | Назначить ответственного за документацию |
| Дублирование содержания | Единый источник информации, в других местах — ссылки |

## 5. Помощь ИИ: повышение качества документации с помощью больших моделей

Большие модели в области технического письма почти «одарены от природы» — генерация документации, улучшение формулировок, перевод содержания являются их сильными сторонами.

### 5.1 Генерация документации API

> **Промпт**:
> ```
> На основе следующего кода маршрутов Express сгенерируй полную документацию API, включающую:
> - путь эндпоинта и метод
> - параметры запроса (параметры пути, query-параметры, тело запроса) и их типы
> - примеры успешного и ошибочного ответов
> - пример вызова с помощью curl
>
> [вставьте свой код маршрутов]
> ```

### 5.2 Улучшение технического письма

> **Промпт**:
> ```
> Улучши формулировки следующей технической документации с требованиями:
> 1. Язык лаконичный и ясный, убрать избыточные обороты
> 2. Использовать активный залог вместо пассивного
> 3. Сохранить точность профессиональных терминов
> 4. Добавить необходимые примеры кода
> Сохрани исходный смысл, улучши только качество изложения.
>
> [вставьте содержание вашей документации]
> ```

### 5.3 Генерация README

> **Промпт**:
> ```
> На основе следующей информации о проекте сгенерируй качественный README.md:
> - Название проекта: [название]
> - Описание в одну фразу: [описание]
> - Стек технологий: [перечислить]
> - Ключевые функции: [перечислить]
>
> Требуется включить: описание проекта, быстрый старт, возможности,
> шаги установки (с кодом), примеры использования, руководство по вкладу, лицензию.
> ```

::: tip Рекомендации по использованию ИИ
В сгенерированной ИИ документации нужно проверять точность технических деталей — он может выдумать несуществующие параметры API или неверные возвращаемые значения. Всегда сверяйтесь с реальным кодом.
:::

## 6. Заключение

1. **Соответствие типу**: у разных документов разная структура и манера написания
2. **Ясность прежде всего**: конкретно, точно, ориентируясь на читателя
3. **Управление через примеры**: хороший пример кода стоит тысячи слов
4. **Постоянное сопровождение**: документация как код, развивается вместе с проектом

::: tip Финальное размышление
Писать документацию — не пустая трата времени, а **экономия будущего времени**. Документация, на которую вы сегодня потратили 30 минут, может сэкономить по часу каждому из 10 человек. Хорошая документация — лучшая инвестиция в команду.
:::
