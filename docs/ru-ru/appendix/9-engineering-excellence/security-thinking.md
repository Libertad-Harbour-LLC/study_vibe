# Мышление в терминах безопасности и основы атаки и защиты

::: tip Введение
**Безопасен ли ваш сайт?** Многие разработчики думают, что «безопасность — дело команды безопасности», пока их собственный проект не атакуют, а данные пользователей не утекут. Безопасность — это не опция, а базовый навык каждого разработчика.

Эта глава поможет вам выработать мышление в терминах безопасности и понять самые распространённые угрозы веб-безопасности и методы защиты.
:::

После изучения этой главы вы обретёте базовое осознание безопасности и сможете распознавать и отражать самые распространённые угрозы веб-безопасности.

## 0. Общая картина: зачем разработчику понимать безопасность?

Представьте, что вы построили дом: со всеми удобствами, с красивой отделкой, но забыли поставить замок. Уязвимость безопасности — это и есть «забытый замок» в мире кода.

::: tip Ключевые принципы безопасности
- **Минимальные привилегии**: давайте только необходимые права, ни на каплю больше
- **Эшелонированная защита**: не полагайтесь на единственную линию обороны, выстраивайте защиту слоями
- **Никогда не доверяйте вводу**: любые данные извне могут оказаться вредоносными
- **Безопасно по умолчанию**: конфигурация по умолчанию должна быть безопасной, а не удобной
:::

<WebSecurityDemo />

### 1.1 XSS (межсайтовый скриптинг)

Атакующий внедряет вредоносный скрипт в веб-страницу, и когда её посещают другие пользователи, скрипт выполняется в их браузерах.

```javascript
// Опасно: напрямую вставлять пользовательский ввод в HTML
element.innerHTML = userInput
// Если userInput равен <script>вредоносный код</script>, он выполнится

// Безопасно: использовать textContent или экранирование
element.textContent = userInput
// Или использовать автоэкранирование фреймворка (Vue: {{ }}, React: JSX)
```

**Ключевые моменты защиты**:
- При выводе экранируйте специальные символы HTML (`<`, `>`, `&`, `"`, `'`)
- Используйте механизм автоэкранирования современных фреймворков
- Установите HTTP-заголовок `Content-Security-Policy`

### 1.2 SQL-инъекция

Атакующий с помощью специально сконструированного ввода изменяет логику SQL-запроса.

```javascript
// Опасно: склейка SQL из строк
const query = `SELECT * FROM users WHERE name = '${userInput}'`
// Если userInput равен ' OR '1'='1, вернутся все пользователи

// Безопасно: использовать параметризованные запросы
const query = 'SELECT * FROM users WHERE name = ?'
db.execute(query, [userInput])
```

**Ключевые моменты защиты**:
- Всегда используйте параметризованные запросы / подготовленные выражения
- Используйте ORM-фреймворки (например, Prisma, Sequelize)
- Ограничивайте права учётной записи базы данных

### 1.3 CSRF (межсайтовая подделка запроса)

Атакующий заманивает вошедшего пользователя на вредоносную страницу и, используя его состояние авторизации, отправляет запросы.

**Ключевые моменты защиты**:
- Используйте CSRF Token
- Проверяйте заголовки `Referer` / `Origin`
- Для критичных операций используйте POST, а не GET
- Устанавливайте у Cookie атрибут `SameSite`

## 2. Стратегии защиты

### 2.1 Валидация ввода

```javascript
// Валидация по белому списку: разрешать только ожидаемый формат
function isValidEmail(email) {
  return /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email)
}

// Ограничение длины
function isValidUsername(name) {
  return name.length >= 2 && name.length <= 50
}
```

### 2.2 Защита чувствительных данных

| Тип данных | Меры защиты |
|---------|---------|
| Пароли | Хеширование bcrypt/argon2, никогда не хранить в открытом виде |
| API-ключи | Переменные окружения, не коммитить в репозиторий |
| Данные пользователей | Передача по HTTPS, хранение в зашифрованном виде |
| Сессионные токены | Cookie с HttpOnly + Secure + SameSite |

### 2.3 Заголовки безопасности HTTP

```
Content-Security-Policy: default-src 'self'
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Strict-Transport-Security: max-age=31536000
```

### 3.1 Этап разработки

- [ ] Весь пользовательский ввод проходит валидацию и экранирование

- [ ] Включён HTTPS

- [ ] База данных использует учётную запись с минимальными привилегиями
- [ ] Регулярно обновляются зависимости (`npm audit`)

## 4. Помощь ИИ: усиление защиты с помощью больших моделей

Большие модели могут выступить в роли вашего «консультанта по безопасности» — помочь провести аудит уязвимостей в коде и сгенерировать решения по безопасности.

### 4.1 Аудит безопасности кода

> **Промпт**:
> ```
> Проведи аудит безопасности следующего кода, проверь, есть ли:
> - уязвимости XSS (неэкранированный пользовательский ввод)
> - SQL-инъекции (запросы со склейкой строк)
> - риски CSRF (отсутствие проверки Token)
> - утечки чувствительных данных (захардкоженные ключи, пароли в открытом виде)
> Для каждой проблемы укажи уровень риска, конкретное место и способ исправления.
>
> [вставьте свой код]
> ```

### 4.2 Генерация конфигурации безопасности

> **Промпт**:
> ```
> Мой проект использует Express.js + PostgreSQL и скоро будет развёрнут.
> Сгенерируй полный чек-лист конфигурации безопасности, включающий:
> - код настройки заголовков безопасности HTTP
> - конфигурацию CORS
> - настройки безопасности подключения к базе данных
> - схему управления переменными окружения
> Приведи готовые к использованию фрагменты кода.
> ```

### 4.3 Объяснение принципа уязвимости

> **Промпт**:
> ```
> На конкретном примере объясни полный процесс CSRF-атаки:
> 1. Как атакующий конструирует вредоносную страницу
> 2. Почему браузер автоматически добавляет Cookie
> 3. Как сервер защищается с помощью CSRF Token
> Продемонстрируй кодом полный процесс атаки и защиты.
> ```

::: tip Рекомендации по использованию ИИ
Аудит безопасности от ИИ не может заменить профессиональное тестирование безопасности. Воспринимайте его как первый этап отсева, но критичные системы всё равно требуют аудита профессиональной командой безопасности.
:::

## 5. Заключение

1. **Мышление о безопасности**: никогда не доверяйте внешнему вводу, минимальные привилегии, эшелонированная защита
2. **Распространённые атаки**: XSS, SQL-инъекция, CSRF — самые частые угрозы веб-безопасности
3. **Стратегии защиты**: валидация ввода, кодирование вывода, параметризованные запросы, заголовки безопасности HTTP
4. **Привычки безопасности**: перед запуском пройдитесь по чек-листу безопасности, регулярно проводите аудит зависимостей

::: tip Финальное размышление
Безопасность — это не разовая работа, а привычка, пронизывающая весь процесс разработки. Это как пристёгивать ремень в машине — не потому, что вы ожидаете аварию, а потому, что это базовое осознание безопасности. **Когда пишете каждую строку кода, спрашивайте себя: что произойдёт, если этот ввод окажется вредоносным?**
:::
