# Методология выбора технологий

::: tip Введение
**React или Vue? MySQL или PostgreSQL?** Выбор технологий — одно из важнейших решений в начале любого проекта. Ошибётесь — возможно, придётся потратить несколько месяцев на переписывание; выберете правильно — эффективность команды удвоится.

Эта глава поможет вам выработать системное мышление при выборе технологий, чтобы больше не выбирать технологии «на ощущениях».
:::

## 0. Общая картина: суть выбора технологий

Выбор технологий — это не вопрос «какая технология лучшая», а вопрос «какая технология лучше всего подходит к текущей ситуации». Это как выбор транспорта: самолёт самый быстрый, но чтобы добраться до соседнего двора, лететь на самолёте не нужно.

::: tip Ключевые принципы выбора
- **Серебряной пули нет**: ни одна технология не подходит для всех сценариев
- **Управляется сценарием**: сначала определите потребности, потом выбирайте технологию
- **Команда прежде всего**: технология, знакомая команде, зачастую и есть лучший выбор
- **Обратимость**: отдавайте предпочтение решениям, которые легко заменить
:::

## 1. Измерения выбора

### 1.1 Ключевые измерения оценки

| Измерение | На что обращать внимание | Рекомендуемый вес |
|------|--------|---------|
| **Возможности команды** | Знакома ли команде технология? Насколько высоки затраты на обучение? | Высокий |
| **Сообщество и экосистема** | Качество документации, сторонние библиотеки, число ответов на Stack Overflow | Высокий |
| **Требования к производительности** | Удовлетворяет ли требованиям по производительности? | Средний-высокий |
| **Состояние сопровождения** | Активно ли сопровождается? Когда был последний релиз? | Средний |
| **Лицензия** | Совместима ли с бизнес-моделью проекта? | Средний |
| **Рынок найма** | Можно ли нанять людей, знакомых с этой технологией? | Средний |

### 1.2 Практический кейс: выбор фронтенд-фреймворка

```
Проект: внутренняя система управления для предприятия
Команда: 5 человек, 3 знакомы с Vue, 1 знаком с React, 1 новичок
Требования: много форм, сложные права, SEO не нужен

Анализ:
- 60% команды знакомы с Vue → приоритет Vue
- Много форм → зрелая экосистема Element Plus
- SSR не нужен → не нужны Next.js/Nuxt
- Вывод: Vue 3 + Element Plus
```

## 2. Матрица решений

Когда несколько вариантов сложно оценить интуитивно, используйте матрицу решений для количественного сравнения.

С помощью интерактивного компонента ниже опробуйте метод использования матрицы решений:

<DecisionMatrixDemo />

### 2.1 Как использовать матрицу решений

1. **Перечислите кандидатов**: например, React vs Vue vs Svelte
2. **Определите измерения оценки**: возможности команды, экосистема, производительность, кривая обучения
3. **Распределите веса**: исходя из потребностей проекта, задайте каждому измерению вес (в сумме 100%)
4. **Оцените по пунктам**: каждому варианту по каждому измерению поставьте от 1 до 5 баллов
5. **Взвешенная сумма**: получите итоговую оценку

### 2.2 Пример

| Измерение | Вес | React | Vue | Svelte |
|------|------|-------|-----|--------|
| Возможности команды | 30% | 3 | 5 | 1 |
| Сообщество и экосистема | 25% | 5 | 4 | 2 |
| Кривая обучения | 20% | 3 | 4 | 5 |
| Производительность | 15% | 4 | 4 | 5 |
| Рынок найма | 10% | 5 | 4 | 2 |
| **Взвешенная сумма** | | **3.75** | **4.35** | **2.75** |

## 3. Распространённые ловушки

### 3.1 Разработка ради резюме

> «Используем эту новую технологию — и в резюме можно будет дописать ещё строчку»

Выбор технологии должен основываться на потребностях проекта, а не на личном резюме. Новая технология означает больше неизвестных рисков и меньше поддержки сообщества.

### 3.2 Слепая погоня за новинками

| Установка | Реальность |
|------|------|
| «Новое обязательно лучше старого» | В новой технологии могут быть необнаруженные баги |
| «Крупные компании используют — и нам надо» | Сценарии крупных компаний могут совершенно отличаться от ваших |
| «У этой технологии больше всего Star» | Число Star не равно пригодности для вашего проекта |

### 3.3 Игнорирование стоимости миграции

При выборе нужно смотреть не только на то, «как с этим работать», но и на то, «во сколько обойдётся замена, если придётся менять». Отдавайте предпочтение:
- решениям, следующим стандартным протоколам (например, SQL vs проприетарный язык запросов)
- решениям с чётким путём миграции
- решениям без глубокого вендорлока

## 4. Помощь ИИ: содействие выбору технологий с помощью больших моделей

Большие модели помогут быстро исследовать технические решения, сравнить их плюсы и минусы, сгенерировать отчёт по принятию решения.

### 4.1 Сравнение технических решений

> **Промпт**:
> ```
> Мне нужно выбрать базу данных для проекта электронной коммерции, кандидаты:
> MySQL, PostgreSQL, MongoDB.
> Особенности проекта: много чтения и мало записи, нужны сложные запросы, объём данных ожидается порядка десятков миллионов.
>
> Сравни три варианта по следующим измерениям:
> производительность, экосистема, кривая обучения, затраты на эксплуатацию, масштабируемость.
> Представь в виде таблицы и дай итоговую рекомендацию с обоснованием.
> ```

### 4.2 Генерация записи об архитектурном решении (ADR)

> **Промпт**:
> ```
> Помоги написать запись об архитектурном решении (ADR) в следующем формате:
> - Заголовок: выбор Vue 3 в качестве фронтенд-фреймворка
> - Контекст: [контекст проекта и потребности]
> - Кандидаты: React, Vue 3, Svelte
> - Решение: Vue 3
> - Обоснование: [на основе возможностей команды, экосистемы, производительности и т. д.]
> - Последствия: [влияние и риски после выбора]
> ```

### 4.3 Исследование новой технологии

> **Промпт**:
> ```
> Я думаю, стоит ли внедрить в проекте Bun вместо Node.js. Помоги проанализировать:
> 1. Ключевые преимущества и недостатки Bun по сравнению с Node.js
> 2. Текущую зрелость экосистемы (совместимость с npm, поддержка популярных фреймворков)
> 3. Рисковые моменты при использовании в продакшене
> 4. Сценарии, в которых Bun подходит и не подходит
> Дай объективную оценку, не говори только о плюсах.
> ```

::: tip Рекомендации по использованию ИИ
Знания ИИ имеют срок актуальности — он может не знать об изменениях в новейших версиях. Для быстро развивающихся технологий после предварительного исследования с помощью ИИ обязательно сверяйтесь с официальной документацией, чтобы подтвердить самую свежую информацию.
:::

## 5. Заключение

1. **Технологический радар**: понимайте зрелость технологий, различайте принять/испытать/оценить/отложить
2. **Измерения выбора**: возможности команды > сообщество и экосистема > требования к производительности > состояние сопровождения
3. **Матрица решений**: количественное сравнение снижает субъективную предвзятость
4. **Избегайте ловушек**: не гонитесь за новинками, не следуйте за толпой, учитывайте стоимость миграции

::: tip Финальное размышление
Лучший выбор технологий зачастую — **самый скучный выбор**. Выбирайте зрелые, стабильные и знакомые команде технологии, а энергию для инноваций оставьте для самого бизнеса. Помните: **технология — это средство, а не цель. Пользователям не важно, какой фреймворк вы использовали, им важно лишь, удобен ли продукт.**
:::
