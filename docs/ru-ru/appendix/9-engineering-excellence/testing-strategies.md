# Стратегии тестирования

::: tip Введение
**Действительно ли с вашим кодом «всё в порядке»?** После каждого изменения вручную прокликать всё, чтобы проверить, не сломалось ли что-нибудь, — пока проект маленький, это ещё сойдёт, но когда объём кода вырастает до десятков тысяч строк, а команда расширяется до десятка человек, «прокликать вручную» превращается в катастрофу.

Эта глава поможет вам понять ключевые стратегии тестирования ПО — от пирамиды тестирования до TDD — и выработать системное мышление в обеспечении качества.
:::

## 0. Общая картина: зачем нужно автоматизированное тестирование?

Представьте, что вы инженер-строитель. После каждого изменения в чертежах вы не будете лично взбираться на каждый этаж, чтобы проверить, безопасна ли конструкция, — вы положитесь на **автоматизированную систему контроля**. Тестирование ПО и есть «система контроля конструкции» в мире кода.

::: tip Ценность автоматизированного тестирования
- **Защита от регрессий**: при изменении функции A автоматически проверяется, не затронуты ли функции B, C, D
- **Уверенность при рефакторинге**: код, покрытый тестами, можно рефакторить со спокойной душой
- **Живая документация**: хорошие тесты — лучшая инструкция по использованию
- **Быстрая обратная связь**: вы за секунды узнаёте, корректен ли код, а не обнаруживаете проблему уже после развёртывания
:::

## 1. Пирамида тестирования: уровни и пропорции тестов

### 1.1 Трёхуровневая пирамида

Пирамида тестирования, предложенная Майком Коном, — классическая модель стратегии тестирования. Она говорит нам: **тесты разных типов должны быть в разном количественном соотношении**.

### 1.2 Почему форма пирамиды?

Форма пирамиды отражает ключевой компромисс: **выбор между скоростью и реалистичностью**.

- **Нижний уровень (юнит-тесты)**: предельно быстрые, самые многочисленные, самые дешёвые, но проверяют лишь отдельную деталь
- **Средний уровень (интеграционные тесты)**: умеренная скорость, умеренное количество, проверяют взаимодействие деталей друг с другом
- **Верхний уровень (E2E-тесты)**: максимально близки к реальному пользователю, но медленные, дорогие в сопровождении, легко падают из-за проблем окружения

> **Антипаттерн: рожок мороженого** — если в вашем проекте больше всего E2E-тестов и меньше всего юнит-тестов, то это перевёрнутый «рожок мороженого». Это значит, что набор тестов работает медленно, часто падает и крайне дорог в сопровождении.

## 2. Юнит-тесты на практике

### 2.1 Что такое хороший юнит-тест?

Хороший юнит-тест следует принципу **FIRST**:

| Принцип | Значение | Описание |
|------|------|------|
| **F**ast | Быстрый | Выполняется за миллисекунды, разработчик готов запускать часто |
| **I**ndependent | Независимый | Тесты не зависят друг от друга, могут запускаться по отдельности |
| **R**epeatable | Воспроизводимый | Результат одинаков в любом окружении |
| **S**elf-validating | Самопроверяемый | Результат однозначен: пройдено/провалено, без участия человека |
| **T**imely | Своевременный | Тесты пишутся одновременно с кодом (или до него) |

### 2.2 Структура теста: паттерн AAA

Каждый тест должен иметь чёткую трёхчастную структуру:

```javascript
test('должен корректно вычислять цену с налогом', () => {
  // Arrange (подготовка) — установка тестовых данных
  const price = 100
  const taxRate = 0.13

  // Act (выполнение) — вызов тестируемой функции
  const result = calculateTotalWithTax(price, taxRate)

  // Assert (проверка) — проверка результата
  expect(result).toBe(113)
})
```

### 2.3 Что тестировать, а что нет?

**Что следует тестировать:**
- Ключевую бизнес-логику (расчёт цены, проверку прав, преобразование данных)
- Граничные условия (пустые значения, ноль, отрицательные числа, очень большие числа)
- Пути обработки ошибок

**Что не нужно тестировать:**
- Внутреннюю реализацию сторонних библиотек
- Простые getter/setter
- Функциональность самого фреймворка (например, систему реактивности Vue)

## 3. TDD: разработка через тестирование

### 3.1 Цикл «красный-зелёный-рефакторинг»

Суть TDD (Test-Driven Development) — это простой цикл: **сначала пишем тест, затем реализацию, в конце рефакторим**.

### 3.2 Три правила TDD

1. **Не пишите никакого продакшен-кода, кроме как для того, чтобы заставить упавший тест пройти**
2. **Пишите ровно столько тестового кода, сколько нужно, чтобы тест упал** (непрохождение компиляции тоже считается падением)
3. **Пишите ровно столько продакшен-кода, сколько нужно, чтобы тест прошёл**

### 3.3 Истинная ценность TDD

Ценность TDD не только в том, чтобы «писать тесты сначала», а ещё и в том, что он **заставляет вас думать о проектировании интерфейса**. Когда вы пишете тест первым, вы думаете с позиции «пользователя»: какие параметры должна принимать эта функция? Какой результат возвращать? Это естественным образом ведёт к лучшему дизайну API.

::: tip TDD — не серебряная пуля
TDD подходит для кода, насыщенного логикой (алгоритмы, бизнес-правила, преобразование данных), но для таких сценариев, как UI-вёрстка или исследовательские прототипы, принудительный TDD, наоборот, замедлит работу. Главное — понять его идею и применять гибко.
:::

## 4. Выбор стратегии тестирования

### 4.1 Акценты тестирования для разных проектов

| Тип проекта | Акцент тестирования | Рекомендуемое соотношение |
|----------|----------|----------|
| **Библиотека/SDK** | В основном юнит-тесты | 90% юнит + 10% интеграция |
| **API-сервис** | В основном интеграционные тесты | 30% юнит + 60% интеграция + 10% E2E |
| **Веб-приложение** | Сбалансированное распределение | 50% юнит + 30% интеграция + 20% E2E |
| **MVP/прототип** | E2E ключевых путей | Достаточно немного основных тестов |

### 4.2 Распространённые инструменты тестирования

| Инструмент | Тип | Сценарий применения |
|------|------|----------|
| **Vitest** | Юнит/интеграция | Первый выбор для проектов на Vite, совместим с API Jest |
| **Jest** | Юнит/интеграция | Самый популярный в экосистеме Node.js |
| **Playwright** | E2E | Кроссбраузерный, от Microsoft |
| **Cypress** | E2E | Хороший опыт разработки, удобная отладка |
| **Testing Library** | Тестирование компонентов | Тестирование UI-компонентов с позиции пользователя |

## 5. Помощь ИИ: повышение эффективности тестирования с помощью больших моделей

Возможности больших моделей в области тестирования уже очень мощные — они могут помочь сгенерировать тестовые сценарии, обнаружить граничные условия и даже написать полный тестовый код.

### 5.1 Генерация юнит-тестов

> **Промпт**:
> ```
> Напиши юнит-тесты для следующей функции с использованием фреймворка Vitest, требования:
> 1. Следовать паттерну AAA (Arrange-Act-Assert)
> 2. Покрыть нормальный путь, граничные условия и пути ошибок
> 3. У каждого тестового сценария должно быть понятное описание на русском
>
> [вставьте код вашей функции]
> ```

### 5.2 Обнаружение граничных условий

> **Промпт**:
> ```
> Проанализируй следующую функцию, перечисли все возможные граничные условия и сценарии экстремального ввода,
> включая: пустые значения, ноль, отрицательные числа, очень большие числа, специальные символы, конкурентность и т. д.
> Для каждого сценария опиши ожидаемое поведение и возможные риски.
>
> [вставьте код вашей функции]
> ```

### 5.3 Генерация тестов из требований (помощь TDD)

> **Промпт**:
> ```
> Мне нужно реализовать модуль корзины покупок со следующими требованиями:
> - добавление товара, удаление товара, изменение количества
> - автоматический расчёт итоговой суммы (с учётом скидок)
> - сообщение об ошибке при недостатке товара на складе
>
> Следуя подходу TDD, сначала напиши тестовые сценарии (без реализации),
> используй Vitest, покрой все ключевые сценарии.
> ```

::: tip Рекомендации по использованию ИИ
В сгенерированных ИИ тестах нужно проверять, осмысленны ли проверки — избегайте бесполезных тестов вроде `expect(true).toBe(true)`. Хороший тест должен действительно падать, когда в коде есть ошибка.
:::

## 6. Заключение

1. **Пирамида тестирования**: внизу много, вверху мало, баланс скорости и реалистичности
2. **Юнит-тесты**: следуйте принципу FIRST и паттерну AAA, тестируйте ключевую логику
3. **TDD**: цикл «красный-зелёный-рефакторинг», управление проектированием через тесты
4. **Выбор стратегии**: в зависимости от типа и этапа проекта выбирайте подходящее соотношение тестов

::: tip Финальное размышление
Тесты — не бремя, а **ускоритель**. В краткосрочной перспективе написание тестов действительно отнимает время; в долгосрочной — оно экономит бесчисленные часы ручной проверки, поиска регрессионных багов и срочных ночных исправлений. Хорошие тесты дают вам уверенность сказать ту самую фразу: **«Меняй смело, тесты подскажут, есть ли проблема».**
:::
