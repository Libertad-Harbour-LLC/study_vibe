## 1. Шаг первый: оформление «заказа» — разбор URL

::: tip 🤔 Ключевой вопрос
**Почему адрес пишется именно так?** `https://www.example.com:8080/path/page.html?id=123#section` — что вообще означает эта строка символов?
:::

### Житейская аналогия: заполнение списка покупок

Допустим, в заказе вы написали лишь «купить обувь» — склад точно не поймёт, какую пару отправлять. Нужно указать всё чётко:

- **Тип магазина** (официальный флагман / обычный магазин)
- **Название магазина** (официальный магазин Nike)
- **Расположение товара** (отдел мужской обуви / линейка беговых кроссовок)
- **Конкретная модель** (Air Max 90)
- **Примечание** (хочу красные)

### Реальный процесс: браузер разбирает URL

**URL (Uniform Resource Locator, единый указатель ресурса)** — это «код локации товара» в мире браузеров. Когда вы вводите в адресной строке `https://www.example.com:8080/path/page.html?id=123#section`, браузер тут же разбирает его на части:

| Часть URL                   | Пример значения               | Аналогия с онлайн-покупкой                                           | Техническая роль                                                                 |
| -------------------------- | -------------------- | -------------------------------------------------- | ------------------------------------------------------------------------ |
| **Протокол** `https://`        | Безопасный протокол передачи гипертекста   | **Способ доставки**: конфиденциальная доставка (HTTPS) vs обычная (HTTP) | Определяет, по каким правилам идёт обмен. `http` — обычная передача, `https` — шифрованная              |
| **Доменное имя** `www.example.com` | Человекочитаемое имя сервера | **Название магазина**: супермаркет JD                             | Сообщает браузеру, какой сервер искать. Доменное имя нужно, чтобы людям было легко запомнить, в итоге оно превращается в IP-адрес       |
| **Порт** `:8080`           | Конкретный «номер двери» сервера | **Номер стойки**: стойка №3 (по умолчанию не пишется)                  | На сервере может быть несколько служб, порт указывает, к какой обращаться. Для HTTP по умолчанию 80, для HTTPS — 443 |
| **Путь** `/path/page.html` | Расположение файла на сервере   | **Место на полке**: отдел товаров повседневного спроса / третий ряд                      | Указывает конкретное расположение ресурса на сервере                                               |
| **Параметры запроса** `?id=123`     | Дополнительная информация             | **Примечание к заказу**: красный, размер XL                           | Дополнительные данные для сервера, например ключевые слова поиска, номер страницы и т. д.                             |
| **Якорь** `#section`        | Позиция внутри страницы         | **Номер страницы инструкции**: открыть на 5-й странице                          | После загрузки страницы автоматически прокручивает к указанной позиции, серверу не отправляется                             |

<UrlParserDemo />

URL существует для того, чтобы **человек** мог запомнить и ввести его. Компьютеру в итоге нужен **IP-адрес** (как курьеру в итоге нужен конкретный адрес склада, а не название «официальный магазин Nike»).

## 2. Шаг второй: просмотр «адресной книги» — DNS-запрос

::: tip 🤔 Ключевой вопрос
**Почему браузер может найти сайт?** Вы вводите человекочитаемое доменное имя (например, `baidu.com`), но компьютеру на самом деле нужен числовой адрес (IP). Что происходит между этим?
:::

### Житейская аналогия: поиск адреса склада

В заказе вы написали «официальный магазин Nike», но логистическая система не знает, где находится склад. Ей нужно заглянуть в адресную книгу:

1. Сначала проверить **частые адреса** (покупали ли недавно у этого магазина) → кэш браузера
2. Если нет — спросить у **пункта выдачи в районе** (они знают распределение по крупным зонам) → локальный DNS-сервер
3. Спросить **центр диспетчеризации головного офиса** (он знает, кому принадлежат магазины типа .com) → корневой DNS-сервер
4. Спросить **управление бренда** (в итоге находит реальный склад отправки магазина Nike) → авторитетный DNS-сервер

### Реальный процесс: иерархический DNS-запрос

**DNS (Domain Name System, система доменных имён)** — это «распределённая система запроса адресной книги» интернета. Поскольку в мире миллиарды доменных имён, используется иерархическая архитектура для распределения нагрузки запросов:

```
ты (браузер)
    ↓ спрашивает: какой IP у google.com?
локальный DNS-сервер (твой интернет-провайдер, например Telecom/Unicom)
    ↓ спрашивает: кому принадлежит .com?
корневой DNS-сервер (13 групп корневых серверов по всему миру, управляют всеми доменами верхнего уровня)
    ↓ отвечает: спроси у управляющего .com
сервер домена верхнего уровня (Verisign управляет .com)
    ↓ отвечает: спроси у управляющего google.com
авторитетный DNS-сервер (собственный DNS-сервер Google)
    ↓ отвечает: IP у google.com — 142.250.80.46
возвращает IP-адрес браузеру
```

**Пояснение типов запросов:**

- **Рекурсивный запрос (Recursive Query)**: браузер отправляет всего один запрос, локальный DNS поэтапно опрашивает остальных и возвращает результат
- **Итеративный запрос (Iterative Query)**: каждый уровень лишь подсказывает следующему, куда обращаться, браузеру приходится делать несколько запросов
- **Механизм кэширования**: результаты запросов кэшируются, в следующий раз возвращаются напрямую, что сильно ускоряет доступ

<DnsLookupDemo />

::: info 💡 Зачем нужно столько уровней?
Представьте, что во всём мире была бы всего одна адресная книга, а миллиарды людей одновременно к ней обращались — она бы давно рухнула. Иерархическая структура позволяет каждому уровню управлять только своей «зоной», что одновременно эффективно и надёжно.

Это и есть ключевая идея устройства интернета: **распределённые системы**.
:::

## 3. Шаг третий: звонок для подтверждения — тройное рукопожатие TCP

::: tip 🤔 Ключевой вопрос
**Зачем нужно «тройное рукопожатие»?** После того как найден адрес сервера, почему нельзя сразу отправлять данные? Зачем сначала проводить три обмена?
:::

### Житейская аналогия: установка логистического канала

Допустим, грузовик едет прямо на склад, а в итоге:

- Склад закрыт → поездка впустую
- Склад переполнен и не принимает заказы → отправить невозможно
- Не найти разгрузочную площадку → невозможно состыковаться

**Поэтому перед реальной отправкой нужно сначала установить надёжный транспортный канал.**

### Реальный процесс: тройное рукопожатие TCP

**TCP (Transmission Control Protocol, протокол управления передачей)** — это правила, обеспечивающие надёжную передачу данных. Перед передачей товара (данных) нужно через «тройное рукопожатие» установить соединение:

```
клиент (твой компьютер)              сервер (склад продавца)
   |                                |
   |--- SYN=1 --------------------->|  1-й раз: привет, я дома, готов принять товар! (SYN)
   |                                |
   |<-- SYN=1, ACK=1 ---------------|  2-й раз: принято! Я тоже готов отправить, ты дома? (SYN-ACK)
   |                                |
   |--- ACK=1 --------------------->|  3-й раз: дома! Отправляйте, пожалуйста. (ACK)
   |                                |
   ===== канал установлен, начинается отправка =====
```

**Почему три раза, а не два?**

- **Первый раз (SYN)**: клиент доказывает, что умеет отправлять
- **Второй раз (SYN-ACK)**: сервер доказывает, что умеет принимать и отправлять
- **Третий раз (ACK)**: клиент доказывает, что умеет принимать

Тройное рукопожатие гарантирует: **обе стороны умеют отправлять и обе умеют принимать** — только при выполнении всех четырёх условий возможна надёжная передача.

**TCP также отвечает за:**

- **Разбиение на пакеты**: большие данные дробятся на маленькие пакеты для передачи
- **Сборку по порядку**: гарантирует сборку пакетов в правильном порядке
- **Повторную передачу при ошибках**: при потере пакета автоматически отправляет его заново
- **Управление потоком**: подстраивает скорость отправки под состояние сети

> **Дополнительный шаг HTTPS**: если это HTTPS (защищённый сайт), то после рукопожатия TCP проводится ещё **рукопожатие TLS** (1-RTT или 2-RTT), стороны обмениваются ключами шифрования, чтобы дальнейшее содержимое диалога понимали только они — словно разговор на условном языке.

## 4. Шаг четвёртый: диалог «покупателя» и «продавца» — HTTP-запрос и ответ

::: tip 🤔 Ключевой вопрос
**О чём говорят браузер и сервер?** После установки соединения как браузер «сообщает» серверу, что ему нужно? И как сервер «отвечает»?
:::

### Житейская аналогия: отправка со склада

Грузовик прибывает на склад: «Вот заказ (HTTP-запрос), **я хочу забрать товар (исходный HTML-код страницы)!**»
Кладовщик сверяет: «Заказ действителен, вот ваша посылка (**HTML-файл**), держите.»

### Реальный процесс: обмен по протоколу HTTP

**HTTP (HyperText Transfer Protocol, протокол передачи гипертекста)** — это «правила диалога» между браузером и сервером. После установки канала браузер отправляет **запрос на получение**, а **главная цель — забрать исходный код страницы (HTML-файл)**:

**Пример HTTP-запроса:**

```http
GET /index.html HTTP/1.1          ← метод запроса + путь + версия протокола
Host: www.example.com             ← целевой хост (поддержка виртуальных хостов, один сервер может хостить несколько сайтов)
User-Agent: Chrome/120.0          ← идентификатор клиента (сервер может на его основе вернуть адаптированный контент)
Accept: text/html,application/xhtml+xml  ← допустимые форматы ответа
Accept-Language: zh-CN,zh;q=0.9   ← предпочтительный язык
Accept-Encoding: gzip, deflate    ← поддерживаемые форматы сжатия
Connection: keep-alive            ← поддержание соединения (переиспользование TCP-соединения)
Cookie: session_id=abc123         ← удостоверение личности
```

::: tip 💡 Озарение разработчика: так это же API?
**Один в один!**
Те API-вызовы, что вы обычно пишете (`fetch` / `axios`), и посещение веб-страницы браузером **на уровне HTTP — абсолютно одно и то же**.

И там, и там отправляется запрос, а сервер возвращает порцию текстовых данных.

- Если сервер отдаёт **HTML**, браузер его **отрисовывает** (превращает в веб-страницу).
- Если сервер отдаёт **JSON**, ваш код его **сохраняет** (для обработки логики).

**Нет никаких «двух видов» запросов — есть один и тот же HTTP-запрос, отличается лишь формат возвращаемых данных (Content-Type).**
Именно поэтому, поняв HTTP, вы поймёте 90% принципов работы бэкенд-API.

Если вы хотите углублённо изучить разработку API, обратитесь к [главе про API](./api-intro.md).
:::

**Распространённые методы HTTP:**

- `GET`: получение ресурса (безопасный, идемпотентный, может кэшироваться)
- `POST`: отправка данных (создание ресурса, например регистрация, вход)
- `PUT`: обновление ресурса (полная замена)
- `PATCH`: частичное обновление ресурса
- `DELETE`: удаление ресурса
- `HEAD`: получение заголовков ответа (без тела, для проверки существования ресурса)

**Сервер возвращает HTTP-ответ:**

```http
HTTP/1.1 200 OK                   ← версия протокола + код состояния + описание состояния
Date: Mon, 23 May 2025 12:00:00 GMT  ← время сервера
Content-Type: text/html; charset=UTF-8  ← тип контента и кодировка
Content-Length: 1234              ← длина контента (байты)
Cache-Control: max-age=3600       ← стратегия кэширования
Set-Cookie: user_id=xyz789        ← установка Cookie

<!DOCTYPE html>...                ← тело ответа (содержимое страницы)
```

**Классификация кодов состояния HTTP:**

| Код состояния      | Категория       | Значение             | Житейская аналогия                         |
| ----------- | ---------- | ---------------- | -------------------------------- |
| **200**     | Успех       | Запрос успешно обработан     | «Заказ подтверждён, сейчас отправим»             |
| **301/302** | Перенаправление     | Ресурс перемещён       | «Магазин переехал, оформляйте заказ в новом»       |
| **304**     | Не изменён     | Кэш всё ещё актуален       | «То, что вы купили в прошлый раз, ещё годится, заново отправлять не нужно» |
| **400**     | Ошибка клиента | Неверный формат запроса     | «Заказ заполнен невнятно, ничего не понять»           |
| **401**     | Не авторизован     | Требуется аутентификация     | «Сначала предъявите карту клиента»                 |
| **403**     | Доступ запрещён   | Недостаточно прав         | «Посторонним вход воспрещён»               |
| **404**     | Не найдено     | Ресурс не существует       | «Такого товара на складе нет»               |
| **500**     | Ошибка сервера | Внутренняя ошибка сервера   | «На складе пожар, временно отправить не можем»       |
| **502**     | Ошибка шлюза   | Вышестоящий сервер не отвечает | «На главном складе нет товара, и со вспомогательного не подвезти»     |
| **503**     | Сервис недоступен | Сервер перегружен или на обслуживании | «Завал заказов, приостановили приём»               |

## 5. Шаг пятый: распаковка «посылки» — отрисовка в браузере

::: tip 🤔 Ключевой вопрос
**Как код превращается в картинку?** Сервер прислал скучный код HTML/CSS/JavaScript — как браузер превращает его в красочную веб-страницу?
:::

### Житейская аналогия: распаковка и сборка

Вы наконец получили посылку (HTTP-ответ), но открыв её, обнаруживаете внутри не готовую мебель, а кучу **деталей** (HTML) и **инструкцию по сборке** (CSS). Как «покупатель» (браузер), вы должны собрать всё сами:

1.  **Распаковка**: достать все детали, сверить с описью (разбор HTML → дерево DOM).
2.  **Чтение инструкции**: понять инструкцию, узнать, какая деталь куда крепится и какого цвета (разбор CSS → дерево CSSOM).
3.  **Сортировка**: отобрать нужные для сборки детали, выбросить упаковочную пену (`display: none`), подготовиться к сборке (построение дерева отрисовки).
4.  **Измерение позиций**: линейкой отмерить размеры комнаты, решить, где конкретно поставить каждый предмет мебели (компоновка / reflow).
5.  **Покраска и декор**: покрасить мебель, наклеить наклейки (отрисовка).
6.  **Финальная демонстрация**: убраться, включить свет и показать результат (композитинг).

### Реальный процесс: движок отрисовки браузера

Браузер получает **код HTML/CSS/JavaScript** (скучный текст), но должен превратить его в **картинку из пикселей** (изящную веб-страницу). Этот процесс называется **отрисовкой (Rendering)** и выполняется **движком отрисовки** браузера (например, Blink в Chrome, WebKit в Safari).

#### Шаг 1: разбор HTML → построение дерева DOM (опись деталей)

Браузер читает поток байтов HTML и разбирает его в **дерево DOM (Document Object Model, объектная модель документа)**. Это как привести кучу разрозненных деталей к иерархической описи:

```html
<!-- Исходный HTML -->
<div class="header">Заголовок</div>
<div class="content">Содержимое</div>
```

```text
Структура дерева DOM:
Document
 └─ html
     └─ body
         ├─ div.header ("Заголовок")
         └─ div.content ("Содержимое")
```

#### Шаг 2: разбор CSS → построение дерева CSSOM (инструкция)

Браузер разбирает весь CSS (встроенный, внешние файлы) и строит **дерево CSSOM (CSS Object Model)**. Это как разобраться в правилах стилей из инструкции:

```css
.header {
  color: blue;
  font-size: 24px;
} /* заголовок должен быть синим */
.content {
  display: none;
} /* содержимое пока скрыто */
```

#### Шаг 3: объединение → дерево отрисовки (подготовка к сборке)

Дерево DOM + дерево CSSOM = **дерево отрисовки (Render Tree)**.
Ключевой момент: **в дерево отрисовки попадают только «видимые» элементы**.

- `.header`: в дереве отрисовки (видимый).
- `.content`: **отсутствует** в дереве отрисовки (из-за `display: none`, как выброшенная упаковочная бумага, которую не нужно собирать).

#### Шаг 4: компоновка (Layout / Reflow) — измерение размеров

Браузер вычисляет **точные координаты и размеры** каждого узла дерева отрисовки на экране.

- «Этот блок заголовка шириной 100px, высотой 50px, расположен в левом верхнем углу экрана (0,0).»
- Этот процесс называется **перекомпоновкой (Reflow)**. Если размер окна изменился (например, поворот телефона в горизонтальный режим), позиции всех элементов приходится пересчитывать заново, что сильно нагружает производительность.

#### Шаг 5: отрисовка (Paint) — раскрашивание

Зная позиции, браузер начинает заполнять пиксели: рисует фоновый цвет, цвет текста, рамки, тени и т. д.

#### Шаг 6: композитинг (Composite) — финальная демонстрация

Современные браузеры разбивают страницу на несколько **слоёв (Layers)** и отрисовывают их по отдельности (например, 3D-преобразования, полоса прокрутки — отдельный слой), а затем GPU накладывает их друг на друга, как слои в Photoshop, и выводит на экран.

::: info 💡 А вы знали?
**Компоновка и отрисовка** — самое загруженное время для браузера. Чем больше элементов на странице и чем сложнее структура, тем больше времени браузеру требуется на вычисление позиций и раскрашивание. Именно поэтому некоторые сложные страницы открываются с подтормаживанием.
:::

## 5.5 Как «генерируется» веб-страница? Статический сайт vs динамический сайт

::: tip 🤔 Ключевой вопрос
**Откуда берётся содержимое веб-страницы?** Выше мы рассказали, как браузер отрисовывает страницу, но откуда берётся HTML-файл на сервере? Он сделан заранее или прямо сейчас?
:::

Выше мы говорили о том, как браузер «распаковывает посылку» — отрисовывает присланные сервером HTML/CSS/JS в страницу. Но задумывались ли вы: **откуда берётся тот HTML-файл на сервере?**

Ответ: **есть два способа**, и в этом разница между статическим и динамическим сайтами.

### Статический сайт: сделан заранее, отдаётся напрямую

Представьте, что вы пришли в супермаркет за печеньем. Печенье на полке уже произведено на фабрике, вы просто берёте его и уходите, ждать не нужно.

**Статический сайт** — это такой «готовый продукт»: страница на сервере уже подготовлена, при обращении сервер напрямую отдаёт вам готовый HTML-файл, не выполняя никакой дополнительной обработки.

**Особенности:**
- ✅ Высокая скорость доступа (сервер сразу отдаёт файл, без вычислений)
- ✅ Простота создания (написал HTML — и работает)
- ✅ Высокая пропускная способность (можно раздавать через CDN, сколько бы людей ни заходило)
- ❌ Сложно обновлять контент (чтобы изменить контент, нужно заново генерировать файл)

**Типичные примеры:** страница о компании, документация продукта, центр помощи, личный блог

### Динамический сайт: готовится по запросу, каждый раз разный

На этот раз представьте, что вы пришли в ресторан и сделали заказ. Повар готовит по вашему заказу: если вы заказали курицу гунбао, вам не подадут свинину в кисло-сладком соусе.

**Динамический сайт** — это страница, которая «изготавливается на месте» только при вашем обращении: получив ваш запрос, сервер обращается к базе данных за данными, выполняет вычисления, а затем генерирует совершенно новый HTML и отдаёт его вам.

**Особенности:**
- ✅ Контент в реальном времени (корзина показывает актуальный остаток, новости обновляются в любой момент)
- ✅ Индивидуально для каждого (после входа вы видите свою личную информацию)
- ✅ Мощный функционал (поиск, комментарии, рекомендации, оплата — всё реализуемо)
- ❌ Низкая скорость доступа (серверу нужно время на вычисления)
- ❌ Высокая нагрузка на сервер (при одновременном заходе многих людей образуется очередь)

**Типичные примеры:** Taobao, Weibo, онлайн-банк, онлайн-документы

**Нужен ли сервер?** Динамическому сайту действительно нужен какой-то «бэкенд» для генерации контента, но формы бывают разные:
- **Традиционный сервер**: купить/арендовать сервер самому (Alibaba Cloud ECS, AWS EC2)
- **Serverless**: не нужно управлять сервером, облачный провайдер запускает ваш код за вас (AWS Lambda, Function Compute от Alibaba Cloud, Cloudflare Workers)
- **Вызов сторонних API**: оплата через Stripe, погода через API метеослужбы — свой бэкенд писать не нужно

::: tip 💡 Сочетание статики и динамики
Сейчас многие сайты «гибридные»: основная часть страницы статическая, но некоторые части (например, раздел комментариев, строка поиска) загружаются динамически. JavaScript может после загрузки страницы вызвать API за данными, реализуя «статическую страницу + динамический функционал».
:::

### 📊 Статика vs динамика — сравнение всё проясняет

| | Статический сайт | Динамический сайт |
|---|---------|---------|
| **Откуда берётся** | Сделан заранее, хранится на сервере | Изготавливается при обращении |
| **На что похоже** | Товар на полке супермаркета | Блюдо, заказанное в ресторане |
| **Скорость** | Быстро | Медленно (нужны вычисления) |
| **Можно ли менять контент** | Сложно (нужно заново генерировать) | Легко (правится прямо в админке) |
| **Для чего подходит** | Демонстрационный контент (страницы-визитки, документация) | Интерактивные приложения (покупки, общение) |
| **Типичные примеры** | Официальный сайт компании, справочная документация | Taobao, WeChat, онлайн-банк |

### 🤔 Частые вопросы

**В: Значит, статический сайт не может использовать JavaScript?**

Конечно может! Карусели, складные меню, валидация форм — все эти интерактивные функции статический сайт может реализовать на JavaScript. Когда мы говорим «статический»/«динамический», мы имеем в виду, **подготовлено ли содержимое страницы заранее**, а это не то же самое, что наличие интерактивных функций.

**В: Динамическому сайту обязательно покупать собственный сервер?**

Не обязательно. Помимо традиционного сервера, можно использовать Serverless (облачные функции) или напрямую вызывать сторонние API. Сейчас тренд — «по возможности не трогать сервер»: способ «статический сайт + вызов API на JavaScript» одновременно быстрый и экономный.

::: tip 💡 Важное замечание
Будь то статический или динамический сайт, **принцип отрисовки в браузере одинаков**! Что сервер прислал, то браузер и отрисовывает. Разница лишь в том:
- Статический сайт: сервер присылает «готовый продукт»
- Динамический сайт: сервер присылает «изготовленное на месте»

Как фронтенд-разработчика, вас в основном интересует то, как браузер обрабатывает полученный контент, а не то, как сервер его сгенерировал.
:::

- Различать статические и динамические сайты

:::

Давайте вспомним всё путешествие:

| Этап        | Технический термин   | Аналогия с покупкой | Главная задача           | Ключевые технологии                       |
| ----------- | ---------- | -------- | ------------------ | ------------------------------ |
| **1. Разбор** | Разбор URL   | Оформление заказа | Понять, что хочет купить покупатель   | Протокол, доменное имя, порт, путь, параметры   |
| **2. Запрос** | DNS-запрос   | Поиск адреса склада | Найти склад отправки магазина | Рекурсивный/итеративный запрос, механизм кэширования        |
| **3. Соединение** | TCP-рукопожатие   | Установка канала | Обеспечить бесперебойную логистику       | Тройное рукопожатие, порядковый номер, управление потоком     |
| **4. Диалог** | HTTP-обмен  | Отправка со склада | Оформить заказ и получить товар     | Метод запроса, код состояния, поля заголовка     |
| **5. Показ** | Отрисовка в браузере | Распаковка и сборка | Показать товар     | DOM, CSSOM, дерево отрисовки, компоновка, отрисовка |

**Весь процесс обычно завершается за несколько сотен миллисекунд** — подумайте, насколько это поразительно!

Ваш браузер менее чем за 1 секунду:

- Разобрал сложный адрес
- Опросил DNS-серверы, распределённые по всему миру
- Установил надёжное соединение с сервером за тысячи километров
- Провёл полный HTTP-диалог
- Превратил скучный код в изящную картинку

В этом и есть очарование интернета: **сложные технологии, простой опыт**.

## 7. Краткий словарь терминов (Glossary)

| Термин        | Полное название                          | Простое объяснение                                                                   |
| ----------- | ----------------------------- | -------------------------------------------------------------------------- |
| **URL**     | Uniform Resource Locator      | **Единый указатель ресурса**. «Адрес» веб-страницы, сообщающий браузеру, где искать ресурс.                 |
| **DNS**     | Domain Name System            | **Система доменных имён**. «Телефонная книга» интернета, превращает человекочитаемое доменное имя в машиночитаемый IP-адрес. |
| **IP-адрес** | Internet Protocol Address     | **Адрес интернет-протокола**. Уникальный «номер» каждого устройства в сети, например `192.168.1.1`.         |
| **TCP**     | Transmission Control Protocol | **Протокол управления передачей**. «Правила», обеспечивающие надёжную передачу данных, соединение устанавливается тройным рукопожатием.         |
| **HTTP**    | HyperText Transfer Protocol   | **Протокол передачи гипертекста**. Правила «диалога» между браузером и сервером.                           |
| **HTTPS**   | HTTP Secure                   | **Безопасный HTTP**. Добавляет к HTTP шифрование (TLS/SSL) для защиты данных.         |
| **HTML**    | HyperText Markup Language     | **Язык гипертекстовой разметки**. «Скелет» веб-страницы, определяет структуру содержимого.                         |
| **CSS**     | Cascading Style Sheets        | **Каскадные таблицы стилей**. «Кожа» веб-страницы, определяет внешний вид содержимого.                             |
| **DOM**     | Document Object Model         | **Объектная модель документа**. Древовидная структура, в которую браузер преобразует HTML для удобства работы.               |
| **CSSOM**   | CSS Object Model              | **Объектная модель CSS**. Древовидная структура, в которую браузер преобразует CSS.                          |
| **Отрисовка**    | Rendering                     | Процесс преобразования браузером кода в пиксели на экране.                                         |
| **RTT**     | Round Trip Time               | **Время кругового пути**. Время от отправки пакета до получения подтверждения, влияет на скорость загрузки страницы.             |

Вы поняли:

- Как браузер превращает код в картинку (конвейер отрисовки)
