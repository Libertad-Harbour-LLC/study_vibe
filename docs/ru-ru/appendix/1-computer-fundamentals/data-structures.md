# Структуры данных

::: tip Введение
**Программа = структуры данных + алгоритмы.** Ранее мы изучили, как CPU выполняет инструкции и как операционная система управляет ресурсами. Но главный объект, который обрабатывает программа, — это **данные**: информация о пользователях, списки товаров, социальные связи… То, как эти данные организованы в памяти, напрямую определяет быстродействие программы. Возможно, вы сталкивались с таким недоумением: почему одни программы быстро обрабатывают десятки тысяч записей, а другие зависают на нескольких сотнях? Ответ часто кроется в **выборе структуры данных**.
:::

**Чему вас научит эта статья?**

После изучения этой главы вы получите:

- **Интуитивное суждение**: увидев требование, вы будете автоматически представлять в голове, какую структуру данных использовать
- **Взгляд через призму анализа производительности**: вы сможете определить, в чём узкое место — в неверном выборе структуры данных или в низкой эффективности алгоритма
- **Мышление в терминах компромиссов**: понимание «памяти в обмен на время» и «времени в обмен на память», знание того, что идеальной структуры данных не существует
- **Навык чтения кода**: слова HashMap, Stack, Queue больше не будут вам незнакомы
- **Базу для дальнейшего обучения**: фундамент для индексов баз данных, систем кэширования, поисковых движков и других технологий

## 1. Общая картина: что такое структура данных?

Представьте, что вам нужно разобрать кучу книг:

- **Свалить на пол**: чтобы найти книгу, придётся перебирать одну за другой — это самое примитивное хранение
- **Расставить по полкам по номерам**: сразу идёшь к нужному месту и берёшь — это **массив**
- **Разложить по шкафам по категориям**: сначала определяешь шкаф, потом ищешь книгу — это **хеш-таблица**
- **Расставить по многоярусным полкам, отсортировав по названию**: каждый раз отбрасываешь половину — это **дерево**

В зависимости от способа разбора эффективность поиска книги отличается как небо и земля. **Структура данных — это и есть «способ организации» данных** — она определяет, как данные хранятся, как находятся, как изменяются.

<DataStructureOverviewDemo />

Все структуры данных можно отнести к четырём основным классам:

| Тип | Отношение данных | Типичные представители | Житейская аналогия |
|------|---------|---------|---------|
| **Линейные структуры** | Один к одному, выстроены в ряд | Массив, связный список, стек, очередь | Вагоны поезда, очередь людей |
| **Хеш-структуры** | Отображение ключ→значение | Хеш-таблица, словарь, множество | Каталожные карточки библиотеки |
| **Древовидные структуры** | Один ко многим, иерархическое отношение | Бинарное дерево, B-дерево, куча | Родословная семьи, папки |
| **Графовые структуры** | Многие ко многим, сетевое отношение | Ориентированный граф, неориентированный граф | Схема линий метро, социальная сеть |

::: tip Зачем учить столько видов?
Потому что **универсальной структуры данных не существует**. Каждая структура — это компромисс между «скоростью поиска», «скоростью вставки» и «расходом памяти». Как вы не станете перевозить мебель в рюкзаке и не отправите грузовиком одно письмо — выбрав правильный инструмент, добиваешься вдвое большего вдвое меньшими усилиями.
:::

## 2. Линейные структуры: самый базовый способ организации

Линейная структура — это самый интуитивный способ организации данных: данные выстроены одно за другим, как вагоны поезда. Но различия в том, «как соединены» и «с какого конца оперируют», породили четыре варианта, у каждого свой конёк.

<LinearStructuresDemo />

### 2.1 Массив vs связный список: два совершенно разных способа хранения

Массив и связный список — две самые базовые линейные структуры, их ключевое различие в **расположении в памяти**:

| Измерение сравнения | Массив | Связный список |
|---------|------|------|
| **Расположение в памяти** | Один непрерывный блок | Разбросаны повсюду, связаны указателями |
| **Доступ к n-му** | Адрес вычисляется напрямую, O(1) | Поиск с начала по одному, O(n) |
| **Вставка в середину** | Все последующие нужно сдвигать, O(n) | Достаточно изменить два указателя, O(1) |
| **Размер** | Фиксируется при создании | Может расти в любой момент |
| **Житейская аналогия** | Ряд пронумерованных шкафчиков | Цепочка подсказок в игре-поиске сокровищ |

::: tip Когда использовать массив? Когда связный список?
- **Объём данных известен, частый доступ по позиции** → массив (например, таблица оценок студентов, матрица пикселей)
- **Объём данных неизвестен, частая вставка/удаление** → связный список (например, плейлист, история отмен)
- **Не уверены?** → начните с массива. В большинстве сценариев преимущество массива в производительности из-за дружелюбия к кэшу больше
:::

### 2.2 Стек и очередь: линейные структуры с «правилами»

Стек и очередь по сути и есть массив или связный список, просто с **ограниченным способом операций**. На вид функционала стало меньше, но именно это ограничение придаёт им чёткое назначение:

| Структура | Правило | Операции | Аналогия | Где это в вашем коде? |
|------|------|------|------|-----------------|
| **Стек** | Последним пришёл — первым ушёл (LIFO) | push / pop | Стопка тарелок | Стек вызовов функций, кнопка «назад» в браузере, отмена Ctrl+Z |
| **Очередь** | Первым пришёл — первым ушёл (FIFO) | enqueue / dequeue | Очередь за билетами | Планирование задач, очередь сообщений, очередь печати |

::: tip Почему «ограничение» — это, наоборот, хорошо?
Представьте стек всего с двумя операциями — «положить тарелку» и «взять тарелку» — вы никогда не перепутаете порядок. **Ограничение даёт определённость, определённость даёт надёжность.** Стек вызовов функций именно за счёт «последним пришёл — первым ушёл» гарантирует, что последняя вызванная функция вернётся первой; если разрешить произвольный доступ к функциям в середине, программа пойдёт вразнос.
:::

## 3. Хеш-таблица: самый быстрый поиск

Поиск в линейных структурах недостаточно быстр — массив приходится перебирать за O(n), даже при сортировке с бинарным поиском нужно O(log n). Есть ли структура, способная **найти напрямую за O(1)**? Есть — это хеш-таблица.

<HashTableDemo />

### 3.1 Ключевая идея хеш-таблицы

Принцип хеш-таблицы на самом деле очень прост:

1. Вы даёте **ключ** (например, "apple")
2. **Хеш-функция** вычисляет из ключа число (например, `hash("apple") = 3`)
3. Идёте напрямую к 3-й позиции массива за значением — не перебирая, в один шаг

Это как система индексов в библиотеке: вам не нужно искать на рядах полок, достаточно посмотреть каталожную карточку, чтобы сразу найти место книги.

### 3.2 Хеш-коллизия: что делать, если два ключа столкнулись?

Два разных ключа могут вычислить один и тот же индекс — это называется **хеш-коллизией**. Как если бы у двух книг был одинаковый индексный номер, указывающий на одно и то же место.

| Способ решения | Принцип | Аналогия |
|---------|------|------|
| **Метод цепочек** | В одной позиции хранится несколько значений через связный список | В один шкаф кладётся несколько книг |
| **Открытая адресация** | При коллизии ищем дальше свободное место | Шкаф полон — кладём в соседний |

### 3.3 Производительность хеш-таблицы

| Операция | В среднем | В худшем случае (полные коллизии) |
|------|---------|-------------------|
| **Поиск** | O(1) | O(n) |
| **Вставка** | O(1) | O(n) |
| **Удаление** | O(1) | O(n) |

::: warning Когда происходит деградация?
Когда все ключи отображаются в один индекс, хеш-таблица деградирует в связный список, и все операции становятся O(n). Способ избежать: выбрать хорошую хеш-функцию + динамическое расширение (расширение при превышении порога коэффициента загрузки).
:::

::: tip Хеш-таблица в вашем коде повсюду
- Объект `{}` и `Map` в JavaScript → хеш-таблица
- `dict` в Python → хеш-таблица
- `HashMap` в Java → хеш-таблица
- Индекс базы данных → на нижнем уровне тоже использует хеширование

Каждый раз, когда вы пишете `user["name"]` или `map.get("key")`, за этим работает хеш-таблица.
:::

## 4. Древовидные структуры: выражение иерархических отношений

Хеш-таблица ищет быстро, но данные не упорядочены. Если вам нужно **и быстро искать, и поддерживать данные упорядоченными**, понадобится древовидная структура.

Ключевая особенность дерева: у каждого узла может быть несколько «детей», но только один «родитель» (кроме корневого узла). Это отношение «один ко многим» встречается в реальности повсюду.

<TreeStructureDemo />

### 4.1 Двоичное дерево поиска: упорядоченное дерево

У двоичного дерева поиска простое, но мощное правило: **слева меньше, справа больше**.

- Все значения левого поддерева < корневого узла
- Все значения правого поддерева > корневого узла

При поиске каждое сравнение отбрасывает половину узлов, временная сложность O(log n). Как в игре «угадай число» — «больше 50 или меньше?», «больше», «больше 75 или меньше?» — каждый раз отбрасываем половину.

### 4.2 Сбалансированное дерево: предотвращение деградации

У двоичного дерева поиска есть проблема: если данные вставляются по порядку (1, 2, 3, 4, 5), дерево деградирует в цепочку, и поиск снова становится O(n). Сбалансированное дерево избегает этой проблемы за счёт автоматической корректировки структуры:

| Тип | Стратегия балансировки | Особенности | Типичное применение |
|------|---------|------|---------|
| **AVL-дерево** | Строгая балансировка (разница высот ≤ 1) | Самый быстрый поиск, вставка/удаление чуть медленнее | Сценарии с частым поиском |
| **Красно-чёрное дерево** | Приближённая балансировка | Хорошая комплексная производительность | Java TreeMap, ядро Linux |
| **B-дерево** | Многопутевая балансировка, один узел хранит несколько значений | Сокращение дискового ввода-вывода | Индексы баз данных |

::: tip Где деревья в вашем коде?
- **Файловая система**: вложенность папок — это древовидная структура
- **HTML DOM**: `<html>` → `<body>` → `<div>` → `<p>` — это дерево
- **Индекс базы данных**: B+-дерево позволяет искать среди миллионов записей всего за 3-4 чтения с диска
- **JSON/XML**: вложенные форматы данных по сути и есть дерево
:::

## 5. Графовые структуры: сеть сложных отношений

Дерево может выразить лишь иерархическое отношение «один ко многим». Но в реальности многие отношения — «многие ко многим»: у вашего друга тоже есть друзья, между городами есть несколько дорог. Такая структура, где **между любыми узлами возможны связи**, и есть граф.

<GraphStructureDemo />

### 5.1 Три формы графа

| Тип | Особенности | Аналогия | Типичное применение |
|------|------|------|---------|
| **Неориентированный граф** | У рёбер нет направления, A→B равно B→A | Друзья в WeChat (взаимные) | Социальные сети, сети связи |
| **Ориентированный граф** | У рёбер есть направление, A→B не равно B→A | Подписки в Weibo (односторонние) | Ссылки веб-страниц, отношения зависимостей |
| **Взвешенный граф** | У рёбер есть вес (расстояние, стоимость и т. д.) | Шоссе между городами (с километражом) | Навигация по карте, кратчайший путь |

### 5.2 Обход графа

Обход графа сложнее, чем линейной структуры, потому что возможны циклы (A→B→C→A), и нужно отмечать «посещённые» узлы:

| Способ обхода | Стратегия | Аналогия | Сценарий применения |
|---------|------|------|---------|
| **BFS (поиск в ширину)** | Сначала посещаем всех соседей, затем соседей соседей | Расходящиеся круги на воде | Кратчайший путь, обход по уровням |
| **DFS (поиск в глубину)** | Идём по одному пути до конца, при тупике возвращаемся | Блуждание по лабиринту | Поиск пути, проверка связности |

::: tip Применение графов в реальности
- **Навигация по карте**: города — узлы, дороги — рёбра, навигация — это поиск кратчайшего пути на графе
- **Социальные сети**: пользователи — узлы, подписки/друзья — рёбра, «возможно, вы знакомы» — это рекомендация графового алгоритма
- **Менеджер пакетов**: отношения зависимостей npm/pip — это ориентированный граф, `npm install` — это топологическая сортировка графа
:::

<DataStructureDemo />

**Ключевая таблица сравнения производительности:**

| Структура данных | Доступ | Поиск | Вставка | Удаление | Память |
|---------|------|------|------|------|------|
| **Массив** | O(1) | O(n) | O(n) | O(n) | O(n) |
| **Связный список** | O(n) | O(n) | O(1) | O(1) | O(n) |
| **Стек/очередь** | O(n) | O(n) | O(1) | O(1) | O(n) |
| **Хеш-таблица** | — | O(1) | O(1) | O(1) | O(n) |
| **Двоичное дерево поиска** | — | O(log n) | O(log n) | O(log n) | O(n) |
| **Граф** | — | O(V+E) | O(1) | O(E) | O(V+E) |

::: tip Как читать эту таблицу?
- **O(1)**: независимо от объёма данных время операции постоянно — самое быстрое
- **O(log n)**: объём данных удваивается, время увеличивается лишь на один шаг — очень быстро
- **O(n)**: объём данных удваивается, время тоже удваивается — обычно
- **O(V+E)**: зависит от числа узлов и рёбер — особое представление графа

Внимание: всё это **средние случаи**. В худшем случае хеш-таблица деградирует до O(n), двоичное дерево поиска тоже деградирует до O(n).
:::

## 7. Руководство по выбору: какую структуру данных использовать?

Изучив столько структур данных, как же выбирать перед лицом реального требования? Главное — **исходить из требования**, задав себе несколько вопросов:

1. **Какая операция самая частая?** Поиск? Вставка? Удаление? Обход?
2. **Какое отношение между данными?** Один к одному? Один ко многим? Многие ко многим?
3. **Каков объём данных?** Оптимальный выбор для десятков и для миллионов записей может быть совершенно разным
4. **Нужна ли упорядоченность?** Требуется ли обход данных в каком-то порядке

<DataStructureSelectorDemo />

**Быстрый процесс принятия решения:**

| Ваше требование | Рекомендуемая структура | Причина |
|---------|---------|------|
| Быстрый доступ по позиции | Массив | Произвольный доступ за O(1) |
| Частая вставка/удаление в середине | Связный список | Вставка/удаление за O(1), без сдвига элементов |
| Последним пришёл — первым ушёл (отмена, рекурсия) | Стек | Семантика LIFO подходит естественно |
| Первым пришёл — первым ушёл (очередь задач) | Очередь | Семантика FIFO подходит естественно |
| Быстрый поиск по ключу | Хеш-таблица | Поиск за O(1) в среднем |
| Упорядоченные данные + быстрый поиск | Двоичное дерево поиска | Поиск за O(log n) с сохранением упорядоченности |
| Сложные отношения «многие ко многим» | Граф | Может выразить связи между любыми узлами |

::: tip Эмпирическое правило в реальной разработке
- В **80% сценариев** хватает массива и хеш-таблицы
- Когда **нужна упорядоченность** — рассмотрите дерево
- Когда **отношения сложны** — рассмотрите граф
- **Не уверены?** Сначала используйте самое простое, при проблемах с производительностью замените. Преждевременная оптимизация — корень всех зол
:::

> Структуры данных — это скелет программы. **Массив** как ряд пронумерованных шкафчиков — быстрее всего брать вещи по позиции; **связный список** как цепочка подсказок в поиске сокровищ — самый гибкий для вставки/удаления; **хеш-таблица** как библиотечный индекс — быстрее всего находить вещи по названию; **дерево** как родословная семьи — выражает иерархические отношения и сохраняет упорядоченность; **граф** как схема линий метро — выражает сколь угодно сложные сетевые отношения. Лучшей структуры данных не существует, есть лишь наиболее подходящая — главное понять преимущества и цену каждой структуры и сделать компромисс исходя из реального требования.
