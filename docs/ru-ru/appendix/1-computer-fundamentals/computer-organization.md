## 0. Общая картина: аппаратная система компьютера

В предыдущей главе «От транзистора до CPU» мы уже поняли, как работает CPU внутри — от выборки, декодирования, исполнения до записи результата. Но сам CPU — лишь исполнительный блок, чтобы компьютер по-настоящему «работал», нужно содействие целого ряда периферийных компонентов.

<CpuArchitectureDemo />

::: tip Послойная деконструкция: аппаратная система компьютера
- **Уровень первый: ядро CPU**
  Отвечает за исполнение инструкций, включает устройство управления (выдаёт управляющие сигналы) и вычислительный блок (выполняет арифметико-логические операции)

- **Уровень второй: файл регистров**
  Высокоскоростные единицы хранения внутри CPU, включают регистры общего назначения и специализированные регистры (PC, IR, MAR, MDR и др.)

- **Уровень третий: основная память**
  Память для хранения программ и данных, к которой CPU обращается через адресную и данных шины

- **Уровень четвёртый: устройства ввода-вывода**
  Устройства ввода-вывода подключаются к системной шине через контроллер ввода-вывода

- **Уровень пятый: системная шина**
  Канал данных, соединяющий CPU, память, ввод-вывод, включает адресную шину, шину данных, шину управления
:::

## 1. Архитектура фон Неймана: «конституция» современного компьютера

### 1.1 Принцип хранимой программы

В 1945 году математик Джон фон Нейман (John von Neumann) предложил эпохальную идею архитектуры **хранимой программы (Stored-program)**. Эта идея заложила основу современного компьютера.

::: tip Ключевая концепция
**Хранимая программа**: сама программа как особый вид данных хранится в памяти наравне с обычными данными. CPU может, как читает и записывает данные, считывать и исполнять инструкции программы, хранящиеся в памяти.
:::

Это означает:
- **Ранние компьютеры**: программа реализовывалась фиксированной разводкой проводов, изменение программы требовало перепайки схемы
- **Архитектура фон Неймана**: программа хранится в памяти, изменение программы требует лишь изменения содержимого памяти

### 1.2 Пять основных компонентов

Архитектура фон Неймана делит компьютер на пять ключевых компонентов:

<RegisterDemo />

| Компонент | По-английски | Функция | Основной состав |
|------|------|------|---------|
| **Арифметико-логическое устройство** | ALU (Arithmetic Logic Unit) | Выполняет арифметические и логические операции | Сумматор, сдвигатель, компаратор |
| **Устройство управления** | CU (Control Unit) | Командует и координирует работу компонентов | Регистр инструкций, декодер, генератор синхросигналов |
| **Память** | Memory | Хранит программы и данные | Регистр адреса памяти (MAR), регистр данных памяти (MDR) |
| **Устройство ввода** | Input | Ввод информации | Клавиатура, мышь, сканер |
| **Устройство вывода** | Output | Вывод информации | Монитор, принтер |

### 1.3 Тракт данных

**Тракт данных (Data Path)** — это путь, по которому данные перетекают между функциональными компонентами. Внутри CPU тракт данных соединяет:

- Файл регистров
- Арифметико-логическое устройство (ALU)
- Регистр данных памяти (MDR)

Ширина тракта данных (сколько бит можно передать за раз) напрямую влияет на производительность компьютера.

### 1.4 Узкое место фон Неймана

У архитектуры фон Неймана есть знаменитое **узкое место производительности**:

> Скорость передачи данных между CPU и памятью намного ниже скорости обработки CPU.

Из-за этого CPU часто пребывает в простое «ожидания данных». Многие технологии оптимизации современных компьютеров развёрнуты вокруг этой проблемы:

| Технология оптимизации | Принцип |
|---------|------|
| **Кэш (Cache)** | Размещение малой быстрой памяти рядом с CPU |
| **Конвейер инструкций** | Несколько инструкций одновременно находятся на разных этапах |
| **Суперскалярность** | Выдача нескольких инструкций за один такт |
| **Многоядерный параллелизм** | Несколько ядер CPU делят вычислительные задачи |

## 2. Система инструкций: интерфейс между CPU и ПО

В предыдущем разделе мы узнали ключевую идею архитектуры фон Неймана: **программа хранится в памяти наравне с данными**. Но это порождает ключевой вопрос — как же выглядит «программа», хранящаяся в памяти? Как CPU её понимает?

Ответ — **система инструкций (Instruction Set Architecture, ISA)**. Если уподобить CPU сервису, то система инструкций — это его **документация API**: она определяет все команды, понятные CPU, формат каждой команды, а также диапазон данных, которым команда может оперировать. Каждая написанная вами строка кода в итоге переводится компилятором в последовательность вызовов этого «API».

### 2.1 От кода к инструкции: переводческое путешествие одной строки кода

Сначала выстроим общее представление: между кодом, что вы пишете в редакторе, и тем, что реально исполняет CPU, лежит несколько уровней перевода.

<CodeToInstructionDemo />

Эта цепочка перевода — ключ к пониманию системы инструкций:

| Уровень | Содержание | Кто понимает |
|------|------|---------|
| Высокоуровневый язык | `int a = 10 + 5;` | Человек |
| Язык ассемблера | `MOV R1, #10` / `ADD R3, R1, R2` | Человек (требует подготовки) |
| Машинный код | `0001 0001 0000 1010` | CPU |

::: tip Зачем понимать эту цепочку?
- Увидев ошибку компиляции, вы знаете, что она возникла на шаге «высокоуровневый язык → ассемблер»
- Увидев падение во время выполнения, вы знаете, что проблема на этапе исполнения инструкций CPU
- Понимая оптимизацию производительности, вы знаете, какие оптимизации компилятор сделал в процессе «перевода»
- Выбирая архитектуру CPU (x86 vs ARM), вы знаете, что разница в разном «API набора инструкций»
:::

### 2.2 Как выглядит одна инструкция?

Зная, что код переводится в инструкции, следующий вопрос: **какова внутренняя структура одной инструкции?**

Каждая машинная инструкция по сути — цепочка двоичных чисел, но у неё строгий внутренний формат. Две самые ключевые части:

- **Код операции (Opcode)**: сообщает CPU «что делать» — сложение? переход? чтение памяти?
- **Операнд (Operand)**: сообщает CPU «над чем делать» — какой регистр? какой адрес памяти? какая константа?

Подобно тому как в предложении есть структура «глагол + дополнение», у инструкции есть структура «операция + объект»:

```
инструкция:  ADD  R3, R1, R2
             ───  ──────────
             код  операнды
             операции  (R3 = R1 + R2)
             (сложение)
```

В зависимости от количества операндов формат инструкции от простого к сложному делится на четыре вида:

<InstructionFormatDemo />

| Формат | Структура | Пример | Сценарий использования |
|------|------|------|---------|
| Безадресный | Только код операции | `RET` (возврат) | Стековый компьютер, операнды подразумеваются на вершине стека |
| Одноадресный | Код операции + 1 адрес | `INC R1` (R1 плюс 1) | Операции с одним операндом |
| Двухадресный | Код операции + 2 адреса | `MOV R1, R2` | Самый используемый, пересылка данных и операции |
| Трёхадресный | Код операции + 3 адреса | `ADD R3, R1, R2` | Не разрушает исходные операнды |

::: tip Почему столько форматов?
Это **компромисс между пространством и гибкостью**. Безадресная инструкция самая короткая (экономит память), но требует дополнительных операций со стеком; трёхадресная инструкция самая гибкая (не разрушает исходные данные), но занимает больше бит. Разные архитектуры CPU выбирают разные сочетания форматов инструкций.
:::

### 2.3 Как CPU находит данные? — способы адресации

Инструкция говорит CPU «сложить», но где же два слагаемых? Они могут быть прямо записаны в инструкции, могут лежать в регистре, а могут быть по какому-то адресу в памяти. **Способ адресации** — это правило, сообщающее CPU, «где искать операнд».

Сравним с житейским «поиском человека»:

| Способ адресации | Аналогия | Пример инструкции | Пояснение |
|---------|------|---------|------|
| **Непосредственная адресация** | Человек стоит прямо перед тобой | `MOV R1, #100` | Данные записаны прямо в инструкции, самый быстрый |
| **Регистровая адресация** | Позвонить коллеге по внутренней линии | `MOV R1, R2` | Данные в регистре внутри CPU, очень быстро |
| **Прямая адресация** | Знаешь номер двери, идёшь прямо | `MOV R1, [0x1000]` | В инструкции записан адрес памяти |
| **Косвенная адресация** | Спросить на ресепшене «в какой комнате Чжан Сань» | `MOV R1, [R2]` | В регистре хранится адрес, нужна ещё одна проверка |
| **Индексная адресация** | «Корпус 3 + 5-й этаж» вычисляет комнату | `MOV R1, [R2+10]` | Базовый адрес + смещение, для доступа к массивам |

<AddressingModeDemo />

::: tip Зачем столько способов адресации?
Разные сценарии требуют разной стратегии «поиска данных»:
- **Присваивание константы** (`x = 100`) → непосредственная адресация, данные прямо в инструкции
- **Операции с переменными** (`a + b`) → регистровая адресация, данные уже загружены в регистр
- **Доступ к массиву** (`arr[i]`) → индексная адресация, базовый адрес + смещение индекса
- **Операции с указателями** (`*ptr`) → косвенная адресация, в регистре хранится адрес

Когда вы пишете `arr[i]`, вы не думаете о способе адресации, но компилятор автоматически выбирает наиболее подходящий способ.
:::

### 2.4 Перечень возможностей CPU — классификация инструкций

Теперь мы знаем формат инструкции и способы адресации, последний вопрос: **что же вообще умеет делать CPU?**

Все инструкции можно отнести к шести основным классам, охватывающим всё, что может делать компьютер:

| Тип | Что делает | Представители инструкций | Соответствие коду, что вы пишете |
|------|-------|---------|-------------|
| **Пересылка данных** | Перемещение данных | MOV, LOAD, STORE | `let x = y`, передача параметров в функцию |
| **Арифметические операции** | Сложение, вычитание, умножение, деление | ADD, SUB, MUL, DIV | `a + b`, `count++` |
| **Логические операции** | Битовые операции | AND, OR, NOT, XOR | `flags & 0xFF`, проверка прав |
| **Операции сдвига** | Сдвиг влево, вправо | SHL, SHR | `x << 2` (эквивалентно умножению на 4) |
| **Управление передачей** | Переходы и вызовы | JMP, CALL, RET | `if`, `for`, вызов функции |
| **Ввод-вывод** | Связь с периферией | IN, OUT | Чтение клавиатуры, запись на экран |

::: tip Ключевое наблюдение
Весь код, что вы пишете — какой бы сложной ни была бизнес-логика, какой бы крутой ни была анимация UI — в итоге разбирается на комбинацию этих шести классов базовых операций. «Интеллект» CPU не в том, что он умеет делать сколь угодно сложные вещи, а в том, что он способен исполнять эти простые операции со скоростью несколько миллиардов раз в секунду.
:::

### 2.5 Две философии проектирования: CISC vs RISC

В проектировании систем инструкций есть фундаментальное расхождение: **делать каждую инструкцию как можно более мощной или как можно более простой?**

Это расхождение породило два больших лагеря, напрямую влияющих на каждое устройство, которым вы пользуетесь сегодня:

<CISCvsRISCDemo />

Поймём через аналогию:
- **CISC как швейцарский нож**: один нож совмещает ножницы, открывашку, отвёртку… функций много, но каждая не обязательно самая удобная
- **RISC как набор профессиональных инструментов**: каждый инструмент делает лишь одно дело, но делает быстро и хорошо

::: tip Почему в вашем телефоне ARM, а в компьютере x86?
- **x86 (CISC)** правит рынком ПК и серверов уже 40 лет, накопив огромную программную экосистему. Смена архитектуры означает перекомпиляцию всего ПО
- **ARM (RISC)** благодаря преимуществу низкого энергопотребления правит мобильными устройствами. У телефона маленький аккумулятор, каждый милливатт на счету
- **Apple Silicon** доказал, что RISC тоже может быть высокопроизводительным — чипы серии M превзошли конкурентов на x86 одновременно по производительности и энергопотреблению
- **RISC-V** — это открытая архитектура RISC, стремительно набирающая обороты в области IoT, образования, ИИ-чипов
:::

---

> **Резюме**: система инструкций — это мост, соединяющий ПО и аппаратуру. Написанный вами код компилятором переводится в инструкции, инструкции через код операции и операнды сообщают CPU, что делать и над чем, способ адресации определяет, откуда приходят данные. Разные проекты наборов инструкций (CISC/RISC) определяют характеристики производительности CPU и сценарии применения.
>
> Теперь мы знаем «статическую структуру» инструкции — как она выглядит, какие бывают типы. Следующий вопрос: **как же CPU внутри шаг за шагом исполняет эти инструкции?** Это и есть работа устройства управления.

## 3. Устройство управления: «командный центр» CPU

### 3.1 Состав устройства управления

Устройство управления — это «мозг» CPU, отвечающий за координацию работы компонентов согласно требованиям инструкции:

<ControllerDemo />

| Компонент | Функция |
|------|------|
| **Счётчик команд (PC)** | Хранит адрес следующей инструкции |
| **Регистр инструкций (IR)** | Хранит текущую исполняемую инструкцию |
| **Декодер инструкций** | Разбирает код операции и операнды инструкции |
| **Генератор синхросигналов** | Производит тактовые сигналы, управляет синхронизацией компонентов |
| **Генератор последовательности микроопераций** | Производит серию управляющих сигналов, нужных для исполнения инструкции |

<PSWFlagDemo />

### 3.2 Цикл инструкции

Чтобы исполнить одну инструкцию, CPU проходит полный **цикл инструкции**, обычно включающий:

1. **Цикл выборки (Fetch)**: чтение инструкции из памяти в IR
2. **Цикл декодирования (Decode)**: разбор смысла инструкции
3. **Цикл исполнения (Execute)**: выполнение операции
4. **Цикл обращения к памяти (Memory Access)**: при необходимости обращение к памяти
5. **Цикл записи результата (Write Back)**: запись результата обратно в регистр или память

### 3.3 Микрооперации

**Микрооперация** — это самая базовая операция, управляемая управляющим сигналом. Например, этап «выборка» можно разложить на следующие микрооперации:

| Такт | Микрооперация | Управляющий сигнал |
|------|--------|---------|
| T1 | PC → MAR | PCout, MARin |
| T2 | MEM → MDR | MEMout, MDRin |
| T3 | MDR → IR | MDRout, IRin |
| T4 | PC + 1 → PC | PC+1, PCin |

### 3.4 Жёсткая логика vs микропрограммное устройство управления

| Характеристика | Устройство управления на жёсткой логике | Микропрограммное устройство управления |
|------|------------|-------------|
| **Способ реализации** | Комбинационная логическая схема | Последовательность микроинструкций (прошивка) |
| **Скорость** | Высокая | Чуть медленнее |
| **Сложность проектирования** | Сложно | Проще |
| **Гибкость** | Плохая (изменение требует переработки схемы) | Хорошая (достаточно изменить микропрограмму) |
| **Типичное применение** | RISC-процессоры | Ранние CISC-процессоры |

## 4. Система памяти: зачем нужен кэш?

### 4.1 Иерархия памяти

Устройства хранения компьютера образуют пирамидальную структуру:

<StorageHierarchyDemo />

| Уровень | Тип хранения | Время доступа | Типичная ёмкость | Расположение |
|------|---------|---------|---------|------|
| **Регистры** | SRAM | <1 нс | Несколько КБ | Внутри CPU |
| **Кэш L1** | SRAM | ~1 нс | 32-64 КБ | Рядом с ядром CPU |
| **Кэш L2** | SRAM | ~3-10 нс | 256 КБ-1 МБ | Внутри чипа CPU |
| **Кэш L3** | SRAM | ~10-20 нс | 2-16 МБ | Внутри чипа CPU / общий |
| **Основная память (ОЗУ)** | DRAM | ~50-100 нс | 8-64 ГБ | На материнской плате |
| **SSD** | Flash | ~10-100 мкс | 256 ГБ-2 ТБ | На материнской плате |
| **HDD** | Магнитный диск | ~5-10 мс | 1-10 ТБ | Внутри корпуса |

::: tip Аналогия для разницы в скорости
Если уподобить обращение CPU к кэшу L1 **взятию листа бумаги со стола**:
- Обращение к памяти → спуститься на лифте в магазинчик внизу за бумагой
- Обращение к SSD → поехать на машине в другой город за бумагой
- Обращение к HDD → полететь на самолёте в другую страну за бумагой

Разница в скорости может достигать **миллионов раз**!
:::

### 4.2 Принцип кэша

**Кэш (Cache)** — это быстрая память между CPU и памятью, ключевая идея которой основана на двух принципах локальности:

::: tip Принцип локальности
- **Временная локальность**: если к данным только что обратились, к ним, скорее всего, скоро обратятся снова
- **Пространственная локальность**: если к данным обратились, то к соседним данным, скорее всего, тоже обратятся
:::

#### Как работает кэш

1. **Попадание (Hit)**: данные, нужные CPU, есть в кэше — читаются напрямую
2. **Промах (Miss)**: данных нет в кэше — нужно загрузить из памяти

```
коэффициент попаданий = число попаданий / общее число обращений
среднее время доступа = коэффициент попаданий × время кэша + (1 - коэффициент попаданий) × время памяти
```

<CacheDemo />

### 4.3 Способы отображения кэша

| Способ | Принцип | Достоинства | Недостатки |
|------|------|------|------|
| **Прямое отображение** | Каждый блок памяти может попасть только в одно фиксированное место | Просто и быстро | Высокий уровень конфликтов |
| **Множественно-ассоциативное** | Каждый блок памяти может попасть в N мест (N-путей) | Баланс скорости и коэффициента попаданий | Сложно реализовать |
| **Полностью ассоциативное** | Любое место | Самый низкий уровень конфликтов | Трудно реализовать (нужно сравнивать все теги) |

### 4.4 Виртуальная память

**Виртуальная память** — это важная абстракция, предоставляемая операционной системой:

- Каждый процесс считает, что владеет полным виртуальным адресным пространством
- Операционная система отвечает за перевод виртуального адреса в физический
- Редко используемые страницы можно выгружать на диск (пространство подкачки)

::: tip Аналогия виртуальной памяти
Представьте виртуальную память как **управление номерами в отеле**:
- Вы (процесс) думаете, что всё здание ваше
- На самом деле отель (ОС) выделяет вам только нужные сейчас номера
- Номера, в которых не живёте, «выгружаются» на склад (диск)
- Нужные номера можно в любой момент «загрузить»
:::

## 5. Шины и ввод-вывод: «сосуды» компьютера

### 5.1 Системная шина

**Шина (Bus)** — это канал данных, соединяющий компоненты компьютера:

<BusSystemDemo />

| Тип шины | Функция | Направление | Типичная ширина |
|---------|------|------|---------|
| **Адресная шина** | Передаёт адрес памяти | Одностороннее (CPU→память) | 32 бита / 64 бита |
| **Шина данных** | Передаёт данные | Двустороннее | 32 бита / 64 бита |
| **Шина управления** | Передаёт управляющие сигналы | Двустороннее | Несколько сигнальных линий |

### 5.2 Арбитраж шины

Когда несколько устройств одновременно запрашивают использование шины, нужен механизм **арбитража**, чтобы решить, кто использует первым:

| Способ арбитража | Пояснение |
|---------|------|
| **Централизованный арбитраж** | Центральный арбитр решает единолично |
| **Распределённый арбитраж** | Устройства договариваются сами |

### 5.3 Способы доступа к устройствам ввода-вывода

| Способ | Принцип | Достоинства | Недостатки |
|------|------|------|------|
| **Программный опрос** | CPU опрашивает состояние ввода-вывода | Просто | Низкая загрузка CPU |
| **Прерывания** | Ввод-вывод после завершения сам уведомляет CPU | CPU может работать параллельно | Обработка прерывания имеет накладные расходы |
| **DMA** | Устройство ввода-вывода напрямую обращается к памяти | CPU вообще не участвует | Нужен контроллер DMA |

<IOMethodDemo />

### 5.4 Принцип DMA

**DMA (Direct Memory Access, прямой доступ к памяти)** позволяет устройству ввода-вывода напрямую обмениваться данными с памятью:

<NetworkOverviewDemo />

- **Без DMA**: CPU участвует во всём процессе передачи данных и не может делать ничего другого
- **С DMA**: CPU сообщает контроллеру DMA «откуда куда передать и сколько», затем уходит выполнять другие задачи, а DMA по завершении уведомляет CPU

::: tip Аналогия DMA
Это как **заказ доставки еды**:
- **Без DMA**: вы сами идёте в магазин за продуктами, домой, моете, готовите (участвуете во всём процессе)
- **С DMA**: вы звоните и делаете заказ, курьер привозит прямо на кухню (другой всё делает за вас, вам нужно лишь в конце «принять заказ»)
:::

### 5.5 Механизм прерываний

**Прерывание** — крайне важный механизм в компьютерной системе:

1. Устройство ввода-вывода после завершения операции отправляет CPU **запрос прерывания**
2. CPU исполняет инструкцию и, завершив текущую, отвечает на прерывание
3. CPU сохраняет текущее состояние, переходит к обработчику прерывания
4. После обработки восстанавливает состояние и продолжает исполнение

## 6. Оптимизация производительности CPU: технология конвейера

### 6.1 Конвейер инструкций

**Конвейер инструкций** — это технология параллелизма, максимизирующая эффективность CPU:

<PipelineDemo />

#### Принцип работы конвейера

```
Последовательное исполнение (5 инструкций, 15 тактов):
инструкция 1: IF→ID→EX→MEM→WB
инструкция 2:            IF→ID→EX→MEM→WB
инструкция 3:                         IF→ID→EX→MEM→WB
...

Конвейерное исполнение (5 инструкций, 9 тактов):
инструкция 1: IF→ID→EX→MEM→WB
инструкция 2:    IF→ID→EX→MEM→WB
инструкция 3:       IF→ID→EX→MEM→WB
...
```

В идеальном случае CPI (число тактов на инструкцию) для N инструкций ≈ 1

### 6.2 Конфликты конвейера

Хотя конвейер может повысить производительность, он также порождает проблему **конфликтов (Hazard)**:

| Тип | Причина | Решение |
|------|------|---------|
| **Структурный конфликт** | Конфликт аппаратных ресурсов | Добавить железо / разнести исполнение |
| **Конфликт данных** | Последующей инструкции нужен результат предыдущей | Перенаправление данных / пузырьки / планирование |
| **Конфликт управления** | Инструкция перехода меняет поток исполнения | Слот задержки / предсказание ветвлений |

## 7. Итог: как компьютер «запускается»?

Свяжем весь процесс воедино в профессиональных терминах:

> **После запуска программы операционная система загружает исполняемый файл с диска в память. Блок выборки CPU (IF) через адресную шину читает инструкцию из памяти в регистр инструкций (IR). Устройство управления декодирует инструкцию (ID), распознав тип операции, производит соответствующие управляющие сигналы. Вычислительный блок (EX) выполняет арифметико-логическую операцию, при необходимости обращения к памяти через шину данных обращается к памяти (MEM), наконец результат записывается обратно (WB) в регистр или память. Весь процесс управляется тактовым сигналом, а последовательность микроопераций, выдаваемая устройством управления, координирует упорядоченную работу компонентов.**
