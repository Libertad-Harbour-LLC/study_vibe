# Введение в теорию компиляции

::: tip Введение
**Когда вы нажимаете кнопку «Запустить», как код превращается в результат на экране?** Каждую написанную вами строку кода компьютер на самом деле «не понимает» — он знает только 0 и 1. Компилятор — это тот самый «переводчик», который переводит человеческий язык в машинный. Поняв теорию компиляции, вы поймёте, откуда берутся сообщения об ошибках, почему одни языки быстрые, а другие медленные, а также логику оптимизации кода на нижнем уровне.
:::

**Чему вас научит эта статья?**

После изучения этой главы вы получите:

- **Общий взгляд**: освоение полного конвейера компиляции от исходного кода до исполняемой программы
- **Лексический анализ**: понимание того, как компилятор разбивает код на отдельные токены
- **Синтаксический анализ**: понимание процесса построения AST (абстрактного синтаксического дерева)
- **Визуализацию AST**: наглядное представление древовидной структуры кода
- **Семантический анализ и оптимизацию**: понимание принципов проверки типов и оптимизации кода
- **Практику технологий оптимизации**: освоение ключевых приёмов оптимизации, таких как свёртка констант, удаление мёртвого кода
- **Модель исполнения**: различение трёх способов исполнения — компилируемого, интерпретируемого и JIT

| Глава | Содержание | Ключевые концепции |

## 0. Общая картина: «переводческое путешествие» кода

Представьте, что вы переводчик и должны перевести китайский роман на английский. Вы не будете переводить слово в слово буквально, а сделаете так:

1. **Распознать слова** — разбить предложение на отдельные слова (лексический анализ)
2. **Понять синтаксис** — определить, верна ли структура предложения (синтаксический анализ)
3. **Понять семантику** — убедиться, что смысл связный и без противоречий (семантический анализ)
4. **Отшлифовать и оптимизировать** — сделать перевод более естественным и плавным (оптимизация кода)
5. **Выдать перевод** — написать финальную английскую версию (генерация кода)

Компилятор делает ровно то же самое, только переводит он язык программирования.

## 1. Шестишаговый конвейер компилятора

Работу компилятора можно разделить на шесть этапов: как заводской конвейер, каждый этап после обработки передаёт результат следующему.

<CompilerDemo />

::: tip Конвейер компиляции
1. **Лексический анализ (Lexical Analysis)**: разбивает исходный код на отдельные токены (слова)
2. **Синтаксический анализ (Syntax Analysis)**: организует токены в синтаксическое дерево (AST)
3. **Семантический анализ (Semantic Analysis)**: проверяет, верны ли типы и объявлены ли переменные
4. **Генерация промежуточного кода (IR Generation)**: создаёт платформонезависимое промежуточное представление
5. **Оптимизация кода (Optimization)**: делает промежуточный код эффективнее
6. **Генерация кода (Code Generation)**: создаёт машинный код целевой платформы
:::

| Этап | Вход | Выход | Аналогия |
|------|------|------|------|
| Лексический анализ | Поток символов исходного кода | Поток токенов | Разбить предложение на слова |
| Синтаксический анализ | Поток токенов | AST (синтаксическое дерево) | Проанализировать структуру предложения |
| Семантический анализ | AST | AST с типами | Проверить, связный ли смысл |
| Промежуточный код | AST с типами | IR | Написать черновик |
| Оптимизация кода | IR | Оптимизированный IR | Шлифовка и сокращение |
| Генерация кода | Оптимизированный IR | Машинный код | Выдать финальную версию |

## 2. Лексический анализ: разбиваем код на «слова»

Лексический анализ — первый шаг компиляции. Компилятор слева направо сканирует каждый символ исходного кода и объединяет их в осмысленные **токены (лексические единицы)**.

<LexerTokenDemo />

Подобно тому, как при чтении английского предложения ваш мозг автоматически собирает буквы в слова, лексический анализатор собирает символы в токены:

```
исходный код: let x = 10 + 5;

поток токенов:
[let]   → ключевое слово (зарезервированное слово языка)
[x]     → идентификатор (имя переменной)
[=]     → оператор (присваивание)
[10]    → числовой литерал
[+]     → оператор (сложение)
[5]     → числовой литерал
[;]     → разделитель (конец инструкции)
```

::: tip Пять основных типов токенов
- **Ключевые слова**: специальные зарезервированные слова языка, такие как `let`, `if`, `return`, `function`
- **Идентификаторы**: имена, заданные программистом, такие как имена переменных, имена функций
- **Литералы**: значения, записанные прямо в коде, такие как число `42`, строка `"hello"`
- **Операторы**: символы, выполняющие операции, такие как `+`, `-`, `=`, `===`
- **Разделители**: символы, разделяющие структуру кода, такие как `;`, `,`, `(`, `)`
:::

## 3. Синтаксический анализ: построение синтаксического дерева (AST)

Лексический анализ разбил код на токены, но токены — это лишь отдельные изолированные «слова». Задача синтаксического анализа — организовать эти токены по правилам синтаксиса в **абстрактное синтаксическое дерево (Abstract Syntax Tree, AST)** — оно отражает структуру кода и приоритет операций.

```
выражение: 1 + 2 * 3

синтаксическое дерево:   почему так?
       +       потому что приоритет *
      / \      выше, чем у +, поэтому
     1   *     2 * 3 сначала связывается
        / \    становясь поддеревом
       2   3
```

::: tip Важность AST
AST — это «ключевая структура данных» компилятора, последующие семантический анализ, оптимизация, генерация кода — всё опирается на него. Современные инструменты разработки тоже широко используют AST:
- **ESLint**: разбирает код в AST, проверяет нарушения правил
- **Prettier**: разбирает в AST, затем заново форматирует вывод
- **Babel**: разбирает AST → преобразует → генерирует совместимый код
- **Рефакторинг в IDE**: на основе AST безопасно переименовывает переменные, выделяет функции
:::

| Синтаксическая конструкция | Последовательность токенов | Узел AST |
|---------|-----------|---------|
| Объявление переменной | `let` `x` `=` `10` | VariableDeclaration → Identifier + Literal |
| Вызов функции | `add` `(` `1` `,` `2` `)` | CallExpression → Identifier + Arguments |
| Условная инструкция | `if` `(` `a` `>` `b` `)` | IfStatement → BinaryExpression + Block |

## 4. Визуализация AST: видим «скелет» кода

Выше мы словами описали структуру AST, но «увидеть» нагляднее, чем «прочитать». Интерактивный компонент ниже позволяет выбирать разные выражения и в реальном времени наблюдать, как выглядит их синтаксическое дерево.

<ASTVisualizerDemo />

Через визуализацию вы обнаружите, что ключевая закономерность AST на самом деле очень проста:

| Структура кода | Корневой узел AST | Дочерние узлы |
|---------|-----------|-------|
| `1 + 2 * 3` | BinaryExpression (+) | левый: NumericLiteral(1), правый: BinaryExpression(*) |
| `let x = 10` | VariableDeclaration | VariableDeclarator → Identifier(x) + NumericLiteral(10) |
| `add(a, b)` | CallExpression | Identifier(add) + Arguments(a, b) |

::: tip Применение AST в повседневной разработке
Возможно, вы никогда не писали компилятор напрямую, но каждый день пользуетесь инструментами на основе AST:
- **ESLint / Prettier**: разбирают код в AST, проверяют правила или заново форматируют
- **Babel / SWC**: разбирают AST → преобразуют синтаксис → генерируют совместимый код
- **Рефакторинг в IDE**: на основе AST безопасно переименовывает, выделяет функции
- **Tree-shaking**: анализирует import/export в AST, удаляет неиспользуемый код
:::

## 5. Семантический анализ и оптимизация кода

Синтаксический анализ гарантирует, что код «структурно верен», но структурная верность не означает «верность смысла». Семантический анализ отвечает за проверку того, законен ли смысл кода, а оптимизация кода заставляет программу работать быстрее.

<CompilationPracticeDemo />

### 4.1 Семантический анализ: проверяем, верен ли «смысл»

| Содержание проверки | Пример | Результат |
|---------|------|------|
| Проверка типов | `int x = "hello"` | ❌ Несоответствие типов |
| Проверка области видимости | Использование необъявленной переменной `y` | ❌ Переменная не существует |
| Вывод типов | `1 + 2.0` | ✅ Результат выводится как float |
| Проверка параметров | `add(1, 2, 3)`, но функция принимает только 2 параметра | ❌ Несоответствие количества параметров |

::: tip Большинство ошибок, что вы видели, исходят из семантического анализа
- `TypeError: Cannot read properties of undefined` — проверка типов
- `ReferenceError: x is not defined` — проверка области видимости
- `Expected 2 arguments, but got 3` — проверка параметров
:::

### 4.2 Оптимизация кода: делаем программу быстрее

Перед генерацией финального кода компилятор выполняет различные оптимизации промежуточного кода. Эти оптимизации прозрачны для программиста, но способны заметно повысить производительность.

| Технология оптимизации | До оптимизации | После оптимизации | Принцип |
|---------|-------|-------|------|
| Свёртка констант | `x = 10 + 5` | `x = 15` | Результат вычисляется прямо при компиляции |
| Удаление мёртвого кода | `if (false) { ... }` | Просто удаляется | Код, который никогда не выполнится |
| Распространение констант | `x = 15; y = x * 2` | `y = 30` | Известное значение подставляется напрямую |
| Вынос инварианта цикла | Повторное вычисление `len = arr.length` внутри цикла | Вынос за цикл | Избежание повторных вычислений |

## 6. Практика технологий оптимизации: как компилятор ускоряет код

Выше мы упомянули названия нескольких технологий оптимизации, теперь рассмотрим подробнее, как именно компилятор это делает. Интерактивный компонент ниже показывает 5 самых распространённых оптимизаций компилятора — вы можете наглядно сравнить разницу кода до и после оптимизации.

<CodeOptimizationDemo />

Современные компиляторы и JIT-движки (такие как V8, GCC, LLVM) автоматически применяют десятки оптимизаций. Как разработчику, вам не нужно делать эти оптимизации вручную, но их понимание поможет вам:

- **Писать код, который легче оптимизировать**: например, использовать `const` вместо `let`, чтобы компилятору было проще свернуть константы
- **Понимать разницу в производительности**: почему маленькие функции быстрее больших? Потому что компилятор может их встроить
- **Избегать «деоптимизации»**: некоторые способы написания мешают компилятору оптимизировать, например `eval()` и `with`

| Технология оптимизации | Условие срабатывания | Влияние на производительность | Что может сделать разработчик |
|---------|---------|---------|-------------|
| Свёртка констант | В выражении только константы | Устранение вычислений во время выполнения | Чаще использовать объявление const |
| Удаление мёртвого кода | Код недостижим или результат не используется | Уменьшение объёма кода | Своевременно убирать бесполезный код |
| Вынос инварианта цикла | В цикле есть неизменное вычисление | Сокращение повторных вычислений | Ручной вынос — тоже хорошая привычка |
| Встраивание функций | Маленькая функция часто вызывается | Устранение накладных расходов на вызов | Держать функции маленькими и сфокусированными |
| Распространение констант | Значение переменной определимо при компиляции | Устраняется вся цепочка вычислений | Заменять «магические числа» константами |

## 7. Компилируемый vs интерпретируемый vs JIT

После написания кода есть три «способа перевода», чтобы он заработал. У каждого из этих способов свои плюсы и минусы, что напрямую определяет характеристики производительности языка и сценарии его использования.

<CompileVsInterpretDemo />

| Измерение | Компилируемый | Интерпретируемый | JIT (компиляция на лету) |
|------|-------|-------|------------|
| Процесс | Сначала весь код компилируется в машинный, затем исполняется | Читает и сразу исполняет, переводит строка за строкой | Сначала интерпретирует, затем горячий код компилирует |
| Скорость выполнения | Самая высокая | Самая низкая | Средняя (горячий код близок к компилируемому) |
| Скорость запуска | Низкая (нужна компиляция) | Высокая (запуск напрямую) | Средняя (нужен прогрев) |
| Кроссплатформенность | Нужна перекомпиляция | Кроссплатформенный по природе | Кроссплатформенный |
| Языки-представители | C, Rust, Go | Python, Ruby | JavaScript (V8), Java |

::: tip Почему JavaScript такой быстрый?
JIT-компилятор движка V8 отслеживает, какой код выполняется часто (горячий код), а затем компилирует его в высокооптимизированный машинный код. Поэтому, хотя JavaScript — «интерпретируемый язык», в V8 его производительность может приближаться к компилируемым языкам. В этом и уверенность Node.js, позволяющая ему работать на стороне сервера.
:::

## Итог

Теория компиляции — это знание не только для разработчиков компиляторов. Понимание процесса компиляции поможет вам лучше понимать сообщения об ошибках, выбирать подходящий язык, писать более эффективный код.

Вспомним ключевые моменты этой главы:

1. **Компилятор — это переводчик**: переводит человекочитаемый код в исполняемые машиной инструкции
2. **Шестишаговый конвейер**: лексический анализ → синтаксический анализ → семантический анализ → промежуточный код → оптимизация → генерация кода
3. **Лексический анализ разбивает на токены**: разбивает поток символов на осмысленные единицы — ключевые слова, идентификаторы, операторы и т. д.
4. **Синтаксический анализ строит AST**: по правилам синтаксиса организует токены в древовидную структуру, отражающую приоритет операций
5. **Семантический анализ обеспечивает корректность**: проверка типов, проверка области видимости — большинство виденных вами ошибок исходят отсюда
6. **Компилятор автоматически оптимизирует**: технологии вроде свёртки констант, удаления мёртвого кода, встраивания функций автоматически ускоряют код
7. **Три модели исполнения**: компилируемый — самый быстрый, интерпретируемый — самый гибкий, JIT сочетает оба
