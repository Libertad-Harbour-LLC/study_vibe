# Эволюция от монолита к микросервисам

::: tip Вступление
**Нет «лучшей» архитектуры, есть только «наиболее подходящая для текущего этапа».** Переход от монолита к микросервисам — не одномоментный скачок, а процесс постепенной эволюции по мере роста бизнеса и команды. Слишком раннее дробление на микросервисы так же опасно, как и слишком позднее.
:::

**Чему вас научит эта статья?**

После изучения этой главы вы получите:

- **Путь эволюции**: понимание четырёх этапов перехода от монолита к микросервисам
- **Момент дробления**: знание того, когда дробить, а когда не стоит
- **Стратегию дробления**: владение методологией дробления по бизнес-доменам
- **Паттерны коммуникации**: представление о выборе между синхронной и асинхронной коммуникацией сервисов
- **Дробление данных**: понимание вызовов и решений при дроблении базы данных

## 1. Путь эволюции архитектуры

Эволюция архитектуры движима не технологиями, а **масштабом организации**. Когда команда вырастает с 5 до 500 человек, эффективность совместной работы в монолитной архитектуре резко падает.

| Этап | Архитектура | Размер команды | Особенности |
|------|------|---------|------|
| Старт | Монолитное приложение | 1~10 человек | Весь код в одном проекте, развёртывание простое |
| Рост | Модульный монолит | 10~50 человек | Код разделён по модулям, но развёртывается всё ещё вместе |
| Расширение | SOA (сервис-ориентированная) | 50~200 человек | Дробление на крупноблочные сервисы по бизнес-линиям |
| Масштаб | Микросервисы | 200+ человек | Мелкоблочные сервисы, каждая команда разрабатывает и развёртывает независимо |

<ArchEvolutionDemo />

::: tip Закон Конвея
«Организации, проектирующие системы, производят архитектуры, копирующие структуру коммуникаций этих организаций.» — Мелвин Конвей

Проще говоря: 3 команды делают одну систему — в итоге получатся 3 сервиса. Суть дробления архитектуры — это **дробление организации**.

**Обратный закон Конвея**: раз структура организации определяет архитектуру системы, то, желая определённую архитектуру, сначала перестройте организацию под неё. Например, если вы хотите выделить независимый платёжный сервис, сначала сформируйте независимую платёжную команду. Во многих компаниях дробление на микросервисы проваливается не из-за технических проблем, а из-за того, что организация не перестроилась следом.
:::

## 2. Когда стоит дробить на микросервисы?

Не всем системам нужны микросервисы. Слишком раннее дробление привносит ненужную сложность.

| Сигнал | Пояснение | Рекомендация |
|------|------|------|
| Частые конфликты при развёртывании | Несколько команд меняют один репозиторий, часто конфликтуют | Рассмотреть дробление |
| Модуль требует независимого масштабирования | Модуль поиска требует в 10 раз больше ресурсов, чем другие | Рассмотреть дробление |
| Нужна разнородность стека технологий | AI-модуль на Python, основной сайт на Java | Рассмотреть дробление |
| Команда < 10 человек | Издержки коммуникации низки, монолита достаточно | Не дробить |
| Бизнес ещё в фазе исследования | Требования быстро меняются, границы размыты | Не дробить |
| Нет компетенций DevOps | Нет CI/CD, контейнеризации, системы мониторинга | Не дробить |

## 3. Стратегия дробления

### 3.1 Дробление по бизнес-доменам (ограниченный контекст DDD)

Ограниченный контекст (Bounded Context) из DDD (предметно-ориентированное проектирование) — лучший руководящий принцип дробления на микросервисы. Каждый ограниченный контекст соответствует независимому бизнес-домену со своей моделью данных и бизнес-правилами.

**Что такое ограниченный контекст?** Одно и то же слово в разных бизнес-доменах имеет разный смысл. Например, «пользователь» в домене пользователей — это регистрационная информация (имя, e-mail), в домене заказов — это заказчик (адрес доставки, способ оплаты), в домене рекомендаций — это поведенческий профиль (история просмотров, теги предпочтений). Ограниченный контекст очерчивает границу, внутри которой термины и модели имеют чёткий единый смысл.

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│ Домен польз. │  │ Домен заказ. │  │ Домен оплаты │
│             │  │             │  │             │
│ User        │  │ Order       │  │ Payment     │
│ Profile     │  │ OrderItem   │  │ Refund      │
│ Address     │  │ Cart        │  │ Transaction │
│             │  │             │  │             │
│ Сервис      │  │ Сервис      │  │ Сервис      │
│ пользоват.  │  │ заказов     │  │ оплаты      │
└──────┬──────┘  └──────┬──────┘  └──────┬──────┘
       │                │                │
       └── Вызов API / коммуникация по событиям ──┘
```

| Ограниченный контекст | Ключевые сущности | Соответствующий сервис |
|-----------|---------|---------|
| Домен пользователей | User, Profile, Address | Сервис пользователей |
| Домен товаров | Product, Category, SKU | Сервис товаров |
| Домен заказов | Order, OrderItem | Сервис заказов |
| Домен оплаты | Payment, Refund | Сервис оплаты |
| Домен логистики | Shipment, Tracking | Сервис логистики |

### 3.2 Паттерн «душитель» (Strangler Fig Pattern)

Не переписывайте весь монолит за раз, а, подобно фикусу-душителю, постепенно заменяйте старые модули новыми сервисами:

1. Создать новый сервис вне монолита
2. Через прокси-слой направить часть трафика на новый сервис
3. Убедившись в стабильности нового сервиса, постепенно мигрировать больше трафика
4. В итоге полностью заменить старый модуль

## 4. Паттерны коммуникации сервисов

| Способ | Протокол | Особенности | Сценарий применения |
|------|------|------|---------|
| REST | HTTP/JSON | Прост и универсален, хорошая экосистема | Внешние API, CRUD-операции |
| gRPC | HTTP/2 + Protobuf | Высокая производительность, строгая типизация | Частые вызовы между внутренними сервисами |
| Очередь сообщений | AMQP/Kafka | Асинхронная развязка, сглаживание пиков | Уведомления о событиях, асинхронные задачи |
| GraphQL | HTTP/JSON | Клиент запрашивает по потребности | Слой BFF, мобильные приложения |

::: tip Выбор между синхронным и асинхронным
- **Нужно вернуть результат немедленно** → синхронно (REST/gRPC)
- **Не нужно возвращать немедленно** → асинхронно (очередь сообщений)
- **Одно событие запускает несколько действий** → асинхронно (publish-subscribe)

Эмпирическое правило: что можно сделать асинхронно — делайте асинхронно; чем длиннее цепочка синхронных вызовов, тем хрупче система.
:::

## 5. Дробление данных: самая трудная часть

Самое мучительное при дроблении на микросервисы — не дробление кода, а дробление базы данных. Каждый сервис должен владеть своей базой данных, но это означает, что межсервисные запросы становятся сложными.

| Вызов | Описание | Решение |
|------|------|---------|
| Межсервисный JOIN | Нельзя напрямую сделать JOIN таблиц двух сервисов | Композиция запросов через API, дублирование данных |
| Распределённая транзакция | Транзакцию между базами нельзя реализовать локальной транзакцией | Saga, таблица локальных сообщений |
| Согласованность данных | Данные нескольких сервисов могут быть временно несогласованны | Итоговая согласованность, событийно-ориентированный подход |
| Миграция данных | Переход с общей базы на независимые | Двойная запись на переходный период, инструменты синхронизации данных |

## Заключение

Переход от монолита к микросервисам — это постепенный процесс, а не одномоментная революция.

Вспомним ключевые моменты этой главы:

1. **Путь эволюции**: монолит → модульный монолит → SOA → микросервисы, у каждого шага есть чёткая движущая сила
2. **Момент дробления**: размер команды, конфликты при развёртывании, потребность в масштабировании — сигналы к дроблению
3. **Стратегия дробления**: используйте ограниченный контекст DDD для руководства дроблением, паттерн «душитель» — для постепенной миграции
4. **Выбор коммуникации**: что можно сделать асинхронно — делайте асинхронно, цепочка синхронных вызовов должна быть как можно короче
5. **Дробление данных**: самое трудное, но самое важное; принятие итоговой согласованности — ключевой ментальный сдвиг
