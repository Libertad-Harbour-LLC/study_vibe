# Суть фронтенд-фреймворков

> 💡 **Учебный гид**: эта статья ответит на фундаментальный вопрос — **что же на самом деле делают фронтенд-фреймворки (Vue, React, Svelte и т. д.)?** Если вы изучали только HTML, CSS и немного JavaScript — это совершенно нормально, мы начнём с самого начала.

Прежде чем начать, убедитесь, что вы знакомы с этими двумя базовыми понятиями. Если не уверены, можете сначала прочитать соответствующие главы:

- **HTML**: скелет веб-страницы, определяет, какие элементы есть на странице (заголовки, абзацы, кнопки, изображения...). См. [HTML и компоновка CSS](./html-css-layout.md).
- **JavaScript**: язык программирования, который «оживляет» веб-страницу, может изменять содержимое страницы и реагировать на действия пользователя. См. [Глубокое руководство по JavaScript](./javascript-deep-dive.md).

Есть ещё одно понятие, которое будет часто встречаться дальше, и здесь мы дадим ему полное объяснение.

### Что такое DOM?

Полное название DOM — Document Object Model, по-русски «объектная модель документа».

Когда вы открываете веб-страницу в браузере, первое, что делает браузер, — считывает код HTML. После чтения браузер не берёт текст HTML напрямую для отображения страницы, а сначала **преобразует код HTML в древовидную структуру** и хранит её в памяти. Это дерево и называется деревом DOM.

Каждый узел (Node) дерева соответствует одному тегу в HTML. Отношения вложенности между тегами в дереве DOM превращаются в отношения родительского и дочернего узлов.

👇 **Попробуйте сами**:
Наведите мышь на код HTML слева — соответствующий узел в дереве DOM справа подсветится. И наоборот. Каждая строка HTML-тега соответствует одному узлу дерева DOM.

<WhatIsDomDemo />

**Зачем разбираться в DOM?** Потому что способ, которым JavaScript изменяет страницу, — это работа с этим деревом DOM: добавление узлов, удаление узлов, изменение содержимого узлов. А ключевая работа фронтенд-фреймворка как раз и состоит в том, чтобы автоматизировать для вас эти операции с DOM. Далее мы будем многократно упоминать DOM, и его понимание — основа понимания принципов работы фреймворков.

## 0. Введение: что такое «фронтенд-фреймворк»?

Сначала объясним слово «фреймворк». В программировании **фреймворк (Framework)** — это набор уже написанного кода и правил, который задаёт, как должен быть организован и как должен работать ваш код. Вы пишете код по его правилам, а он берёт на себя массу повторяющейся, рутинной низкоуровневой работы.

**Фронтенд-фреймворк** — это фреймворк, специально помогающий вам **строить интерфейс веб-страниц**. Сейчас самые распространённые — это Vue, React, Svelte, Angular.

## 1. Ключевой вопрос: данные изменились — что делать с интерфейсом?

### 1.1 Сначала разберёмся, что такое «данные» и «интерфейс»

В любом веб-приложении одновременно существуют две вещи:

- **Данные (Data / State)**: информация, хранящаяся внутри программы. Например, «в корзине 3 товара», «имя пользователя — Чжан Сань», «сейчас выбрана 2-я вкладка». Эти данные хранятся в переменных JavaScript, пользователь их не видит.
- **Интерфейс (UI)**: то, что пользователь видит на экране. Например, на странице отображается «Корзина(3)», отображается «Добро пожаловать, Чжан Сань», 2-я вкладка подсвечена. Это визуальный результат, выдаваемый HTML-элементами.

**Между данными и интерфейсом есть соответствие**: если данные — «3 товара», на интерфейсе должно отображаться «3». Если данные станут «4 товара», на интерфейсе тоже должно измениться на «4».

Вопрос в том: **кто отвечает за этот процесс «изменения вслед»?**

### 1.2 Почему при изменении переменной JavaScript интерфейс не меняется автоматически?

Это место, где новички с нуля чаще всего путаются, поэтому разберём низкоуровневый принцип шаг за шагом.

В JavaScript переменная — это участок памяти для хранения данных. Когда вы выполняете `count = count + 1`, движок JavaScript делает нечто очень простое: меняет значение в ячейке памяти count с 3 на 4. **На этом всё заканчивается, больше ничего не происходит.**

А отображаемое на странице содержимое (например, DOM-узел `<span>3</span>`) хранится в совершенно другом участке памяти. Изменяя переменную, движок JavaScript вообще не знает, что на странице есть DOM-узел, показывающий значение этой переменной, и нет никакого механизма, который заставил бы его это проверить.

Поэтому коренная причина такова: **переменные JavaScript и узлы DOM — это два независимых участка памяти, между которыми нет никакого автоматического механизма связи.** Изменение переменной меняет лишь память, где находится переменная, а память DOM-узла никак не затрагивается.

```javascript
let count = 3

// На странице есть DOM-узел, показывающий значение count:
// <span id="counter">3</span>

count = 4
// Что сделал движок JavaScript?
//   → изменил значение переменной count в памяти с 3 на 4
//   → конец. Всё.
// В <span> на странице по-прежнему отображается "3"
```

Если вы хотите, чтобы отображение на странице тоже стало «4», вам нужно **написать дополнительный код**: вручную найти тот DOM-узел и изменить его содержимое:

```javascript
count = 4  // Шаг 1: меняем переменную

// Шаг 2: вы должны написать сами — найти DOM-узел и поменять его текст на новое значение
document.getElementById('counter').textContent = count
```

Если на странице значение count отображается в 5 местах (количество в корзине, список товаров, общая сумма, промежуточный итог, подсказка статуса), вам придётся написать 5 таких фрагментов кода. **Пропустите любой из них — и в том месте отобразится старое значение, а пользователь увидит ошибочную информацию.**

### 1.3 Что делает фреймворк? Двумя шагами устанавливает автоматическую связь

Автоматическая синхронизация во фреймворке держится на **взаимодействии двух шагов** — без любого из них ничего не выйдет.

**Шаг первый: вы в шаблоне «регистрируете», где нужно отображать эту переменную**

В HTML-шаблоне фреймворка вы синтаксисом вроде `{{ count }}` помечаете «здесь нужно отображать значение count»:

```html
<!-- Шаблон Vue -->
<span>Корзина: {{ count }} шт.</span>    <!-- Место A: я хочу показать count -->
<span>Сумма: ¥{{ count * 99 }}</span>   <!-- Место B: я тоже использую count -->
<span>{{ count > 5 ? 'Слишком много' : 'Норма' }}</span>  <!-- Место C: я тоже использую count -->
```

При первой отрисовке страницы фреймворк фиксирует эту «связь регистрации»: **места A, B, C все зависят от count**.

**Шаг второй: фреймворк следит за переменной, при изменении сверяется с реестром и автоматически обновляет**

Фреймворк с помощью встроенного в JavaScript `Proxy` (прокси) «оборачивает» вашу переменную, превращая её в «отслеживаемую переменную». Когда вы изменяете эту переменную, Proxy одновременно с присваиванием тихо делает ещё одну вещь: уведомляет фреймворк, что «count изменился». Получив уведомление, фреймворк сверяется с реестром из первого шага и обновляет все три места A, B, C.

```
Нативный JS:
  Вы пишете HTML → <span id="counter">3</span> (без всякой связи с переменной)
  Вы меняете переменную → count = 4 → конец, интерфейс никак не реагирует
  Вы вручную дописываете → document.getElementById('counter').textContent = 4 → только тогда интерфейс обновляется

Фреймворк Vue:
  Вы пишете шаблон → <span>{{ count }}</span> (фреймворк запоминает: здесь зависимость от count)
  Вы меняете переменную → count = 4 → Proxy перехватывает → уведомляет фреймворк → фреймворк сверяется с реестром → автоматически обновляет A/B/C
```

Вот почему «автоматически синхронизировать может только фреймворк» — между `<span>` в нативном HTML и переменной JS вообще нет никакой связи, и именно синтаксис шаблона фреймворка (`{{ }}`) устанавливает эту связь. Вы написали `{{ count }}` — и только тогда фреймворк узнаёт, что здесь нужно показывать count; и только тогда фреймворк может при изменении count точно найти это место и обновить его.

👇 **Попробуйте понажимать**:
Сначала выберите «Нативный JavaScript», нажмите «Выполнить» и обратите внимание — переменная изменилась, а интерфейс ни с места, вам нужно шаг за шагом вручную синхронизировать каждое место. Затем переключитесь на «Использовать фреймворк» и так же нажмите «Выполнить» — стоит измениться переменной, как фреймворк автоматически выполняет все шаги, и интерфейс мгновенно догоняет.

## 2. Ключевая идея фреймворка: описывать интерфейс данными

### 2.1 Разница между двумя способами записи

Поняв ценность «автоматической синхронизации», давайте посмотрим, как именно фреймворк её реализует.

В эпоху без фреймворков (например, при использовании jQuery) код писался так — вы шаг за шагом говорите браузеру, что делать:

```javascript
// Шаг 1: найти на странице элемент с id, равным counter
var element = document.getElementById('counter')
// Шаг 2: изменить текстовое содержимое этого элемента на новое значение
element.textContent = '4'
// Шаг 3: найти другой элемент и тоже изменить
document.getElementById('total').textContent = '¥396'
// Шаг 4: если количество больше 5, ещё и изменить подсказку статуса...
```

Этот способ записи называется **императивным (Imperative)** — вы «приказываете» браузеру шаг за шагом выполнять операции.

С появлением фреймворка код становится таким — вы лишь описываете, «как должен выглядеть интерфейс»:

```html
<!-- Меня не волнует, как это значение обновится на странице -->
<!-- Я лишь говорю: здесь должно отображаться значение count -->
<span>{{ count }}</span>
<span>Сумма: ¥{{ count * 99 }}</span>
<span v-if="count > 5">Слишком много товаров!</span>
```

Этот способ записи называется **декларативным (Declarative)** — вы «декларируете» конечное состояние интерфейса, а как достичь этого состояния, фреймворк разбирается сам.

### 2.2 Ключевая формула: UI = f(State)

Все современные фронтенд-фреймворки — будь то Vue, React или Svelte — следуют одной ключевой идее, которую можно выразить формулой:

> **UI = f(State)**

Смысл этой формулы:

- **State (состояние)**: данные вашего приложения. Те самые переменные в JavaScript: сколько товаров в корзине, вошёл ли пользователь, какая страница сейчас открыта...
- **f (функция)**: механизм рендеринга фреймворка. Он знает, как превратить данные в интерфейс.
- **UI (интерфейс)**: конечный результат, который пользователь видит на экране.

**Смысл**: при заданном наборе данных (State), пройдя обработку фреймворком (f), детерминированно получается соответствующий интерфейс (UI). Данные изменились — интерфейс меняется вслед. Разработчику нужно заботиться только о данных, а не о том, как обновляется интерфейс.

👇 **Попробуйте понажимать**:
Изменяйте данные (State) слева и наблюдайте, как интерфейс (UI) справа автоматически меняется вслед. Это наглядное воплощение `UI = f(State)`.

### 2.3 Почему декларативный подход лучше императивного?

Преимущества декларативной записи:

| Параметр сравнения | Императивный (без фреймворка) | Декларативный (с фреймворком) |
| :--- | :--- | :--- |
| **Объём кода** | Для каждого обновления нужно писать конкретный код операции | Шаблон пишется один раз, фреймворк обрабатывает автоматически |
| **Вероятность ошибки** | Легко пропустить обновление какого-то места | Фреймворк гарантирует обновление всех мест |
| **Читаемость** | В коде намешано много операций с DOM | Код чётко описывает структуру интерфейса |
| **Стоимость сопровождения** | Изменение одной функции требует правок во многих местах | Достаточно изменить логику данных, интерфейс следует сам |

Проще говоря: декларативный подход позволяет сосредоточить силы на «бизнес-логике» (как меняются данные), не заботясь о повторяющемся и подверженном ошибкам деле «как обновлять интерфейс».

## 3. Реактивная система: как фреймворк узнаёт, что данные изменились?

### 3.1 Что такое «реактивность»?

Раньше мы говорили «данные изменились — интерфейс обновляется автоматически». Но здесь есть техническая проблема: **у самого JavaScript нет способности «при изменении переменной автоматически уведомлять других»**.

Вы пишете `count = 4`, и JavaScript лишь меняет значение `count` с 3 на 4, не уведомляя никого автоматически. Фреймворку нужен механизм, чтобы «обнаружить», что вы изменили данные.

**Реактивность (Reactivity)** — это общее название такого механизма: когда данные изменяются, система может автоматически почувствовать изменение и выполнить соответствующую операцию обновления.

### 3.2 Три разных способа реализации

Разные фреймворки применяют разные технические подходы к реализации реактивности. Это и есть самое фундаментальное различие между Vue, React и Svelte.

**Способ первый: перехват через прокси (подход Vue)**

Vue использует встроенный в JavaScript механизм `Proxy` (прокси). `Proxy` может автоматически выполнять заданный вами код при чтении или изменении свойства объекта.

Vue оборачивает ваш объект данных в `Proxy`. Когда вы выполняете `count = 4`, `Proxy` перехватывает эту операцию записи и уведомляет Vue: «значение count изменилось», после чего Vue обновляет все части интерфейса, использующие `count`.

Вам как разработчику не нужно делать ничего дополнительного — просто присваивайте значение, Vue почувствует это автоматически.

**Способ второй: явный вызов (подход React)**

React не использует `Proxy`. Он требует, чтобы вы изменяли данные обязательно через специальную функцию:

```javascript
// Запись в React
const [count, setCount] = useState(0)

// Нельзя писать напрямую count = 4 (React этого не почувствует)
// Нужно вызвать setCount:
setCount(4)
```

Только когда вы вызываете `setCount()`, React узнаёт, что данные изменились, и обновляет интерфейс. Если вы напишете напрямую `count = 4`, React вообще ничего не узнает, и интерфейс не обновится.

Этот способ более «явный» — каждое изменение данных вы активно сообщаете фреймворку, и неожиданных обновлений не будет.

**Способ третий: анализ компилятором (подход Svelte)**

Svelte пошёл совершенно иным путём. У него есть компилятор (Compiler), который анализирует ваш исходный код до его запуска.

Когда компилятор видит, что вы написали оператор присваивания вроде `count += 1`, он автоматически вставляет после этой строки фрагмент кода, «уведомляющий интерфейс об обновлении». То есть к моменту выполнения кода действие «уведомления» уже заранее организовано компилятором.

Ваш код выглядит как обычное присваивание JavaScript, но в скомпилированном коде появляется логика обновления интерфейса.

### 3.3 Сравнение трёх способов

| Параметр сравнения | Vue (прокси Proxy) | React (явный вызов) | Svelte (компилятор) |
| :--- | :--- | :--- | :--- |
| **Запись для разработчика** | Прямое присваивание `count = 4` | Обязательно через `setCount(4)` | Прямое присваивание `count = 4` |
| **Момент обнаружения изменения** | Автоматический перехват во время выполнения | Активное уведомление разработчиком | Вставка кода уведомления заранее при компиляции |
| **Издержки во время выполнения** | У Proxy небольшие издержки на перехват | У планирования setState небольшие издержки | Почти нет дополнительных издержек |
| **Сложность отладки** | Средняя | Поток данных ясен, относительно легко | Нужно понимать скомпилированный код |
| **Подходящие сценарии** | Стремление к эффективности разработки и естественной записи | Стремление к предсказуемому потоку данных | Стремление к предельной производительности |

У трёх способов нет абсолютно хорошего или плохого. Vue писать естественнее всего, поток данных React наиболее управляем, производительность Svelte во время выполнения наилучшая. Что выбрать — зависит от конкретных нужд проекта.

## 4. Компоненты: разбиваем интерфейс на переиспользуемые блоки

### 4.1 Зачем разбивать?

В полноценной веб-странице могут быть навигационная панель, боковая панель, область контента, поле поиска, аватар пользователя, всевозможные кнопки... Если весь код написать в одном файле, этот файл станет очень длинным и крайне трудным в сопровождении.

**Компонент (Component)** — это разбиение интерфейса на отдельные небольшие блоки, каждый из которых управляет своими данными, своим интерфейсом, своей логикой.

Например, страницу интернет-магазина можно разбить на такие компоненты:

- Компонент `NavBar`: отвечает за верхнюю навигационную панель
- Компонент `SearchBox`: отвечает за поле поиска
- Компонент `ProductCard`: отвечает за одну карточку товара
- Компонент `ShoppingCart`: отвечает за корзину

Каждый компонент независим. `ProductCard` не нужно знать, какой код написан в `NavBar`, ему достаточно управлять собой.

### 4.2 Три преимущества компонентов

**Преимущество первое: переиспользование.** Один раз написанный компонент `ProductCard` можно использовать на странице 100 раз — каждый раз передавая разные данные товара, вы получаете разные карточки товаров. Не нужно копировать-вставлять 100 копий HTML-кода.

**Преимущество второе: инкапсуляция.** Данные и логика внутри компонента независимы. Изменение кода компонента `SearchBox` не повлияет на компонент `ProductCard`. При командной работе разные люди могут одновременно разрабатывать разные компоненты, не мешая друг другу.

**Преимущество третье: сопровождаемость.** Когда с какой-то функцией возникает проблема, вы можете сразу локализовать её в соответствующем компоненте и исправить, не роясь в огромном файле на несколько тысяч строк.

👇 **Попробуйте понажимать**:
Нажимайте на имена компонентов слева, чтобы увидеть соответствующую им область на странице. Обратите внимание: один и тот же компонент `ProductCard` переиспользуется многократно, каждый раз отображая разные данные.

### 4.3 Как компонент выглядит в коде?

На примере Vue: компонент — это файл `.vue`, содержащий три части:

```html
<!-- ProductCard.vue -->
<template>
  <!-- Здесь пишется структура HTML — «внешний вид» компонента -->
  <div class="card">
    <h3>{{ name }}</h3>
    <p>Цена: ¥{{ price }}</p>
    <button @click="addToCart">В корзину</button>
  </div>
</template>

<script setup>
// Здесь пишется логика JavaScript — «поведение» компонента
const props = defineProps(['name', 'price'])

function addToCart() {
  // Обработка логики «в корзину»
}
</script>

<style scoped>
/* Здесь пишутся стили CSS — «стиль» компонента */
.card {
  border: 1px solid #ccc;
  padding: 16px;
}
</style>
```

При использовании этого компонента всё выглядит как использование собственного HTML-тега:

```html
<!-- Использование компонента ProductCard в других местах -->
<ProductCard name="Беспроводные наушники" price="299" />
<ProductCard name="Механическая клавиатура" price="599" />
<ProductCard name="Монитор" price="1999" />
```

Три строки кода отрисовали три разные карточки товаров.

## 5. Цена операций с DOM: почему фреймворки тратят на это столько сил?

### 5.1 Что такое операции с DOM?

Ранее упоминался DOM — древовидная структура, которую браузер формирует после разбора HTML. **Операции с DOM** — это изменение узлов этого дерева с помощью JavaScript. Например, поменять фрагмент текста, добавить элемент, удалить элемент, изменить стиль.

Сами по себе эти операции несложны, но после их выполнения браузеру нужно проделать много дополнительной работы, чтобы обновить отображение на экране:

1. **Заново вычислить стили**: нужно ли изменить CSS-стили этого узла и его потомков?
2. **Заново скомпоновать (Layout / Reflow)**: нужно заново вычислить положение и размер всех элементов страницы. Потому что изменение одного элемента может повлиять на положение других.
3. **Заново отрисовать (Paint)**: нарисовать вычисленное содержимое на экране.

Каждый из этих трёх шагов имеет вычислительную стоимость. Если ваш код часто запускает операции с DOM, браузер раз за разом выполняет эти шаги, и страница начинает тормозить.

👇 **Попробуйте понажимать**:
Сравните время прямых операций с DOM и пакетных операций с DOM. По мере роста числа изменений время «поэлементных операций» резко возрастает.

### 5.2 Как фреймворк решает эту проблему?

Раз прямые операции с DOM дороги, фреймворк стремится **сократить число операций с DOM**. Есть две стратегии:

**Стратегия первая: виртуальный DOM + сравнение различий (подход Vue, React)**

Виртуальный DOM (Virtual DOM) — это объект JavaScript, структура которого один к одному соответствует реальному дереву DOM, но существует он только в памяти и не запускает компоновку и отрисовку браузера.

Когда данные изменяются, фреймворк действует так:

1. Создаёт средствами JavaScript «новое дерево виртуального DOM», описывающее, как должен выглядеть интерфейс после изменения данных
2. Сравнивает это новое дерево со старым (этот процесс называется **Diff**, то есть сравнением различий) и находит, какие узлы изменились
3. Применяет к реальному DOM только реально изменившиеся части (этот процесс называется **Patch**, то есть наложением заплатки)

В итоге, как бы ни менялись данные, число операций над реальным DOM всегда минимально.

👇 **Попробуйте понажимать**:
Нажмите «Изменить данные» и наблюдайте, как виртуальный DOM сравнивает старое и новое деревья, находя изменившиеся узлы. Обратите внимание на «реальный DOM» справа — мигают только реально изменившиеся части.

<VirtualDomDiffDemo />

**Стратегия вторая: точная локализация при компиляции (подход Svelte)**

Svelte не использует виртуальный DOM. Его компилятор уже при написании вами кода анализирует: «когда `count` изменится, нужно обновить элемент `<span>` в строке 3». Во время выполнения он напрямую обращается к этому элементу для обновления, без всякого сравнения старого и нового деревьев.

Этот подход пропускает шаг Diff и теоретически даёт лучшую производительность. Но он зависит от аналитических способностей компилятора — компилятор должен быть достаточно умён, чтобы правильно выявить все места, требующие обновления.

## 6. Время выполнения vs время компиляции: ключевой компромисс в дизайне фреймворков

### 6.1 Два этапа

Фронтенд-код от момента написания до итогового выполнения в браузере проходит два этапа:

- **Время компиляции (Compile-time / Build-time)**: ваш исходный код обрабатывается инструментом сборки (например, Vite, Webpack) и преобразуется в код, который браузер может выполнить напрямую. Этот процесс происходит на вашем компьютере, до того как пользователь откроет страницу.
- **Время выполнения (Runtime)**: преобразованный код выполняется в браузере пользователя. Ключевая логика фреймворка (например, Diff виртуального DOM, отслеживание реактивности) работает именно на этом этапе.

### 6.2 Распределение работы фреймворка между этими двумя этапами

Разные фреймворки распределяют объём работы между этими двумя этапами по-разному, и это определяет их характеристики производительности и размер пакета:

- **React**: большая часть работы выполняется во время выполнения. Создание виртуального DOM, Diff, Patch — всё происходит в браузере. Плюс — высокая гибкость; цена — нужно отправить браузеру весь код среды выполнения фреймворка (около 40 КБ).
- **Vue**: смешанный подход. Шаблон оптимизируется при компиляции (компилятор помечает, какие узлы статичны и не изменятся), но итоговое обновление интерфейса по-прежнему выполняется через виртуальный DOM во время выполнения. Код среды выполнения около 30 КБ.
- **Svelte**: большая часть работы выполняется при компиляции. Компилятор анализирует ваш код и напрямую генерирует точные инструкции обновления DOM. Во время выполнения кода фреймворка почти нет — в итоговую сборку попадает только ваш бизнес-код. Размер пакета минимальный.

Нажимайте на разные вкладки фреймворков, чтобы увидеть их положение на спектре «время выполнения ↔ время компиляции», а также их компромиссы по размеру пакета, производительности во время выполнения и опыту разработки.

### 6.3 Отраслевой тренд

Направление развития фреймворков в последние годы очень чёткое: **переносить всё больше работы со времени выполнения на время компиляции**. Потому что вычисления при компиляции не расходуют ресурсы устройства пользователя и не влияют на скорость загрузки страницы.

- **Vue** разрабатывает Vapor Mode (паровой режим), который позволяет пропустить виртуальный DOM и при компиляции напрямую генерировать код операций с DOM
- **React** выпустил React Compiler, автоматически оптимизирующий поведение перерисовки компонентов при компиляции
- **Svelte 5** ввёл систему Runes, ещё больше усилившую аналитические возможности при компиляции

## 7. Итог

Вспомним ключевые моменты этой статьи:

**Фундаментальная проблема, которую решают фронтенд-фреймворки**: когда данные в приложении изменяются — автоматически, эффективно и надёжно обновлять интерфейс, не заставляя разработчика вручную работать с DOM.

**Общая ключевая идея, которой они следуют**: UI = f(State) — интерфейс является функцией данных, разработчику нужно лишь следить за изменениями данных, а фреймворк отвечает за отражение этих изменений на интерфейсе.

**Их ключевые технические различия**:

| Технический аспект | Смысл |
| :--- | :--- |
| **Реактивная система** | Как фреймворк обнаруживает изменения данных. Vue использует перехват Proxy, React — явный setState, Svelte — анализ компилятором. |
| **Виртуальный DOM** | Vue и React используют объект JavaScript для имитации дерева DOM, через сравнение старого и нового деревьев (Diff) находят минимальный объём обновлений, сокращая операции над реальным DOM. |
| **Компонентность** | Разбиение интерфейса на отдельные переиспользуемые блоки, каждый компонент управляет своими данными и интерфейсом. |
| **Оптимизация при компиляции** | Выполнение анализа и оптимизации заранее, на этапе сборки кода, для сокращения вычислений во время выполнения. Svelte зашёл в этом дальше всех. |

**В одной фразе**: суть работы фронтенд-фреймворка в том, чтобы взять на себя процесс синхронизации «от данных к интерфейсу», позволив разработчику думать только о логике данных и больше не работать с интерфейсом вручную.

## Таблица соответствия терминов

| Английский термин | Русское соответствие | Пояснение |
| :--- | :--- | :--- |
| **Framework** | Фреймворк | Набор заранее написанного кода и правил, предоставляющий разработчику базовую структуру приложения и распространённый функционал. |
| **DOM** | Объектная модель документа | Древовидная структура данных, которую браузер формирует после разбора HTML; JavaScript изменяет страницу, работая с ней. |
| **Virtual DOM** | Виртуальный DOM | Имитация дерева DOM объектом JavaScript; через алгоритм Diff находит минимальный путь обновления, сокращая число операций над реальным DOM. |
| **State** | Состояние | Данные в приложении, например информация о пользователе, содержимое корзины, текущее состояние страницы и т. п. |
| **Reactivity** | Реактивность | Способность системы автоматически чувствовать изменение данных и выполнять соответствующее обновление интерфейса. |
| **Proxy** | Прокси | Встроенный механизм JavaScript, способный перехватывать операции чтения и записи объекта. Vue 3 использует его для реализации реактивности. |
| **Component** | Компонент | Отдельный переиспользуемый фрагмент кода интерфейса, содержащий собственную структуру HTML, логику JavaScript и стили CSS. |
| **Declarative** | Декларативный | Способ программирования: вы описываете, «какой конечный результат хотите», а фреймворк решает, как это реализовать. |
| **Imperative** | Императивный | Способ программирования: вы шаг за шагом говорите программе, «как именно делать». |
| **Diff** | Сравнение различий | Сравнение старого и нового деревьев виртуального DOM для поиска изменившихся узлов. |
| **Patch** | Наложение заплатки | Применение найденных при Diff изменений к реальному DOM. |
| **Compile-time** | Время компиляции | Период обработки кода на этапе сборки, происходит до того, как пользователь откроет страницу. |
| **Runtime** | Время выполнения | Период выполнения кода в браузере пользователя. |
| **Compiler** | Компилятор | Программа, преобразующая исходный код в другую форму кода. Компилятор Svelte преобразует файлы `.svelte` в эффективный JavaScript. |
