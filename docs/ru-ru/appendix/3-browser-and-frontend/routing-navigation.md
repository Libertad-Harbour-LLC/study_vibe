# Маршрутизация и навигация
::: tip 🎯 Ключевой вопрос
**Почему некоторые сайты при переключении страниц не белеют и не перезагружаются, работая плавно, как приложение?** Это и есть магия фронтенд-маршрутизации. Эта глава проведёт вас от «перелистывания страниц как в книге» традиционных сайтов в мир «переключения слайдов» одностраничных приложений и поможет понять, как фронтенд-маршрутизация поднимает пользовательский опыт на новый уровень.
:::

## 1. Зачем нужна «фронтенд-маршрутизация»?

### 1.1 От традиционного сайта к одностраничному приложению: качественный скачок пользовательского опыта

Вспоминая опыт просмотра ранних сайтов, каждое нажатие на ссылку было процессом «полного перелистывания страницы»: страница на мгновение белела, крутился индикатор загрузки, вся страница перерисовывалась заново. Если сеть была медленной, приходилось ещё несколько секунд тупо смотреть на крутящийся индикатор. Сегодня такой опыт кажется устаревшим, но тогда это был стандарт.

Современная фронтенд-разработка полностью изменила эту модель. Мы используем технологию фронтенд-маршрутизации, благодаря которой переключение страниц происходит так же плавно, как в мобильном приложении — без белого экрана, без индикатора загрузки, пользователь почти не ощущает процесс «перехода». Это улучшение опыта не магия, а заслуга системы фронтенд-маршрутизации.

### 1.2 Реальная история о ловушке: почему вам нужно понимать режимы маршрутизации

Вы можете сказать: «Я использую Vue Router или React Router, настроил и работает, зачем мне понимать эти низкоуровневые принципы?» Расскажу реальную историю, и вы поймёте, почему эти знания так важны.

::: warning История о ловушке развёртывания у Сяо Ли
Сяо Ли — новичок во фронтенде, который только устроился на работу и сразу отвечал за разработку одностраничного приложения на Vue. При локальной разработке всё было нормально, переходы по маршрутам шли как по маслу. Но когда он развернул проект на тестовом сервере, появилась проблема: при прямом обращении к какому-то маршруту (например, `example.com/user/123`) или при обновлении страницы деталей пользователь видел ошибку **404 Not Found**.

Сяо Ли был в недоумении: локально ведь всё открывается нормально, почему после развёртывания 404? Он долго искал причину, даже заподозрил проблему в настройках сервера.

Позже он обратился к старшему коллеге, и тот с одного взгляда увидел проблему: Сяо Ли использовал режим History, но на сервере не был настроен fallback. Когда пользователь напрямую обращается к `/user/123`, сервер ищет файл, соответствующий этому пути, но все маршруты SPA на самом деле указывают на один и тот же `index.html`. Решение очень простое: настроить сервер так, чтобы все маршруты откатывались к `index.html`, и передать дальнейшую обработку фронтенд-маршрутизации.

С тех пор Сяо Ли усвоил истину: **не понимая принципов режимов маршрутизации и требований к настройке сервера, ты даже не знаешь, почему возникает ошибка, не говоря уже о её решении.**
:::

::: info 💡 Ключевая идея
Фронтенд-маршрутизация — это не «чёрная магия», понимание принципов её работы позволяет быстро локализовать и точно решать проблемы развёртывания, производительности и SEO. Что ещё важнее, это помогает делать более разумный выбор при проектировании архитектуры — когда использовать режим Hash, когда режим History, как избежать распространённых ловушек.
:::

## 2. Основные концепции: маршрут, режим, навигация

Прежде чем углубляться в конкретную реализацию, нам нужно разобраться с несколькими основными концепциями. Чтобы вам было легче понять, мы используем метафору библиотеки для аналогии их взаимосвязи.

::: tip 🤔 Как эти концепции связаны с маршрутизацией?
Маршрут, режим и навигация — это три столпа системы фронтенд-маршрутизации.

Когда вы используете Vue Router или React Router, фреймворк помогает вам обработать:
1. **Сопоставление маршрутов** → определение соответствия между URL и компонентами
2. **Выбор режима** → решение, использовать ли режим Hash или History
3. **Управление навигацией** → обработка переходов между страницами, кнопок «вперёд/назад» браузера

Поэтому **понимание этих трёх концепций позволяет вам узнать, что именно делает система маршрутизации, почему иногда нужна особая настройка и почему при развёртывании возникают проблемы.**
:::

### 2.1 Понимание системы маршрутизации через метафору библиотеки

Представьте, что вы ищете книгу в библиотеке, этот процесс поразительно похож на принцип работы фронтенд-маршрутизации:

| Концепция | 📚 Метафора библиотеки | Реальное назначение | Конкретный пример |
|------|-------------|----------|----------|
| **Маршрут (Route)** | Соответствие между номером стеллажа и книгой | Определяет соответствие между URL и компонентом страницы | Путь `/user/123` соответствует компоненту `UserDetail.vue` |
| **Маршрутизатор (Router)** | Система навигации и поиска в библиотеке | Основной модуль, управляющий всеми маршрутами и обрабатывающий навигацию | Vue Router, React Router — это маршрутизаторы |
| **Режим маршрутизации** | Способ индексирования (карточный каталог vs электронная система) | Определяет форму URL и способ низкоуровневой реализации | Режим Hash использует `#`, режим History — обычный путь |
| **Навигация** | Переход от одного стеллажа к другому | Действие переключения между разными страницами | Нажатие на ссылку, программный переход, кнопки «вперёд/назад» браузера |

::: tip 📊 Что вы можете увидеть из таблицы?
Разберём эту таблицу построчно:

**Маршрут**: это всего лишь «конфигурация», которая сообщает системе, «какому URL соответствует какая страница». Как номер книги в библиотеке соответствует её местоположению.

**Маршрутизатор**: это «управляющий», отвечающий за поиск соответствующего компонента по текущему URL и его рендеринг. Как библиотекарь помогает найти книгу по предоставленному вами номеру.

**Режим маршрутизации**: это «способ реализации», определяющий, как выглядит URL и какая технология используется на низком уровне. Как библиотека может использовать бумажный каталог или электронную систему поиска.

**Навигация**: это «действие», действие пользователя, запускающее переключение страниц. Как вы в библиотеке переходите из зоны A в зону B.

Понимать разницу между этими четырьмя очень важно: **маршрут — это статическая конфигурация, маршрутизатор — динамический управляющий, режим — технологический выбор, навигация — действие пользователя.**
:::

### 2.2 Маршрут (Route): контракт сопоставления URL и компонента

Маршрут, по сути, — это «контракт», который определяет, какое содержимое должно отображаться при обращении к некоторому URL. В Vue Router типичная конфигурация маршрута выглядит так:

```javascript
const routes = [
  {
    path: '/',           // URL 路径
    component: Home      // 对应的组件
  },
  {
    path: '/user/:id',   // 带参数的动态路由
    component: UserDetail,
    children: [          // 嵌套路由
      { path: 'profile', component: UserProfile },
      { path: 'posts', component: UserPosts }
    ]
  }
]
```

**У вас может возникнуть вопрос: почему бы не использовать тег `<a>` для перехода, зачем обязательно маршрутизация?**

Ответ кроется в самой сути «одностраничного приложения»: у SPA только одна HTML-страница, и всё переключение страниц на самом деле — это замена компонентов внутри одной страницы. Если вы используете традиционный `<a href="/user/123">`, браузер действительно запросит путь `/user/123`, что приведёт к перезагрузке страницы или ошибке 404. Роль маршрутизации — перехватывать эти действия перехода и динамически заменять компоненты с помощью JavaScript, реализуя переключение без перезагрузки.

::: details 🔧 Несколько распространённых паттернов конфигурации маршрутов
**Статический маршрут** (самый простой):
```javascript
{ path: '/home', component: Home }
{ path: '/about', component: About }
```

**Динамический маршрут** (с параметрами):
```javascript
{ path: '/user/:id', component: UserDetail }
// 可以匹配 /user/123、/user/abc 等
// 组件内可以通过 route.params.id 获取参数
```

**Вложенные маршруты** (отношение родитель-потомок):
```javascript
{
  path: '/user/:id',
  component: UserLayout,    // 父组件
  children: [
    { path: 'profile', component: UserProfile },   // 实际路径 /user/:id/profile
    { path: 'posts', component: UserPosts }        // 实际路径 /user/:id/posts
  ]
}
```

**Маршрут с подстановочным знаком** (страница 404):
```javascript
{ path: '/:pathMatch(.*)*', component: NotFound }
// 匹配所有未定义的路由
```
:::

### 2.3 Режим маршрутизации: сущностная разница между Hash и History

У фронтенд-маршрутизации есть два основных режима реализации: режим Hash и режим History. Они принципиально отличаются по форме URL, низкоуровневой реализации, совместимости и т. д.

::: tip 🤔 Зачем нужны два режима?
Это, по сути, результат исторических причин и технических компромиссов.

**Режим Hash** — самый ранний способ реализации фронтенд-маршрутизации, он использует hash-часть URL (то есть содержимое после `#`). Изменение hash не вызывает перезагрузки страницы, и совместимость отличная (поддерживается даже IE8).

**Режим History** — это «стандартный подход» после выхода HTML5, он использует методы `pushState` и `replaceState` из History API, что позволяет сделать URL более «нормальным» (без `#`), но требует поддержки со стороны сервера.

Сравнение: режим Hash — как «приклеить стикер на дверь комнаты» (не влияет на структуру комнаты), режим History — как «заново пронумеровать комнаты» (требует обновления системы табличек).
:::

| Характеристика | Режим Hash | Режим History |
|------|-----------|--------------|
| **Пример URL** | `https://example.com/#/user/123` | `https://example.com/user/123` |
| **Принцип реализации** | Прослушивание события `hashchange` | Использование History API (`pushState`, `replaceState`) |
| **Настройка сервера** | Не требуется (hash не отправляется на сервер) | **Обязательна настройка fallback на index.html** |
| **Совместимость с браузерами** | IE8+ (почти все браузеры) | IE10+ (современные браузеры) |
| **Дружелюбность к SEO** | Хуже (поисковики могут игнорировать hash) | Хорошо (чёткая структура URL) |
| **Пользовательский опыт** | В URL есть `#`, выглядит как «переход к якорю» | URL красивый, близок к традиционному сайту |
| **Сложность развёртывания** | Низкая, без особой настройки | Высокая, нужна правильная настройка сервера |

::: tip 📊 Что вы можете увидеть из таблицы?
Разберём эту таблицу построчно:

**Пример URL**: в URL режима Hash есть заметный `#`, пользователь с одного взгляда поймёт, что это «одностраничное приложение»; URL режима History такой же, как у традиционного сайта, выглядит более «профессионально».

**Принцип реализации**: режим Hash прослушивает событие `hashchange` (срабатывает при изменении hash); режим History использует History API из HTML5, может «притворяться», что страница перешла, но на самом деле не перезагружается.

**Настройка сервера**: это самое ловушечное место! Содержимое после `#` в режиме Hash не отправляется на сервер, поэтому серверу не нужно знать о существовании маршрутов; но полный путь в режиме History отправляется на сервер, и если сервер не настроен, вернётся 404.

**Дружелюбность к SEO**: поисковые краулеры обычно не выполняют JavaScript, URL режима Hash могут быть проигнорированы; структура URL режима History чёткая, легче индексируется.

**Сложность развёртывания**: режим Hash работает «из коробки», режим History требует знаний по администрированию (Nginx, Apache и т. д.). Именно поэтому многие персональные проекты по умолчанию используют режим Hash.

## 3. Путь эволюции: от традиционного сайта к современной маршрутизации

Поговорив о стольких концепциях, давайте посмотрим на реальный кейс: как один интернет-магазин шаг за шагом эволюционировал от «традиционных многостраничных» к «современной маршрутизации одностраничного приложения». Через этот кейс вы нагляднее поймёте, какую проблему решает фронтенд-маршрутизация.

::: tip 📖 Фоновые знания: что такое MPA, SPA, SSR?
Прежде чем начать кейс, кратко представим эти термины:

- **MPA (Multi-Page Application)**: **многостраничное приложение**, традиционный способ разработки сайтов. Каждая страница — отдельный HTML-файл, переход между страницами перезагружает всю страницу.
- **SPA (Single-Page Application)**: **одностраничное приложение**, основной способ современного фронтенда. Только один входной HTML, переключение страниц через динамическую замену компонентов на JavaScript, без перезагрузки.
- **SSR (Server-Side Rendering)**: **серверный рендеринг**, полный HTML генерируется на стороне сервера. Сочетает преимущества SPA и MPA, быстрый рендеринг первого экрана, хорошее SEO.

**Простое понимание**: MPA — это «каждый раз перерисовываем всю страницу», SPA — «стираем и рисуем заново на одном листе», SSR — «заранее рисуем на листе и отдаём вам».
:::

### 3.1 Полная панорама эволюции

Таблица ниже показывает четыре этапа эволюции фронтенд-приложений, вы можете увидеть, как шаг за шагом развивалась технология маршрутизации:

| Этап | Тип приложения | Реализация маршрутизации | Ключевые особенности | Пользовательский опыт |
|------|---------|---------|---------|---------|
| **Этап 1: традиционный многостраничный** | MPA | Серверная маршрутизация | Каждая страница — отдельный HTML-файл | Каждый переход перезагружает |
| **Этап 2: ранний SPA** | SPA (режим Hash) | Hash-маршрутизация | URL с `#`, хорошая совместимость | Без перезагрузки, но URL некрасивый |
| **Этап 3: современный SPA** | SPA (режим History) | History-маршрутизация | Красивый URL, нужна настройка сервера | Плавно, URL близок к традиционному сайту |
| **Этап 4: гибридный рендеринг** | SPA + SSR | Изоморфная маршрутизация | Первый экран — серверный рендеринг, далее фронтенд-маршрутизация | Быстрый первый экран, хорошее SEO, плавный опыт |

::: tip 📊 Что вы можете увидеть из таблицы?
Разберём эту таблицу построчно:

**Этап 1 → Этап 2**: от «с перезагрузкой» к «без перезагрузки», это качественный скачок. Пользователь впервые ощутил плавность «как в приложении», но ценой стал `#` в URL, выглядящий не очень профессионально.

**Этап 2 → Этап 3**: от «работает» к «удобно использовать». Режим History делает URL красивым, ближе к традиционному сайту, но ценой стало увеличение сложности развёртывания (нужна настройка сервера).

**Этап 3 → Этап 4**: от «хорошего опыта» к «хороший опыт + хорошее SEO». SSR решает проблему SEO у SPA, скорость рендеринга первого экрана тоже выше, но сложность реализации значительно возрастает.

**Подведём итог**: эволюция фронтенд-маршрутизации — это не просто «переключение стало быстрее», а **обновление всей архитектуры приложения** — от доминирования сервера к доминированию фронтенда, а затем к сочетанию фронтенда и бэкенда, каждый шаг балансирует множество измерений: пользовательский опыт, стоимость разработки, SEO.
:::

### 3.2 Этап 1: традиционное многостраничное приложение — перезагрузка каждый раз

Почему оно называется «традиционным многостраничным приложением»? Потому что на этом этапе каждая страница — отдельный HTML-файл, и при переходе между страницами браузер заново загружает все ресурсы (HTML, CSS, JS). Это самый ранний способ веб-разработки, многие традиционные сайты до сих пор работают так.

На этом этапе интернет-магазин «Купи больше» использовал типичную архитектуру MPA:

**Способ разработки**:
- **Реализация маршрутизации**: серверная маршрутизация, каждая страница соответствует одному HTML-файлу на сервере
- **Переход между страницами**: используется `<a href="/products/123">`, что вызывает полную перезагрузку страницы
- **Управление состоянием**: при каждом переходе теряется предыдущее состояние страницы (позиция прокрутки, содержимое формы и т. д.)

**Особенности этого этапа**:
- ✅ **Преимущества**: простая реализация, дружелюбно к поисковикам (хорошее SEO), кнопки «вперёд/назад» браузера работают из коробки
- ❌ **Недостатки**: каждый переход перезагружает, плохой пользовательский опыт, большая нагрузка на сервер (повторная загрузка одних и тех же ресурсов)

::: details Посмотреть структуру проекта и процесс обращения того времени
**Структура проекта** (типичная структура серверного рендеринга):
```
server/
├── views/              # HTML 模板
│   ├── index.html      # 首页模板
│   ├── products.html   # 商品列表页模板
│   └── product.html    # 商品详情页模板
├── public/             # 静态资源
│   ├── css/
│   ├── js/
│   └── images/
└── server.js           # 服务器入口
```

**Процесс перехода между страницами**:
```
1. 用户点击链接 <a href="/products/123">
       ↓
2. 浏览器发送 GET 请求到服务器
       ↓
3. 服务器渲染 product.html，插入数据
       ↓
4. 返回完整的 HTML 页面
       ↓
5. 浏览器解析 HTML、下载 CSS/JS、渲染页面
       ↓
6. 用户看到页面（这个过程通常需要 1-3 秒）
```

**Боли пользователя**:
- После нажатия на ссылку страница белеет, долгое время ожидания
- При каждом переходе заново загружаются одни и те же файлы CSS/JS
- Кнопки «вперёд/назад» браузера заново загружают страницу
- Невозможно сохранить сложное состояние страницы (например, условия фильтрации, позицию прокрутки)
:::

Такой способ разработки ещё приемлем для маленьких сайтов, но по мере роста масштаба сайта и повышения требований пользователей к опыту эти проблемы начинают серьёзно влиять на удержание и конверсию пользователей.

### 3.3 Этап 2: раннее одностраничное приложение — эпоха Hash-маршрутизации

Когда проблемы традиционного многостраничного приложения накопились до определённого уровня, команда «Купи больше» решила внедрить фронтенд-маршрутизацию и перейти к архитектуре одностраничного приложения. Это важный поворотный момент — переход от «доминирования сервера» к «доминированию фронтенда».

Но у этого этапа тоже есть цена: в URL присутствует `#`, что выглядит недостаточно профессионально, и с индексацией поисковиками тоже проблемы.

**Способ разработки**:
- **Реализация маршрутизации**: Hash-маршрутизация, использующая часть `#` в URL
- **Переход между страницами**: JavaScript перехватывает клики по ссылкам и динамически заменяет компоненты
- **Управление состоянием**: состояние страницы сохраняется на клиенте, не нужно перезагружать

**Особенности этого этапа**:
- ✅ **Преимущества**: переключение без перезагрузки, плавный опыт, снижение нагрузки на сервер
- ❌ **Недостатки**: URL с `#`, недружелюбно к SEO, первая загрузка медленнее

::: details Посмотреть способ реализации Hash-маршрутизации
**Структура проекта** (типичная структура раннего SPA):
```
project/
├── index.html          # 唯一的 HTML 入口文件
├── css/
│   └── app.css         # 所有样式打包在一个文件
├── js/
│   ├── router.js       # 简单的路由实现
│   ├── views/          # 页面组件
│   │   ├── Home.js
│   │   ├── ProductList.js
│   │   └── ProductDetail.js
│   └── app.js          # 应用入口
└── server.js           # 简单的静态文件服务器
```

**Основной код Hash-маршрутизации**:
```javascript
// router.js - 简化的 Hash 路由实现
class HashRouter {
  constructor(routes) {
    this.routes = routes
    this.currentPath = null

    // 监听 hash 变化
    window.addEventListener('hashchange', () => {
      this.matchRoute()
    })

    // 初始化
    this.matchRoute()
  }

  matchRoute() {
    // 获取当前 hash（去掉 #）
    const hash = window.location.hash.slice(1) || '/'
    const route = this.routes.find(r => r.path === hash)

    if (route) {
      this.render(route.component)
    } else {
      this.render(NotFoundComponent)
    }
  }

  render(component) {
    const app = document.getElementById('app')
    app.innerHTML = component.template()
    component.mount?.(app)
  }

  navigate(path) {
    window.location.hash = path
  }
}

// 使用
const router = new HashRouter([
  { path: '/', component: Home },
  { path: '/products', component: ProductList },
  { path: '/products/:id', component: ProductDetail }
])

// 导航
router.navigate('/products/123')
```

**Форма URL**:
- Главная: `https://example.com/#/`
- Список товаров: `https://example.com/#/products`
- Детали товара: `https://example.com/#/products/123`

**Принесённые улучшения**:
1. **Улучшение пользовательского опыта**: переключение страниц без перезагрузки, плавно и естественно
2. **Снижение нагрузки на сервер**: HTML/CSS/JS загружаются лишь один раз, далее запрашиваются только данные
3. **Сохранение состояния**: позиция прокрутки, содержимое формы и т. д. сохраняются при переключении страниц
4. **Дружелюбность к офлайну**: в связке с Service Worker можно реализовать офлайн-доступ

**Новые боли**:
1. **Некрасивый URL**: `#` делает URL похожим на «переход к якорю», недостаточно профессионально
2. **Проблема SEO**: поисковые краулеры могут игнорировать содержимое после hash, из-за чего страница не индексируется
3. **Медленная первая загрузка**: нужно разом загрузить весь JavaScript, время первого экрана довольно велико
:::

### 3.4 Этап 3: современное одностраничное приложение — History-маршрутизация становится основной

Боли Hash-маршрутизации (некрасивый URL, плохое SEO) мучили разработчиков многие годы. С распространением HTML5 и повышением совместимости браузеров History-маршрутизация постепенно стала основной.

History-маршрутизация использует HTML5 History API, что позволяет сделать URL «нормальным» (без `#`), но ценой является необходимость поддержки со стороны сервера.

**Способ разработки**:
- **Реализация маршрутизации**: History-маршрутизация, использующая `pushState` и `replaceState`
- **Библиотека маршрутизации**: зрелые библиотеки вроде Vue Router, React Router
- **Настройка сервера**: нужно настроить сервер так, чтобы все маршруты откатывались к `index.html`

**Особенности этого этапа**:
- ✅ **Преимущества**: красивый URL, дружелюбно к SEO, плавный пользовательский опыт
- ❌ **Недостатки**: развёртывание требует особой настройки, обязательна поддержка со стороны сервера

::: details Реализация History-маршрутизации и настройка развёртывания
**Структура проекта** (типичная структура современного SPA):
```
project/
├── public/
│   └── index.html          # 唯一的 HTML 入口
├── src/
│   ├── router/
│   │   └── index.js        # 路由配置
│   ├── views/              # 页面组件
│   │   ├── Home.vue
│   │   ├── ProductList.vue
│   │   └── ProductDetail.vue
│   ├── App.vue
│   └── main.js
├── package.json
└── vite.config.js          # 构建配置
```

**Пример конфигурации Vue Router**:
```javascript
// src/router/index.js
import { createRouter, createWebHistory } from 'vue-router'

const router = createRouter({
  history: createWebHistory(),  // History 模式
  routes: [
    { path: '/', component: () => import('@/views/Home.vue') },
    { path: '/products', component: () => import('@/views/ProductList.vue') },
    { path: '/products/:id', component: () => import('@/views/ProductDetail.vue') },
    { path: '/:pathMatch(.*)*', component: () => import('@/views/NotFound.vue') }
  ]
})

export default router
```

**Форма URL**:
- Главная: `https://example.com/`
- Список товаров: `https://example.com/products`
- Детали товара: `https://example.com/products/123`

**Ключевое: настройка Nginx** (обязательна при развёртывании):
```nginx
server {
    listen 80;
    server_name example.com;
    root /var/www/app;
    index index.html;

    # 关键配置：所有路由都指向 index.html
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

**Зачем нужна эта настройка?**

```
场景：用户直接访问 https://example.com/products/123

❌ 没有配置的情况：
1. 浏览器向服务器请求 /products/123
2. Nginx 在文件系统中查找 /products/123
3. 找不到这个文件，返回 404

✅ 配置了 try_files 的情况：
1. 浏览器向服务器请求 /products/123
2. Nginx 尝试查找文件 → 不存在
3. 回退到 /index.html（根据 try_files 规则）
4. 浏览器加载 index.html
5. Vue Router 接管，解析 /products/123
6. 渲染 ProductDetail 组件
7. 页面正常显示！
```

**Сравнение различий с режимом Hash**:
| Критерий сравнения | Режим Hash | Режим History |
|--------|----------|-------------|
| URL | `/#/products/123` | `/products/123` |
| Настройка сервера | Не нужна | **Обязательна** |
| Прямое обращение | ✅ Работает нормально | ❌ Нужна поддержка сервера |
| SEO | ⚠️ Хуже | ✅ Хорошо |
:::

### 3.5 Этап 4: гибридный рендеринг — предельное решение SPA + SSR

Когда History-маршрутизация стала зрелой, команда начала обращать внимание на более глубокие проблемы: как сохранить плавный опыт SPA и при этом решить проблемы SEO и медленной загрузки первого экрана?

Ядро этого этапа — «изоморфный рендеринг»: первый экран рендерится на сервере (хорошее SEO, быстрая загрузка), последующее взаимодействие — через фронтенд-маршрутизацию (плавный опыт).

**Способ разработки**:
- **Выбор фреймворка**: Next.js (React), Nuxt.js (Vue)
- **Стратегия рендеринга**: серверный рендеринг + клиентская гидратация (Hydration)
- **Режим маршрутизации**: режим History (на сервере уже настроен)

**Особенности этого этапа**:
- ✅ **Преимущества**: быстрый первый экран, хорошее SEO, плавное последующее взаимодействие
- ❌ **Недостатки**: высокая сложность реализации, нужна серверная среда выполнения

::: details Принцип работы гибридного рендеринга
**Процесс загрузки страницы**:
```
1. 用户访问 /products/123
       ↓
2. 服务端接收到请求
       ↓
3. 服务端渲染 ProductDetail 组件 → 生成完整 HTML
       ↓
4. 返回 HTML 到浏览器（包含了完整的内容）
       ↓
5. 浏览器快速显示内容（首屏渲染快）
       ↓
6. 加载 JavaScript，执行"水合"（Hydration）
       ↓
7. 后续页面切换由前端路由接管（无刷新）
```

**Сравнение первого экрана традиционного SPA vs SSR**:

| Критерий сравнения | Традиционный SPA | SSR |
|--------|---------|-----|
| Содержимое первого экрана | Белый экран → загрузка JS → рендеринг | Содержимое отображается сразу |
| SEO | Краулер может не увидеть содержимое | Краулер видит полный HTML |
| Время первого экрана | Медленнее (нужно загрузить JS) | Быстрее (HTML уже содержит контент) |
| Последующее взаимодействие | Плавно (фронтенд-маршрутизация) | Плавно (фронтенд-маршрутизация) |
:::

## 4. Углубление в принципы: как работает маршрутизация?

Познакомившись с реальным кейсом, давайте углубимся в принцип работы фронтенд-маршрутизации и поймём, в чём же отличие двух режимов — Hash и History.

<RouterArchitectureDemo />

### 4.1 Принцип работы режима Hash

Ядро режима Hash — использование hash-части URL (то есть содержимого после `#`). У hash есть два важных свойства:

1. **Изменение hash не вызывает перезагрузки страницы**
2. **Изменение hash записывается в стек истории браузера**

Это значит, что мы можем менять URL без перезагрузки страницы, и при этом кнопки «вперёд/назад» браузера работают нормально.

**Рабочий процесс**:

```
用户点击链接 <a href="#/user/123">
       ↓
浏览器更新 URL（不刷新页面）
https://example.com/#/user/123
       ↓
触发 hashchange 事件
       ↓
路由监听器捕获事件
       ↓
解析 hash 值 → /user/123
       ↓
匹配路由配置 → 找到 UserDetail 组件
       ↓
渲染组件到页面
```

**Реализация основного кода**:

```javascript
class HashRouter {
  constructor(routes) {
    this.routes = routes

    // 监听 hash 变化
    window.addEventListener('hashchange', () => {
      this.loadRoute()
    })

    // 初始化加载
    this.loadRoute()
  }

  loadRoute() {
    // 获取当前 hash，去掉开头的 #
    const hash = window.location.hash.slice(1) || '/'
    const route = this.matchRoute(hash)

    if (route) {
      this.render(route.component)
    }
  }

  matchRoute(path) {
    return this.routes.find(r => r.path === path)
  }

  render(component) {
    document.getElementById('app').innerHTML = component.template()
  }

  push(path) {
    window.location.hash = path
  }
}
```

::: tip 💡 Преимущества режима Hash
- **Хорошая совместимость**: поддерживается IE8+, подходит почти для всех браузеров
- **Простое развёртывание**: не нужна настройка сервера, работает из коробки
- **Простая реализация**: нужно лишь прослушивать событие `hashchange`
:::

### 4.2 Принцип работы режима History

Режим History использует HTML5 History API, предоставляющий методы `pushState`, `replaceState` и др., которые позволяют менять URL без перезагрузки страницы.

**Основные API**:

```javascript
// 添加新的历史记录
history.pushState(state, title, url)
// 示例：history.pushState({id: 123}, '用户详情', '/user/123')

// 替换当前历史记录
history.replaceState(state, title, url)

// 监听历史记录变化（前进/后退按钮）
window.addEventListener('popstate', (event) => {
  // event.state 包含 pushState 时传入的 state
})
```

**Рабочий процесс**:

```
用户点击链接 <a href="/user/123">
       ↓
JavaScript 拦截点击事件
event.preventDefault()
       ↓
调用 history.pushState
history.pushState({id: 123}, '用户详情', '/user/123')
       ↓
URL 更新（不刷新页面）
https://example.com/user/123
       ↓
路由匹配并渲染组件
       ↓
用户点击浏览器后退按钮
       ↓
触发 popstate 事件
       ↓
路由监听器捕获事件
       ↓
根据新 URL 渲染对应组件
```

**Реализация основного кода**:

```javascript
class HistoryRouter {
  constructor(routes) {
    this.routes = routes

    // 拦截所有链接点击
    document.addEventListener('click', (e) => {
      const link = e.target.closest('a')
      if (link && link.getAttribute('href').startsWith('/')) {
        e.preventDefault()
        this.push(link.getAttribute('href'))
      }
    })

    // 监听浏览器前进/后退
    window.addEventListener('popstate', () => {
      this.loadRoute()
    })

    // 初始化加载
    this.loadRoute()
  }

  loadRoute() {
    const path = window.location.pathname
    const route = this.matchRoute(path)

    if (route) {
      this.render(route.component)
    }
  }

  push(path) {
    history.pushState({}, '', path)
    this.loadRoute()
  }

  render(component) {
    document.getElementById('app').innerHTML = component.template()
  }
}
```

::: warning ⚠️ Ловушка режима History
Самая большая проблема режима History в том, что: **когда пользователь напрямую обращается к какому-то URL или обновляет страницу, браузер отправляет запрос на сервер**.

Если сервер настроен неправильно, вернётся 404. Решение — настроить сервер так, чтобы все маршруты откатывались к `index.html`, и передать дальнейшую обработку фронтенд-маршрутизации.
:::

## 5. Практическое руководство по настройке маршрутизации

С теорией почти разобрались, ниже — паттерны конфигурации маршрутов и лучшие практики, часто применяемые в реальных проектах.

### 5.1 Базовая конфигурация маршрутов

::: details Полный пример конфигурации Vue Router

```javascript
// src/router/index.js
import { createRouter, createWebHistory } from 'vue-router'
import Home from '@/views/Home.vue'
import NotFound from '@/views/NotFound.vue'

const router = createRouter({
  history: createWebHistory(import.meta.env.BASE_URL),
  routes: [
    {
      path: '/',
      name: 'Home',
      component: Home
    },
    {
      path: '/user/:id',
      name: 'UserDetail',
      component: () => import('@/views/UserDetail.vue'),
      props: true  // 将路由参数作为 props 传递
    },
    {
      path: '/:pathMatch(.*)*',
      name: 'NotFound',
      component: NotFound
    }
  ],
  scrollBehavior(to, from, savedPosition) {
    // 滚动行为：返回时保持滚动位置，否则滚动到顶部
    if (savedPosition) {
      return savedPosition
    } else {
      return { top: 0 }
    }
  }
})

export default router
```

:::

### 5.2 Ленивая загрузка маршрутов: повышение производительности первого экрана

Ленивая загрузка маршрутов означает загрузку соответствующего компонента только при обращении к маршруту, а не загрузку всех компонентов сразу. Это может значительно сократить время загрузки первого экрана.

```javascript
// ❌ 一次性加载所有组件（首屏慢）
import Home from '@/views/Home.vue'
import About from '@/views/About.vue'
import User from '@/views/User.vue'

const routes = [
  { path: '/', component: Home },
  { path: '/about', component: About },
  { path: '/user', component: User }
]

// ✅ 懒加载（首屏快）
const routes = [
  { path: '/', component: () => import('@/views/Home.vue') },
  { path: '/about', component: () => import('@/views/About.vue') },
  { path: '/user', component: () => import('@/views/User.vue') }
]
```

<CodeSplittingDemo />

::: tip 💡 Принцип ленивой загрузки
Когда вы используете `import('@/views/Home.vue')`, Webpack/Vite собирает этот компонент в отдельный файл. Соответствующий файл загружается только тогда, когда пользователь обращается к этому маршруту.

Сравнение: ленивая загрузка — как «заказывать блюда по мере надобности», а не подавать все блюда сразу. Это сокращает время загрузки первого экрана и улучшает пользовательский опыт.
:::

### 5.3 Навигационные сторожа: контроль доступа и перехват навигации

Навигационные сторожа позволяют выполнять логику до и после перехода по маршруту, часто используются для проверки прав, установки заголовка страницы, предзагрузки данных и т. д.

```javascript
// 全局前置守卫
router.beforeEach(async (to, from, next) => {
  // 设置页面标题
  document.title = to.meta.title || 'My App'

  // 权限验证
  if (to.meta.requiresAuth) {
    const isAuthenticated = await checkAuth()
    if (!isAuthenticated) {
      next('/login')
      return
    }
  }

  next()
})

// 全局后置钩子
router.afterEach((to, from) => {
  // 页面访问统计
  analytics.trackPageView(to.path)
})

// 路由级守卫
const routes = [
  {
    path: '/admin',
    component: Admin,
    meta: { requiresAuth: true, roles: ['admin'] },
    beforeEnter: (to, from, next) => {
      // 这个路由的专属逻辑
      if (hasPermission()) {
        next()
      } else {
        next('/403')
      }
    }
  }
]
```

::: tip 💡 Распространённые применения навигационных сторожей
- **Проверка прав**: проверка, есть ли у пользователя право на доступ к странице
- **Заголовок страницы**: динамическая установка document.title
- **Предзагрузка данных**: заблаговременное получение данных перед входом на страницу
- **Индикатор прогресса**: отображение прогресса переключения страниц
- **Статистика посещений**: запись посещений страниц
:::

## 6. Распространённые проблемы и решения

### 6.1 404 при обновлении после развёртывания

**Проблема**: локальная разработка работает нормально, но после развёртывания на сервере прямое обращение к маршруту или обновление страницы выдаёт 404.

**Причина**: в режиме History сервер ищет URL как путь к файлу, но все маршруты SPA на самом деле указывают на `index.html`.

**Решение**: настроить fallback на сервере.

```nginx
# Nginx 配置
location / {
    try_files $uri $uri/ /index.html;
}
```

```apache
# Apache 配置（.htaccess）
<IfModule mod_rewrite.c>
  RewriteEngine On
  RewriteBase /
  RewriteRule ^index\.html$ - [L]
  RewriteCond %{REQUEST_FILENAME} !-f
  RewriteCond %{REQUEST_FILENAME} !-d
  RewriteRule . /index.html [L]
</IfModule>
```

### 6.2 Потеря параметров маршрута

**Проблема**: после обновления страницы параметры маршрута `$route.params` теряются.

**Причина**: параметры маршрута существуют только при переходе по маршруту, после обновления их нужно заново разобрать из URL.

**Решение**:

```javascript
// ❌ 错误做法：只在 created 时获取参数
created() {
  const userId = this.$route.params.id
  this.fetchUser(userId)
}

// ✅ 正确做法：监听路由变化
watch: {
  '$route.params.id': {
    immediate: true,
    handler(newId) {
      this.fetchUser(newId)
    }
  }
}
```

### 6.3 Аномалия позиции прокрутки при переключении страниц

**Проблема**: после переключения страницы позиция прокрутки не сбрасывается или при возврате не сохраняется прежняя позиция.

**Решение**: настроить `scrollBehavior` маршрутизатора.

```javascript
const router = createRouter({
  scrollBehavior(to, from, savedPosition) {
    // 返回时保持滚动位置
    if (savedPosition) {
      return savedPosition
    }
    // 跳转到锚点
    if (to.hash) {
      return { el: to.hash }
    }
    // 否则滚动到顶部
    return { top: 0 }
  }
})
```

## 7. Итоги

Давайте используем таблицу, чтобы вспомнить основные концепции фронтенд-маршрутизации:

| Концепция | Объяснение одной фразой | Решаемая проблема | Типичное решение |
|------|-----------|-----------|----------|
| **Маршрут** | Соответствие URL и компонента | Обращение к разным URL показывает разное содержимое | Vue Router, React Router |
| **Режим Hash** | Реализация маршрутизации через hash URL | Хорошая совместимость, простое развёртывание | Режим Hash в Vue Router |
| **Режим History** | Реализация маршрутизации через History API | Красивый URL, хорошее SEO | Режим History в Vue Router |
| **Ленивая загрузка маршрутов** | Загрузка компонентов маршрута по мере надобности | Сокращение времени загрузки первого экрана | `() => import('./Page.vue')` |
| **Навигационные сторожа** | Хук-функции до и после перехода по маршруту | Контроль доступа, предзагрузка данных | `beforeEach`, `beforeEnter` |
| **Динамический маршрут** | Маршрут с параметрами | Сопоставление класса путей, а не единичного | `/user/:id` |

::: info Напоследок
Фронтенд-маршрутизация — одна из ключевых технологий современных одностраничных приложений. От раннего режима Hash до ныне основного режима History технология маршрутизации постоянно эволюционирует, предоставляя пользователям более плавный опыт просмотра.

Понимание принципов и режимов маршрутизации позволяет быстро локализовать и точно решать проблемы развёртывания, производительности и SEO. Что ещё важнее, это помогает делать более разумный выбор при проектировании архитектуры — когда использовать Hash, когда History, как избежать распространённых ловушек.

Надеюсь, эта статья поможет вам сформировать целостное представление о фронтенд-маршрутизации. Когда в реальном проекте вы столкнётесь с проблемами, связанными с маршрутизацией, вы будете знать, с чего начать, как локализовать и как решить.
:::
