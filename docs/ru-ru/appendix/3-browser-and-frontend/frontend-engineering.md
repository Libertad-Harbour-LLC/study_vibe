## 1. Зачем нужен «инжиниринг»?

### 1.1 От простого к сложному: эволюция фронтенд-разработки

Вспомним фронтенд-разработку десять лет назад: тогда мы работали очень просто — писали несколько HTML-страниц, встраивали немного CSS и JavaScript, перетаскивали файлы прямо в браузер и сразу видели результат, а при развёртывании достаточно было загрузить папку на сервер; общий объём кода сайта мог составлять всего несколько десятков КБ. Это была эпоха «что вижу, то и получаю», процесс разработки был прост и прям, и понятия «инжиниринг» почти не существовало.

Но современная фронтенд-разработка выглядит совершенно иначе. Сейчас мы используем TypeScript вместо JavaScript, а это требует компиляции; используем компонентный подход разработки Vue или React, что требует дополнительного преобразования; пишем CSS на Sass или Less, что требует предобработки; устанавливаем разные пакеты зависимостей через npm, и в итоге всё это нужно собрать. У средне-крупного проекта может быть тысяча с лишним фронтенд-зависимостей общим объёмом в сотни МБ — резкий контраст с «простотой и прямотой» десятилетней давности.

### 1.2 Реальная история с граблями: зачем вам понимать принципы сборки

Вы можете сказать: «Я использую Vite или Create React App, всё работает из коробки, зачем мне понимать эти принципы сборки?» Расскажу реальную историю, и вы поймёте, почему эти знания так важны.

::: warning История граблей Сяо Мина
Сяо Мин — новичок-фронтендер, только устроившийся в компанию, где используют проект на Vite. Однажды пришёл менеджер по продукту и сказал, что главная страница загружается слишком медленно, пользователи жалуются, нужно срочно оптимизировать.

Сяо Мин тут же взялся за дело: сжал изображения, реализовал ленивую загрузку маршрутов, включил Gzip-сжатие... энергично провернул кучу операций, но скорость загрузки главной страницы по-прежнему была очень низкой, проблема совсем не решилась.

Позже он обратился за помощью к наставнику. Тот открыл инструменты разработчика в браузере, бросил взгляд на сетевые запросы и сразу нашёл проблему: файл `vendor.js` весил аж 2 МБ! Оказалось, что ради одной функции форматирования даты Сяо Мин подключил всю библиотеку `moment.js` целиком, а `moment.js` содержит locale-файлы более чем для 100 языков, большинство из которых проекту вообще не нужны.

Решение оказалось простым: заменить `moment.js` на `dayjs` либо подключить `date-fns` по необходимости. После такого изменения объём в 2 МБ мгновенно превратился в 2 КБ, а скорость загрузки главной страницы выросла более чем в десять раз.

С тех пор Сяо Мин усвоил истину: **не понимая принципов сборки и упаковки, ты даже не знаешь, где кроется проблема, не говоря уже о том, чтобы её решить.**
:::

## 2. Ключевые понятия: транспиляция, упаковка, сборка

::: tip 🤔 Как эти понятия связаны со сборкой?
Транспиляция и упаковка — ключевые операции на конвейере.

Когда вы запускаете `npm run build`, инструмент сборки последовательно выполняет:
1. **Проверку кода** → находит ошибки
2. **Транспиляцию** → переводит новый синтаксис в понятный браузеру код
3. **Упаковку** → объединяет разрозненные файлы
4. **Оптимизацию** → сжимает объём, удаляет неиспользуемый код

Так что **транспиляция и упаковка — ключевые звенья процесса сборки**. Поняв их, вы узнаете, что именно делает инструмент сборки, почему иногда сборка медленная и почему иногда объём после упаковки большой.
:::

Прежде чем углубляться в конкретные инструменты, нужно разобраться с этими ключевыми понятиями. Чтобы вам было проще понять, проведём аналогию между ними на примере ресторана.

### 2.1 Понимаем три понятия на примере ресторана

Представьте, что вы управляете рестораном и каждый день предлагаете посетителям разные блюда. Этапы этого процесса удивительно похожи на три ключевых понятия фронтенд-инжиниринга:

| Понятие | 🍽️ Сравнение с рестораном | Реальная роль | Конкретный пример |
|------|-------------|----------|----------|
| **Транспиляция** | Перевести меню с китайского на английский, чтобы иностранный повар тоже понял | Преобразовать новый синтаксис в понятный браузеру старый | Вы пишете `const name = user?.name`, после транспиляции это становится `var name = user && user.name` |
| **Упаковка** | Сложить заказанные за разными столиками блюда в коробки навынос для удобной доставки | Объединить разрозненные файлы модулей в небольшое число файлов | Вы написали 50 файлов .js, после упаковки их стало 2 |
| **Сборка** | Полный процесс от приёма заказа, готовки и упаковки до доставки | Полный процесс преобразования от исходного кода до продакшен-кода | После выполнения `npm run build` папка src превращается в папку dist |

### 2.2 Транспиляция (Transpile): «переводчик» кода

Транспиляция, как следует из названия, — это «преобразование + компиляция», её главная задача — преобразовать один язык программирования (или его новую версию) в другой (или его старую версию). У вас может возникнуть вопрос: зачем так делать? Не проще ли сразу писать код, поддерживаемый браузером?

Ответ кроется в проблеме совместимости браузеров. Хотя JavaScript каждый год выпускает новые версии с более мощным синтаксисом и API, скорость обновления браузеров сильно отстаёт. Если вы используете новейший синтаксис ES2022, в старых браузерах он может вообще не запуститься. Задача инструментов транспиляции — превратить ваш «опережающий код» в «консервативный код», гарантируя корректную работу во всех браузерах.

::: details 🔧 Пример транспиляции: посмотрим, что она делает
Рассмотрим конкретный пример. Ниже код, который вы написали, используя оператор опциональной цепочки и оператор нулевого слияния из ES2020:

```js
// То, что вы написали (ES2020+)
const result = data?.items?.map(item => item.name) ?? []
```

Этот код лаконичен и элегантен, но в старых браузерах выдаст синтаксическую ошибку. Инструмент транспиляции преобразует его в эквивалентный код с лучшей совместимостью:

```js
// После транспиляции (версия, совместимая с ES5)
var _data$items, _data$items$map
var result =
  (_data$items$map =
    (_data$items = data == null ? void 0 : data.items) == null
      ? void 0
      : _data$items.map(function (item) {
          return item.name
        })) != null
    ? _data$items$map
    : []
```

Как видите, одна лаконичная строка кода превратилась в многострочный «многословный» код, но последний корректно работает в любом браузере.
:::

**Распространённые инструменты транспиляции:**

- **Babel** — самый заслуженный транспилятор JavaScript с богатейшей экосистемой, способный обработать практически весь современный синтаксис. Его система плагинов очень мощная, но высокая гибкость делает настройку относительно сложной.
- **SWC** — транспилятор, переписанный на языке Rust, более чем в 20 раз быстрее Babel; его берут на вооружение всё больше проектов, включая такие известные фреймворки, как Next.js.
- **esbuild** написан на языке Go и тоже славится скоростью; Vite использует его в режиме разработки для быстрой транспиляции.

::: details 🔍 Какой инструмент транспиляции использует мой проект?
Вам не нужно специально выбирать — обычно это определяется стартовым шаблоном проекта:

| Тип проекта | Инструмент транспиляции по умолчанию |
|---------|-------------|
| Проект на Vite | esbuild (режим разработки) + esbuild/rollup (продакшен) |
| Create React App | Babel |
| Next.js | SWC (новые версии) / Babel (старые версии) |
| Vue CLI | Babel |

Хотите узнать, что использует ваш проект? Откройте `package.json`, поищите ключевые слова `babel`, `@babel/core`. Если нашли — значит, используется Babel; если нет — скорее всего, esbuild или SWC.

**На самом деле вам не нужно об этом беспокоиться** — эти инструменты «прозрачны» для разработчика, вы просто пишете код, а они тихо работают в фоне.
:::

### 2.3 Упаковка (Bundle): «упаковщик» модулей

Упаковка означает процесс объединения множества разрозненных файлов модулей в один (или несколько) файл. В ранней фронтенд-разработке мы привыкли писать весь код в одном JS-файле, но с ростом масштаба проекта такой подход становился трудным в поддержке. Современный фронтенд использует модульную разработку — по файлу на каждую функцию, но загрузка браузером множества мелких файлов вызывает проблемы с производительностью, и здесь на помощь приходят инструменты упаковки.

::: tip 📦 Что такое ES-модули?
Вы, возможно, слышали термин «ES-модули» — что же это такое?

**Сначала разграничим два понятия**:
- **ECMAScript (ES)**: стандарт языка JavaScript, определяющий синтаксис и API
- **ES-модули**: схема модульности, определённая в стандарте ECMAScript, импорт и экспорт кода через синтаксис `import` и `export`

Для сравнения: ECMAScript — это как «стандарт литературного языка», а ES-модули — как «определённый способ выражения внутри этого языка».

```js
// utils.js - экспорт модуля
export function add(a, b) { return a + b }
export function subtract(a, b) { return a - b }

// main.js - импорт модуля
import { add, subtract } from './utils.js'
console.log(add(1, 2))  // 3
```

**Полезное о версиях ES**: ECMAScript каждый год выпускает новую версию:
- **ES5 (2009)**: классическая версия, поддерживается практически всеми браузерами
- **ES6/ES2015**: знаковое крупное обновление, ввело `let/const`, стрелочные функции, **ES-модули**, `class` и т. д.
- **ES2016–ES2024**: ежегодное добавление новых возможностей (например, `async/await`, опциональная цепочка `?.` и т. д.)

ES-модули были введены именно в ES6 (2015 год). До этого у JavaScript не было официальной системы модулей, и разработчики могли пользоваться лишь разными «народными решениями» (например, CommonJS, AMD), что приводило к проблеме разрозненности спецификаций модулей. ES-модули унифицировали эти спецификации и стали краеугольным камнем современной фронтенд-разработки.
:::

**Зачем нужна упаковка?** В основном по трём причинам: во-первых, хотя современные браузеры уже поддерживают ES-модули, загрузка сотни мелких файлов в продакшен-среде всё равно влечёт издержки производительности; во-вторых, в процессе упаковки можно выполнить Tree Shaking — автоматически удалить неиспользуемый код, уменьшив объём файлов; в-третьих, после упаковки можно сделать разделение кода и реализовать загрузку по необходимости, ускоряя отрисовку первого экрана.

::: details 📁 Сравнение до и после упаковки: посмотрим, что делает упаковка
**Структура исходного кода до упаковки** (множество разрозненных файлов):
```
src/
├── index.js          (входной файл, импортирует другие модули)
├── utils/
│   ├── a.js          (вспомогательная функция A)
│   ├── b.js          (вспомогательная функция B)
│   └── c.js          (вспомогательная функция C)
└── components/
    └── Button.vue    (компонент кнопки)
```

**Результат после упаковки** (небольшое число объединённых файлов):
```
dist/
├── index.[hash].js      (основной входной код)
├── vendor.[hash].js     (код сторонних библиотек)
└── assets/
    └── logo.[hash].png  (статические ресурсы)
```

Инструмент упаковки анализирует зависимости между файлами и объединяет их в правильном порядке, попутно выполняя различные оптимизации.
:::

### 2.4 Сборка (Build): полноценный «производственный конвейер»

Сборка — более широкое понятие, охватывающее весь процесс преобразования от исходного кода до готового к развёртыванию результата. Полноценный процесс сборки обычно включает следующие шаги:

1. **Этап предкомпиляции**: компиляция TypeScript в JavaScript, компиляция Sass в CSS
2. **Этап проверки кода**: запуск ESLint для проверки соблюдения стандартов кода, запуск проверки типов TypeScript
3. **Этап разрешения зависимостей**: анализ зависимостей между модулями, построение графа зависимостей

4. **Этап транспиляции**: преобразование синтаксиса с помощью таких инструментов, как Babel, обеспечение совместимости
5. **Этап упаковки**: объединение файлов модулей, применение Tree Shaking для удаления бесполезного кода
6. **Этап оптимизации**: сжатие кода, разделение кода, выделение общих модулей
7. **Этап обработки ресурсов**: сжатие изображений, генерация спрайтов, обработка файлов шрифтов
8. **Этап генерации результата**: вывод итоговых файлов в каталог dist

Понимание этого полного процесса очень важно, потому что при возникновении проблем сборки вам нужно знать, на каком этапе кроется проблема, чтобы решить её прицельно.

## 3. Практика: путь развития инжиниринга в одной команде

::: tip 🤔 Что такое «инжиниринг»?
Мы долго говорили об «инжиниринге» — что же это всё-таки значит?

**Проще говоря, инжиниринг — это процесс превращения «ручной мастерской» в «современную фабрику».**

Представьте: вы готовите дома, хотите есть что угодно — готовите что угодно, полная свобода. Но если открыть ресторан, обслуживающий каждый день сотни посетителей, нельзя больше «готовить что захочется» — вам нужны стандартизированные рецепты, регламентированные процессы работы, единые закупки сырья, и только так можно обеспечить стабильное качество каждого блюда и высокую скорость подачи.

С фронтенд-разработкой так же. Один человек пишет маленький проект — пиши как хочешь. Но при командной работе и росте проекта нужны:
- **Единые стандарты кода**: все пишут код одинаковым образом
- **Инструменты автоматизации**: машина помогает нам находить ошибки, преобразовывать код, упаковывать файлы
- **Стандартизированный процесс**: от разработки до выпуска есть чёткая последовательность шагов

**Это и есть инжиниринг: с помощью инструментов и стандартов сделать разработку эффективнее, код надёжнее, а сотрудничество — более гладким.**
:::

После стольких понятий давайте рассмотрим реальный кейс: как один стартап шаг за шагом эволюционировал от «прямого написания HTML» к «современному инженерному процессу». На этом примере вы нагляднее поймёте, что же на самом деле решает инжиниринг.

::: tip 📖 Базовые знания: что такое jQuery, Vue, React?
Прежде чем начать кейс, кратко представим эти термины:

- **jQuery**: самая популярная более десяти лет назад JavaScript-библиотека для упрощения работы с DOM (например, «после нажатия кнопки изменить текст»). Сейчас её вытеснили современные фреймворки вроде Vue, React, но многие старые проекты всё ещё её используют.
- **Vue / React**: основные фреймворки современной фронтенд-разработки. Они позволяют организовывать код в виде «компонентов», данные и представление синхронизируются автоматически, эффективность разработки выше. То, что вы сейчас изучаете, скорее всего, один из них.

**Простое понимание**: jQuery — это «ручная коробка передач», где нужно самому управлять каждым элементом; Vue/React — «автомат», где достаточно сказать, какие данные, а интерфейс обновится автоматически.
:::

### 3.1 Панорама эволюции

::: tip 🤔 Что такое стартовый шаблон (scaffolding)?
Стартовый шаблон — это инструмент, который помогает вам «выстроить каркас проекта». Например, `npm create vite@latest` автоматически создаст настроенный проект со структурой каталогов, конфигурационными файлами и примером кода — вы сразу начинаете писать бизнес-логику.

**Эпоха без стартовых шаблонов**: нужно вручную создавать папки, писать конфиги, устанавливать зависимости... на разворачивание проекта могло уходить полдня.
**Эпоха со стартовыми шаблонами**: одна команда, 30 секунд — и готово.
:::

В таблице ниже показаны четыре этапа эволюции инжиниринга, и вы увидите, как шаг за шагом развивались инструменты сборки, стартовые шаблоны и фреймворки:

| Этап | Инструмент сборки | Стартовый шаблон | Фреймворк | Ключевое изменение |
|------|---------|--------|------|----------|
| **Этап 1: первобытная эпоха** | Нет (прямой запуск) | Нет (файлы вручную) | jQuery | Никаких инструментов, всё вручную |
| **Этап 2: модульность** | Webpack + Babel | Простое копирование шаблона | Vue 2 / React | Появился процесс сборки, но настройка хлопотная |
| **Этап 3: современность** | Vite | create-vite / create-react-app | Vue 3 / React 18 | Работает из коробки, запуск без конфигурации |
| **Этап 4: непрерывная оптимизация** | Vite + плагины | Собственные шаблоны стартового набора | Фреймворк + TypeScript | Стандартизация и шаблонизация в команде |

::: tip 📊 Что можно увидеть из таблицы?
Разберём эту таблицу построчно:

**Этап 1 → Этап 2**: от «нет инструментов» к «есть инструменты». Это качественный скачок — вы начинаете обрабатывать код инструментом сборки и организовывать проект с помощью фреймворка. Но цена этому — сложная настройка, новичкам трудно освоиться.

**Этап 2 → Этап 3**: от «работает» к «удобно». Vite автоматизировал то, что раньше приходилось настраивать вручную, стартовый шаблон создаёт проект одной командой, опыт разработки заметно улучшается. Вы сейчас, скорее всего, как раз на этом этапе.

**Этап 3 → Этап 4**: от «удобно одному» к «эффективно команде». Когда команда разрастается, нужны единый технологический стек и стандарты, и тогда создаются собственные шаблоны стартового набора, чтобы все проекты сохраняли единый стиль.

**Подытожим**: эволюция инжиниринга — это не только «инструменты сборки стали быстрее», а **повышение всего опыта разработки** — от ручного разворачивания проекта к созданию одной командой, от сложной настройки к работе из коробки, от разрозненных усилий к командным стандартам.
:::

### 3.2 Этап 1: первобытная эпоха — всё вручную

Почему «первобытная эпоха»? Потому что на этом этапе нет никаких инструментов автоматизации, всё приходится делать вручную — создавать папки, писать код, управлять зависимостями, отлаживать проблемы, всё силами человека.

На этом этапе в команде было всего 3 фронтенд-инженера, делавших проект административной панели. Проект маленький, все писали по отдельности, и казалось, проблем нет. Но по мере роста проекта проблемы начали вылезать наружу.

**Способ разработки**:
- **Инструмент сборки**: нет, пишем HTML/JS/CSS напрямую, браузер запускает напрямую
- **Стартовый шаблон**: нет, папки и файлы создаём вручную
- **Фреймворк**: jQuery, работа с DOM через селекторы

**Особенности этого этапа**:
- ✅ **Плюсы**: просто и прямо, нет порога входа, написал — и сразу работает
- ❌ **Минусы**: при росте кода начинается хаос, командная работа затруднена, без проверки кода легко наплодить багов

::: details Посмотреть тогдашнюю структуру проекта и способ написания кода
**Структура проекта** (создана вручную):
```
project/
├── index.html
├── login.html
├── css/
│   ├── bootstrap.css
│   └── custom.css
├── js/
│   ├── jquery.js
│   ├── bootstrap.js
│   └── app.js
└── images/
```

**Возникшие проблемы**:
1. **Загрязнение глобальными переменными**: все переменные в глобальном пространстве имён, одноимённые переменные в разных файлах перекрывают друг друга
2. **Хаос в управлении зависимостями**: плагины jQuery должны загружаться после самого jQuery, перепутал порядок тегов script — получай ошибку
3. **Код трудно переиспользовать**: чтобы переиспользовать функцию, остаётся только копировать-вставлять
4. **Нет проверки кода**: такие примитивные проблемы, как опечатка в имени переменной, обнаруживаются только после запуска

**Тогдашнее временное решение**:
```js
// Имитация модульности через самовызывающуюся функцию (паттерн IIFE)
var ModuleA = (function () {
  var privateVar = 'private'  // приватная переменная, снаружи недоступна

  function privateFn() {
    console.log(privateVar)
  }

  return {
    publicMethod: function () {
      privateFn()  // открываем публичный метод
    }
  }
})()

// Управление зависимостями целиком держится на комментариях
/**
 * @requires jquery.js (must load first)
 * @requires bootstrap.js
 */
```
:::

Такой способ разработки ещё годится для маленьких проектов, но по мере роста команды до 8 человек и усложнения проекта эти проблемы начали серьёзно сказываться на эффективности разработки и качестве кода, и команде остро понадобился более удобный способ организации.

### 3.3 Этап 2: эпоха модульности — появляется цепочка инструментов

Когда проблемы первобытной эпохи накопились до определённого предела, команда наконец решилась внедрить современную цепочку инструментов. Это важный поворотный момент — переход от «ручного труда» к «механизированному производству».

Но у этого этапа есть и цена: высокий порог освоения цепочки инструментов, сложные конфигурационные файлы, новичкам нужно время, чтобы освоиться.

**Способ разработки**:
- **Инструмент сборки**: Webpack + Babel, нужно писать конфигурационные файлы
- **Стартовый шаблон**: копирование шаблона старого проекта, ручная правка конфигурации
- **Фреймворк**: Vue 2 / React, компонентная разработка

**Особенности этого этапа**:
- ✅ **Плюсы**: модульная разработка, поддерживаемость кода резко возросла, есть проверка кода
- ❌ **Минусы**: сложная настройка, медленный запуск, примитивный стартовый шаблон легко приводит к ошибкам

::: details Посмотреть изменения после внедрения цепочки инструментов
**Структура проекта** (эпоха Webpack + Vue 2):
```
my-project/
├── build/               # конфигурация сборки (на этом этапе она очень сложная!)
│   ├── webpack.base.js
│   ├── webpack.dev.js
│   └── webpack.prod.js
├── config/              # конфигурация окружений
│   ├── index.js
│   ├── dev.env.js
│   └── prod.env.js
├── src/
│   ├── components/      # компоненты
│   ├── views/           # страницы
│   ├── router/          # маршрутизация
│   ├── store/           # управление состоянием
│   ├── App.vue
│   └── main.js
├── static/              # статические ресурсы
├── .eslintrc.js         # конфигурация ESLint
├── .babelrc             # конфигурация Babel
├── package.json
└── index.html
```

**Пример конфигурационного файла** (вот почему говорят «сложная настройка»):
```js
// webpack.base.js - даже базовая конфигурация содержит столько всего
const path = require('path')
const VueLoaderPlugin = require('vue-loader/lib/plugin')

module.exports = {
  entry: './src/main.js',
  output: {
    path: path.resolve(__dirname, '../dist'),
    filename: '[name].[contenthash].js'
  },
  module: {
    rules: [
      { test: /\.vue$/, loader: 'vue-loader' },
      { test: /\.js$/, loader: 'babel-loader', exclude: /node_modules/ },
      { test: /\.css$/, use: ['style-loader', 'css-loader'] },
      { test: /\.scss$/, use: ['style-loader', 'css-loader', 'sass-loader'] },
      { test: /\.(png|jpg|gif)$/, loader: 'url-loader', options: { limit: 8192 } }
    ]
  },
  plugins: [new VueLoaderPlugin()],
  resolve: {
    extensions: ['.js', '.vue', '.json'],
    alias: { '@': path.resolve(__dirname, '../src') }
  }
}
```

**Принесённые улучшения**:
1. **Модульная разработка**: каждый файл — это модуль, зависимости чётко управляются через import/export
2. **Переиспользование кода**: компоненты и вспомогательные функции можно переиспользовать в разных проектах, без копипасты
3. **Качество кода**: ESLint автоматически проверяет при сохранении, TypeScript обнаруживает ошибки типов при компиляции
4. **Оптимизация производительности**: разделение кода и ленивая загрузка в Webpack заметно ускоряют отрисовку первого экрана

**Новые болевые точки**:
1. **Сложная настройка**: webpack.config.js запросто разрастается до нескольких сотен строк, новичкам трудно освоить
2. **Медленный запуск**: холодный запуск больше 30 секунд, после правки кода горячего обновления приходится ждать 5 секунд
3. **Примитивный стартовый шаблон**: копируешь шаблон старого проекта, часто забываешь поправить конфигурацию, отсюда всякие странные проблемы
:::

### 3.4 Этап 3: современная эпоха — работа из коробки

Болевые точки этапа 2 (сложная настройка, медленный запуск) изводили разработчиков много лет. Пока в 2021 году появление Vite не изменило всё кардинально.

Ключевая идея Vite — «соглашение важнее конфигурации»: в нём встроены разумные настройки по умолчанию, и вам не нужно писать конфигурационный файл на сотни строк, всё работает из коробки. Это как перейти от «самостоятельной сборки компьютера» к «покупке брендового», избавив себя от массы возни.

После 2021 года команда начала заменять Webpack на Vite, и опыт разработки качественно улучшился.

**Способ разработки**:
- **Инструмент сборки**: Vite, запуск без конфигурации, горячее обновление за доли секунды
- **Стартовый шаблон**: `npm create vite@latest`, создание проекта одной командой
- **Фреймворк**: Vue 3 / React 18, более мощная система компонентов

**Особенности этого этапа**:
- ✅ **Плюсы**: запуск за секунды, очень быстрое горячее обновление, простая настройка, дружелюбно к новичкам
- ❌ **Минусы**: экосистема ещё дорабатывается, для некоторых особых нужд может понадобиться дополнительная настройка

::: details Изменения, которые принёс Vite
**Структура проекта** (эпоха Vite + Vue 3):
```
my-project/
├── src/
│   ├── components/      # компоненты
│   ├── views/           # страницы
│   ├── router/          # маршрутизация
│   ├── stores/          # управление состоянием (Pinia)
│   ├── assets/          # статические ресурсы
│   ├── App.vue
│   └── main.js
├── public/              # общие ресурсы
├── vite.config.js       # конфигурационный файл (лаконичный!)
├── package.json
└── index.html
```

**Сравнение конфигурационных файлов** (насколько лаконична конфигурация Vite):
```js
// vite.config.js - весь конфигурационный файл вот настолько мал
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig({
  plugins: [vue()],
  resolve: {
    alias: { '@': '/src' }
  }
})
// Сравните с конфигурацией Webpack выше — насколько же лаконичнее, правда?
```

| Параметр сравнения | Этап 2 (Webpack) | Этап 3 (Vite) | Прирост удобства |
|--------|---------|------|------|
| Создание проекта | Копировать шаблон, править конфиг вручную | `npm create vite@latest` | 30 секунд — и готово |
| Холодный запуск | 30s+ | <1s | **в 30 раз быстрее** |
| Горячее обновление | 3-5s | <100ms | **в 30 раз быстрее** |
| Конфигурационный файл | Несколько сотен строк | Несколько десятков строк или вовсе не нужен | **значительное упрощение** |

**Сравнение реального опыта**:
```bash

npm create vite@latest my-project  # создание проекта одной командой
cd my-project && npm install
npm run dev
# ждём 300 миллисекунд... не успел и опомниться, как готово
# [INFO] ready in 312ms
# правка кода -> сохранение -> результат виден мгновенно
```

### 3.5 Этап 4: непрерывная оптимизация — стандартизация в команде

Когда цепочка инструментов созрела, команда начала уделять внимание более глубоким вопросам: как сделать командную работу эффективнее? Как избегать повторных граблей? Как унифицировать стиль кода?

Ядро этого этапа — «стандартизация»: не просто удобство инструментов, а чтобы все в команде работали одинаковым образом.

**Способ разработки**:
- **Инструмент сборки**: Vite + собственные плагины, адаптация под особые нужды команды
- **Стартовый шаблон**: внутрикомандные шаблоны стартового набора, единый технологический стек и стандарты
- **Фреймворк**: Vue 3 / React 18 + TypeScript, типобезопасность

**Особенности этого этапа**:
- ✅ **Плюсы**: эффективная командная работа, единый стиль кода, новичкам есть на что опереться при онбординге
- ❌ **Минусы**: нужно вкладывать время в поддержку стартового набора и стандартов, есть определённые издержки на сопровождение

**Что делается на этом этапе?**
1. **Собственные шаблоны стартового набора**: упаковать привычную команде конфигурацию, структуру каталогов, общие компоненты в шаблон, создание нового проекта одной командой
2. **Внедрение TypeScript**: проверка типов в коде, снижение числа ошибок времени выполнения
3. **Установление стандартов кода**: правила ESLint, стандарты Git-коммитов, процесс code review
4. **Непрерывная интеграция/непрерывное развёртывание (CI/CD)**: автоматическое тестирование и развёртывание после коммита кода

::: details Структура проекта на этапе командной стандартизации
**Структура проекта** (внутрикомандный шаблон + TypeScript):
```

├── src/
│   ├── components/      # компоненты
│   ├── views/           # страницы
│   ├── router/          # маршрутизация
│   ├── stores/          # управление состоянием
│   ├── api/             # API-интерфейсы
│   ├── utils/           # вспомогательные функции
│   ├── types/           # определения типов TypeScript
│   ├── assets/          # статические ресурсы
│   ├── App.vue
│   └── main.ts          # обратите внимание: .ts, а не .js
├── public/
├── .eslintrc.cjs        # конфигурация ESLint (единые правила команды)
├── .prettierrc          # конфигурация Prettier (форматирование кода)
```

**Распространённые грабли и решения**:

**Грабли первые: подключение всей библиотеки вместо подключения по необходимости**

Это одна из самых частых ошибок. Часто нам нужна лишь одна функция из библиотеки, а мы по неосторожности подключаем библиотеку целиком.

```js
// ❌ Неправильно: подключаем весь moment.js (2,5 МБ!)
import moment from 'moment'
const formattedDate = moment(date).format('YYYY-MM-DD')

// ✅ Правильно: используем более лёгкий dayjs (2 КБ)
import dayjs from 'dayjs'
const formattedDate = dayjs(date).format('YYYY-MM-DD')

// Либо подключаем функцию из date-fns по необходимости
import { format } from 'date-fns'
const formattedDate = format(date, 'yyyy-MM-dd')
```

**Грабли вторые: Tree Shaking не срабатывает**

Tree Shaking — это функция автоматического удаления неиспользуемого кода инструментом упаковки, но для её работы нужен правильный способ импорта.

```js
// ❌ Неправильно: это подключит весь lodash (70 КБ+)
import _ from 'lodash'
_.debounce(fn, 200)

// ✅ Правильно: импортируем только нужную функцию
import debounce from 'lodash/debounce'

// Либо используем lodash-es (версия в виде ES-модулей, поддерживает Tree Shaking)
import { debounce } from 'lodash-es'
```

## 4. Углубляемся в принципы: почему Vite такой быстрый?

Разобрав реальный кейс, давайте глубже рассмотрим принцип работы Vite и поймём, почему он может быть настолько быстрее традиционных инструментов.

<BundlerComparisonDemo />

### 4.1 Два совершенно разных способа работы

Способ работы традиционных инструментов упаковки (например, Webpack) — «сначала упаковать, потом обслуживать»: прежде чем запустить сервер разработки, ему нужно сначала упаковать все модули приложения в один или несколько bundle-файлов. В этом процессе нужно обойти все исходные файлы, разобрать зависимости, преобразовать код, объединить файлы — и чем больше проект, тем медленнее этот процесс.

```
Процесс работы традиционного инструмента упаковки:

Исходный код (100+ файлов)
    ↓
[Упаковка всего на этапе сборки] ← этот шаг очень затратен по времени!
    ↓
Bundle (один/несколько больших файлов)
    ↓
Запрос браузера → возврат упакованных файлов
```

Способ работы Vite совершенно иной, он применяет стратегию «компиляции по необходимости»: при запуске почти не делает никакой упаковки, а сразу запускает сервер разработки. Когда браузер запрашивает некий модуль, Vite компилирует этот модуль в реальном времени и возвращает его.

```
Процесс работы Vite:

Исходный код (100+ файлов)
    ↓
[Не упаковываем! Сразу запускаем сервер] ← выполняется почти мгновенно
    ↓
Браузер запрашивает index.html
    ↓
Браузер обнаруживает <script type="module"> и продолжает запрашивать JS-файлы
    ↓
Vite компилирует запрошенный модуль в реальном времени → возвращает скомпилированный код
    ↓
Браузер загружает по необходимости, запрашивает только то, что используется
```

### 4.2 Три ключевых момента в работе Vite

**При запуске: моментальный холодный старт**

При запуске Vite делает лишь две вещи: запускает сервер статических файлов и предобрабатывает некоторую информацию о зависимостях. Ему не нужно упаковывать и компилировать все файлы, поэтому запуск завершается почти мгновенно.

**При запросе: компиляция по необходимости**

Когда браузер запрашивает JavaScript-файл через `<script type="module">`, Vite перехватывает этот запрос, компилирует код в реальном времени и возвращает его. Он преобразует TypeScript в JavaScript, разбивает однофайловый компонент Vue на template/script/style, компилирует CSS-препроцессоры в нативный CSS.

**При изменении: молниеносное горячее обновление**

Когда вы меняете код и сохраняете, Vite через WebSocket уведомляет браузер и обновляет только изменившийся модуль, а не перезагружает всю страницу. Поскольку гранулярность модулей очень мелкая (один файл — это один модуль), скорость обновления очень высока, обычно в пределах 100 миллисекунд.

::: tip 💡 Почему в продакшене всё-таки нужна упаковка?
Вы можете спросить: раз без упаковки так быстро, почему в продакшене всё равно упаковывают? Причин несколько: во-первых, хотя HTTP/2 поддерживает мультиплексирование, загрузка множества мелких файлов всё равно влечёт издержки производительности; во-вторых, в процессе упаковки можно выполнить более агрессивные оптимизации — сжатие кода, scope hoisting, более тщательный Tree Shaking; в-третьих, после упаковки можно применить более удачные стратегии кеширования и распространение через CDN. Поэтому при продакшен-сборке Vite использует для упаковки Rollup.

## 5. Loader и Plugin в Webpack

Хотя Vite становится всё популярнее, многие старые проекты по-прежнему используют Webpack, и его идеи проектирования очень полезны для понимания инструментов сборки. Если вам нужно сопровождать проект на Webpack, знание двух его ключевых понятий — Loader и Plugin — обязательно.

### 5.1 Loader: преобразователь файлов

Ключевая идея Webpack — «всё есть модуль», но сам Webpack понимает только JavaScript. Задача Loader — преобразовать файлы других типов в модули JavaScript, которые Webpack может обработать.

Например, когда вы импортируете файл `.vue`, `vue-loader` преобразует его в объект JavaScript-компонента; когда вы импортируете файл `.scss`, `sass-loader` компилирует его в CSS, затем `css-loader` разбирает в нём `@import` и `url()`, и наконец `style-loader` внедряет CSS в тег `<style>` страницы.

### 5.2 Plugin: расширитель функционала

Возможности Plugin мощнее, чем у Loader: он имеет доступ ко всему жизненному циклу сборки Webpack и может выполнять свою логику на разных этапах. Например, `HtmlWebpackPlugin` может автоматически генерировать HTML-файл и внедрять в него ссылки на упакованные ресурсы; `MiniCssExtractPlugin` может выделять CSS в отдельный файл, а не встраивать его в JS; `BundleAnalyzerPlugin` может анализировать состав упакованных файлов, помогая найти модули с чрезмерным объёмом.

### 5.3 Различия между Loader и Plugin

| Параметр сравнения | Loader | Plugin |
|--------|--------|--------|
| **Ключевая задача** | Преобразование файлов, превращение не-JS файлов в JS-модули | Расширение функционала, вмешательство в разные звенья процесса сборки |
| **Момент выполнения** | Выполняется при загрузке модуля, нацелен на отдельный файл | Пронизывает весь жизненный цикл сборки, может слушать разные события |
| **Место настройки** | Настраивается в массиве `module.rules` | Инстанцируется в массиве `plugins` |
| **Типичные примеры** | `babel-loader`, `vue-loader`, `sass-loader` | `HtmlWebpackPlugin`, `MiniCssExtractPlugin` |

## 6. Шаблон конфигурации Vite

Теории уже достаточно, ниже готовый к использованию шаблон конфигурации Vite, охватывающий распространённые возможности, нужные большинству проектов. Вы можете сокращать и подстраивать его под нужды своего проекта.

::: details Нажмите, чтобы посмотреть полную конфигурацию

```javascript
// vite.config.js
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'
import { resolve } from 'path'

export default defineConfig(({ mode }) => ({
  // Настройка базового пути
  base: './',  // базовый путь при развёртывании, относительный путь гибче

  // Псевдонимы путей, чтобы import был лаконичнее
  resolve: {
    alias: {
      '@': resolve(__dirname, 'src'),
      '@components': resolve(__dirname, 'src/components'),
      '@utils': resolve(__dirname, 'src/utils'),
      '@api': resolve(__dirname, 'src/api')
    }
  },

  // Настройка CSS
  css: {
    preprocessorOptions: {
      scss: {
        // Автоматический импорт глобальных переменных стилей
        additionalData: `@use "@/styles/vars.scss" as *;`
      }
    }
  },

  // Настройка сервера разработки
  server: {
    port: 3000,           // номер порта
    open: true,           // автоматически открывать браузер
    cors: true,           // разрешить кросс-доменные запросы
    // Настройка прокси API, решает проблему CORS в среде разработки
    proxy: {
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, '')
      }
    }
  },

  // Настройка сборки
  build: {
    outDir: 'dist',
    sourcemap: mode !== 'production',  // в продакшене не генерировать sourcemap

    // Настройка упаковки Rollup
    rollupOptions: {
      output: {
        // Стратегия разделения кода: упаковать разные типы зависимостей в разные файлы
        manualChunks: {
          'vue-vendor': ['vue', 'vue-router', 'pinia'],
          'ui-vendor': ['element-plus'],
          'utils-vendor': ['lodash-es', 'axios', 'dayjs']
        },
        // Правила именования файлов
        entryFileNames: 'js/[name]-[hash].js',
        chunkFileNames: 'js/[name]-[hash].js',
        assetFileNames: (assetInfo) => {
          const info = assetInfo.name.split('.')
          const ext = info[info.length - 1]
          if (/\.(png|jpe?g|gif|svg|webp|ico)$/i.test(assetInfo.name)) {
            return 'img/[name]-[hash][extname]'
          }
          if (/\.(woff2?|eot|ttf|otf)$/i.test(assetInfo.name)) {
            return 'fonts/[name]-[hash][extname]'
          }
          return '[ext]/[name]-[hash][extname]'
        }
      }
    },

    // Настройка сжатия кода
    minify: 'terser',
    terserOptions: {
      compress: {
        drop_console: true,   // удалить console
        drop_debugger: true   // удалить debugger
      }
    },

    // Чанки больше 500 КБ вызовут предупреждение
    chunkSizeWarningLimit: 500
  },

  // Настройка плагинов
  plugins: [
    vue()  // поддержка Vue 3
  ]
}))
```

:::

Эта конфигурация охватывает основные потребности повседневной разработки: псевдонимы путей делают операторы import лаконичнее, прокси сервера разработки решает проблему CORS, стратегия разделения кода оптимизирует производительность загрузки, а настройка сжатия удаляет отладочный код.

## 6.1 SourceMap: секретное оружие для отладки сжатого кода

Вы могли заметить в конфигурации опцию `sourcemap`. Что такое SourceMap? Почему он так важен?

В продакшен-среде наш код сжимается, объединяется, транспилируется и в итоге превращается в однострочную нечитаемую «абракадабру». Когда в коде возникает ошибка, браузер может лишь сообщить, что ошибка произошла в строке 1, символ 1234 сжатого кода — для отладки это бесполезно. Задача SourceMap — установить соответствие, чтобы в инструментах разработчика браузера вы по-прежнему видели исходный код.

## 6.2 Отпечаток ресурса: долгосрочное кеширование и контроль версий

В конфигурации вы могли заметить, что имя файла содержит `[hash]` — это и есть отпечаток ресурса. Его задача — реализовать стратегию долгосрочного кеширования: когда содержимое файла не меняется, hash тоже не меняется, и браузер может напрямую использовать кеш; когда содержимое файла меняется, вместе с ним меняется и hash, и браузер автоматически получает новую версию.

Подытожим ключевые понятия фронтенд-инжиниринга в одной таблице:

| Понятие | Объяснение в одной фразе | Какую проблему решает | Характерные инструменты |

| **Сборка** | Полный процесс от исходного кода до результата | Автоматизация, оптимизация | Все вышеперечисленные инструменты |
| **Tree Shaking** | Удалить неиспользуемый код | Уменьшение объёма файлов | Webpack, Rollup |

| **HMR** | Горячая замена модулей, обновление без перезагрузки | Опыт разработки | Webpack, Vite |

Поняв эти базовые принципы, вы сможете быстро освоиться и спокойно справляться с любыми сменами инструментов.
