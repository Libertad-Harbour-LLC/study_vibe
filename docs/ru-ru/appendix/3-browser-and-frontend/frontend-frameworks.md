# Глубокое руководство по фронтенд-фреймворкам

::: tip Предисловие
Вы уже освоили основы HTML, CSS и JavaScript и можете делать простые веб-страницы. Но по мере усложнения функций страниц вы, возможно, заметите: писать код на нативном JavaScript становится трудно поддерживать, изменение в одном месте требует правок во многих, а при командной работе постоянно возникают конфликты.

Именно поэтому нам нужны фронтенд-фреймворки — они делают код более упорядоченным, удобным в сопровождении и эффективным в разработке. В vibecoding ИИ напишет за вас большую часть кода. Прочитав эту статью, вы сможете:

- Знать, чем особенны Vue, React, Svelte, Angular
- Разбираться в ключевых понятиях «управления данными» и «компонентности»
- Выбирать подходящий фреймворк под проект
:::

## 1. Зачем следить за историей эволюции фронтенда?

::: tip 🤔 Ключевой вопрос
**Почему веб-страницы становятся всё сложнее? Почему фронтенд-технологии непрерывно развиваются?** Этот вопрос приведёт вас к пониманию пути технической эволюции от простых страниц к современным веб-приложениям.
:::

### 1.1 От «электронного плаката» к «настольному приложению»

Представьте **плакат**, который вы видите на улице:

- ✅ Есть содержание (текст, изображения)
- ✅ Есть дизайн (цвет, вёрстка)
- ❌ Но если заговорить с ним, он не ответит
- ❌ Если нажать на какое-то место, ничего не произойдёт

**Самые ранние веб-страницы** были именно такими «электронными плакатами»: только смотреть, нельзя изменить, содержимое фиксировано.

**Современные веб-страницы** совсем другие. Они как **настольные приложения** (VS Code, Figma):

- ✅ Можно редактировать документы, рисовать, играть в игры
- ✅ Реагируют в реальном времени на каждое ваше действие
- ✅ Могут даже работать офлайн

**Ключевая причина этого перехода: функции веб-страниц становятся всё сложнее, нужны более эффективные технологии и способы разработки.**

### 1.2 Жизненная аналогия: строительство дома

Эволюция фронтенд-технологий похожа на эволюцию способов строительства дома:

| Эпоха | 🏠 Аналогия со строительством | Реальные особенности | Плюсы и минусы |
|------|-----------|---------|--------|
| **2000-е** | **Расклеить плакаты** | Статические страницы, достаточно написать HTML | ✅ Просто ❌ Нет интерактивности |
| **2010-е** | **Нанять рабочих для ручной отделки** | Эпоха jQuery, ручная работа с каждым элементом | ✅ Есть интерактивность ❌ Код хаотичен, трудно поддерживать |
| **2020-е** | **Собрать дом из лего** | Эпоха Vue/React, компонентная разработка | ✅ Эффективно, поддерживаемо ❌ Кривая обучения |

::: tip 💡 Что можно увидеть из таблицы?

**Этап 1 → Этап 2**: от «не двигается» к «двигается». Это качественный скачок — у страниц появилась интерактивность, но ценой стал хаос в коде.

**Этап 2 → Этап 3**: от «работает» к «удобно». Компонентность делает код переиспользуемым как кубики, заметно повышая эффективность разработки.

**Ключевая идея**: эволюция технологий — это не «новое ради нового», а решение болевых точек предыдущего этапа.
:::

## 2. Первый этап: статические страницы и «нарезка макетов» (2000-е)

**Как выглядели самые ранние страницы? Почему тогда не нужны были фреймворки?** Поняв ограничения этого этапа, вы осознаете необходимость последующей эволюции технологий.
:::

<FrontendEvolutionDemo />

### 2.1 Как выглядела эта эпоха?

**Способ разработки**:

- Написать несколько HTML-файлов
- Встроить немного CSS и JavaScript
- Перетащить файлы прямо в браузер и сразу увидеть результат
- Загрузить папку на сервер — и развёртывание завершено

**Особенности**:

- ✅ **Плюсы**: просто и прямо, нет порога входа, написал — и сразу работает
- ❌ **Минусы**: невозможно реализовать сложную интерактивность, при росте кода начинается хаос

::: details Посмотреть тогдашнюю структуру проекта

```
project/
├── index.html
├── login.html
├── css/
│   ├── bootstrap.css
│   └── custom.css
├── js/
│   ├── jquery.js
│   └── app.js
└── images/
```

**Возникшие проблемы**:

1. **Загрязнение глобальными переменными**: все переменные в глобальном пространстве имён, легко перекрывают друг друга
2. **Хаос в управлении зависимостями**: JS-файлы нужно загружать в правильном порядке, иначе будет ошибка
3. **Код трудно переиспользовать**: чтобы переиспользовать функцию, остаётся только копировать-вставлять
:::

### 2.2 Что такое «нарезка макетов»?

Вы, возможно, слышали термин «нарезка макетов». Это была основная работа раннего фронтенда:

**Что такое нарезка макетов?**

Дизайнер проектирует страницу в Photoshop → фронтендер нарезает дизайн на мелкие изображения → собирает изображения в страницу с помощью HTML

**Почему это так медленно?**

Для каждого мелкого изображения на странице браузер должен отправить один **сетевой запрос**. Чем больше запросов, тем медленнее загрузка.

::: tip 💡 Спрайты (Sprite)

Чтобы сократить число запросов, появилась технология «спрайтов»: множество мелких изображений объединяется в одно большое.

Плюс — число запросов уменьшается, минус — создание и поддержка довольно хлопотны.

Урок этого этапа: **слишком много запросов — главный враг производительности**.

## 3. Второй этап: эпоха jQuery — «таскать кирпичи вручную» (2010-е)

::: tip 🤔 Ключевой вопрос
**Зачем нужен был jQuery? Какую проблему он решил и какую новую принёс?** Поняв ограничения jQuery, вы осознаете ценность Vue/React.
:::

### 3.1 Зачем нужен был jQuery?

По мере усложнения страниц проявились проблемы нативного JavaScript:

- ❌ **Громоздкий API**: даже простая операция требует много кода
- ❌ **Совместимость браузеров**: API в разных браузерах различаются, приходится писать много кода совместимости
- ❌ **Слабые селекторы**: искать элементы очень хлопотно

Родился **jQuery**. Он сделал JavaScript простым:

```javascript
// Нативный JavaScript (громоздко)
const element = document.getElementById('title')

// jQuery (лаконично)
const element = $('#title')
```

### 3.2 Идея jQuery: менять страницу своими руками

Ключевая идея jQuery — **императивность**: вы говорите браузеру, «как делать».

```javascript
// Найти элемент заголовка
$('#title').text('Новый заголовок')

// Найти кнопку и отключить
$('#submit-btn').attr('disabled', true)

// Найти список и добавить пункт
$('ul').append('<li>Новый пункт</li>')
```

**Проблема**: вам нужно помнить, какие элементы есть на странице, и при каждом изменении данных вручную обновлять все связанные элементы.

👇 **Попробуйте сами**: сравните подход jQuery и подход управления данными

<JQueryVsStateDemo />

::: warning ⚠️ Болевая точка jQuery

Представьте, что вы делаете корзину:

```javascript
// Пользователь нажимает «Добавить в корзину»
function addToCart() {
  cartCount++ // данные изменились

  // Вам нужно вручную обновить все связанные места
  $('#cart-count').text(cartCount) // красный кружок в правом верхнем углу
  $('#cart-page-count').text(cartCount) // страница корзины
  $('#checkout-price').text(calculatePrice()) // кнопка оформления

  // Пропустите одно место — и страница станет несогласованной!
}
```

**Это и есть цена «таскания кирпичей вручную»**: легко ошибиться, трудно поддерживать.
:::

### 3.3 Распространение мобильных устройств: появление адаптивного дизайна

На этом этапе произошло ещё одно важное изменение: **начали распространяться телефоны и планшеты**.

Страницы должны были подстраиваться под разные экраны. Для этого нужна **адаптивная вёрстка**: один и тот же HTML/CSS автоматически меняет компоновку в зависимости от ширины экрана.

**Ядро адаптивной вёрстки: медиазапросы (Media Query)**

```css
/* Экран компьютера (больше 640px) */
@media (min-width: 640px) {
  .container {
    display: flex;
  }
}

/* Экран телефона (меньше 640px) */
@media (max-width: 640px) {
  .container {
    display: block;
  }
}
```

<ResponsiveGridDemo />

::: tip 💡 Адаптивность — как «умная фоторамка»

Представьте, что вы смотрите одну и ту же фотографию в разных комнатах:

- В **большой гостиной** (экран компьютера) фотографию можно поставить побольше, а рядом ещё разместить другие украшения
- В **маленькой спальне** (экран телефона) фотографию нужно уменьшить, а другие украшения убрать

**Адаптивная вёрстка** — это «умная фоторамка», которая автоматически подстраивает способ показа под размер комнаты.

## 4. Третий этап: от «таскания кирпичей вручную» к «управлению данными» (Vue/React)

::: tip 🤔 Ключевой вопрос
**Зачем нужны Vue/React? В чём их принципиальное отличие от jQuery?** Понимание «декларативности» и «управления данными» — ключ к освоению современных фронтенд-фреймворков.
:::

### 4.1 Зачем нужны новые фреймворки?

Проблемы эпохи jQuery накопились до определённого предела:

- **При росте кода начинается хаос**: операции с DOM повсюду, трудно поддерживать
- **Легко поймать баг**: пропустил обновление одного места — страница несогласованна
- **Сложно сотрудничать**: несколько человек правят один файл, легко получить конфликты

Ключевая идея **Vue / React**: **меняй только данные, страница обновится сама**.

### 4.2 Идея Vue/React: декларативный UI

**jQuery (императивный)**:

```javascript
// Вы должны указать браузеру каждый шаг
$('#title').text('Новый заголовок')
$('#title').css('color', 'red')
$('#title').show()
```

**Vue (декларативный)**:

```javascript
// Вам нужно лишь сказать браузеру, «что показывать»
data() {
  return {
    title: "Новый заголовок",
    color: "red",
    visible: true
  }
}
```

<ImperativeVsDeclarativeDemo />

::: tip 💡 Императивный vs декларативный

Это как писать картину:

- **Императивный**: вы говорите художнику «возьми кисть, обмакни в красную краску, нарисуй круг в координатах (10,10)»
- **Декларативный**: вы просто даёте художнику фотографию: «нарисуй мне вот так»

Vue/React и есть «декларативный»: вы описываете, «как выглядит страница», а фреймворк отвечает за то, «как её нарисовать».
:::

### 4.3 Компонентность: писать страницы как сборку лего

Самая мощная особенность **Vue / React** — **компонентность**: разбиение страницы на отдельные «кубики».

Представьте, что вы собираете лего:

- Вам не нужно «вырезать каждый кубик с нуля» (писать HTML/CSS с нуля)
- Вам нужно лишь «соединить кубики по инструкции» (скомбинировать компоненты)
- Каждый кубик **независим**, и вы можете **переиспользовать** его в разных наборах

**Преимущества компонентов**:

- **Переиспользование**: написал один компонент «карточка товара» — можно использовать 100 раз
- **Инкапсуляция**: внутреннее состояние компонента не влияет на других
- **Сопровождаемость**: изменил один компонент — обновятся все места, где он используется

::: info 💡 Приёмы распознавания
- Увидели `<ComponentName />` → это компонент
- Увидели `import xxx from './xxx.vue'` → импортируется компонент
- Увидели `props: {...}` → параметры, принимаемые компонентом
- Увидели `emit('xxx')` → компонент отправляет событие родительскому компоненту
:::

### 4.4 SPA: рождение одностраничного приложения

В эпоху **Vue / React** есть ещё одно важное изменение: **от MPA к SPA**.

**MPA (Multi-Page Application, многостраничное приложение)**:

- Нажал на ссылку → перезагрузка всей страницы → показ новой страницы
- Это как **листать книгу**: чтобы перевернуть страницу, нужно закрыть старую книгу и взять с полки новую

**SPA (Single-Page Application, одностраничное приложение)**:

- Нажал на ссылку → обновляется только область контента → страница не перезагружается
- Это как **сменить главу в той же книге**: лишь стираешь старое содержимое и пишешь новое

## 5. Стратегии рендеринга: от CSR к SSR/SSG

::: tip 🤔 Ключевой вопрос
**Страница генерируется на сервере или в браузере?** У разных стратегий рендеринга свои плюсы и минусы, а выбор подходящей стратегии критичен для производительности и SEO.
:::

**CSR (Client-Side Rendering) — рендеринг на стороне клиента**:

- Браузер скачивает JavaScript → выполняет код → генерирует страницу
- Плюсы: плавная интерактивность, низкая нагрузка на сервер
- Минусы: медленный первый экран, неблагоприятно для SEO

**SSR (Server-Side Rendering) — рендеринг на стороне сервера**:

- Сервер генерирует HTML → отправляет браузеру → браузер сразу показывает
- Плюсы: быстрый первый экран, благоприятно для SEO
- Минусы: высокая нагрузка на сервер, сложная реализация

**SSG (Static Site Generation) — генерация статического сайта**:

- HTML всех страниц генерируется на этапе сборки
- Плюсы: предельно быстро, полностью статично, дружелюбно к CDN
- Минусы: не подходит для динамического контента

::: info 💡 Как выбрать?
- **Контентные сайты** (блоги, документация): в приоритете SSG
- **Динамические сайты с потребностью в SEO** (электронная коммерция, новости): используйте SSR
- **Системы административных панелей**: используйте CSR
- **Смешанные потребности**: рассмотрите смешанный рендеринг в Nuxt/Next.js

## 6. Четвёртый этап: инжиниринг и инструменты сборки (2015–2020)

::: tip 🤔 Ключевой вопрос
**Зачем фронтенду «инжиниринг»? Что же на самом деле делают инструменты сборки?** Поняв инжиниринг, вы разберётесь в рабочем процессе современного фронтенд-проекта.
:::

### 6.1 Зачем нужен «инжиниринг»?

Фронтенд-проекты становятся всё больше, и больше нельзя полагаться на «ручное подключение скриптов».

**Инжиниринг** — это применение инструментов и стандартов, чтобы сделать разработку эффективнее, код надёжнее, а сотрудничество — более гладким.

::: tip 💡 Инжиниринг = от «ручной мастерской» к «современной фабрике»

Представьте, как вы готовите дома vs открываете ресторан:

- **Готовка дома**: хочешь есть что угодно — готовишь что угодно, полная свобода
- **Открытие ресторана**: нужны стандартизированные рецепты, регламентированные процессы, единые закупки сырья

С фронтенд-разработкой так же:

- **Маленький проект**: пиши как хочешь
- **Большой проект**: нужны единые стандарты кода, инструменты автоматизации, стандартизированные процессы
:::

### 6.2 Инструменты сборки: Webpack → Vite

**Webpack** (традиционный):

- Способ работы: **сначала упаковать, потом обслуживать**
- При запуске: упаковать весь код → запустить сервер
- Проблема: **медленно**. Чем больше проект, тем медленнее запуск (можно ждать 30 секунд)

**Vite** (современный):

- Способ работы: **компиляция по необходимости**
- При запуске: не упаковывает, сразу запускает сервер
- Какой файл запросит браузер, тот и компилируется в реальном времени
- Преимущество: **быстро**. Обычно запуск менее чем за 1 секунду

| Параметр сравнения | Webpack | Vite | Прирост |
|--------|---------|------|------|
| Холодный запуск | 30s+ | <1s | **в 30 раз быстрее** |
| Горячее обновление | 3-5s | <100ms | **в 30 раз быстрее** |
| Конфигурационный файл | Несколько сотен строк | Несколько десятков строк | **значительное упрощение** |

::: tip 💡 Почему Vite такой быстрый?

**Webpack** — как **полный переезд со всем скарбом**: сначала упаковать все вещи, потом выходить.

**Vite** — как **путешествие налегке**: берёшь только необходимое, а что понадобится — докупаешь по дороге.

В среде разработки большую часть времени вам нужно изменить лишь несколько файлов, и Vite компилирует только эти файлы — конечно, это быстро.
:::

## 7. Сравнение основных фреймворков

::: tip 🤔 Ключевой вопрос
**Чем особенны Vue, React, Svelte, Angular? Как выбрать подходящий вам фреймворк?** Только зная их идеи проектирования и сценарии использования, можно сделать разумный выбор.
:::

### 7.1 Сравнение четырёх главных фреймворков

| Характеристика | Vue | React | Svelte | Angular |
|------|-----|-------|--------|---------|
| **Идея проектирования** | Прогрессивный фреймворк | UI-библиотека | Фреймворк времени компиляции | Полноценная платформа |
| **Кривая обучения** | ⭐⭐ Простая | ⭐⭐⭐ Средняя | ⭐⭐ Простая | ⭐⭐⭐⭐ Крутая |
| **Производительность** | Быстро | Быстро | **Предельно быстро** | Быстро |
| **Экосистема** | Развитая | **Самая развитая** | Растущая | Развитая |
| **Размер пакета** | Маленький | Средний | **Минимальный** | Большой |
| **Подходящие сценарии** | Малые и средние проекты | Крупные проекты | Высокие требования к производительности | Корпоративные приложения |
| **Поддержка компании** | Эван Ю (независимо) | Meta | Сообщество | Google |

### 7.2 Vue: прогрессивный фреймворк

**Ключевая идея**: прогрессивное внедрение, можно использовать лишь часть, а можно весь набор

```vue
<template>
  <div>{{ message }}</div>
</template>

<script>
export default {
  data() {
    return {
      message: 'Hello Vue'
    }
  }
}
</script>
```

**Плюсы**:
- ✅ Пологая кривая обучения, развитая документация на китайском
- ✅ Синтаксис шаблонов интуитивен, легко понять
- ✅ Однофайловые компоненты (.vue) с ясной структурой
- ✅ Подходит для быстрой разработки

**Минусы**:
- ❌ Управление состоянием в крупных проектах требует дополнительно изучить Vuex/Pinia
- ❌ Гибкость чуть уступает React

**Сценарии применения**:
- Малые и средние веб-приложения
- Быстрое прототипирование
- Команды, говорящие на китайском (дружелюбная документация)

### 7.3 React: UI-библиотека

**Ключевая идея**: отвечает только за слой представления, остальные вопросы — на откуп сообществу

```jsx
function App() {
  const [message, setMessage] = useState('Hello React')
  return <div>{message}</div>
}
```

**Плюсы**:
- ✅ Самая развитая экосистема, богатые библиотеки компонентов
- ✅ Гибкий синтаксис JSX, мощная выразительность
- ✅ Отличная производительность виртуального DOM
- ✅ Подходит для крупных проектов

**Минусы**:
- ❌ Довольно крутая кривая обучения, нужно освоить дополнительные понятия
- ❌ Приходится самому выбирать и сочетать разные библиотеки
- ❌ JSX требует компиляции, не запускается в браузере напрямую

**Сценарии применения**:
- Крупные сложные приложения
- Проекты, которым нужна богатая экосистема
- Кроссплатформенная разработка (React Native)

### 7.4 Svelte: фреймворк времени компиляции

**Ключевая идея**: нет виртуального DOM, компоненты преобразуются в эффективный нативный код при компиляции

```svelte
<script>
  let message = 'Hello Svelte'
</script>

<div>{message}</div>
```

**Плюсы**:
- ✅ **Лучшая производительность** (нет издержек виртуального DOM во время выполнения)
- ✅ Минимальный размер пакета
- ✅ Простой и интуитивный синтаксис
- ✅ Реактивная система поддерживается естественным образом

**Минусы**:
- ❌ Относительно небольшая экосистема
- ❌ Размер сообщества уступает Vue/React
- ❌ Мало сторонних библиотек

**Сценарии применения**:
- Приложения с крайне высокими требованиями к производительности
- Проекты, чувствительные к размеру пакета
- Команды, готовые пробовать новые технологии

### 7.5 Angular: полноценная платформа

**Ключевая идея**: предоставляет готовое комплексное решение из коробки

```typescript
@Component({
  selector: 'app-root',
  template: '<div>{{ message }}</div>'
})
export class AppComponent {
  message = 'Hello Angular'
}
```

**Плюсы**:
- ✅ Полный функционал: маршрутизация, HTTP, формы — всё есть
- ✅ Нативная поддержка TypeScript
- ✅ Подходит для крупных команд и проектов
- ✅ Единые стандарты кода

**Минусы**:
- ❌ Крутая кривая обучения
- ❌ Много понятий, высокая сложность
- ❌ Большой размер пакета
- ❌ Не подходит для маленьких проектов

**Сценарии применения**:
- Крупные корпоративные приложения
- Команды, которым нужны строгие стандарты
- Проекты с уже имеющимся технологическим стеком TypeScript

## 8. Итог: суть эволюции

Эволюция фронтенд-технологий по сути решает две проблемы:

### 8.1 Эффективность: от ручного к автоматическому

| Эпоха | Способ разработки | Эффективность |
|------|---------|------|
| **2000-е** | Ручное написание HTML/CSS/JS | ⭐ |
| **2010-е** | jQuery + ручные операции с DOM | ⭐⭐ |
| **2020-е** | Vue/React + управление данными | ⭐⭐⭐ |
| **Сейчас** | Компонентность + инжиниринг + автоматизация | ⭐⭐⭐⭐⭐ |

### 8.2 Масштаб: от одиночки к команде

| Эпоха | Масштаб проекта | Способ сотрудничества |
|------|---------|---------|
| **2000-е** | Несколько файлов | Поддерживает один человек |
| **2010-е** | Несколько десятков файлов | Маленькая команда, легко поймать конфликты |
| **2020-е** | Несколько сотен файлов | Средняя команда, нужны стандарты |
| **Сейчас** | Несколько тысяч файлов | Большая команда, нужна полноценная инженерная система |

## Краткий справочник терминов

| Термин | Английский | Объяснение простыми словами |
|------|------|-----------|
| **DOM** | Document Object Model | Объектная модель документа. Представляет страницу деревом объектов, доступным для чтения и записи из JS. |
| **jQuery** | - | Популярная в ранние времена JS-библиотека, упростившая операции с DOM. |
| **Vue/React** | - | Современные фронтенд-фреймворки с управлением данными и компонентной разработкой. |
| **Компонент** | Component | Переиспользуемый элемент UI, например кнопка, карточка, навигационная панель. |
| **MPA** | Multi-Page Application | Многостраничное приложение. Каждый переход заново загружает всю страницу. |
| **SPA** | Single-Page Application | Одностраничное приложение. Загружается один раз, последующие переходы не перезагружают страницу. |
| **Маршрутизация** | Routing | Правила и процесс управления переключением между страницами. |
| **SSR** | Server-Side Rendering | Серверный рендеринг. Сервер генерирует HTML и отправляет браузеру. |
| **SSG** | Static Site Generation | Генерация статического сайта. Предрендеринг страниц в статический HTML на этапе сборки. |
| **CSR** | Client-Side Rendering | Клиентский рендеринг. Браузер генерирует страницу с помощью JS. |
| **Webpack** | - | Традиционный инструмент упаковки, сначала упаковывает, потом обслуживает. |
| **Vite** | - | Современный инструмент сборки, компиляция по необходимости, предельно быстрый. |
| **Адаптивность** | Responsive Design | Дизайн, при котором страница автоматически подстраивается под разные размеры экранов. |
| **Медиазапрос** | Media Query | Условная проверка в CSS, применяющая разные стили в зависимости от ширины экрана. |
| **Императивный** | Imperative | Говорить программе, «как делать». |
| **Декларативный** | Declarative | Говорить программе, «что нужно». |
| **Управление данными** | Data-Driven | Изменяешь только данные, интерфейс обновляется сам. |
| **Tree Shaking** | - | Отряхивание дерева. Автоматическое удаление неиспользуемого кода, уменьшение размера пакета. |
| **Разделение кода** | Code Splitting | Разбиение кода на мелкие части с загрузкой по необходимости. |
