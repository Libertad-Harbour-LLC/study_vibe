# Механизмы обмена данными в реальном времени (Polling / SSE / WebSocket)

::: tip Ключевой обзор
**Как браузер реализует обновление данных в реальном времени?**
Традиционный протокол HTTP основан на модели «запрос-ответ»: клиент должен сам инициировать запрос, и только тогда сервер может вернуть данные. Если нам нужно реализовать сценарии реального времени, такие как чат-комнаты или трансляция биржевых котировок, эта модель сталкивается с трудностями.

В этой главе мы рассмотрим три основные технологии, с помощью которых фронтенд справляется с обменом данными в реальном времени: короткий опрос (Polling), события, отправляемые сервером (SSE), и полнодуплексный WebSocket, а также обсудим их принципы работы и сценарии применения.
:::

---

## 1. Ограничения традиционного HTTP

Протокол HTTP изначально был разработан для извлечения документов и обладает свойствами **без сохранения состояния (Stateless)** и **одностороннего инициирования со стороны клиента**:
1. Клиент инициирует HTTP-запрос.
2. Сервер обрабатывает запрос и возвращает ответ.
3. После выполнения задачи соединение обычно освобождает соответствующий логический запрос (хотя HTTP/1.1 поддерживает повторное использование постоянных соединений, модель «запрос-ответ» на уровне бизнес-логики не меняется).

В этой модели сервер не может самостоятельно в любой момент уведомить ожидающего клиента об изменении состояния. Чтобы получить актуальные данные, приходится искать другие архитектурные решения.

---

## 2. Короткий опрос (Polling)

Самое прямое решение — это **короткий опрос**. То есть клиент с помощью таймера (например, `setInterval`) через фиксированные интервалы времени автоматически отправляет HTTP-запрос на сервер, спрашивая, появились ли новые данные.

**Технические особенности и ограничения:**
- **Преимущества**: механизм реализации крайне прост, полностью опирается на стандартный протокол HTTP и технологии AJAX/Fetch.
- **Недостатки**: может приводить к огромным сетевым издержкам и расточительству ресурсов. Большую часть времени ответ сервера может быть «новых данных нет». Независимо от того, есть данные или нет, каждый запрос должен нести полные HTTP-заголовки (Headers, Cookies и т. д.), что при высокой нагрузке приводит к тому, что сетевые ресурсы занимаются массой бессмысленных опросов.

## 3. События, отправляемые сервером (Server-Sent Events)

Чтобы снизить издержки от частого установления HTTP-соединений, **Server-Sent Events (SSE)** предоставляет облегчённую архитектуру одностороннего потока данных.

SSE построен поверх протокола HTTP. После того как клиент отправляет HTTP-запрос со специальным заголовком (`Accept: text/event-stream`), сервер при отправке ответа сохраняет базовое TCP-соединение открытым. Затем сервер может через этот постоянный канал непрерывно отправлять клиенту данные в текстовом формате.

**Технические особенности и ограничения:**
- **Преимущества**: соединение постоянное, сетевые издержки малы; браузер изначально поддерживает механизм автоматического переподключения при разрыве связи; очень хорошо подходит для **однонаправленной** потоковой передачи данных от сервера к клиенту (например, посимвольный вывод текста большой языковой модели, трансляция биржевых котировок в реальном времени).
- **Недостатки**: канал связи односторонний. Если клиенту нужно отправить серверу управляющие команды или новые данные, он должен дополнительно установить обычный HTTP-запрос.

## 4. WebSocket: протокол полнодуплексной связи

Когда сценарий применения предполагает высокочастотное двустороннее взаимодействие (например, многопользовательские онлайн-экшен-игры, точное совместное редактирование документов), нам нужна технология, которая одновременно снижает издержки связи и обеспечивает по-настоящему дуплексную коммуникацию — **WebSocket**.

WebSocket — это самостоятельный сетевой протокол связи. Он остроумно использует протокол HTTP для начального установления соединения:
1. **Этап рукопожатия**: клиент отправляет специальный HTTP-запрос, заявляя о желании обновить его до нового протокола (с заголовком `Upgrade: websocket`).
2. **Качественное изменение соединения**: если сервер поддерживает и соглашается на этот протокол, он отвечает кодом состояния `101 Switching Protocols`.
3. **Полная свобода**: на этом нормативная миссия HTTP завершается, базовое TCP-соединение передаётся протоколу WebSocket. После этого клиент и сервер обладают равными правами на полнодуплексную (Full-Duplex) связь, и обе стороны могут в любой момент отправлять и принимать кадры данных в максимально простом формате.

**Технические особенности и ограничения:**
- **Преимущества**: поддерживает по-настоящему двунаправленную связь в реальном времени; заголовочная информация кадров данных крайне мала, задержка связи низкая, пропускная способность высокая; поддерживает передачу нативных двоичных данных (ArrayBuffer).
- **Недостатки**: высокая архитектурная сложность и сложность разработки; поскольку поддерживается постоянное долгое соединение, к серверной системной архитектуре, стратегиям балансировки нагрузки и проектированию контроля «сердцебиения» предъявляются более строгие инженерные требования.

## 5. Итоги: сравнение технологий для выбора

| Критерий | Короткий опрос (Polling) | События от сервера (SSE) | WebSocket |
| :--- | :--- | :--- | :--- |
| **Направление связи** | Клиент сам опрашивает и извлекает данные (одностороннее) | Сервер постоянно сам отправляет данные (одностороннее) | Клиент и сервер обладают равными правами на приём/отправку (двунаправленное, полнодуплексное) |
| **Базовый протокол** | Стандартный HTTP | Стандартный HTTP | Самостоятельный протокол WebSocket (на основе TCP) |
| **Издержки данных** | Очень высокие (включают полные HTTP-заголовки) | Относительно низкие | Очень низкие (минимальные заголовки кадров данных) |
| **Типичные сценарии применения** | Периодическая проверка статуса завершения фоновых асинхронных задач | Однонаправленный потоковый вывод диалога большой модели, push-уведомления новостей или системы | Сигнализация для аудио/видео в реальном времени, многопользовательские онлайн-сражения, совместная доска и редактирование |

В реальной инженерной практике разработчик должен исходя из требований конкретного бизнес-сценария к режиму реального времени и частоте двустороннего взаимодействия найти баланс между сложностью поддержки системы и эффективностью связи, выбрав наиболее подходящий технологический стек.
