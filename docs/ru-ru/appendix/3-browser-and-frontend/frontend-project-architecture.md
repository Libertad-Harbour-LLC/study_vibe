# Проектирование архитектуры фронтенд-проекта

::: tip 🎯 Ключевой вопрос
**От простой HTML-страницы до сложного корпоративного приложения — как выбрать подходящую архитектуру для проектов разного масштаба?** Это всё равно что спросить: от квартиры-студии до большого торгового центра — как спроектировать разную планировку пространства в зависимости от потребностей? Хорошая архитектура должна развиваться вместе с ростом проекта, а не быть чрезмерно сложной с самого начала.
:::

---

## 1. Эволюция архитектуры: от простого к сложному

### 1.1 Обзор трёх уровней сложности

Архитектура фронтенд-проекта должна соответствовать его сложности. По двум измерениям — **технической сложности** и **масштабу аудитории** — мы делим проекты на три уровня:

| Уровень | Технологический стек | Масштаб аудитории | Типичные сценарии | Ключевой фокус |
|------|--------|----------|----------|------------|
| **Начальный** | HTML/CSS/JS | Личный / небольшая команда | Личный блог, промо-страница, простой инструмент | Быстрый запуск, простая поддержка |
| **Продвинутый** | Vue/React + инструменты сборки | Малый и средний бизнес | Системы управления, витрины интернет-магазинов, SaaS | Переиспользование компонентов, управление состоянием |
| **Корпоративный** | Фреймворк + микрофронтенды/SSR | Крупные приложения | Большие платформы, сложные бизнес-системы | Оптимизация производительности, командная работа, масштабируемость |

::: tip 💡 Как выбрать?
**Не усложняйте без необходимости!** Многие проекты начинаются с простого HTML и по мере роста потребностей постепенно вводят фреймворки и инструменты.

- Личный проект → начальный уровень
- MVP стартапа → начальный или продвинутый уровень
- Корпоративная система управления → продвинутый уровень
- Крупная интернет-платформа → корпоративный уровень
:::

## 2. Начальный уровень: проект на HTML/CSS/JS

### 2.1 Сценарии применения

- Личный блог, страница резюме
- Промо-страница продукта (Landing Page)
- Простые страницы-инструменты (калькулятор, конвертер и т. д.)
- Проверка прототипов, быстрое Demo

  }

### 2.4 Лучшие практики

✅ **Что следует делать**:
- Использовать семантические HTML-теги
- Управлять цветами и отступами через CSS-переменные
- Сжимать изображения и применять ленивую загрузку
- Добавлять базовые SEO meta-теги

❌ **Чего следует избегать**:
- Встроенные стили (`style="..."`)
- Засорение глобальными переменными
- Дублирование кода (копипаст)

### 3.4 Подробный разбор ключевых концепций

#### Принципы проектирования компонентов

**Единственная ответственность**: один компонент делает только одну вещь

```vue
<!-- ❌ 不好的例子：组件做了太多事 -->
<template>
  <div>
    <form @submit="handleSubmit">
      <!-- 表单内容 -->
    </form>
    <table>
      <!-- 数据表格 -->
    </table>
    <div class="charts">
      <!-- 统计图表 -->
    </div>
  </div>
</template>

<!-- ✅ 好的例子：拆分成独立组件 -->
<template>
  <div>
    <UserForm @submit="fetchData" />
    <UserTable :data="users" />
    <UserStats :data="users" />
  </div>
</template>
```

#### Стратегия управления состоянием

| Тип состояния | Место хранения | Пример |
|----------|----------|------|
| **Глобальное состояние** | Pinia/Redux | Информация о пользователе, статус входа, настройки темы |
| **Состояние страницы** | Компонент страницы | Условия поиска по списку, информация о пагинации |
| **Состояние компонента** | Внутри компонента | Ввод в форме, показ/скрытие модального окна |
| **Состояние со стороны сервера** | TanStack Query/SWR | Данные сервера, кеш |

#### Выбор способа организации каталогов

**Способ первый: организация по типам (подходит для небольших проектов)**

```
src/
├── components/     # 所有组件
├── views/          # 所有页面
├── stores/         # 所有状态
└── services/       # 所有服务
```

**Способ второй: организация по функциям (подходит для средних и крупных проектов)**

```
src/
├── features/
│   ├── auth/       # 认证功能的所有代码
│   ├── user/       # 用户功能的所有代码
│   └── product/    # 商品功能的所有代码
├── shared/         # 共享资源
└── App.vue
```

::: tip 💡 Как выбрать?
- Страниц в проекте < 10 → организация по типам
- Страниц в проекте > 20 → организация по функциям
- Команда > 5 человек → организация по функциям, удобно для параллельной разработки
:::

## 4. Корпоративный уровень: архитектура крупного приложения

### 4.1 Сценарии применения

- Крупные интернет-платформы (электронная коммерция, социальные сети, контент-платформы)
- Сложные корпоративные приложения
- Проекты, требующие совместной работы нескольких команд
- Проекты с крайне высокими требованиями к производительности и поддерживаемости

### 4.2 Архитектура микрофронтендов

Когда проект достигает определённого масштаба и единую кодовую базу становится трудно поддерживать, можно рассмотреть архитектуру **микрофронтендов**.

```
大型电商平台/
├── 基座应用（主框架）
│   ├── 顶部导航
│   ├── 侧边菜单
│   ├── 用户中心入口
│   └── 子应用容器
├── 商品子应用（独立部署）
│   ├── 商品列表
│   ├── 商品详情
│   └── 商品管理
├── 订单子应用（独立部署）
│   ├── 购物车
│   ├── 订单列表
│   └── 支付流程
├── 用户子应用（独立部署）
│   ├── 个人中心
│   ├── 收货地址
│   └── 优惠券
└── 营销子应用（独立部署）
    ├── 活动页面
    ├── 优惠券发放
    └── 积分商城
```

**Преимущества микрофронтендов**:
- Автономность команд: каждое подприложение разрабатывается и развёртывается независимо
- Независимость от технологического стека: разные команды могут использовать разные фреймворки
- Постепенное обновление: можно поэтапно рефакторить старую систему

### 4.3 Структура каталогов корпоративного уровня

```
enterprise-project/
├── apps/                       # 微前端子应用
│   ├── main/                   # 基座应用
│   ├── product/
│   ├── order/
│   └── user/
├── packages/                   # 共享包（Monorepo）
│   ├── ui-components/          # 通用组件库
│   ├── utils/                  # 工具函数
│   ├── constants/              # 常量定义
│   └── types/                  # TypeScript 类型
├── shared/                     # 共享配置
│   ├── eslint-config/
│   ├── ts-config/
│   └── vite-config/
├── docs/                       # 项目文档
├── scripts/                    # 构建脚本
└── package.json
```

### 4.4 Архитектура оптимизации производительности

Крупные приложения должны уделять внимание оптимизации производительности:

```
性能优化策略/
├── 构建时优化
│   ├── 代码分割（Code Splitting）
│   ├── 路由懒加载
│   ├── Tree Shaking
│   └── 资源压缩
├── 运行时优化
│   ├── 虚拟滚动（长列表）
│   ├── 图片懒加载
│   ├── 组件按需渲染
│   └── 缓存策略
└── 网络优化
    ├── CDN 加速
    ├── HTTP 缓存
    ├── 资源预加载
    └── Service Worker
```

### 4.5 Архитектура SSR/SSG

Для сценариев, требующих SEO или производительности при первой загрузке:

| Решение | Сценарии применения | Представительные фреймворки |
|------|----------|----------|
| **SSR** | Нужен SEO, быстрая отрисовка первого экрана | Next.js, Nuxt.js |
| **SSG** | Контент статичный, обновляется нечасто | Astro, VitePress |
| **Гибридный** | Часть статична, часть динамична | Next.js (ISR) |

## 5. Выбор архитектуры в зависимости от масштаба аудитории

### 5.1 Личный проект / небольшая команда (DAU < 1000)

**Особенности**: быстрая итерация, ограниченные ресурсы, быстро меняющиеся требования

**Рекомендуемая архитектура**:
- Технологический стек: Vue 3 + Vite или React + Vite
- Управление состоянием: Pinia или Zustand (легковесные)
- UI-библиотека: Element Plus / Ant Design
- Развёртывание: Vercel / Netlify / облачный сервер

**Структура каталогов**: достаточно простой организации по типам

### 5.2 Средний бизнес (DAU 1k–100k)

**Особенности**: сложная бизнес-логика, командная работа, требуется стабильность

**Рекомендуемая архитектура**:
- Технологический стек: Vue 3 + TypeScript или React + TypeScript
- Управление состоянием: Pinia + композиционные функции или Redux Toolkit
- UI-библиотека: собственная библиотека компонентов + библиотека бизнес-компонентов
- Тестирование: модульные тесты + E2E-тесты
- Развёртывание: конвейер CI/CD + Docker

**Структура каталогов**: организация по функциям, установление стандартов

### 5.3 Крупная платформа (DAU > 100k)

**Особенности**: высокая нагрузка, совместная работа нескольких команд, долгосрочная поддержка

**Рекомендуемая архитектура**:
- Технологический стек: React/Vue + TypeScript (строгий режим)
- Архитектура: микрофронтенды + Monorepo
- Управление состоянием: тонкозернистое управление состоянием + кеширование серверного состояния
- Производительность: SSR/SSG + CDN + граничные вычисления
- Мониторинг: фронтенд-мониторинг + отслеживание ошибок + анализ производительности

**Структура каталогов**: Monorepo + микрофронтенды

## 6. Дорожная карта эволюции архитектуры

### 6.1 Пример эволюции: от блога к платформе

```
阶段 1：个人博客（HTML/CSS/JS）
    ↓ 需求：需要后台管理
阶段 2：增加管理后台（Vue/React + 简单结构）
    ↓ 需求：用户系统、评论功能
阶段 3：功能模块化（按功能组织）
    ↓ 需求：多团队协作、独立部署
阶段 4：微前端架构（Monorepo）
```

### 6.2 Когда стоит обновлять архитектуру?

| Сигнал | Описание | Рекомендация |
|------|------|------|
| Время сборки > 5 минут | Проект слишком большой | Разделение кода, микрофронтенды |
| Частые конфликты между людьми | Сложно работать вместе | Организация по функциям, разбиение на модули |
| Изменение в одном месте ломает многое | Сильная связанность | Рефакторинг, усиление тестирования |
| Загрузка первого экрана > 3 секунд | Проблема с производительностью | Ленивая загрузка, SSR, оптимизация |
| Новые члены команды медленно осваиваются | Хаотичная структура | Документация, стандарты, рефакторинг |

## 7. Итоги

::: tip 💡 Ключевая идея
**Серебряной пули в архитектуре нет — лучшая та, что подходит.**

- **В небольших проектах** не усложняйте — HTML/CSS/JS достаточно
- **В средних проектах** устанавливайте стандарты, компонентизацию, модульность
- **В крупных проектах** думайте о микрофронтендах, оптимизации производительности, командной работе

**Запомните эти пункты**:
1. **Постепенная эволюция**: начинайте с простого, растите вместе с потребностями
2. **Единые соглашения**: именование, структура, стиль кода должны быть согласованными
3. **Документация прежде всего**: архитектурные решения нужно фиксировать, чтобы их можно было передать
4. **Регулярный рефакторинг**: технический долг нужно вовремя погашать

**Конечная цель**: сделать код похожим на хорошо организованное пространство, которое — независимо от размера — работает эффективно.
