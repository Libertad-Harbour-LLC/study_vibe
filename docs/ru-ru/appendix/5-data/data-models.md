# Обзор моделей данных (документ / граф / временные ряды / вектор)

::: tip 🎯 Ключевой вопрос
**Почему нельзя засунуть все данные в таблицы MySQL?** Когда ваши данные — это сеть социальных связей, поток с датчиков по миллиону записей в секунду или семантические векторы, которые должен понимать AI, реляционные таблицы оказываются бессильны. Разные формы данных требуют разных способов моделирования.
:::

---

## 1. За пределами реляционной модели: зачем нужны другие модели данных?

Реляционные базы данных (MySQL, PostgreSQL) организуют данные через «таблицы + строки + столбцы» и подходят для бизнес-данных с фиксированной структурой и чёткими связями. Но данные реального мира далеко не сводятся к одной этой форме:

| Форма данных | Боль реляционной модели | Более подходящая модель |
|----------|-------------|-------------|
| Профиль пользователя (поля не фиксированы, вложенная структура) | Частые ALTER TABLE, множество NULL-столбцов | **Документная модель** |
| Социальная сеть (друзья друзей друзей) | Производительность многоуровневого JOIN падает экспоненциально | **Графовая модель** |
| Метрики мониторинга (миллионы записей в секунду) | Узкое место записи, разрастание исторических данных | **Модель временных рядов** |
| Семантический поиск AI («близкое по смыслу» содержимое) | Невозможно выразить семантическое сходство | **Векторная модель** |

::: info 💡 Ключевая мысль
Речь не о «замене» реляционной модели, а о её «дополнении». Ядро большинства систем по-прежнему работает на MySQL/PostgreSQL, но внедрение специализированной модели данных в конкретном сценарии даёт прирост производительности на порядки.
:::

## 2. Документная модель (Document)

### 2.1 Что такое документная модель?

Документная модель хранит данные в виде **документов JSON/BSON**. Каждая запись — самодостаточный документ, который может иметь свою структуру полей.

```json
{
  "_id": "user_1001",
  "name": "Иван",
  "tags": ["VIP", "активный"],
  "address": { "city": "Москва", "district": "Центральный" },
  "orders": [
    { "id": "o1", "amount": 299 },
    { "id": "o2", "amount": 599 }
  ]
}
```

**Ключевые особенности:**
- **Без ограничений Schema**: не нужно заранее определять структуру таблицы, поля можно добавлять и убирать в любой момент
- **Вложенная структура**: адрес и заказы вложены прямо в документ, все данные читаются за одно чтение
- **Горизонтальное масштабирование**: естественно подходит для шардирования (Sharding), легко справляется с огромными объёмами данных

### 2.2 Документная модель vs реляционная

| Измерение сравнения | Реляционная (MySQL) | Документная (MongoDB) |
|----------|----------------|------------------|
| Структура данных | Фиксированная Schema, изменение через ALTER TABLE | Гибкая Schema, поля добавляются в любой момент |
| Вложенные данные | Нужен JOIN нескольких таблиц | Вложены прямо в документ |
| Связи между записями | JOIN очень силён | Связанные запросы слабее |
| Подходящий сценарий | Бизнес-данные со стабильной структурой | Контентные данные с меняющейся структурой |

### 2.3 Типичные сценарии

- **Управление контентом CMS**: статьи, комментарии, теги — структуры разные
- **Профили пользователей**: у разных пользователей разные наборы полей
- **Каталог товаров**: у телефона есть «диагональ экрана», у продуктов — «срок годности», поля совершенно разные
- **Центр конфигураций**: структуры конфигураций разных сервисов не унифицированы

::: warning ⚠️ Распространённое заблуждение
«MongoDB не требует проектирования структуры данных» — неверно! Документная модель тоже требует тщательного проектирования: уровень вложенности не должен быть слишком глубоким, а часто обновляемые вложенные документы стоит выделять в отдельные коллекции.
:::

## 3. Графовая модель (Graph)

### 3.1 Что такое графовая модель?

Графовая модель выражает сущности и их связи через **узлы (Node)** и **рёбра (Edge)**. Каждый узел — это сущность, каждое ребро — связь, и узлы, и рёбра могут нести атрибуты.

```
(Иван) --[подписан]--> (Пётр) --[подписан]--> (Сергей)
   |                                            |
   +--------[купил]----> (iPhone) <--[купил]----+
```

### 3.2 Убойная способность графовой модели: многоступенчатые запросы

**Сценарий**: найти в социальной сети «друзей друзей друзей»

Подход реляционной модели (JOIN в 3 уровня):
```sql
SELECT DISTINCT f3.name
FROM friends f1
JOIN friends f2 ON f1.friend_id = f2.user_id
JOIN friends f3 ON f2.friend_id = f3.user_id
WHERE f1.user_id = 1001;
```

Подход графовой БД (язык запросов Cypher):
```cypher
MATCH (me)-[:FOLLOWS*1..3]->(target)
WHERE me.name = 'Иван'
RETURN DISTINCT target.name
```

В реляционной модели каждый дополнительный «прыжок» — это ещё один JOIN, и производительность падает экспоненциально. Графовая БД обходит связи напрямую по указателям, и производительность многоступенчатых запросов почти не меняется.

### 3.3 Типичные сценарии

- **Социальные сети**: рекомендация друзей, общие подписки, распространение влияния
- **Граф знаний**: вывод связей между сущностями («кто чей учитель чьего ученика»)
- **Обнаружение мошенничества**: выявление денежных циклов, сетей связанных аккаунтов
- **Рекомендательные системы**: рекомендации на основе графа связей «пользователь — товар — тег»

## 4. Модель временных рядов (Time-Series)

### 4.1 Что такое модель временных рядов?

Модель временных рядов строится вокруг **временной метки** как главной оси и специально оптимизирована под сценарии «запись в хронологическом порядке, запрос по временному диапазону».

```
timestamp            device      cpu_usage   memory
2024-01-15 10:00:01  server-01   45%         12.3GB
2024-01-15 10:00:02  server-01   67%         12.5GB
2024-01-15 10:00:03  server-01   92%         14.1GB
```

### 4.2 Почему не хранить временные ряды в MySQL?

| Проблема | MySQL | БД временных рядов (InfluxDB) |
|------|-------|----------------------|
| Скорость записи | Десятки тысяч/сек | **Миллионы/сек** |
| Исторические данные | Ручная очистка, таблица всё растёт | **Автоматическая политика устаревания** (TTL) |
| Агрегирующие запросы | GROUP BY медленный | **Встроенное прореживание** (5 сек → среднее за 1 минуту) |
| Эффективность хранения | Универсальное хранилище, расход места | **Колоночное сжатие**, экономия 90% места |

### 4.3 Типичные сценарии

- **Мониторинг серверов**: сбор CPU, памяти, диска каждую секунду
- **Датчики IoT**: температура, влажность, GPS-трек
- **Финансовые котировки**: данные о ценах акций и объёмах торгов с секундной детализацией
- **Анализ логов**: агрегация логов приложений по временной шкале

## 5. Векторная модель (Vector)

### 5.1 Что такое векторная модель?

Векторная модель преобразует неструктурированные данные — текст, изображения, аудио — в многомерные числовые векторы с помощью **модели эмбеддингов (Embedding)**, а затем измеряет семантическое сходство, вычисляя расстояние между векторами.

```
"вкусная японская кухня" → Embedding → [0.82, 0.15, 0.91, 0.33, ...]
                                    ↓ косинусное сходство
"мастер суши с Гиндзы"   → [0.80, 0.18, 0.89, ...] → 96% сходства
"итальянская пицца"      → [0.12, 0.85, 0.20, ...] → 31% сходства
```

### 5.2 Векторный поиск vs поиск по ключевым словам

| Сравнение | Поиск по ключевым словам (LIKE / полнотекстовый индекс) | Векторный поиск |
|------|---------------------------|---------|
| Способ поиска | Точное совпадение строки | Совпадение по семантическому сходству |
| «вкусная японская кухня» | Совпадает только с текстом, содержащим «японская кухня» | Найдёт «суши», «сашими», «идзакая» |
| Многоязычность | Нужно обрабатывать каждый язык отдельно | Межъязыковое понимание смысла |
| Мультимодальность | Только текст | Единый поиск по тексту, изображениям, аудио |

### 5.3 Типичные сценарии

- **RAG (генерация с дополнением через поиск)**: предоставление LLM релевантных фрагментов знаний
- **Семантический поиск**: понимание намерения пользователя, а не ключевых слов
- **Поиск по изображению**: загрузите картинку — найдутся визуально похожие изображения
- **Рекомендательные системы**: рекомендации по семантическому сходству содержимого

::: tip 💡 Выбор векторной базы данных
- **Отдельная векторная БД**: Pinecone, Milvus, Weaviate — заточены под векторный поиск, лучшая производительность
- **Расширение традиционной БД**: pgvector (PostgreSQL), Atlas Vector Search (MongoDB) — снижают сложность архитектуры
- **Векторная библиотека в памяти**: FAISS, Annoy — подходят для небольших объёмов и сценариев с низкой задержкой
:::

## 6. Выбор решения: как выбрать модель данных?

| Как выглядят ваши данные? | Рекомендуемая модель | Представители |
|-------------------|---------|---------|
| Структура фиксирована, связи чёткие (заказы, пользователи) | Реляционная | MySQL, PostgreSQL |
| Структура гибкая, много уровней вложенности (контент, конфигурации) | Документная | MongoDB, DynamoDB |
| Сложные связи между сущностями, нужен многоступенчатый обход | Граф | Neo4j, Amazon Neptune |
| Запись в хронологическом порядке, запрос по временному диапазону | Временные ряды | InfluxDB, TimescaleDB |
| Неструктурированные данные, нужен поиск по семантическому сходству | Вектор | Pinecone, Milvus, pgvector |

::: info 🎯 Практический совет
Современные системы обычно используют **смесь нескольких моделей**:
- **Ядро бизнеса** — на PostgreSQL (реляционная)
- **Логи поведения пользователей** — на InfluxDB (временные ряды)
- **База знаний AI** — на Milvus + pgvector (вектор)
- **Рекомендательный движок** — на Neo4j (граф)

Не гонитесь за «одной базой данных на все случаи жизни» — пусть каждый вид данных найдёт свой самый подходящий дом.
:::
