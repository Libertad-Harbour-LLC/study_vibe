# Управление данными и качество данных

::: tip Вступление
**Сталкивались ли вы с такой ситуацией: цифры в отчёте не сходятся с реальным бизнесом, информация об одном и том же пользователе в двух системах различается, а результаты анализа полностью недостоверны из-за «грязных» данных?** Управление данными (Data Governance) — это системный подход к решению таких проблем. В эпоху «решений на основе данных» качество данных напрямую определяет качество решений — мусор на входе, мусор на выходе (Garbage In, Garbage Out).
:::

**Чему вас научит эта статья?**

После изучения этой главы вы получите:

- **Измерения качества данных**: понимание шести ключевых измерений качества — полноты, точности, согласованности и др.
- **Систему управления данными**: представление о фреймворке управления — от организации и процессов до технологий
- **Происхождение данных (Data Lineage)**: умение прослеживать данные от источника до потребления по всей цепочке
- **Управление метаданными**: понимание важности «данных, описывающих данные»
- **Слоистая архитектура хранилища данных**: модель слоёв ODS → DWD → DWS → ADS
- **Практические навыки**: знание того, как внедрять управление данными в проектах

| Глава | Содержание | Ключевые концепции |
|-----|------|---------|
| **Глава 1** | Измерения качества данных | Полнота, точность, согласованность, своевременность |

## 0. Общая картина: зачем нужно управление данными?

Управление данными — это не техническая, а **управленческая** проблема. Оно отвечает на ключевые вопросы: **кто отвечает за данные? Каков стандарт данных? Как обеспечить, чтобы данным можно было доверять постоянно?**

Представьте компанию со 100 таблицами данных, каждую из которых ведёт своя команда: нет единых правил именования, нет словаря данных, нет проверок качества. В результате один и тот же показатель «месячная активная аудитория» отдел маркетинга считает как 5 миллионов, а продуктовый отдел — как 3 миллиона, потому что определения разные.

::: tip Четыре опоры управления данными
1. **Организация**: чётко определить роли и обязанности владельца данных (Owner) и распорядителя данных (Data Steward)
2. **Процессы**: установить стандартные процессы подключения, изменения и вывода данных из эксплуатации
3. **Технологии**: развернуть инструменты мониторинга качества данных, управления метаданными, отслеживания происхождения и др.
4. **Культура**: добиться, чтобы вся компания признавала «данные — это актив», а не «данные — это побочный продукт»
:::

## 1. Шесть измерений качества данных

Качество данных — не размытое понятие, его можно измерять по шести конкретным измерениям. У каждого измерения есть чёткое определение и метод проверки.

<DataQualityDemo />

| Измерение | Определение | Метод проверки | Типичные проблемы |
|------|------|---------|---------|
| Полнота | Есть ли пропуски в данных | Проверка доли пустых значений | Пустые обязательные поля, отсутствие связанных данных |
| Точность | Корректны ли данные | Проверка по правилам, выборочная сверка | Отрицательная сумма, недопустимая дата |
| Согласованность | Согласованы ли данные из разных источников | Сравнение между системами | Разные имена пользователя в CRM и системе заказов |
| Своевременность | Обновляются ли данные вовремя | Проверка времени обновления | Запаздывание данных о складских остатках, несинхронизированные цены |
| Уникальность | Есть ли дублирующиеся записи | Проверка на дубликаты | Двойная регистрация одного пользователя |
| Валидность | Соответствуют ли формату | Проверка по регулярным выражениям / диапазонам | Ошибочный формат e-mail, отрицательный возраст |

::: tip Правило 1-10-100 для качества данных
- **1 рубль**: проверка на входе данных, профилактика попадания «грязных» данных
- **10 рублей**: очистка уже существующих «грязных» данных в хранилище данных
- **100 рублей**: убытки от ошибочных решений, вызванных «грязными» данными

Чем раньше обнаружить и исправить проблему качества данных, тем ниже издержки.
:::

## 2. Фреймворк управления данными: управление полным жизненным циклом

Управление данными — это не разовый проект, а непрерывный процесс, охватывающий весь жизненный цикл данных. От появления данных до их уничтожения каждый этап требует чётких правил и ответственных лиц.

<DataGovernanceFrameworkDemo />

| Этап | Ключевой результат | Ключевая роль |
|------|---------|---------|
| Определение стандартов | Словарь данных, правила именования, стандарты классификации и категоризации | Архитектор данных |
| Сбор и подключение | Правила подключения, правила проверки, запись происхождения | Инженер данных |
| Управление хранением | Слоистая модель, матрица прав доступа, политика жизненного цикла | DBA / инженер платформы |
| Использование и потребление | Каталог данных, правила обезличивания, отчёты о качестве | Аналитик данных / бизнес-заказчик |
| Архивирование и уничтожение | Политика архивирования, записи об удалении, журналы аудита | Команда безопасности и комплаенса |

## 2. Фреймворк управления данными

Управление данными нельзя решить покупкой одного инструмента — для его поддержки нужен целостный фреймворк. Самый используемый в отрасли эталонный фреймворк — DAMA-DMBOK (Свод знаний по управлению данными).

| Область управления | Ключевое содержание | Ключевой результат |
|---------|---------|---------|
| Архитектура данных | Определение моделей данных, потоков данных, стратегий хранения | Диаграмма архитектуры данных, ER-диаграмма |
| Стандарты данных | Единые правила именования, кодирования, определения показателей | Словарь данных, библиотека показателей |
| Качество данных | Создание правил качества, мониторинг и оповещения, процесс исправления | Отчёт о качестве, дашборд SLA |
| Безопасность данных | Категоризация и классификация, контроль доступа, обезличивание и шифрование | Политика безопасности, журналы аудита |
| Управление мастер-данными | Единая «золотая запись» ключевых сущностей: клиентов, товаров и т. д. | Центр мастер-данных |
| Жизненный цикл данных | Управление данными от создания до архивирования и уничтожения | Политика хранения, правила архивирования |

::: tip Модель зрелости управления данными
- **Уровень 1 — Начальный**: нет единых стандартов, каждая команда действует сама по себе
- **Уровень 2 — Повторяемый**: есть базовая документация по правилам, но исполнение непоследовательно
- **Уровень 3 — Определённый**: есть единые процессы и инструменты управления, которым следует большинство команд
- **Уровень 4 — Управляемый**: есть количественные показатели качества и автоматизированный мониторинг
- **Уровень 5 — Оптимизируемый**: непрерывное улучшение, управление данными встроено в повседневный процесс разработки
:::

## 3. Происхождение данных: откуда пришли и куда уходят

Происхождение данных (Data Lineage) фиксирует полный путь движения данных от источника до конечного потребления. Это похоже на «родословную» данных, позволяющую проследить историю любого фрагмента данных.

<DataLineageDemo />

В реальной работе происхождение данных имеет три ключевых сценария применения:

| Сценарий | Проблема | Как помогает происхождение |
|------|------|------------|
| Анализ влияния | Нужно изменить поле в таблице пользователей — какие нисходящие отчёты это затронет? | Прослеживание всех зависимостей вниз по цепочке происхождения |
| Поиск первопричины | Сегодня данные отчёта по GMV аномальны — на каком шаге проблема? | Возврат по цепочке происхождения вверх через каждое звено |
| Аудит соответствия | Через какие системы прошёл номер телефона пользователя? Везде ли его обезличили? | Прослеживание движения чувствительного поля по всей цепочке |

::: tip Два способа сбора происхождения
- **Активный сбор**: разбор SQL-запросов и конфигураций ETL, автоматическое извлечение связей происхождения на уровне таблиц/полей
- **Пассивный сбор**: перехват через хук планов выполнения движков запросов (например, Hive, Spark), фиксация происхождения в реальном времени

Основные инструменты, такие как Apache Atlas, DataHub, OpenLineage, поддерживают автоматизированный сбор происхождения.
:::

## 4. Управление метаданными: «данные, описывающие данные»

Метаданные (Metadata) — это данные о данных. Если данные — это содержание книги, то метаданные — это оглавление, автор, дата издания, номер ISBN. Без метаданных данные — это просто куча непонятных чисел и строк.

| Тип метаданных | Описание | Пример |
|-----------|------|------|
| Технические метаданные | Информация о физическом хранении данных | Имя таблицы, тип поля, способ партиционирования, место хранения |
| Бизнес-метаданные | Бизнес-смысл данных | Понятное название поля, бизнес-определение, методика расчёта |
| Операционные метаданные | Состояние выполнения данных | Время выполнения ETL, объём данных, частота обновления |

::: tip Важность словаря данных
Словарь данных — самый базовый результат управления метаданными. Хороший словарь данных должен содержать:
- **Имя поля**: техническое и понятное название
- **Тип данных**: VARCHAR(50), INT, DATETIME и др.
- **Бизнес-определение**: что означает это поле? Как оно рассчитывается?
- **Диапазон значений**: какие значения допустимы? Допускаются ли пустые значения?
- **Ответственный**: кто ведёт это поле? К кому обращаться при проблеме?

Команде без словаря данных новичку может потребоваться неделя, чтобы понять смысл одной таблицы; команде со словарём данных хватит 10 минут.
:::

## 5. Слоистая архитектура данных: ODS → DWD → DWS → ADS

Хранилище данных — это не свалка всех данных в одну кучу, а хранение, разбитое по **степени обработки**. У каждого слоя есть чёткая зона ответственности; верхние слои зависят от нижних, постепенно преобразуя исходные данные в данные, пригодные для бизнеса.

| Слой | Полное название | Зона ответственности | Особенности данных |
|------|------|------|---------|
| ODS | Слой операционных данных | Синхронизация бизнес-БД «как есть» | Самые сырые, необработанные |
| DWD | Слой детальных данных | Очистка, стандартизация, дедупликация | Чистые детальные записи |
| DWS | Слой агрегированных данных | Агрегация по темам (день/неделя/месяц) | Предрассчитанные агрегированные показатели |
| ADS | Слой прикладных данных | Под конкретные отчёты/интерфейсы | Готовые к использованию результаты |

::: tip Зачем разбивать на слои?
- **Переиспользование**: слой DWD очищается один раз, и все верхние слои его используют, избегая повторной очистки
- **Развязка**: изменение структуры таблиц бизнес-БД затрагивает только слой ODS и не доходит до отчётов
- **Производительность**: слой DWS предагрегирован, запросы отчётов читают напрямую, без вычислений в реальном времени
- **Прослеживаемость**: каждый слой сохраняется, при проблеме можно разбирать слой за слоем
:::

## 6. Инструменты и практики управления

| Инструмент | Назначение | Ключевые возможности | Сценарий применения |
|------|------|---------|---------|
| Great Expectations | Качество данных | Декларативные правила проверки данных, автогенерация отчётов о качестве | Python-конвейеры данных |
| dbt | Преобразование данных | Разработка SQL-моделей, встроенные тесты и генерация документации | Моделирование хранилища данных |
| DataHub | Управление метаданными | Каталог данных, отслеживание происхождения, обнаружение данных | Управление данными уровня предприятия |
| Apache Atlas | Управление метаданными | Отслеживание происхождения в экосистеме Hadoop | Платформы больших данных |
| OpenMetadata | Управление метаданными | Открытый каталог данных, поддержка различных источников | Небольшие и средние команды |
| Amundsen | Обнаружение данных | Платформа обнаружения данных через поиск | Демократизация данных |

::: tip Путь управления данными с нуля
Если в вашей команде ещё нет управления данными, рекомендуется двигаться в таком порядке:
1. **Сначала создайте словарь данных**: зафиксируйте смысл существующих таблиц и полей (хотя бы в Excel)
2. **Добавьте проверки качества**: внесите базовые проверки на пустые значения и диапазоны в ключевые конвейеры данных
3. **Унифицируйте определения показателей**: приведите к единому виду методику расчёта ключевых показателей — «DAU», «MAU», «GMV»
4. **Внедрите инструменты**: когда издержки ручного управления станут слишком высокими, внедрите DataHub, dbt и т. п.
5. **Установите процессы**: изменения данных требуют ревью, у проблем качества есть SLA и оповещения
:::

## Заключение

Управление данными — это системная инженерная работа, превращающая данные из «пригодных к использованию» в «удобные, достоверные и прослеживаемые». Это не разовый проект, а постоянно поддерживаемый процесс.

Вспомним ключевые моменты этой главы:

1. **Шесть измерений качества**: полнота, точность, согласованность, своевременность, уникальность, валидность
2. **Четыре опоры управления**: организация, процессы, технологии, культура — без любой из них не обойтись
3. **Происхождение данных**: прослеживание истории данных, поддержка анализа влияния и поиска проблем
4. **Управление метаданными**: словарь данных — самый базовый и важный результат управления
5. **Слоистая архитектура**: ODS → DWD → DWS → ADS, послойное извлечение ценности данных
6. **Постепенное внедрение**: начните со словаря данных, постепенно вводя инструменты и процессы
