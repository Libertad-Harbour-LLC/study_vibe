## 1. Зачем нужен «вывод сервиса в онлайн»?

Представьте, что вы приготовили дома целый стол вкусных блюд. Но проблема в том, что попробовать их могут только домашние, а соседи, охранник, незнакомцы — никто из них не отведает.

Что делать? Вам нужно **отнести блюда в ресторан**. Это и есть то, что делает «вывод сервиса в онлайн» — перенести написанный вами код с личного компьютера на «общедоступный компьютер», который работает круглосуточно 7 дней в неделю. Тогда любой, у кого есть интернет, сможет зайти на ваш сайт.

<DeploymentOverviewDemo />

Вывод сервиса в онлайн затрагивает множество звеньев. Как открытие ресторана — это не только вынести блюда, но и арендовать помещение, сделать ремонт, оформить лицензию, нанять официантов и т.п. С разработкой сайта так же. От кода до сайта, к которому может обратиться пользователь, лежит множество шагов. Нужно шаг за шагом выполнить сборку, развёртывание, настройку сети, обеспечение безопасности и прочее.

Ниже я разберу весь процесс по частям. Каждое звено разложу и разжую так, чтобы понял даже новичок без всякой базы.

## 2. Сборка: превращаем код в «переносимую посылку»

### 2.1 Зачем нужна сборка?

Новички часто спрашивают: код написан, почему нельзя просто положить его на сервер, чтобы пользователи к нему обращались?

Чтобы ответить на этот вопрос, сначала разберёмся, в каком формате написан ваш код. Вы могли использовать фреймворки вроде Vue, React, Express, Koa. У этих фреймворков есть общая черта: **они не предназначены для прямого использования браузером или сервером**.

Приведём пример. Когда вы пишете код на Vue, вы наверняка использовали теги вроде `<template>`, `<script setup>`? Этот синтаксис понимает только Vue. Браузер его вообще не понимает. Браузер знает лишь три языка: HTML (структура страницы), CSS (стили страницы), JavaScript (логика страницы). Синтаксис компонентов Vue для браузера — как тарабарщина, совершенно непонятная.

Поэтому перед тем как положить код на сервер, необходимо сделать одну важную вещь: **перевести его на язык, понятный браузеру**. Этот процесс перевода называется «сборкой» (Build).

### 2.2 Что конкретно делает сборка?

Сборка — это не только перевод. Она ещё выполняет множество оптимизаций. Чтобы сайт работал быстрее и экономил ресурсы. Подробно расскажу, какие именно работы она выполняет:

**Шаг первый: разбор зависимостей**

При написании кода используются различные сторонние библиотеки. Например, Vue, Vue Router, Axios, Vite и т.п. Эти библиотеки нельзя каждый раз заставлять пользователя скачивать с npm. Это слишком медленно. Инструмент сборки проанализирует код, найдёт все зависимости. Затем «упакует» их вместе.

**Шаг второй: компиляция и преобразование**

Это самый ключевой шаг. Компонент Vue компилируется в HTML и JavaScript. SASS/LESS компилируется в CSS. Новый синтаксис ES6+ преобразуется в более совместимый код ES5. После этого шага код превращается из «формата, понятного разработчику» в «формат, исполняемый машиной».

**Шаг третий: сжатие и обфускация**

Сжатие — это удаление всех пробелов, переносов строк, комментариев. Имена переменных меняются с английских слов на отдельные буквы. Например, `userName` становится `a`, `calculateTotalPrice` становится `b`. Так размер файла значительно уменьшается. Пользователю скачивать гораздо быстрее. Обфусцированный код человек практически не понимает. Это также немного «защищает код».

**Шаг четвёртый: разделение кода**

Возможно, вы написали 10 страниц. У каждой страницы свой код. Но пользователь может зайти лишь на одну из них. Зачем скачивать код остальных 9 страниц? Инструмент сборки разделит код на множество мелких блоков. Пользователь заходит на какую-то страницу — скачивается код этой страницы. Это и есть «загрузка по требованию». Она значительно повышает скорость первого визита.

**Шаг пятый: генерация хеша**

Это очень важный шаг. Но многие его упускают. После завершения сборки имена файлов становятся похожими на `app.abc123.js`, `vendor.def456.css`. Та строка из смеси букв и цифр в конце называется «хешем».

Назначение хеша таково: при любом изменении кода значение хеша меняется. Браузер тогда понимает, что «этот файл изменился, нужно скачать заново». Неизменившиеся файлы браузер продолжает брать из кэша. Не нужно скачивать повторно. Так и пользователь видит самый свежий код, и кэш используется в полной мере для повышения скорости.

### 2.3 Как выполнить сборку?

В большинстве современных фронтенд-проектов инструмент сборки уже настроен. Нужно лишь запомнить одну команду:

```bash
# 如果用 npm
npm run build

# 如果用 yarn
yarn build

# 如果用 pnpm
pnpm build
```

После выполнения зайдите в корневой каталог проекта и найдите папку с именем `dist` (иногда называется `build` или `.output`). Внутри — все собранные файлы. Эти файлы и есть то, что в итоге нужно загрузить на сервер. Больше не нужно вносить никаких изменений. Просто перетащите на сервер.

### 2.4 Что внутри артефактов сборки?

Откройте папку dist, и вы увидите внутри в основном три типа файлов:

- **HTML-файл**: обычно называется `index.html`. Это входной файл. Браузер загружает его первым.
- **JS-файлы**: весь код JavaScript. Может быть один, а может быть несколько.
- **CSS-файлы**: весь код стилей. Может быть встроен в HTML, а может быть отдельным CSS-файлом.

Если это более сложный бэкенд-проект (например, Node.js), артефактом сборки может быть исполняемый файл или Docker-образ. Но принцип тот же: превратить код в форму, которую сервер может напрямую запустить.

## 3. Сервер: найти «дом», который никогда не закрывается

### 3.1 Что вообще такое сервер?

Многие, впервые услышав слово «сервер», думают, что это какое-то крутое таинственное устройство. На самом деле всё не так сложно. **Сервер — это просто компьютер**. Компьютер, который никогда не выключается и постоянно подключён сетевым кабелем.

Кто-то может спросить: разве у меня дома нет компьютера? Зачем дополнительно тратить деньги на аренду сервера?

Хороший вопрос. Разберём его:

Во-первых, ваш домашний компьютер не может работать 24 часа в сутки. Вы уходите из дома, ложитесь спать, изредка он ещё и зависает и перезагружается. А с сервером всё иначе. Он специально для этого предназначен. Может работать 365 дней в году без выходных. К сайту можно обратиться в любой момент.

Во-вторых, ваша домашняя сеть тоже не подходит. Скорость отдачи у домашнего интернета обычно очень низкая. К тому же IP домашнего интернета динамически меняется. Сегодня один IP, завтра может быть уже другой. Использовать это как сервер для сайта вообще невозможно. Сервер использует высокоскоростную сеть дата-центра. IP фиксированный, скорость молниеносная.

В-третьих, у вашего домашнего компьютера нет «публичного IP». Что такое публичный IP? Это уникальный во всём мире адрес. Только при наличии такого адреса другие могут найти ваш компьютер в интернете. IP вашего домашнего компьютера обычно работает только в пределах вашей локальной сети. Люди снаружи вас вообще не найдут. С сервером иначе. У него есть фиксированный публичный IP. Люди со всего мира могут найти его по этому IP.

### 3.2 Как выбрать сервер?

При выборе сервера смотрят в основном на три показателя: **число ядер CPU**, **объём памяти**, **объём диска**. Чем выше эти три показателя, тем выше производительность сервера и тем дороже цена.

Для начинающего новичка совершенно ни к чему покупать особо дорогую конфигурацию. Запомните простой способ выбора:

- **Личный проект, учебная практика**: 1 ядро, 2 ГБ памяти — достаточно. В месяц примерно несколько десятков юаней.
- **Небольшой коммерческий проект**: 2 ядра, 4 ГБ памяти. Выдержит от нескольких тысяч до нескольких десятков тысяч посещений в день.
- **Средний проект**: 4 ядра, 8 ГБ или выше. Уже нужна профессиональная команда для эксплуатации.

Есть ещё один момент для рассмотрения: **регион**. Если пользователи в основном в Китае, покупайте отечественный сервер (Alibaba Cloud, Tencent Cloud), скорость доступа будет высокой. Если пользователи в основном за рубежом, покупайте зарубежный сервер (AWS, Google Cloud, DigitalOcean) или сервер в Гонконге. Скорость высокая и не нужна регистрация (ICP-备案).

### 3.3 Отечественный или зарубежный?

Это очень важный вопрос. Многие в начале его не продумывают. А потом сталкиваются с хлопотами.

Плюс **покупки отечественного сервера** — высокая скорость, низкая задержка. Минус — нужна регистрация (подача информации о сайте на проверку в соответствующие государственные органы). Обычно приходится ждать от недели до месяца. К тому же отечественные серверы относительно дороже.

Плюс **покупки зарубежного сервера** — не нужна регистрация. Купил — и сразу пользуешься. Цена тоже может быть дешевле. Минус — у пользователей материкового Китая скорость доступа может быть пониже. Если дата-центр в Гонконге или Сингапуре, будет намного лучше.

Совет таков: если это личный проект, сайт для учёбы и демонстрации, покупайте сервер в Гонконге или за рубежом. Избавит от хлопот с регистрацией. Если это полноценный коммерческий проект для долгосрочной работы, покупайте отечественный сервер. Честно пройдите регистрацию, в дальнейшем это избавит от многих хлопот.

### 3.4 Сравнение основных облачных провайдеров

| Провайдер | Для кого подходит | Особенности | Цена для новых пользователей |
|------|---------|------|-----------|
| Alibaba Cloud | Отечественный бизнес | Первая доля рынка, развитая экосистема | Несколько десятков до сотни с лишним за первый год |
| Tencent Cloud | Мини-программы, игры | Хорошая поддержка облачной разработки мини-программ | Большие скидки за первый год |
| Huawei Cloud | Корпоративные пользователи | Первый выбор для государственных проектов | Цена выше |
| DigitalOcean | Разработчики | Простой и удобный, прозрачная цена | От $4/месяц |
| Vercel | Фронтенд-проекты | Без настройки, push — и сразу онлайн | Бесплатного лимита достаточно |

Новичкам больше всего рекомендуются студенческие/новые тарифы со скидками **Alibaba Cloud** или **Tencent Cloud**. Обычно год стоит всего несколько десятков юаней. Соотношение цена/качество отличное. Если делаете чисто фронтенд-проект и хотите избежать хлопот, можно напрямую использовать **Vercel** или **Netlify**. Даже сервер покупать не нужно. Запушил код — и он автоматически развёртывается.

### 3.5 Что делать после получения сервера?

После покупки сервера вы получите письмо. В нём содержится несколько важных сведений:

- **IP-адрес**: строка цифр вроде `123.45.67.89`. Это «номер дома» сервера в интернете.
- **Имя пользователя для входа**: обычно `root` (аккаунт администратора).
- **Пароль для входа**: начальный пароль или ссылка для его установки.

С этими сведениями можно через **SSH (Secure Shell)** удалённо войти на сервер. И выполнять различные настройки. SSH — это как зашифрованная команда удалённого управления, отправляемая серверу. Позволяет со своего компьютера управлять сервером, находящимся за тридевять земель.

Команда входа такова:

```bash
ssh root@123.45.67.89
# 按回车后会让你输入密码。输入正确的密码后就登录成功了。
```

После успешного входа вы попадаете в командную строку сервера. Выглядит почти как открытое на собственном компьютере окно терминала. Здесь можно устанавливать ПО, создавать папки, менять конфигурацию. Все операции — как на локальном компьютере.

## 4. Развёртывание: переносим код в «дом»

### 4.1 Что такое развёртывание?

Развёртывание — это процесс, когда после аренды сервера (дома) вносишь код (вещи и мебель) внутрь. А затем открываешь дверь и начинаешь работу.

Конкретно развёртывание включает следующие шаги:

1. **Загрузить код на сервер**: передать артефакты сборки с локального компьютера на сервер.
2. **Установить зависимости**: на сервере может не быть различных пакетов, нужных проекту. Их нужно установить.
3. **Настроить переменные окружения**: например, пароль базы данных, API-ключи и прочую чувствительную информацию.
4. **Запустить сервис**: заставить приложение работать. Начать слушать запросы пользователей.

Эти четыре шага звучат довольно сложно. Но на деле сделать их не так трудно. Ниже подробно расскажу, как выполнить каждый шаг.

<DeploymentServerDemo />

### 4.2 Как загрузить код на сервер?

**Способ первый: загрузка по FTP/SFTP**

Это самый наглядный способ. Как при использовании облачного хранилища. Перетаскиваешь файлы на сервер. На свой компьютер можно скачать бесплатную программу под названием **FileZilla**. Введите IP сервера, имя пользователя, пароль. И сможете управлять файлами на сервере как локальными.

**Способ второй: получение через Git**

Это более рекомендуемый способ. Сначала создайте репозиторий кода на GitHub, GitLab или Gitee. Запушьте код в облако. Затем на сервере командой `git clone` стяните код.

Плюс в том, что: для последующего обновления кода достаточно на сервере выполнить команду `git pull`. Не нужно каждый раз загружать вручную. К тому же хранение кода в облаке безопасно. Даже если сервер переустановят, не страшно.

**Способ третий: автоматическое развёртывание CI/CD**

Это самый профессиональный способ. И настоятельно рекомендуемый. Настроив CI/CD (непрерывная интеграция/непрерывное развёртывание), нужно лишь запушить код на GitHub. Система CI/CD автоматически выполнит для вас весь процесс: получение кода → установка зависимостей → сборка → развёртывание. Даже входить на сервер не нужно. Всё выполняется автоматически.

### 4.3 Конкретные шаги развёртывания

Предположим, используем самый простой способ — ручное развёртывание через Git. Шаг за шагом продемонстрирую весь процесс:

**Шаг первый: подключение к серверу**

```bash
ssh root@123.45.67.89
```

**Шаг второй: установка необходимого ПО**

Если это проект на Node.js, сначала нужно установить Node.js:

```bash
# 以 Ubuntu 系统为例
curl -fsSL https://deb.nodesource.com/setup_18.x | sudo -E bash -
sudo apt install -y nodejs
```

**Шаг третий: получение кода**

```bash
# 创建放网站的目录
mkdir -p /var/www/my-website
cd /var/www/my-website

# 克隆代码仓库（需要先在GitHub上创建好仓库）
git clone https://github.com/你的用户名/你的仓库名.git .
```

**Шаг четвёртый: установка зависимостей и сборка**

```bash
# 安装项目依赖
npm install

# 构建项目（生成 dist 目录）
npm run build
```

**Шаг пятый: запуск сервиса через PM2**

Зачем использовать PM2? Это инструмент управления процессами. Позволяет сайту непрерывно работать в фоне. Даже после перезагрузки сервера он автоматически запустится.

```bash
# 全局安装 PM2
sudo npm install -g pm2

# 启动网站（假设入口文件是 index.js）
pm2 start index.js

# 设置开机自启
pm2 startup
pm2 save
```

**Шаг шестой: настройка обратного прокси Nginx**

Приложение на Node.js обычно работает на порту вроде 3000 или 8080. Но пользователи обращаются к порту 80 (порт HTTP по умолчанию). Нужно с помощью Nginx перенаправлять запросы с порта 80 на порт приложения.

```bash
# 安装 Nginx
sudo apt install -y nginx

# 创建 Nginx 配置文件
sudo nano /etc/nginx/sites-available/my-website
```

В открывшемся редакторе впишите следующую конфигурацию:

```nginx
server {
    listen 80;
    server_name example.com www.example.com;

    # 静态文件（构建产物）直接返回
    location / {
        root /var/www/my-website/dist;
        index index.html;
        try_files $uri $uri/ /index.html;
    }

    # API 请求转发到 Node.js 后端
    location /api/ {
        proxy_pass http://localhost:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

После сохранения и выхода активируйте эту конфигурацию:

```bash
# 启用配置
sudo ln -s /etc/nginx/sites-available/my-website /etc/nginx/sites-enabled/

# 测试配置是否有错误
sudo nginx -t

# 重启 Nginx
sudo systemctl restart nginx
```

Теперь, обратившись к `http://example.com` (не забудьте сначала направить доменное имя на этот IP сервера), вы должны увидеть сайт!

## 5. Доменное имя и DNS: дайте сайту хорошее имя

### 5.1 Зачем покупать доменное имя?

Есть IP сервера, зачем ещё покупать доменное имя?

Подумайте. Запомнить строку цифр `123.45.67.89` — разве не сложно? Разве не легко ошибиться при наборе? А запомнить имена вроде `baidu.com`, `taobao.com` — разве не гораздо проще?

Доменное имя — это имя сайта. Легко запоминается, профессионально. Ещё и отражает образ бренда. Представьте. Сказать кому-то «зайди на сделанный мной сайт, IP — 123.45.67.89» или «зайди на woshishuaige.com» — что звучит солиднее?

<DeploymentDnsDemo />

### 5.2 Что такое DNS?

Хорошо. Теперь вы купили доменное имя. Например, `my-awesome-website.com`. Но вот проблема: компьютер понимает только IP-адреса. Он не понимает человеческий язык вроде «my-awesome-website.com».

Тут на сцену и выходит DNS. Полное название DNS — «Domain Name System». В переводе — «система доменных имён». Можно понимать его как огромную «телефонную книгу». Специально отвечает за перевод легко запоминаемых человеком доменных имён в понятные компьютеру IP-адреса.

Когда вы вводите в браузере `my-awesome-website.com` и нажимаете Enter. За кулисами происходит следующее:

1. Браузер спрашивает DNS: «эй, какой IP-адрес у my-awesome-website.com?»
2. DNS заглянул в «телефонную книгу» и сообщает браузеру: «его IP — 123.45.67.89»
3. Браузер по этому IP-адресу находит сервер и отправляет запрос

Весь процесс обычно занимает лишь несколько десятков миллисекунд. Пользователь его совершенно не замечает.

### 5.3 Как настроить DNS?

Настроить DNS обычно можно в двух местах:

**Способ первый: настройка у регистратора доменного имени**

Где купили доменное имя, там и настраивайте DNS-записи. Самый распространённый тип записи — **запись A**:

- **Тип записи**: A
- **Хост-запись**: обычно вписывают `@` (означает само доменное имя, например my-awesome-website.com) или `www` (означает www.my-awesome-website.com)
- **Значение записи**: IP-адрес сервера, например `123.45.67.89`

**Способ второй: использование стороннего DNS-сервиса**

Многие профессионалы не используют DNS, встроенный у регистратора. А используют профессиональных DNS-провайдеров вроде Cloudflare, Alibaba Cloud DNSPod, Tencent Cloud DNS. Эти сервисы обычно стабильнее, скорость разрешения выше. Ещё и со встроенными дополнительными функциями вроде CDN, защиты от DDoS.

### 5.4 Сколько времени нужно для вступления DNS в силу?

Это вопрос, который волнует многих. Ответ: **по-разному. Обычно от нескольких минут до 24 часов**.

После изменения DNS все DNS-серверы по миру должны синхронизировать это изменение. Это как бросить камень в море. Волнам нужно время, чтобы дойти до дальних мест. Некоторые DNS-серверы обновляются быстро, вступают в силу за несколько минут. Некоторые медленнее, возможно, придётся подождать долго.

Проверить, вступил ли DNS в силу, можно следующей командой:

```bash
# Windows
ping 你的域名

# Mac/Linux
ping 你的域名
```

Если ping проходит и показывает IP сервера — значит, DNS уже вступил в силу.

## 6. HTTPS: повесьте на сайт «замок»

### 6.1 Различие между HTTP и HTTPS

Возможно, вы заметили. Адреса некоторых сайтов начинаются с `http://`. Некоторых — с `https://`. Эта «s» очень важна. Она означает «безопасный» (Secure).

**HTTP (HyperText Transfer Protocol)** — это протокол для передачи веб-страниц. Можно понимать его как грузовик, перевозящий данные. Но этот грузовик **прозрачный**. То, что внутри, видят все. Введённый на HTTP-сайте пароль, заполненная личная информация. В процессе передачи их может подсмотреть любой посредник.

**HTTPS (HTTP Secure)** — это добавление к этому грузовику **герметичного контейнера**. Ещё и с ключом. Ключ есть только у отправителя и получателя. Посредник, даже перехватив, не поймёт, что внутри. Это и есть шифрованная передача.

<DeploymentHttpsDemo />

### 6.2 Зачем нужен HTTPS?

Первая причина: **безопасность**. Без HTTPS пароль, вводимый пользователем на сайте, передаётся открытым текстом. Любой, у кого есть хоть немного технических знаний, может его перехватить. В наше время кто рискнёт пользоваться сайтом без HTTPS?

Вторая причина: **предупреждение браузера**. Сейчас Chrome, Edge и другие основные браузеры показывают для сайтов без HTTPS предупреждение «небезопасно». Пользователь видит иконку warning. И убегает не оглядываясь. Не говоря уже о регистрации или пополнении счёта.

Третья причина: **SEO**. Google, Baidu и другие поисковые системы приоритетно индексируют HTTPS-сайты. Эффект SEO будет лучше.

### 6.3 Как получить HTTPS-сертификат?

Раньше HTTPS-сертификаты были очень дорогими. В год приходилось тратить от сотен до тысяч юаней. Теперь всё хорошо. Появилась организация под названием **Let's Encrypt**. Предоставляет полностью бесплатные SSL/TLS-сертификаты. К тому же у сообщества много инструментов автоматизации для их установки и продления.

**Способ первый: использование Certbot (рекомендуется)**

Certbot — инструмент для автоматического запроса и настройки сертификатов Let's Encrypt. Очень просто:

```bash
# 安装 Certbot
sudo apt install -y certbot python3-certbot-nginx

# 一键申请证书并配置 Nginx
sudo certbot --nginx -d example.com -d www.example.com
```

В процессе выполнения зададут несколько вопросов. Например, email (для напоминания об истечении сертификата). После ответа сертификат автоматически настроится. Зайдя на сайт, вы обнаружите, что в адресной строке появился маленький замок 🔒.

Срок действия сертификата — 90 дней. Но Certbot настроит для вас периодическую задачу автоматического продления. Можно практически не беспокоиться об этом.

**Способ второй: использование Cloudflare**

Если вы используете DNS-сервис Cloudflare. То HTTPS-сертификат настраивать самостоятельно вообще не нужно. Cloudflare автоматически обеспечит поддержку HTTPS для доменного имени. Ещё и проблему 90-дневного продления решит за вас.

### 6.4 Что меняется после настройки HTTPS?

После настройки HTTPS обращение пользователя меняется с прежнего `http://example.com` на `https://example.com`. Это изменение приносит ряд гарантий безопасности:

1. **Шифрованная передача**: вся связь между пользователем и сервером зашифрована.
2. **Аутентификация**: сертификат может подтвердить, что «я действительно этот сайт». Защищает от фишинговых сайтов.
3. **Целостность данных**: можно обнаружить, были ли данные подменены.

## 7. CI/CD: пусть робот работает за вас

### 7.1 Что такое CI/CD?

CI/CD — это сокращение двух понятий: **C**ontinuous **I**ntegration (непрерывная интеграция) и **C**ontinuous **D**eployment (непрерывное развёртывание). Можно понимать это как систему роботов, которая автоматически работает за вас.

Когда CI/CD не было. Каждый раз при выпуске новой функции. Процесс был таким:

1. Открыть компьютер, войти в GitHub
2. Стянуть свежий код
3. Запустить тесты, посмотреть, нет ли багов
4. Вручную собрать проект
5. Войти на сервер
6. Стянуть свежий код
7. Установить зависимости
8. Собрать проект
9. Перезапустить сервис

Эти 9 шагов. Каждый раз при выпуске нужно делать вручную. Надоедает? К тому же легко пропустить какой-то шаг. Например, забыть запустить тесты, забыть перезапустить сервис и т.п.

После появления CI/CD. Процесс стал таким:

1. Запушить код на GitHub
2. Пить чай и ждать
3. (Робот автоматически выполняет 9 шагов выше)
4. Сайт автоматически обновился

<DeploymentCicdDemo />

В этом и прелесть CI/CD: **достаточно запушить код. Остальное выполняется автоматически**.

### 7.2 Рабочий процесс CI/CD

Типичный процесс CI/CD выглядит так:

**Шаг первый: коммит кода (Push)**

Завершили разработку новой функции. Запушили код на GitHub.

**Шаг второй: запуск CI (непрерывная интеграция)**

GitHub обнаруживает изменение кода. Уведомляет систему CI (GitHub Actions, GitLab CI и т.п.) о начале работы.

**Шаг третий: установка зависимостей и тестирование**

Система CI запускает виртуальный компьютер. На нём:
- Устанавливает различные зависимости, нужные проекту
- Запускает тестовый код, чтобы убедиться в отсутствии багов
- Собирает проект, формирует артефакты

Если тест проваливается. CI уведомит письмом. Это развёртывание остановится. Проблемный код не будет развёрнут в продакшен-среде.

**Шаг четвёртый: выполнение CD (непрерывное развёртывание)**

После прохождения всех тестов. Система CI:
- Через SSH подключается к серверу
- Стягивает свежий код
- Устанавливает зависимости
- Собирает проект
- Перезапускает сервис

Весь процесс может занять лишь несколько минут. Всё выполняется автоматически.

### 7.3 Как настроить GitHub Actions?

GitHub Actions — встроенная функция CI/CD от GitHub. Не требует дополнительной оплаты (бесплатного лимита достаточно для личных проектов). Настраивается тоже очень просто.

В корневом каталоге проекта создайте файл `.github/workflows/deploy.yml`. Впишите следующую конфигурацию:

```yaml
name: Deploy to Production

# 触发条件：每当 main 分支有代码推送时
on:
  push:
    branches: [main]

# 任务列表
jobs:
  # 部署任务
  deploy:
    # 在什么系统上运行
    runs-on: ubuntu-latest
    
    # 具体步骤
    steps:
      # 1. 检出代码
      - name: Checkout code
        uses: actions/checkout@v3

      # 2. 安装 Node.js 环境
      - name: Setup Node.js
        uses: actions/setup-node@v3
        with:
          node-version: '18'

      # 3. 安装依赖并构建
      - name: Install and Build
        run: |
          npm ci
          npm run build

      # 4. 部署到服务器
      - name: Deploy to Server
        uses: appleboy/ssh-action@master
        with:
          host: ${{ secrets.SERVER_HOST }}
          username: ${{ secrets.SERVER_USER }}
          key: ${{ secrets.SSH_PRIVATE_KEY }}
          script: |
            cd /var/www/my-website
            git pull origin main
            npm install
            npm run build
            pm2 restart all
```

Этот файл конфигурации говорит GitHub Actions:

- Запускаться, когда в ветке main появляется новый код
- Выполнять задачу на компьютере с Ubuntu
- Сначала установить Node.js 18
- Затем установить зависимости и собрать проект
- Наконец через SSH подключиться к серверу и выполнить серию команд развёртывания

После настройки. Каждый раз при `git push origin main`. GitHub автоматически начнёт развёртывание. Очень удобно.

## 8. Мониторинг и логи: будьте «ночным сторожем» сайта

### 8.1 Зачем нужен мониторинг?

После вывода сайта в онлайн. Теоретически он должен работать круглосуточно 7 дней в неделю без перерыва. Но реальный мир не так прекрасен. Сервер может упасть. Сеть может дрожать. В коде могут быть баги. В реальной продакшен-среде. Могут произойти всевозможные неожиданности.

Если нет мониторинга. То остаётся лишь ждать, пока пользователь позвонит и скажет «сайт не открывается». К этому моменту обычно уже поздно. Пользователи, возможно, уже ушли.

С мониторингом можно:

- **Заранее обнаружить проблему**: загрузка CPU достигла 90%. Заранее добавить сервер.
- **Быстро локализовать проблему**: сайт замедлился. Посмотреть в мониторинге, где узкое место.
- **Быть спокойным**: сколько человек заходит в день, в какое время посещаемость максимальная.

<DeploymentMonitorDemo />

### 8.2 Какие метрики мониторить?

Самые важные метрики мониторинга — вот эти несколько:

| Метрика | Норма | Что делать при превышении |
|------|---------|-----------|
| Загрузка CPU | < 70% | Обновить конфигурацию сервера или оптимизировать код |
| Использование памяти | < 80% | Проверить, нет ли утечки памяти |
| Использование диска | < 80% | Очистить логи или ненужные файлы |
| Доступность сайта | 100% | Проверить, нормально ли работает сервис |
| Время отклика | < 2 секунд | Оптимизировать запросы к БД или добавить кэш |
| Частота ошибок | < 1% | Посмотреть лог ошибок для локализации проблемы |

### 8.3 Как настроить мониторинг?

**Самое простое решение: Uptime Robot**

Зарегистрируйтесь на uptimerobot.com. Добавьте URL сайта. Он каждые 5 минут автоматически проверяет, работает ли сайт нормально. Если сайт упал, отправит уведомление по email. Бесплатная версия позволяет мониторить 50 сайтов. Для личного проекта более чем достаточно.

**Продвинутое решение: мониторинг Alibaba Cloud/Tencent Cloud**

Если сервер куплен в Alibaba Cloud или Tencent Cloud. У них есть встроенная функция мониторинга. Достаточно настроить пороговые оповещения.

**Профессиональное решение: Prometheus + Grafana**

Эти два — «швейцарский нож» в области мониторинга. Функции очень мощные. Можно мониторить любую мыслимую метрику. Ещё и строить красивые визуализации в виде графиков. Правда, настройка довольно сложная. Подходит разработчикам с определённым опытом.

### 8.4 Логи: как разобраться, когда что-то пошло не так?

Мониторинг сообщает вам, что «сайт сломался». Но в чём конкретно проблема и почему она возникла. Нужно локализовать с помощью **логов**.

Лог — это «дневник» работы программы. Записывает все мелочи в процессе работы программы:

- Какой пользователь, в какое время, к какой странице обращался
- Сколько времени занял запрос к базе данных
- Были ли ошибки, какое сообщение об ошибке

**Самое базовое использование логов**

Просмотр логов приложения на сервере:

```bash
# 查看 PM2 的日志
pm2 logs

# 查看 Nginx 的访问日志
tail -f /var/log/nginx/access.log

# 查看 Nginx 的错误日志
tail -f /var/log/nginx/error.log
```

**Продвинутые решения для логов**

Если проект довольно сложный. Рекомендуется использовать профессиональные инструменты сбора логов:

- **Loki**: бесплатный open-source. Из одной семьи с Prometheus.
- **ELK (Elasticsearch + Logstash + Kibana)**: мощный функционал. Но сложная настройка.
- **Sentry**: инструмент, специально предназначенный для сбора ошибок приложения. Может автоматически собирать информацию об ошибках.

### 8.5 Оповещения: как узнать о проблеме в первую же секунду?

Мониторинг сообщает вам, что есть проблема. Но если вы не смотрите постоянно на панель мониторинга, что тогда? Тут и нужны **оповещения**.

Оповещение — это когда система мониторинга обнаруживает аномалию. И автоматически уведомляет вас по SMS, WeChat, DingTalk, email и т.п. Можно настроить разные уровни оповещений:

- **Критический (сайт полностью лёг)**: отправить SMS + позвонить. Узнать нужно немедленно.
- **Серьёзный (резкий рост частоты ошибок)**: отправить сообщение в DingTalk/WeChat. Увидел — обрабатывай.
- **Обычный (CPU повышен)**: отправить сводку на email. Достаточно смотреть раз в день.

Ключевой принцип настройки оповещений: **многоуровневые оповещения, не доводите себя до изнеможения**. Если по каждому пустяку вам шлют SMS. Очень скоро вы отключите оповещения.

## 9. Краткий справочник частых проблем

| Симптом проблемы | Возможная причина | Способ решения |
|---------|---------|---------|
| Сайт не открывается | Домен не разрешён / сервер упал / Nginx не запущен | `ping 域名` проверить связь; `pm2 list` посмотреть статус сервиса; `systemctl status nginx` посмотреть Nginx |
| Открывается пустая страница | Неверный путь к артефактам сборки / статические файлы настроены неправильно | Проверить, указывает ли путь root в Nginx на каталог dist |
| Страница 404 не найдена | Маршрут настроен неправильно / опечатка в пути | В конфигурацию Nginx добавить `try_files $uri $uri/ /index.html` |
| 502 Bad Gateway | Бэкенд-сервис упал / порт не открыт | `pm2 list` посмотреть, работает ли процесс; проверить правильность порта |
| 403 Forbidden | Неверные права / не открыт индекс каталога | Проверить права файлов `chmod -R 755`; в конфигурацию Nginx добавить `autoindex on` |
| HTTPS-сертификат истёк | Сертификат истёк, не продлён | `certbot renew` ручное продление; проверить периодическую задачу автопродления |
| После обновления не видно изменений | Кэш браузера / кэш CDN | Ctrl+Shift+R принудительное обновление; в консоли CDN «обновить кэш» |
| Сайт открывается очень медленно | Недостаточная полоса пропускания / не включён кэш / не настроен CDN | Увеличить полосу пропускания сервера; настроить кэш Redis; подключить CDN |
| Не подключается база данных | БД не запущена / неверный пароль / проблема с правами | Проверить статус сервиса БД; сверить данные подключения в конфигурации |

1. **Сборка** → командой `npm run build` превратить код в понятные браузеру HTML/CSS/JS
2. **Развёртывание** → загрузить артефакты сборки на сервер. Настроить обратный прокси через Nginx.
3. **Доменное имя** → купить домен и настроить разрешение DNS на IP сервера
4. **HTTPS** → через Let's Encrypt получить бесплатный сертификат. Защитить безопасность передачи данных.
5. **CI/CD** → настроить автоматизированное развёртывание. После push кода автоматический выход в онлайн.
6. **Мониторинг** → настроить мониторинг и оповещения. Узнавать о проблеме в первую же секунду.

### Рекомендации по пути обучения

- **День 1**: через Vercel/Netlify развернуть статическую страницу. Прочувствовать, как «код превращается в сайт».
- **Неделя 1**: арендовать облачный сервер. Вручную развернуть проект на Node.js. Настроить домен и HTTPS.
- **Недели 2-4**: настроить полноценный процесс CI/CD. Построить систему мониторинга и оповещений.
- **Постоянное обучение**: изучать контейнеризацию Docker, изучать кластеры Kubernetes, изучать микросервисную архитектуру.

## Краткий справочник терминов

| Термин | По-английски | Объяснение простыми словами |
|------|------|-----------|
| Сборка | Build | Перевести и упаковать исходный код в формат, исполняемый браузером |
| Развёртывание | Deploy | Положить код на сервер, чтобы пользователи могли к нему обращаться |
| Сервер | Server | Компьютер, работающий круглосуточно 7 дней в неделю и подключённый к сети |
| Доменное имя | Domain | Легко запоминаемое имя сайта (например, baidu.com) |
| DNS | Domain Name System | «Телефонная книга», переводящая доменное имя в IP-адрес |
| HTTP | HyperText Transfer Protocol | Протокол передачи веб-страниц (небезопасный, передача открытым текстом) |
| HTTPS | HTTP Secure | Протокол веб-страниц с шифрованной передачей (безопасный) |
| Nginx | Engine X | Высокопроизводительный веб-сервер. Делает обратный прокси. |
| Обратный прокси | Reverse Proxy | Официант, стоящий у входа. Перенаправляет запросы на бэкенд. |
| SSH | Secure Shell | Зашифрованный инструмент удалённого входа на сервер |
| CDN | Content Delivery Network | Глобально распределённая сеть серверов. Ускоряет доступ. |
| CI/CD | Continuous Integration/Deployment | Автоматизированный конвейер. После push кода автоматическое тестирование и развёртывание. |
| SSL/TLS | Secure Sockets Layer / Transport Layer Security | Протокол шифрования. Обеспечивает безопасность HTTPS. |
| PM2 | Process Manager 2 | Менеджер процессов Node.js. Обеспечивает непрерывную работу приложения. |
