# Шлюз и обратный прокси
::: tip 🎯 Ключевой вопрос
**В высоконагруженной интернет-архитектуре как доставить трафик к правильному сервису безопасно и эффективно?** Обратный прокси решает вопрос «как распределять трафик», API-шлюз — «как обрабатывать запросы». В этой статье через реальные примеры (стойка ресепшен, система охраны, умная маршрутизация) глубоко разбираются философия проектирования шлюзов и инженерная практика.
:::

---

## 1. Зачем нужен «шлюз»?

### 1.1 Начнём с реального примера: эволюция архитектуры одного e-commerce

Одна e-commerce платформа при быстром росте бизнеса столкнулась с серьёзными архитектурными проблемами:

**Восстановление сценария:**

```
Этап 1: прямое выставление сервисов наружу
Клиент → напрямую вызывает сервис пользователей, сервис заказов, сервис оплаты...
         ↓
Проблема 1: IP сервисов открыты, есть угроза безопасности
Проблема 2: невозможно единообразно делать аутентификацию, лимитирование
Проблема 3: добавление сервиса требует изменения конфигурации клиента
```

::: warning ⚠️ Фатальные проблемы прямого выставления наружу

- **Угроза безопасности**: IP всех сервисов открыты, легко стать мишенью атаки
- **Дублирование функций**: каждый сервис должен делать аутентификацию, лимитирование, логирование
- **Сложность расширения**: добавление сервиса требует изменения всех клиентов
- **Путаница протоколов**: одни используют HTTP, другие gRPC, клиенту приходится подстраиваться
  :::

**Архитектура после улучшения (внедрение шлюза):**

```
Клиент → API-шлюз (Nginx/Kong) → внутренние сервисы
         ↓
      единая аутентификация, лимитирование, маршрутизация
         ↓
      клиент знает только адрес шлюза
```

::: tip ✨ Эффект после улучшения

- **Безопасность**: реальные IP сервисов скрыты, наружу обращён только шлюз
- **Концентрация функций**: аутентификация, лимитирование, логирование обрабатываются единообразно на шлюзе
- **Лёгкость расширения**: добавление сервиса требует лишь настройки маршрута на шлюзе
- **Единый протокол**: наружу — HTTP, внутри можно использовать gRPC
  :::

### 1.2 Бытовая аналогия шлюза

**Стойка ресепшен**

Представьте, что вы пришли в крупную компанию:

- **Без ресепшена**: посетитель напрямую ищет нужный отдел, не знает, где он, в компании царит хаос
- **С ресепшеном**: посетитель сначала подходит к стойке, ресепшен выясняет цель визита и направляет в соответствующий отдел

**API-шлюз — это «ресепшен» системы**:

- **Обратный прокси**: ресепшен, направляющий посетителей в правильный отдел
- **API-шлюз**: умный ресепшен, который ещё и проверяет личность посетителя (аутентификация), ограничивает число посетителей (лимитирование)

## 2. Что такое обратный прокси?

### 2.1 Прямой прокси vs обратный прокси

::: tip 🤔 Пояснение терминов
**Прямой прокси (Forward Proxy)**:

- Разворачивается на стороне клиента
- Обращается к внешним ресурсам вместо клиента
- Типичное применение: VPN, инструменты обхода блокировок
- Пример: корпоративная сеть, вы выходите во внешний интернет через прокси

**Обратный прокси (Reverse Proxy)**:

- Разворачивается на стороне сервера
- Принимает запросы клиента и перенаправляет их внутренним сервисам
- Клиент знает только о существовании прокси, не зная реального сервера
- Пример: Nginx, HAProxy
  :::

**Таблица сравнения:**

| Параметр         | Прямой прокси                 | Обратный прокси                 |
| ------------ | ------------------------ | ------------------------ |
| **Место развёртывания** | Сторона клиента                 | Сторона сервера                 |
| **Обслуживаемый объект** | Клиент                   | Сервер                   |
| **Типичное применение** | VPN, обход блокировок                | Балансировка нагрузки, шлюз           |
| **Прозрачность**   | Сервер видит IP прокси         | Клиент видит IP прокси         |
| **Цель**     | Скрыть реального клиента, ускорить доступ | Скрыть реальный сервер, балансировка нагрузки |

### 2.2 Ключевая ценность обратного прокси

::: details Ценность первая: балансировка нагрузки
Распределение трафика на несколько бэкенд-серверов во избежание перегрузки единственной точки.

```
Клиент
  ↓
Nginx (обратный прокси)
  ↓
┌─────────┬─────────┬─────────┐
│ Сервер1 │ Сервер2 │ Сервер3 │
└─────────┴─────────┴─────────┘
```

:::

::: details Ценность вторая: защита безопасности
Скрытие реального IP сервера, предотвращение прямых атак. Единообразная защита безопасности на уровне прокси.

```
Клиент → видит только IP Nginx
Реальный сервер → только во внутренней сети, извне напрямую недоступен
```

:::

::: details Ценность третья: SSL-терминация
Обработка шифрования/дешифрования HTTPS на уровне прокси, бэкенд-сервисы используют HTTP, снижая вычислительную нагрузку на бэкенд.

```
HTTPS-клиент → Nginx (шифрование/дешифрование) → HTTP бэкенд-сервис
                   ↑
              точка SSL-терминации
```

:::

## 3. Nginx: почему он способен выдержать миллион одновременных подключений?

### 3.1 Процессная модель Master-Worker

Nginx использует **многопроцессную** архитектуру, а не многопоточную:

**Процесс Master (управляющий)**:

- Отвечает за чтение и проверку файла конфигурации
- Управляет процессами Worker (запуск, остановка, перезагрузка)
- Не обрабатывает конкретные запросы

**Процессы Worker (рабочие)**:

- Фактически обрабатывают HTTP-запросы
- Каждый Worker — независимый процесс, изолированный от других
- Количество обычно устанавливается равным числу ядер CPU, чтобы избежать накладных расходов на переключение контекста

::: tip 💡 Преимущества

- **Хорошая изоляция**: падение одного Worker не влияет на другие
- **Полное использование многоядерности**: каждый Worker работает независимо
- **Избегание сложности многопоточности**: не нужно обрабатывать блокировки, состязания и т.п.
  :::

### 3.2 Событийная модель + асинхронная неблокирующая обработка

Это ключевой секрет высокой производительности Nginx:

**Традиционный Apache (модель «процесс/поток»)**:

- Одно соединение = один процесс/поток
- Число одновременных подключений ограничено числом процессов/потоков в системе
- При большом числе соединений накладные расходы на переключение процессов огромны

**Nginx (событийная модель)**:

- Использует эффективные механизмы мультиплексирования ввода-вывода, такие как epoll (Linux) / kqueue (macOS)
- Один процесс Worker может одновременно обрабатывать десятки тысяч соединений
- Когда в соединении нет данных, оно не занимает CPU, а при поступлении новых данных пробуждается через уведомление о событии

::: tip Бытовая аналогия

- **Apache**: в ресторане к каждому посетителю приставлен официант (процесс), много посетителей — нужно много официантов
- **Nginx**: один суперофициант обслуживает всех посетителей одновременно, идёт к тому, кому нужно обслуживание, а не стоит постоянно рядом с одним посетителем
  :::

## 4. Что такое API-шлюз?

### 4.1 Зачем нужен API-шлюз?

**Представьте систему без шлюза:**

- Клиенту нужно знать адреса нескольких сервисов (сервис пользователей, сервис заказов, сервис оплаты...)
- Каждый сервис сам должен делать аутентификацию, лимитирование, логирование
- Протоколы не единообразны: одни используют HTTP, другие gRPC
- При обновлении сервиса клиент тоже должен меняться

::: warning ⚠️ Проблемы без шлюза

- **Сложность на клиенте**: нужно настраивать адреса нескольких сервисов
- **Дублирование функций**: каждый сервис должен реализовывать аутентификацию, лимитирование
- **Путаница протоколов**: клиенту приходится подстраиваться под разные протоколы
- **Сложность обновления**: при обновлении сервиса клиент тоже должен меняться
  :::

**После появления API-шлюза:**

- Клиенту достаточно знать адрес шлюза, шлюз отвечает за маршрутизацию к правильному сервису
- Сквозная логика, такая как аутентификация, лимитирование, логирование, обрабатывается единообразно на шлюзе
- Шлюз может выполнять преобразование протоколов, единообразно выставляя наружу HTTP
- При обновлении бэкенд-сервиса достаточно изменить конфигурацию шлюза, клиент этого не замечает

### 4.2 Ключевые функции API-шлюза

| Функция         | Описание                                       | Типичный сценарий                                         |
| :----------- | :----------------------------------------- | :----------------------------------------------- |
| **Маршрутизация и перенаправление** | Перенаправление запроса к разным сервисам по правилам URL, Header и т.п. | `/api/users` → сервис пользователей, `/api/orders` → сервис заказов |
| **Балансировка нагрузки** | При нескольких экземплярах одного сервиса — распределение трафика | У сервиса пользователей 3 экземпляра, запросы распределяются по кругу |
| **Аутентификация и авторизация** | Единообразная проверка JWT, OAuth Token | Неавторизованный пользователь не может обратиться к `/api/admin` |
| **Лимитирование и предохранитель** | Контроль верхнего предела трафика, предотвращение перегрузки сервиса | Максимум 1000 запросов в секунду, при превышении — возврат 429 |
| **Преобразование протоколов** | Наружу HTTP, внутри можно преобразовать в gRPC | Клиент использует HTTP, шлюз преобразует в gRPC для вызова внутреннего сервиса |
| **Постепенный выкат** | По Header или пропорции направление части трафика на новую версию | 5% пользователей пробуют новую версию, 95% используют старую |
| **Логирование и мониторинг** | Единообразная запись логов запросов, удобство анализа и поиска неполадок | Запись времени выполнения, кода статуса, размера ответа каждого запроса |

### 5.2 Маршрутизация и балансировка нагрузки

Одна из ключевых обязанностей шлюза — **доставить запрос в правильное место**. Это касается двух ключевых способностей: **маршрутизации** (на какой сервер) и **балансировки нагрузки** (как распределять трафик).

::: details Правила маршрутизации: от URL к сервису
Представьте e-commerce систему, где разные URL соответствуют разным сервисам:

- `/api/users/*` → сервис пользователей
- `/api/orders/*` → сервис заказов
- `/api/products/*` → сервис товаров
- `/api/pay/*` → сервис оплаты

**Пример конфигурации Nginx:**

```nginx
server {
    listen 80;
    server_name api.example.com;

    # 用户服务
    location /api/users/ {
        proxy_pass http://user-service;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # 订单服务
    location /api/orders/ {
        proxy_pass http://order-service;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # 商品服务
    location /api/products/ {
        proxy_pass http://product-service;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # 支付服务(需要更高安全级别)
    location /api/pay/ {
        # 限制IP访问
        allow 10.0.0.0/8;
        deny all;

        proxy_pass http://payment-service;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

:::

::: details Балансировка нагрузки: сравнение четырёх стратегий
Когда у одного сервиса несколько экземпляров, как выбрать?

| Стратегия         | Принцип                                              | Сценарий применения           | Преимущества                 | Недостатки                         |
| :----------- | :------------------------------------------------ | :----------------- | :------------------- | :--------------------------- |
| **Round-robin**     | По очереди распределяется на каждый сервер                        | Серверы близки по производительности     | Просто и справедливо             | Не учитывает текущую нагрузку сервера         |
| **Взвешенный round-robin** | Распределение пропорционально весу, с большим весом достаётся больше                   | Производительность серверов неравномерна     | Полное использование высокопроизводительных серверов | Требует разумной настройки весов             |
| **Least connections** | Распределяется на сервер с наименьшим текущим числом соединений                      | Сценарии долгих соединений, видеопотоки | Динамически адаптируется к изменению нагрузки     | Требует подсчёта числа соединений в реальном времени           |
| **IP-hash**   | По IP клиента вычисляется хеш, один IP всегда попадает на один сервер | Нужна привязка к сессии       | Гарантирует согласованность сессии       | При большом трафике одного IP создаётся нагрузка на единую точку |

**Пример конфигурации Nginx:**

```nginx
# 加权轮询
upstream backend_weighted {
    server 10.0.1.10:8080 weight=3;  # 性能好,承担更多流量
    server 10.0.1.11:8080 weight=2;
    server 10.0.1.12:8080 weight=1;  # 性能差,承担较少流量
}

# 最少连接
upstream backend_least_conn {
    least_conn;
    server 10.0.1.10:8080;
    server 10.0.1.11:8080;
    server 10.0.1.12:8080;
}

# IP哈希(会话保持)
upstream backend_ip_hash {
```

## 6. Безопасность шлюза: как охранять главные ворота системы?

### 6.1 Аутентификация и авторизация

**Традиционный способ (каждый сервис аутентифицирует сам):**

- Сервис пользователей, сервис заказов, сервис оплаты... каждый должен проверять JWT
- Дублирование кода, сложность сопровождения
- secret разбросаны по разным сервисам, высокий риск утечки

**Единая аутентификация на шлюзе:**

- Клиент обращается к шлюзу с Token
- Шлюз проверяет легитимность Token (подпись, срок действия)
- После успешной проверки добавляет информацию о пользователе (например, user_id) в заголовок запроса и перенаправляет бэкенд-сервису
- Бэкенд-сервису не нужно проверять, он напрямую получает информацию о пользователе из Header

::: tip 💡 Ключевая идея
**Аутентификация на шлюзе, авторизация в сервисе**:

- **Аутентификация**: кто ты? (проверка Token, получение личности пользователя)
- **Авторизация**: что ты можешь делать? (определение прав по роли пользователя)

Как ресепшен в компании: ресепшен аутентифицирует вашу личность (паспорт), но конкретные права определяет каждый отдел.
:::

### 6.2 HTTPS и SSL-терминация

**Зачем нужен HTTPS?**

1. **Безопасность**: предотвращение перехвата данных в процессе передачи
2. **Соответствие требованиям**: современные браузеры показывают предупреждение «небезопасно» для HTTP-сайтов
3. **SEO**: поисковые системы приоритетно индексируют HTTPS-сайты

**Схема SSL-терминации:**

- HTTPS и сертификаты настраиваются только на уровне шлюза
- Шлюз отвечает за TLS-рукопожатие и шифрование/дешифрование
- Между шлюзом и бэкенд-сервисами используется открытая передача по HTTP (внутренняя сеть доверенная)
- Бэкенд-сервис сосредоточен на бизнес-логике, не обрабатывая TLS

::: tip 💡 Преимущества SSL-терминации

- **Упрощение управления**: сертификаты настраиваются только на шлюзе, на бэкенде настраивать не нужно
- **Снижение накладных расходов**: бэкенд-сервису не нужно обрабатывать TLS-рукопожатие
- **Единое обновление**: обновление сертификата выполняется только на шлюзе
  :::

## 7. Лимитирование и предохранитель: как не дать «потоку трафика» снести систему?

### 7.1 Сравнение алгоритмов лимитирования

| Алгоритм         | Ключевая идея                  | Всплеск трафика                    | Сценарий применения                       | Сложность реализации |
| :----------- | :------------------------ | :-------------------------- | :----------------------------- | :--------- |
| **Token bucket**   | В корзине лежат токены, пройти можно только при наличии токена | Допускает определённую степень всплеска          | Лимитирование API, контроль полосы пропускания              | Средняя       |
| **Leaky bucket**     | Запросы поступают в корзину, вытекают равномерно для обработки     | Принудительное сглаживание, всплеск буферизуется или отклоняется | Сценарии, требующие строго равномерной обработки         | Средняя       |
| **Скользящее окно** | Подсчёт числа запросов в окне времени    | Строгий подсчёт по окну, превышение всегда отклоняется | Точный подсчёт (например, «не более 100 раз за 1 минуту») | Выше       |

### 7.2 Практика настройки лимитирования в Nginx

```nginx
# 定义限流区域(放在http块中)

# 1. 基于IP的限流(漏桶算法)
# zone=mylimit:10m - 区域名称和内存大小(10MB约可存储16万IP)
# rate=10r/s - 每秒允许10个请求
limit_req_zone $binary_remote_addr zone=mylimit:10m rate=10r/s;

# 2. 基于IP的连接数限制(防止单个IP建立过多连接)
limit_conn_zone $binary_remote_addr zone=addr:10m;

# 3. 基于服务端点的限流(不区分IP,保护后端整体)
limit_req_zone $server_name zone=server_limit:10m rate=100r/s;

server {
    listen 80;
    server_name api.example.com;

    # 用户服务 - 普通限流
    location /api/users/ {
        # 应用限流
        # burst=20 - 桶容量,允许突发20个请求
        # nodelay - 不延迟处理突发请求(立即处理或拒绝)
        limit_req zone=mylimit burst=20 nodelay;

        # 限制单个IP的连接数
        limit_conn addr 10;

        proxy_pass http://user-service;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # 订单服务 - 更严格的限流
    location /api/orders/ {
        # 更严格的限流:每秒5个请求
        limit_req_zone $binary_remote_addr zone=order_limit:10m rate=5r/s;
        limit_req zone=order_limit burst=10 nodelay;

        proxy_pass http://order-service;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # 限流后的处理
    # 当请求被限流时,返回429 Too Many Requests
    error_page 429 /429.html;
    location = /429.html {
        internal;
        return 429 '{"error": "Too Many Requests", "message": "Rate limit exceeded. Please try again later."}';
        add_header Content-Type application/json;
    }
}
```

::: tip 💡 Рекомендации по стратегии лимитирования

- **Обычный эндпоинт**: 10 запросов в секунду, допускается всплеск до 20
- **Важный эндпоинт** (оплата, заказы): 5 запросов в секунду, допускается всплеск до 10
- **Глобальная защита**: суммарно все запросы не превышают 100 в секунду
  :::

### 7.3 Предохранитель: предотвращение распространения сбоя

**Принцип работы предохранителя (circuit breaker):**

1. **Закрытое состояние**: нормальное перенаправление запросов с одновременным подсчётом частоты ошибок
2. **Открытое состояние**: когда частота ошибок превышает порог, предохранитель размыкается, сразу возвращает ошибку, перестав перенаправлять запросы
3. **Полуоткрытое состояние**: спустя некоторое время пропускается небольшое число пробных запросов; при успехе предохранитель закрывается

::: tip 💡 Ключевая идея
**Предохранитель похож на электрический плавкий предохранитель**: при слишком большом токе предохранитель автоматически перегорает, защищая всю цепь от выгорания.

Аналогично, когда бэкенд-сервис выдаёт массу ошибок, предохранитель «срабатывает», быстро отказывая, чтобы предотвратить распространение сбоя на всю систему.
:::

## 8. Заключение: ключевое мышление при проектировании шлюза

### 8.1 Обзор ключевых принципов

| Принцип         | Смысл                 | Ключевые моменты практики                       |
| ------------ | -------------------- | ------------------------------ |
| **Маршрутизация**     | Доставить запрос в правильное место | Маршрутизация по пути, домену, Header |
| **Балансировка нагрузки** | Распределить трафик на несколько серверов | Round-robin, взвешенный, least-conn, IP-hash   |
| **Безопасность**     | Охрана главных ворот системы         | Аутентификация/авторизация, HTTPS, WAF           |
| **Лимитирование**     | Не дать снести трафиком       | Token bucket, leaky bucket, скользящее окно         |
| **Предохранитель**     | Предотвращение распространения сбоя         | Быстрый отказ, план деградации             |
| **Наблюдаемость**   | Мониторинг и поиск неполадок           | Логи, метрики, трассировка |

### 8.2 Рекомендации по выбору технологии

::: tip 💡 Дерево решений по выбору

```
│  ├─ Да → Spring Cloud Gateway
│  └─ Нет → Nginx
```

## 9. Краткий справочник терминов

| Термин         | По-английски                     | Пояснение                                                                                                               |
| ------------ | ------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| **Обратный прокси** | Reverse Proxy            | Прокси-сервис, развёрнутый на стороне сервера, принимающий запросы клиента и перенаправляющий их внутренним сервисам. Клиент знает только о существовании обратного прокси, не зная адреса реального сервера.         |
| **Прямой прокси** | Forward Proxy            | Прокси-сервис, развёрнутый на стороне клиента, обращающийся к внешним ресурсам вместо клиента. Сервер видит IP прокси, не зная реального клиента. Типичное применение: VPN, инструменты обхода блокировок. |
| **API-шлюз**  | API Gateway              | Промежуточный слой между клиентом и бэкенд-сервисами, предоставляющий маршрутизацию, аутентификацию, лимитирование, логирование и т.п., — «единые ворота» микросервисной архитектуры.                       |
| **Балансировка нагрузки** | Load Balancing           | Распределение трафика запросов на несколько серверов во избежание перегрузки одного сервера, повышение доступности и производительности системы.                                               |
| **SSL-терминация**  | SSL Termination          | Обработка шифрования/дешифрования HTTPS на уровне шлюза, бэкенд-сервисы используют HTTP, что снижает вычислительную нагрузку на бэкенд и упрощает управление сертификатами.                                         |
| **Лимитирование**     | Rate Limiting            | Ограничение числа запросов в единицу времени для предотвращения перегрузки системы всплеском трафика. Распространённые алгоритмы: token bucket, leaky bucket, скользящее окно.                                 |
| **Предохранитель**     | Circuit Breaking         | При сбое зависимого сервиса автоматически прерывает вызовы, предотвращая распространение сбоя, и предоставляет план деградации.                                                    |
| **Привязка к сессии** | Session Persistence      | Гарантирует, что запросы одного клиента всегда маршрутизируются на один бэкенд-сервер; используется в сценариях, требующих сохранения состояния сессии.                                        |
| **Проверка здоровья** | Health Check             | Периодическая проверка состояния здоровья бэкенд-сервисов, автоматическое исключение неисправных узлов, гарантия отправки трафика только на здоровые экземпляры сервисов.                                       |
| **Постепенный выкат** | Canary Release           | Направление небольшого трафика на новую версию, после проверки стабильности — постепенное расширение доли, снижение рисков выкатки.                                                       |
| **WAF**      | Web Application Firewall | Файрвол веб-приложений, защищающий от SQL-инъекций, XSS, CC-атак и других угроз веб-безопасности.                                                              |
| **CDN**      | Content Delivery Network | Сеть доставки контента, разворачивающая граничные узлы по всему миру для ускорения доступа к статическим ресурсам.                                                                 |
