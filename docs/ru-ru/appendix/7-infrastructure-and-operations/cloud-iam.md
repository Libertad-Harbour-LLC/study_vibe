## 0. Введение: почему сразу после перехода в облако «наступаешь на мину»?

<IamRamComparisonDemo />

Многие, только начав пользоваться облачными сервисами, сталкиваются с похожими ситуациями:

- Ради удобства напрямую вписывают AccessKey в код и коммитят на GitHub;
- Всем сотрудникам выдают «права администратора», в результате кто-то по ошибке удаляет продакшен-базу данных;
- После передачи проекта неизвестно, у кого ещё на руках логин и пароль ушедшего сотрудника;
- Слышали, что надо включить MFA, но считают это «хлопотным» и всё откладывают.

Интуитивно мы думаем, что дело в том, что: **«у этих сотрудников недостаточно осознанности в вопросах безопасности»**.

Но в большинстве случаев проблема не в людях, а в том, что **не выстроена правильная система управления правами**.

<IntroProblemReasonSolution />

Перед лицом этих вызовов одного лишь «осторожного обращения» уже недостаточно. Нам нужна системная методология управления правами, и именно эту проблему пытается решить **IAM (Identity and Access Management, управление идентификацией и доступом)**.

## 1. Что такое IAM/RAM? Начнём с «системы контроля доступа»

### 1.1 Аналогия: умная система контроля доступа в компании

Представьте, что ваша компания переехала в новый офисный центр:

| Сценарий       | Подход без IAM                | Подход с IAM                                |
| :--------- | :----------------------------- | :------------------------------------------- |
| Приём нового сотрудника | Дать ему универсальный ключ, открывающий все двери   | Дать ему карту доступа, открывающую только двери его рабочей зоны         |
| Увольнение сотрудника   | Ключ потерян — и ладно, неизвестно, у кого он | Немедленно аннулировать его карту в системе, все двери перестают открываться |
| Подрядчик      | Одолжить ему ключ на несколько дней               | Выдать временную карту доступа с автоистечением через 3 дня              |
| Посетитель       | Ресепшен выдаёт ему ключ             | Выдать одноразовый код посетителя, открывающий только переговорную                 |

**IAM (Identity and Access Management, управление идентификацией и доступом)** — это как та самая «умная система контроля доступа»:

- **Идентификация (Identity)**: кто? Сотрудник, подрядчик, посетитель, приложение
- **Доступ (Access)**: в какие двери может войти? Какие операции может выполнять?
- **Управление (Management)**: как выдавать ключи, как изымать ключи, как проверять записи

### 1.2 AWS IAM vs Alibaba Cloud RAM

<IamRamComparisonDemo />

У разных облачных провайдеров есть своя реализация IAM:

| Облачный провайдер     | Название сервиса                             | Ключевые концепции                  |
| :--------- | :----------------------------------- | :------------------------ |
| **AWS**    | IAM (Identity and Access Management) | User, Group, Role, Policy |
| **Alibaba Cloud** | RAM (Resource Access Management)     | Пользователь, группа пользователей, роль, политика  |
| **Tencent Cloud** | CAM (Cloud Access Management)        | Пользователь, группа пользователей, роль, политика  |
| **Huawei Cloud** | IAM                                  | Пользователь, группа пользователей, делегирование, политика  |
| **Azure**  | Azure AD + RBAC                      | User, Group, Role, RBAC   |

Хотя названия различаются, **ключевые концепции едины**:

- **Пользователь (User)**: представляет конкретного человека или приложение
- **Группа пользователей (Group)**: массовое управление правами группы пользователей
- **Роль (Role)**: определяет набор прав, которые можно «исполнять»
- **Политика (Policy)**: конкретные правила прав (что разрешено/запрещено делать)

## 2. Пользователь, группа, роль: что же из этого использовать?

### 2.1 Различие трёх «идентичностей»

<IdentityProviderDemo />

Проведём аналогию с офисной обстановкой:

| Концепция                | Аналогия                           | Сценарий применения             | Особенности                               |
| :------------------ | :----------------------------- | :------------------- | :--------------------------------- |
| **Пользователь (User)**    | Штатный сотрудник, со своим рабочим местом и картой доступа | Долгосрочный, стабильный член команды | Имеет постоянные учётные данные (пароль, AK/SK)          |
| **Группа пользователей (Group)** | Отдел, например «технический отдел», «отдел продаж»     | Массовое управление правами         | Не может входить в систему, это лишь контейнер прав             |
| **Роль (Role)**    | Временный пропуск посетителя, временная карта подрядчика         | Временная авторизация, межаккаунтный доступ | Нет постоянных учётных данных, временные данные получают через «исполнение» |

### 2.2 Реальный пример: эволюция прав в одном стартапе

**Этап 1: команда основателей (2-3 человека)**

```
Проблема: вход в консоль напрямую под корневым аккаунтом (Root Account), потому что «так проще»
Риск: корневой аккаунт обладает всеми правами, при утечке весь аккаунт пропал
```

**Этап 2: расширение команды (5-10 человек)**

```
Улучшение: для каждого создаётся IAM User с разными правами
Проблема:
- Уволился сисадмин Ван, на каких серверах разбросаны его AK/SK?
- Новому фронтендеру нужны права чтения S3, бэкендеру — права RDS, настраивать вручную по одному слишком хлопотно
```

**Этап 3: стандартизация (10-30 человек)**

```
Улучшение:
1. Создание IAM Group по ролям:
   - Developers (разработка): чтение/запись S3, EC2, RDS
   - DevOps (эксплуатация): все права, но требуется MFA
   - ReadOnly (только чтение): просмотр всех ресурсов, без изменения
   - QAs (тестирование): доступ к ресурсам тестовой среды

2. Использование IAM Role:
   - Экземпляры EC2 используют Instance Profile, AK/SK больше не размещаются на серверах
   - Межаккаунтный доступ через Role Assume, без общих AK/SK
   - CI/CD через OIDC Federation, без хранения постоянных учётных данных
```

**Этап 4: мульти-аккаунт/корпоративный уровень (30+ человек)**

```
Архитектура:
- Master Account (главный аккаунт): используется только для управления биллингом и оргструктурой, без размещения ресурсов
- Audit Account (аудит-аккаунт): собирает логи всех аккаунтов
- Dev Account (аккаунт разработки): среда разработки
- Staging Account (аккаунт предрелиза): тестовая среда
- Prod Account (продакшен-аккаунт): боевая среда, строжайшие права

Поток прав:
- У разработчиков по умолчанию только права чтения в Dev-аккаунте
- При необходимости изменить продакшен оформляется заявка на Assume временной Role в Prod
- Все операции Assume фиксируются CloudTrail, регулярно аудируются
```

## 3. Роли и политики: «душа» управления правами

### 3.1 Суть роли: доверие + права

<RolePolicyDemo />

У IAM Role две ключевые составляющие:

1. **Политика доверия (Trust Policy)**: кто может исполнять эту роль?
2. **Политика прав (Permission Policy)**: что можно делать после успешного исполнения?

Проведём аналогию с театральной постановкой:

| Концепция                  | Аналогия                   | Пояснение                                                                                       |
| :-------------------- | :--------------------- | :----------------------------------------------------------------------------------------- |
| **Role (роль)**      | «Гамлет» в сценарии     | Определяет, какую пьесу играть (права)                                                                   |
| **Trust Policy**      | Режиссёр говорит «кто может играть Гамлета» | Это могут быть «актёры этой труппы» (пользователи аккаунта), «одолженные актёры из соседней труппы» (межаккаунтный доступ), «приглашённые гости» (внешний IdP) |
| **Permission Policy** | Содержание сценария               | Что может делать Гамлет: произносить реплики, фехтовать, сходить с ума (конкретные права)                                           |
| **Assume Role**       | Актёр выходит на сцену играть           | Ли выбран режиссёром на роль Гамлета, выйдя на сцену, он получает все права, определённые в сценарии                             |
| **Временные учётные данные**          | Пропуск на представление                 | Ли получает «временный пропуск на представление», который перестаёт действовать по окончании спектакля                                               |

### 3.2 Политика (Policy): «синтаксис» прав

<PermissionHierarchyDemo />

IAM Policy — это JSON-документ, определяющий, «кто над каким ресурсом может выполнять какую операцию».

**Пример полной Policy**:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowS3ReadWrite",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::my-app-bucket/*",
      "Condition": {
        "StringEquals": {
          "aws:RequestedRegion": "ap-northeast-1"
        },
        "Bool": {
          "aws:MultiFactorAuthPresent": "true"
        }
      }
    },
    {
      "Sid": "DenySensitiveData",
      "Effect": "Deny",
      "Action": "s3:*",
      "Resource": "arn:aws:s3:::my-app-bucket/sensitive/*"
    }
  ]
}
```

**Пояснение ключевых полей**:

| Поле          | Значение                               | Пример                     |
| :------------ | :--------------------------------- | :----------------------- |
| **Version**   | Версия синтаксиса Policy                    | "2012-10-17"             |
| **Statement** | Массив объявлений прав, может содержать несколько правил       | [...]                    |
| **Sid**       | ID объявления, опционально, для идентификации правила    | "AllowS3ReadWrite"       |
| **Effect**    | Эффект: Allow (разрешить) или Deny (запретить) | "Allow"                  |
| **Action**    | Разрешаемая/запрещаемая операция, поддерживает подстановочные символы        | "s3:GetObject", "s3:\*"  |
| **Resource**  | Ресурс воздействия, идентифицируется через ARN            | "arn:aws:s3:::bucket/\*" |
| **Condition** | Опционально, действует только при выполнении определённых условий         | Ограничение по региону, требование MFA и т.п.     |

### 3.3 Приоритет прав: Deny > Allow > запрет по умолчанию

Логику оценки прав в IAM можно подытожить одной фразой: **явный Deny всегда побеждает, нет Allow — значит запрет**.

Процесс оценки следующий:

```
1. Сначала проверяется наличие политики Deny
   ├─ Есть Deny → запрет (независимо от наличия Allow)
   └─ Нет Deny → продолжить проверку

2. Затем проверяется наличие политики Allow
   ├─ Есть Allow → разрешение
   └─ Нет Allow → запрет (принцип запрета по умолчанию)
```

**Практический пример: защита чувствительных данных**

```json
// 策略1：给开发者的普通权限
{
  "Effect": "Allow",
  "Action": ["s3:*"],
  "Resource": "arn:aws:s3:::company-data/*"
}

// 策略2：保护敏感目录（即使开发者有 s3:* 也不能访问）
{
  "Effect": "Deny",
  "Action": ["s3:*"],
  "Resource": "arn:aws:s3:::company-data/sensitive/*"
}
```

**Ключевые моменты**:

- У разработчика хоть и есть право Allow на `s3:*`
- но для чувствительного каталога есть явное правило Deny
- Deny имеет более высокий приоритет, поэтому разработчик не может получить доступ к чувствительным данным
- Даже если разработчик — администратор, этот Deny действует (если только это не корневой аккаунт)

## 4. Ключ доступа (AK/SK): «ключ», требующий осторожного хранения

### 4.1 Что такое AK/SK?

<AccessKeyManagementDemo />

Access Key (ключ доступа) — это разновидность долгосрочных учётных данных, предоставляемых облачным сервисом для программных вызовов API. Он состоит из двух частей:

| Составная часть              | Название         | Назначение                       | Аналогия       |
| :-------------------- | :----------- | :------------------------- | :--------- |
| **Access Key ID**     | ID ключа доступа  | Идентифицирует, кто ты (как имя пользователя) | Номер банковской карты   |
| **Secret Access Key** | Секретный ключ доступа | Доказывает, что ты — это ты (как пароль)   | PIN-код банковской карты |

### 4.2 Почему AK/SK — «опасный объект»?

**Реальный пример: урок одного стартапа**

Ли — новоиспечённый бэкенд-инженер в стартапе. В первую неделю работы его задачей была отладка функции загрузки файлов.

```python
# Ли написал такой код (серьёзная проблема безопасности!)
import boto3

# Ради удобства отладки напрямую вписал AK/SK в код
s3 = boto3.client(
    's3',
    aws_access_key_id='AKIAIOSFODNN7EXAMPLE',
    aws_secret_access_key='wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY',
    region_name='ap-northeast-1'
)

def upload_file(file_path, bucket_name, object_name):
    s3.upload_file(file_path, bucket_name, object_name)
    print(f"文件已上传到 s3://{bucket_name}/{object_name}")

# 测试上传
upload_file('./test.jpg', 'my-company-bucket', 'uploads/test.jpg')
```

**Что произошло неделю спустя**:

1. Ли закоммитил код на GitHub (вместе с AK/SK)
2. Код на GitHub был просканирован краулером, AK/SK были извлечены
3. Злоумышленник, используя эти учётные данные, создал в аккаунте компании множество экземпляров EC2 для майнинга
4. В конце месяца пришёл счёт: дополнительный расход в 12 000 долларов
5. Аудит выявил утечку AK/SK, с Ли провели беседу...

**Чему нас учит этот пример?**

| Неправильный подход                    | Правильный подход                                         |
| :-------------------------- | :----------------------------------------------- |
| Жёстко зашивать AK/SK в код     | Использовать IAM Role, чтобы программа автоматически получала временные учётные данные            |
| Коммитить AK/SK в Git-репозиторий    | Использовать `.gitignore` для игнорирования файлов конфигурации, использовать сервис управления секретами |
| Долго использовать одни AK/SK без ротации | Регулярно ротировать AK/SK, заменять долгосрочные учётные данные временными         |
| Назначать AK/SK чрезмерные права       | Следовать принципу минимальных привилегий, выдавать только необходимые права               |

### 4.3 Руководство по безопасному использованию AK/SK

**Сценарий 1: локальная разработка**

```bash
# 正确做法：使用 AWS CLI 配置凭证，不写在代码里
aws configure
# 然后根据提示输入 Access Key ID 和 Secret Access Key
# 这些信息会被保存在 ~/.aws/credentials，权限设置为 600

# 代码中不需要任何凭证配置
import boto3
s3 = boto3.client('s3')  # 自动从 ~/.aws/credentials 读取
```

**Сценарий 2: сервер/EC2**

```python
# 正确做法：使用 IAM Instance Profile
# 1. 创建一个 IAM Role，附加需要的权限（如 S3ReadOnly）
# 2. 创建一个 Instance Profile，关联这个 Role
# 3. 启动 EC2 时，选择这个 Instance Profile

# 代码中完全不需要凭证
import boto3
s3 = boto3.client('s3')  # 自动从 EC2 元数据服务获取临时凭证

# 临时凭证会自动轮换，无需担心过期
```

**Сценарий 3: пайплайн CI/CD**

```yaml
# 正确做法：使用 OIDC Federation（OpenID Connect）
# 以 GitHub Actions 为例：

# 1. 在 AWS 创建 OIDC Identity Provider，信任 GitHub
# 2. 创建一个 IAM Role，信任策略允许 GitHub 的特定仓库扮演
# 3. 在 GitHub Actions 中配置

name: Deploy
on: [push]

jobs:
  deploy:
    runs-on: ubuntu-latest
    permissions:
      id-token: write # 关键：允许请求 OIDC token
      contents: read
    steps:
      - uses: actions/checkout@v3

      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v2
        with:
          role-to-assume: arn:aws:iam::123456789012:role/GitHubActionsRole
          aws-region: ap-northeast-1
          # 注意：这里没有 Access Key！完全使用临时凭证

      - name: Deploy
        run: aws s3 sync ./build s3://my-bucket/
```

**Итог: уровни безопасности использования AK/SK**

| Уровень безопасности | Подход                        | Сценарий применения                  | Уровень риска |
| :------- | :-------------------------- | :------------------------ | :------- |
| Наивысший     | Использование IAM Role (без долгосрочных учётных данных) | EC2, Lambda, ECS, CI/CD   | Крайне низкий     |
| Высокий       | Использование OIDC Federation        | GitHub Actions, GitLab CI | Низкий       |
| Средний       | Использование сервиса управления секретами            | Локальная разработка, малая команда          | Средний       |
| Низкий       | Использование переменных окружения                | Быстрый прототип, личный проект        | Высокий       |
| Крайне низкий     | Жёсткое зашивание в код              | Не рекомендуется ни в каком сценарии          | Крайне высокий     |

## 5. Многофакторная аутентификация (MFA): добавьте «замок» на свой аккаунт

### 5.1 Что такое MFA?

<MfaSecurityDemo />

MFA (Multi-Factor Authentication, многофакторная аутентификация), также называемая 2FA (Two-Factor Authentication, двухфакторная аутентификация), — это механизм безопасности, требующий от пользователя при входе предоставить **два или более** различных по типу факторов аутентификации:

| Тип фактора                   | Что это             | Пример           |
| :------------------------- | :----------------- | :------------- |
| **Фактор знания** (что ты знаешь) | Информация, известная только пользователю | Пароль, PIN-код   |
| **Фактор владения** (что у тебя есть)   | Физическое устройство во владении пользователя | Телефон, аппаратный ключ |
| **Биометрический фактор** (что ты есть)   | Биометрические признаки пользователя     | Отпечаток пальца, распознавание лица |

### 5.2 Почему MFA так важна?

**Ответ дают реальные данные**:

| Способ атаки                 | Вероятность успеха без MFA | Вероятность успеха с MFA               |
| :----------------------- | :------------------ | :------------------------------ |
| Подбор пароля/брутфорс        | Очень высокая                | Крайне низкая (нужен ещё второй фактор)          |
| Получение пароля фишингом         | Очень высокая                | Крайне низкая (фишинговая страница не может получить код MFA) |
| Утечка пароля (утечка на другом сайте) | Очень высокая                | Крайне низкая (неизвестен второй фактор)          |

**Отчёт Microsoft по безопасности (2020)**: включение MFA способно остановить **99,9%** автоматизированных атак.

### 5.3 MFA на практике: включение MFA для корневого аккаунта AWS

**Шаг 1: вход в консоль AWS**

1. Войдите, используя email и пароль корневого аккаунта
2. В правом верхнем углу нажмите на имя аккаунта, выберите "Security Credentials"

**Шаг 2: включение MFA**

1. Найдите раздел "Multi-factor authentication (MFA)"
2. Нажмите "Assign MFA device"
3. Выберите тип устройства MFA (рекомендуется "Authenticator app")

**Шаг 3: настройка виртуального MFA**

1. Установите на телефон Google Authenticator или Microsoft Authenticator
2. Отсканируйте QR-код или вручную введите ключ
3. Введите 6-значный код подтверждения, показанный в приложении (введите два подряд, так как код обновляется каждые 30 секунд)

**Готово!** Ваш корневой аккаунт теперь под защитой MFA.

## 6. Межаккаунтный доступ: как безопасно «ходить в гости»?

### 6.1 Зачем нужен межаккаунтный доступ?

<CrossAccountAccessDemo />

По мере роста бизнеса многие компании используют **мульти-аккаунтную архитектуру** для изоляции разных сред:

| Тип аккаунта            | Назначение                   | Требования к правам           |
| :------------------ | :--------------------- | :----------------- |
| **Master Account**  | Управление организацией, расчёт биллинга     | Почти не используется         |
| **Security Audit**  | Централизованный сбор логов всех аккаунтов | Доступ только на чтение к другим аккаунтам   |
| **Shared Services** | Общие ресурсы (репозиторий образов и т.п.) | Доступ только на чтение из других аккаунтов   |
| **Development**     | Среда разработки               | Полные права для разработчиков     |
| **Staging**         | Тестовая/предрелизная среда        | Права тестировщиков       |
| **Production**      | Боевая среда               | Строгие ограничения, требуется согласование |

**Проблема: как сделать так, чтобы EC2 в аккаунте Production забирали образы из аккаунта Shared Services?**

- Вариант A: вписать AK/SK в user data аккаунта Production (опасно! риск утечки AK/SK)
- Вариант B: использовать межаккаунтный Role Assume (рекомендуется! временные учётные данные, автоматическая ротация)

### 6.2 Принцип межаккаунтного Role Assume

```
Аккаунт A (Production)                    Аккаунт B (Shared Services)
    |                                           |
    |  1. Запрос Assume Role                    |
    |  "Я хочу исполнить ECRReadRole аккаунта B"|
    |------------------------------------------>|
    |                                           |
    |                    2. Проверка политики доверия |
    |                    "Может ли аккаунт A исполнять меня?" |
    |                                           |
    |  3. Возврат временных учётных данных      |
    |  AccessKeyId, SecretKey, SessionToken    |
    |<------------------------------------------|
    |                                           |
    |  4. Доступ к ECR по временным данным      |
    |  docker pull аккаунтB.dkr.ecr...         |
```

**Ключевые моменты**:

- Срок действия временных учётных данных по умолчанию 1 час, максимум настраивается до 12 часов
- Не нужно хранить в коде никаких долгосрочных учётных данных
- Политика доверия может ограничивать, кто может исполнять эту роль (например, указанный аккаунт, указанный external ID)

### 6.3 Практика: настройка межаккаунтного доступа к ECR

**Сценарий**: EC2 в аккаунте Production нужно забирать Docker-образы из аккаунта Shared Services.

**Шаг 1: создание IAM Role в аккаунте Shared Services**

1. Войдите в консоль AWS аккаунта Shared Services
2. Перейдите в IAM -> Roles -> Create role
3. Выберите "Another AWS account"
4. Введите Account ID аккаунта Production
5. Опционально: отметьте "Require external ID" и введите случайную строку (повышение безопасности)
6. Прикрепите права: AmazonEC2ContainerRegistryReadOnly
7. Назовите Role: CrossAccountECRReadRole

**Шаг 2: получение Role ARN**

После создания скопируйте ARN роли:

```
arn:aws:iam::SHARED_SERVICES_ACCOUNT_ID:role/CrossAccountECRReadRole
```

**Шаг 3: настройка экземпляра EC2 в аккаунте Production**

Способ A: использование Instance Profile (рекомендуется)

1. Создайте IAM Role в аккаунте Production (для EC2)
2. Политика доверия: доверять сервису EC2
3. Политика прав: разрешить Assume межаккаунтной Role

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "sts:AssumeRole",
      "Resource": "arn:aws:iam::SHARED_SERVICES_ACCOUNT_ID:role/CrossAccountECRReadRole"
    }
  ]
}
```

4. Создайте Instance Profile, привяжите эту Role
5. При запуске EC2 выберите этот Instance Profile

Способ B: динамический Assume Role в user data EC2

```bash
#!/bin/bash
# 安装 AWS CLI
yum install -y aws-cli

# Assume 跨账号 Role
CREDS=$(aws sts assume-role \
  --role-arn arn:aws:iam::SHARED_SERVICES_ACCOUNT_ID:role/CrossAccountECRReadRole \
  --role-session-name EC2PullSession)

# 提取临时凭证
export AWS_ACCESS_KEY_ID=$(echo $CREDS | jq -r '.Credentials.AccessKeyId')
export AWS_SECRET_ACCESS_KEY=$(echo $CREDS | jq -r '.Credentials.SecretAccessKey')
export AWS_SESSION_TOKEN=$(echo $CREDS | jq -r '.Credentials.SessionToken')

# 登录 ECR
aws ecr get-login-password --region ap-northeast-1 | \
  docker login --username AWS --password-stdin SHARED_SERVICES_ACCOUNT_ID.dkr.ecr.ap-northeast-1.amazonaws.com

# 拉取镜像
docker pull SHARED_SERVICES_ACCOUNT_ID.dkr.ecr.ap-northeast-1.amazonaws.com/my-app:latest
```

**Шаг 4: тестирование межаккаунтного доступа**

Выполните на EC2 в Production:

```bash
# 测试能否 Assume Role
aws sts get-caller-identity
# 应该显示：arn:aws:sts::PRODUCTION_ACCOUNT_ID:assumed-role/CrossAccountECRReadRole/EC2PullSession

# 测试能否列出 Shared Services 的 ECR 仓库
aws ecr describe-repositories --registry-id SHARED_SERVICES_ACCOUNT_ID
```

**Готово!** Теперь EC2 в Production может безопасно забирать образы из Shared Services, не используя совместно никаких долгосрочных учётных данных.

## 7. Практика: построение безопасной системы прав

### 7.1 Построение архитектуры прав с нуля

<BestPracticesDemo />

Предположим, вы технический руководитель стартапа из 10 человек, и вам нужно спроектировать архитектуру прав AWS с нуля. Ниже рекомендованные шаги внедрения:

**Этап 1: защита корневого аккаунта (день 1)**

```
Цель: защитить корневой аккаунт, это самый важный аккаунт

1. Включите MFA корневого аккаунта (обязательно)
   - Рекомендуется аппаратный MFA (YubiKey) либо Google Authenticator

2. Создайте IAM-аккаунт администратора
   - Имя пользователя: admin (или ваше имя)
   - Права: AdministratorAccess (но в дальнейшем будут ужесточены)
   - Включите MFA

3. Удалите Access Key корневого аккаунта (если он был создан)
   - У корневого аккаунта никогда не должно быть AK/SK

4. Настройте оповещение об использовании корневого аккаунта
   - Используйте CloudWatch + SNS, при входе в корневой аккаунт отправлять email/SMS
```

**Этап 2: группировка прав команды (неделя 1)**

```
Цель: распределить членов команды по группам, массово управлять правами

1. Анализ ролей в команде:
   - Бэкенд-разработка (2 человека)
   - Фронтенд-разработка (1 человек)
   - Мобильная разработка (1 человек)
   - Продакт-менеджер (1 человек)
   - Дизайнер (1 человек)
   - Основатели/администраторы (3 человека)

2. Создание IAM Groups:

   Group: Developers
   ├── Участники: все разработчики (бэкенд, фронтенд, мобильные)
   ├── Права:
   │   ├── EC2: запуск, остановка, просмотр (но нельзя удалять чужие экземпляры)
   │   ├── S3: чтение/запись bucket среды разработки
   │   ├── RDS: только чтение (нельзя менять продакшен-БД)
   │   └── CloudWatch: просмотр логов
   └── Ограничение: операции только в регионе ap-northeast-1

   Group: ProductTeam
   ├── Участники: продакт-менеджер, дизайнер
   ├── Права:
   │   ├── S3: только чтение (просмотр файлов данных)
   │   ├── CloudWatch Dashboard: просмотр графиков мониторинга
   │   └── Cost Explorer: просмотр биллинга (но нельзя менять)
   └── Ограничение: только чтение, нельзя менять никакие ресурсы

   Group: Administrators
   ├── Участники: основатели, технический руководитель
   ├── Права: AdministratorAccess
   └── Требование: операции возможны только при MFA

3. Для каждого создайте IAM User, добавьте в соответствующую Group
   - Не прикрепляйте права напрямую к человеку, всё управление через Group
   - Включите MFA (обязательное требование)
```

**Этап 3: оптимизация прав на уровне приложений (недели 2-4)**

```
Цель: дать приложениям безопасный доступ к ресурсам AWS

1. Экземпляры EC2 используют Instance Profile
   - Больше не настраиваем AK/SK на серверах
   - Создаём IAM Role, прикрепляем нужные права (например, чтение/запись S3)
   - Создаём Instance Profile, привязываем эту Role
   - При запуске EC2 выбираем этот Instance Profile
   - В коде приложения напрямую используем boto3, без настройки учётных данных

2. Если использовать AK/SK всё же необходимо (сторонняя интеграция)
   - Используйте AWS Secrets Manager для хранения AK/SK
   - Приложение при запуске читает из Secrets Manager
   - Настройте регулярную ротацию (90 дней)
   - Мониторьте использование AK/SK

3. Настройте CloudTrail для записи всех вызовов API
   - Создайте отдельный S3 bucket для хранения логов
   - Настройте проверку файлов логов (защита от подделки)
   - Настройте уведомления SNS о ключевых событиях (использование корневого аккаунта, изменение политик)
```

**Этап 4: усиление безопасности (постоянно)**

```
Цель: построить механизм постоянного мониторинга и улучшения безопасности

1. Включите AWS Config
   - Мониторинг изменений конфигурации ресурсов
   - Проверка соответствия (например, открыта ли security group для 0.0.0.0/0)

2. Включите IAM Access Analyzer
   - Постоянный анализ политик ресурсов
   - Выявление внешнего доступа (например, публичен ли S3 bucket)

3. Регулярно проверяйте конфигурацию IAM
   - Раз в месяц проверяйте неиспользуемых IAM User, Role
   - Проверяйте использование Access Key
   - Проверяйте обоснованность состава Group

4. Постройте процесс реагирования на инциденты безопасности
   - При обнаружении утечки AK/SK: немедленно удалить, ротировать, аудировать зону влияния
   - При обнаружении аномальных вызовов API: немедленно расследовать, ограничить права
```

## 8. Распространённые заблуждения и руководство по обходу ловушек

### 8.1 Десять анти-паттернов IAM

| #   | Анти-паттерн                       | Почему это плохо                                     | Правильный подход                                         |
| :-- | :--------------------------- | :--------------------------------------------- | :----------------------------------------------- |
| 1   | Использование корневого аккаунта для повседневных операций       | Корневой аккаунт обладает всеми правами, при утечке невозможно ограничить ущерб       | Создать IAM-аккаунт администратора, корневой использовать только при необходимости        |
| 2   | Выдача всем AdministratorAccess | Нарушение принципа минимальных привилегий, рост риска ошибок и внутренних угроз     | Группировка по ролям, выдача только необходимых прав                     |
| 3   | Жёсткое зашивание AK/SK в код         | AK/SK легко утекают через GitHub и трудно ротируются         | Использование IAM Role, переменных окружения или сервиса управления секретами            |
| 4   | Долгое отсутствие ротации AK/SK             | Увеличение времени уязвимости после утечки учётных данных                   | Установить политику ротации в 90 дней, или лучше — использовать временные учётные данные       |
| 5   | Игнорирование MFA                     | После утечки пароля аккаунт сразу скомпрометирован                         | Включить MFA для всех IAM-пользователей, особенно высокопривилегированных        |
| 6   | Неиспользование CloudTrail            | Невозможно аудировать, кто что сделал, после инцидента невозможно отследить         | Включить CloudTrail и хранить логи в отдельном аудит-аккаунте    |
| 7   | Слишком вольная IAM Policy          | Например, `Resource: "*"`, `Action: "*"`, расширение поверхности атаки  | Чётко указывать ARN ресурса и конкретный Action                   |
| 8   | Неудаление IAM User уволившихся сотрудников    | Зомби-аккаунт может стать бэкдором                           | Построить процесс увольнения, немедленно отключать и удалять IAM User            |
| 9   | Неиспользование IAM Access Analyzer   | Невозможно обнаружить чрезмерно вольные политики ресурсов (например, публичный S3 bucket) | Включить IAM Access Analyzer, регулярно проверять внешний доступ       |
| 10  | Непроверка Policy в тестовой среде    | Применение Policy напрямую в продакшене может привести к простою сервиса    | Тестировать через IAM Policy Simulator, сначала проверять в тестовой среде |

## Заключение: ключевые принципы управления правами облачного аккаунта

Управление правами облачного аккаунта — это не одномоментная задача, оно должно постоянно эволюционировать в зависимости от размера команды и потребностей бизнеса:

1. **Начальный этап** (1-10 человек):
   - Защита корневого аккаунта (MFA + неиспользование корневого аккаунта для повседневных операций)
   - Создание IAM-аккаунта администратора
   - Базовая группировка (Developers, Admins)

2. **Этап роста** (10-50 человек):
   - Детализированная группировка прав (фронтенд/бэкенд, эксплуатация, продукт и т.п.)
   - Замена AK/SK на IAM Role
   - Включение аудита CloudTrail
   - Регулярная проверка прав

3. **Зрелый этап** (более 50 человек / мульти-аккаунт):
   - Мульти-аккаунтная архитектура (разделение Dev, Staging, Prod)
   - Централизованный аудит-аккаунт логов
   - Автоматизированная проверка прав и оповещения
   - Отлаженный процесс запроса и согласования прав

**Запомните три фразы об основных принципах**:

1. **Принцип минимальных привилегий**: выдавать только необходимые права, не давать AdministratorAccess
2. **Не использовать долгосрочные учётные данные**: приоритетно использовать IAM Role и временные учётные данные, избегая утечки AK/SK
3. **Включить MFA**: особенно для корневого аккаунта и высокопривилегированных аккаунтов, это самая эффективная мера безопасности
