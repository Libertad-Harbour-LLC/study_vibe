# Инфраструктура как код

::: tip Предисловие
**Бывало ли у вас такое кошмарное переживание: продакшен-сервер упал, но никто не помнит, как он был настроен изначально?** Вручную войти на сервер, по памяти набивать команды, молиться, чтобы не опечататься, — вот будни традиционной эксплуатации. Инфраструктура как код (Infrastructure as Code, IaC) полностью всё это изменила: определять и управлять инфраструктурой с помощью кода, делая конфигурацию серверов, как и ПО, версионируемой, воспроизводимой и аудируемой.
:::

**Чему вас научит эта статья?**

После изучения этой главы вы получите:

- **Ключевые концепции**: поймёте, что такое IaC и почему это краеугольный камень современной эксплуатации
- **Понимание рабочего процесса**: освоите четырёхэтапный процесс Terraform Write → Plan → Apply → Destroy
- **Выбор инструментов**: узнаете о плюсах и минусах основных инструментов — Terraform, Pulumi, CloudFormation и др.
- **Осознание рисков**: поймёте вред дрейфа конфигурации и методы его обнаружения
- **Лучшие практики**: освоите методы инженерного управления IaC-проектами

|-----|------|---------|

## 0. Общая картина: зачем инфраструктуре тоже нужен «исходный код»?

Представьте, что вы повар. Если каждое блюдо готовить на глаз — сегодня класть ложку соли, завтра две, — вкус никогда не будет стабильным. Но если записать рецепт — с точностью до граммов каждой приправы, — любой сможет воспроизвести тот же вкус.

Управление инфраструктурой сталкивается с той же проблемой. Конфигурация одного сервера может включать десятки параметров: операционную систему, сетевые правила, security group, тома хранилища, переменные окружения и т.п. Ручная настройка не только склонна к ошибкам, но и **невоспроизводима, неаудируема, необратима**.

::: tip Ключевая ценность IaC
- **Воспроизводимость**: один и тот же код, сколько бы раз его ни выполнили, даёт один результат (идемпотентность)
- **Версионируемость**: изменения инфраструктуры управляются через Git, кто что изменил и почему — ясно с первого взгляда
- **Аудируемость**: все изменения фиксируются, что отвечает требованиям соответствия
- **Автоматизируемость**: автоматическое развёртывание через пайплайн CI/CD устраняет риск ручных операций
- **Возможность совместной работы**: члены команды проверяют изменения инфраструктуры через Pull Request, как ревью кода
:::

## 1. Концепция IaC: от «ручных кликов» к «декларациям в коде»

Традиционный способ работы в эксплуатации таков: войти в консоль облачной платформы, вручную кликами создавать серверы, настраивать сеть, задавать security group. Такой способ ещё годится при управлении несколькими серверами, но когда масштаб вырастает до десятков и сотен, он превращается в кошмар.

Ключевая идея IaC: **описать декларативным кодом желаемое состояние инфраструктуры, чтобы инструмент автоматически его реализовал**. Вам не нужно говорить инструменту «сначала создай VPC, потом подсеть, потом security group» (императивно), достаточно сказать «мне нужна вот такая сетевая среда» (декларативно), и инструмент сам вычислит необходимые шаги.

<IaCConceptDemo />

| Параметр | Ручная эксплуатация | Инфраструктура как код |
|------|---------|--------------|
| Способ работы | Вход в консоль и клики | Написание файлов кода |
| Воспроизводимость | Зависит от документации и памяти | Код как документация, 100% воспроизводимость |
| Отслеживание изменений | Нет записей или неполные записи | Версионирование Git, полная история |
| Способ совместной работы | Устное общение, передача документов | Ревью через Pull Request |
| Возможность отката | Ручные обратные операции | git revert + повторный apply |
| Согласованность | Большие различия между средами | Разработка/тест/продакшен полностью идентичны |

::: tip Декларативный vs императивный
- **Декларативный (Declarative)**: описывает «что я хочу», инструмент сам вычисляет «как сделать». Так работают Terraform, CloudFormation. Плюс — хорошая идемпотентность, минус — ограниченная гибкость.
- **Императивный (Imperative)**: описывает «как сделать», выполняется шаг за шагом. Так работают Ansible, Shell-скрипты. Плюс — гибкость, минус — трудно гарантировать идемпотентность.
- **Гибридный**: Pulumi, AWS CDK пишутся на универсальных языках программирования, сочетая декларативное управление состоянием и императивную гибкость.
:::

## 2. Рабочий процесс Terraform: Write → Plan → Apply

Terraform — на сегодня самый популярный инструмент IaC, разработанный HashiCorp. Его рабочий процесс ясен и интуитивен, делится на четыре этапа, как «кодирование→ревью→развёртывание→очистка» в разработке ПО.

<TerraformWorkflowDemo />

::: tip Четырёхэтапный рабочий процесс
1. **Write (написание)**: написание файлов определения инфраструктуры (.tf) на HCL (HashiCorp Configuration Language). Объявите нужные вам ресурсы: серверы, базы данных, сеть и т.п.
2. **Plan (планирование)**: при запуске `terraform plan` Terraform сравнивает текущее состояние с целевым и формирует «план выполнения» — сообщает, какие ресурсы он намерен создать, изменить, удалить. Это страховочная сетка, позволяющая подтвердить изменения перед реальным выполнением.
3. **Apply (выполнение)**: после подтверждения корректности плана при запуске `terraform apply` Terraform создаёт или изменяет ресурсы по плану. По завершении текущее состояние сохраняется в файл состояния (terraform.tfstate).
4. **Destroy (уничтожение)**: когда что-то больше не нужно, запустите `terraform destroy` для очистки всех ресурсов, чтобы избежать ненужных расходов.
:::

| Команда | Назначение | Изменяет ли инфраструктуру | Сценарий применения |
|------|------|----------------|---------|
| `terraform init` | Инициализация проекта, загрузка Provider | Нет | Первое использование или добавление нового Provider |
| `terraform plan` | Предпросмотр изменений, формирование плана выполнения | Нет | Обязательно перед каждым изменением |
| `terraform apply` | Выполнение изменений, создание/изменение ресурсов | Да | После подтверждения plan |
| `terraform destroy` | Уничтожение всех ресурсов | Да | Очистка тестовой среды, вывод сервиса |
| `terraform state` | Просмотр/управление файлом состояния | Зависит от операции | Миграция состояния, импорт ресурсов |

## 3. Сравнение инструментов: выбор подходящего вам инструмента IaC

В области IaC существует множество инструментов, у каждого свой акцент. При выборе инструмента нужно учитывать технологический стек команды, облачную платформу, масштаб проекта и другие факторы. Нет «лучшего» инструмента, есть лишь наиболее подходящий вашему сценарию.

<IaCToolComparisonDemo />

| Инструмент | Язык | Поддержка облачных платформ | Кривая обучения | Сценарий применения |
|------|------|-----------|---------|---------|
| Terraform | HCL | Мульти-облако (AWS/Azure/GCP) | Средняя | Мульти-облачная среда, совместная работа команды |
| Pulumi | Python/TS/Go | Мульти-облако | Низкая (если знаком язык программирования) | Дружелюбный к разработчикам, сложная логика |
| AWS CloudFormation | JSON/YAML | Только AWS | Средняя | Чистая AWS-среда |
| AWS CDK | Python/TS/Java | Только AWS | Низкая | AWS + предпочтение языка программирования |
| Ansible | YAML | Мульти-облако + bare metal | Низкая | Управление конфигурацией, гибридная среда |

::: tip Как выбрать?
- **Стартап / одно облако**: CloudFormation (AWS) или нативный инструмент соответствующей облачной платформы, лучшая интеграция с экосистемой
- **Мульти-облако / средне-крупная команда**: Terraform, крупнейшее сообщество, богатейший набор Provider, легче нанимать специалистов
- **Команда во главе с разработчиками**: Pulumi или CDK, писать инфраструктуру на знакомом языке программирования, хорошая поддержка IDE
- **Нужно управление конфигурацией**: Ansible, силён во внутренней настройке серверов (установка ПО, изменение файлов конфигурации)
:::

## 4. Дрейф конфигурации: бесшумная бомба замедленного действия

Дрейф конфигурации (Configuration Drift) — самый незаметный враг в практике IaC. Он означает **постепенное возникновение расхождения между фактическим состоянием инфраструктуры и состоянием, определённым в коде**.

Как обычно возникает это расхождение? Кто-то ради «быстрого фикса» проблемы на продакшене напрямую вошёл в консоль и вручную изменил правило security group; кто-то ради отладки временно увеличил конфигурацию какого-то сервера, но забыл вернуть обратно. Эти «мелкие изменения» накапливаются день за днём и в итоге приводят к серьёзному рассогласованию кода и реальной среды.

<ConfigDriftDemo />

::: tip Вред дрейфа конфигурации
1. **Невоспроизводимость**: среда, описанная в коде, не совпадает с реальной, при создании новой среды возникнут проблемы
2. **Сбой отката**: думаешь, что откат к предыдущей версии всё восстановит, но реальная среда уже была изменена вручную
3. **Угроза безопасности**: вручную открытые порты, ослабленные права могут быть забыты и стать точкой входа для атаки
4. **Несостоятельность аудита**: аудит соответствия основан на коде, но код не отражает реальное состояние
:::

| Мера предотвращения | Пояснение |
|---------|------|
| Запрет ручных изменений | Ограничение прав на операции в консоли через политики IAM |
| Регулярное обнаружение дрейфа | Периодический запуск `terraform plan` для проверки расхождений |
| Автоматическое исправление | После обнаружения дрейфа автоматическое выполнение apply для восстановления согласованности |
| Аудит изменений | Включение журналов аудита, таких как CloudTrail, для отслеживания источника всех изменений |

## 5. Лучшие практики: обеспечение устойчивой эволюции IaC-проекта

Код IaC, как и код приложений, требует хороших инженерных практик для обеспечения сопровождаемости. По мере роста масштаба инфраструктуры бессистемный код IaC превращается в другую форму «технического долга».

<IaCBestPracticeDemo />

::: tip Шесть ключевых лучших практик
1. **Модульность**: абстрагируйте переиспользуемую инфраструктуру в модули (например, модуль VPC, модуль базы данных), избегая копирования-вставки. Как при написании функций — определить в одном месте, вызывать во многих.
2. **Изоляция сред**: разработка, тест, продакшен используют отдельные файлы состояния и файлы переменных, изолируются через workspace или структуру каталогов.
3. **Удалённое управление состоянием**: файл состояния (tfstate) хранится в удалённом бэкенде (S3 + DynamoDB), поддерживая совместную работу команды и блокировку состояния во избежание конфликтов параллельного доступа.
4. **Управление чувствительной информацией**: пароли, ключи и прочую чувствительную информацию не пишите в коде, используйте инструменты вроде Vault, AWS Secrets Manager.
5. **Интеграция с CI/CD**: интегрируйте terraform plan в процесс PR, apply выполняйте автоматически через пайплайн, исключив локальные ручные операции.
6. **Ревью кода**: изменения инфраструктуры, как и код приложений, требуют Code Review, особенно изменения, затрагивающие security group и политики IAM.
:::

## Заключение

Инфраструктура как код — краеугольный камень современной облачно-нативной эксплуатации. Она превращает «неописуемые ручные операции» в «версионируемый код», делая управление инфраструктурой из «искусства» «инженерией».

Вспомним ключевые моменты этой главы:

1. **Суть IaC**: объявлять желаемое состояние инфраструктуры в коде, чтобы инструмент его автоматически реализовывал
2. **Рабочий процесс Terraform**: три шага Write → Plan → Apply, Plan — это страховочная сетка
3. **Выбор инструмента**: для мульти-облака — Terraform, для одного облака — нативный инструмент, для команды разработчиков — Pulumi
4. **Дрейф конфигурации**: самый незаметный риск, требует двойной защиты процессами и инструментами
5. **Инженерное управление**: модульность, изоляция сред, удалённое состояние, интеграция с CI/CD — ни одно нельзя упустить
