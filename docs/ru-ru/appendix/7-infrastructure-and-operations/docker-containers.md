::: tip Предисловие
**«У меня на машине работает» — самая классическая отговорка разработчика, и Docker заставил эту отговорку полностью исчезнуть.** Технология контейнеризации упаковывает приложение и все его зависимости в стандартизированную единицу, гарантируя единообразный запуск в любой среде. Это краеугольный камень современной поставки ПО.

## 1. Зачем нужны контейнеры?

До появления контейнеров для развёртывания приложения нужно было вручную устанавливать на сервере среду выполнения, настраивать переменные окружения, разбираться с конфликтами зависимостей. Различия между разными средами (разработка, тест, продакшен) — рассадник багов.

### Какие проблемы решил контейнер?

| Проблема | Традиционный способ | Способ с контейнерами |
|------|---------|---------|
| Несогласованность сред | «У меня локально работает» | Упаковать все зависимости, единообразно везде |
| Конфликты зависимостей | App A нужен Node 14, App B нужен Node 18 | У каждого контейнера независимая среда |
| Расточительство ресурсов | На каждую VM — полная ОС | Общее ядро, накладные расходы порядка МБ |
| Медленное развёртывание | Ручная установка и настройка | docker run одной командой |
| Сложное масштабирование | Создать VM, поставить среду, развернуть | Запуск нового контейнера за секунды |

::: tip Суть контейнера
Контейнер — не лёгкая виртуальная машина. Его суть — **изолированный процесс**. Ядро Linux реализует контейнеры через два механизма:
- **Namespace**: изоляция «поля зрения» процесса (PID, сеть, файловая система и т.п.)
- **Cgroups**: ограничение использования ресурсов процессом (CPU, память, IO)

Процесс внутри контейнера принципиально не отличается от обычного процесса на хосте, он просто «заперт в комнате, из которой не видно, что снаружи».
:::

## 2. Ключевые концепции

Мир Docker строится вокруг трёх ключевых концепций: образ (Image), контейнер (Container), реестр (Registry).

| Концепция | Аналогия | Пояснение |
|------|------|------|
| Образ (Image) | Класс / шаблон | Шаблон приложения только для чтения, содержит код, среду выполнения, библиотеки, конфигурацию |
| Контейнер (Container) | Экземпляр / объект | Запущенный экземпляр образа, доступен для чтения/записи, имеет независимый жизненный цикл |
| Реестр (Registry) | Магазин приложений | Сервис хранения и распространения образов (Docker Hub, ACR, ECR) |
| Dockerfile | Рецепт / чертёж | Текстовый файл, определяющий, как собрать образ |
| Том данных (Volume) | Внешний жёсткий диск | Постоянное хранение данных, данные не теряются после удаления контейнера |

### Многослойная структура образа

Образ Docker состоит из наложения нескольких слоёв только для чтения (Layer), каждая инструкция Dockerfile создаёт один слой:

```
┌─────────────────────────┐
│  CMD ["node", "app.js"] │  ← слой команды запуска
├─────────────────────────┤
│  COPY . /app            │  ← слой кода приложения (часто меняется)
├─────────────────────────┤
│  RUN npm install        │  ← слой установки зависимостей (иногда меняется)
├─────────────────────────┤
│  FROM node:18-alpine    │  ← слой базового образа (редко меняется)
└─────────────────────────┘
```

::: tip Почему слоистость так важна?
Docker кэширует каждый слой. Если какой-то слой не изменился, при сборке кэш используется напрямую. Поэтому в Dockerfile следует **инструкции с низкой частотой изменений ставить в начало** (например, установку зависимостей), а **с высокой частотой изменений — в конец** (например, копирование кода). Так большинство сборок попадает в кэш и идёт намного быстрее.
:::

## 3. Жизненный цикл Docker

От написания Dockerfile до запуска контейнера рабочий процесс Docker представляет собой ясный конвейер.

### Краткий справочник часто используемых инструкций Dockerfile

| Инструкция | Назначение | Пример |
|------|------|------|
| `FROM` | Указать базовый образ | `FROM node:18-alpine` |
| `WORKDIR` | Задать рабочий каталог | `WORKDIR /app` |
| `COPY` | Скопировать файлы в образ | `COPY package.json ./` |
| `RUN` | Выполнить команду при сборке | `RUN npm install` |
| `ENV` | Задать переменную окружения | `ENV NODE_ENV=production` |
| `EXPOSE` | Объявить порт (только документирующая роль) | `EXPOSE 3000` |
| `CMD` | Команда запуска контейнера | `CMD ["node", "app.js"]` |
| `ENTRYPOINT` | Точка входа контейнера (труднее переопределить) | `ENTRYPOINT ["nginx"]` |

## 4. Docker Compose: многосервисная оркестрация

В реальных проектах обычно не один контейнер. Веб-приложению может понадобиться: сервер приложения + база данных + Redis + Nginx. Docker Compose одним YAML-файлом определяет несколько контейнеров и управляет ими.

### Пример docker-compose.yml

```yaml
version: '3.8'
services:
  app:
    build: .
    ports:
      - "3000:3000"
    environment:
      - DB_HOST=db
      - REDIS_HOST=redis
    depends_on:
      - db
      - redis

  db:
    image: postgres:15-alpine
    volumes:
      - db-data:/var/lib/postgresql/data
    environment:
      - POSTGRES_PASSWORD=secret

  redis:
    image: redis:7-alpine

volumes:
  db-data:
```

### Ключевые концепции Compose

| Концепция | Пояснение | Пример |
|------|------|------|
| services | Определение каждого контейнерного сервиса | app, db, redis |
| volumes | Тома для постоянного хранения данных | db-data хранит файлы базы данных |
| networks | Пользовательская сеть (по умолчанию создаётся автоматически) | Сервисы обращаются друг к другу по имени сервиса |
| depends_on | Зависимость порядка запуска | app зависит от db и redis |
| environment | Переменные окружения | Пароль базы данных, адрес подключения |

::: tip Обнаружение сервисов
В Docker Compose имя сервиса является именем хоста. Контейнер app может напрямую обращаться к базе данных по `db:5432`, к Redis по `redis:6379`, не зная IP-адреса. Это заслуга встроенного DNS Docker.
:::

## 5. Лучшие практики

### 5.1 Многоэтапная сборка (Multi-stage Build)

Многоэтапная сборка — мощный инструмент оптимизации размера образа. На этапе сборки устанавливаются все инструменты и зависимости, а в финальном этапе остаются только файлы, необходимые для выполнения.

```dockerfile
# 构建阶段
FROM node:18-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# 运行阶段
FROM node:18-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
EXPOSE 3000
CMD ["node", "dist/server.js"]
```

### 5.2 Чек-лист оптимизации образа

| Пункт оптимизации | Подход | Эффект |
|--------|------|------|
| Выбор маленького базового образа | Использовать `alpine` вместо `ubuntu` | Образ уменьшается с ~200 МБ до ~50 МБ |
| Объединение инструкций RUN | Несколько команд через `&&` | Уменьшение числа слоёв образа |
| Использование .dockerignore | Исключить node_modules, .git и т.п. | Ускорение сборки, уменьшение контекста |
| Многоэтапная сборка | Разделение сред сборки и выполнения | Финальный образ не содержит инструментов сборки |
| Фиксация номера версии | `node:18.17-alpine` вместо `node:latest` | Сборка воспроизводима |

### 5.3 Практики безопасности

| Практика | Пояснение |
|------|------|
| Не запускать от root | `USER node` указывает пользователя не-root |
| Сканирование уязвимостей | Сканирование образа через `docker scout` или Trivy |
| Минимальные привилегии | Устанавливать только необходимые пакеты, не ставить инструменты отладки |
| Не зашивать секреты жёстко | Использовать переменные окружения или Docker Secrets |
| Регулярно обновлять базовый образ | Своевременно устранять уязвимости безопасности |

## Заключение

Контейнеризация Docker — инфраструктура современной поставки ПО, и её понимание критически важно для любого разработчика.

Вспомним ключевые моменты этой главы:

1. **Контейнер vs виртуальная машина**: контейнер использует общее ядро хоста, легче и быстрее, но изоляция немного слабее, чем у VM
2. **Ключевая тройка**: образ (шаблон), контейнер (экземпляр), реестр (распространение)
3. **Dockerfile**: слоистая сборка, использование кэша, инструкции с малой частотой изменений ставить в начало
4. **Docker Compose**: определение многосервисного приложения через YAML, имя сервиса = имя хоста
5. **Продакшен-практики**: многоэтапная сборка для уменьшения образа, базовый образ alpine, запуск не от root
