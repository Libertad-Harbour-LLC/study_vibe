## 0. Введение: почему загрузка и скачивание файлов так «медленно»?

Представьте такой сценарий: вы загрузили в фотосообщество HD-снимок на 10 МБ, и в итоге ждали полминуты, пока он загрузится; а ваш друг в Пекине нажал «скачать» — и ему понадобилось всего 2 секунды. Почему для одного и того же файла опыт загрузки и скачивания так разительно отличается?

Или подумайте ещё: ваш интернет-магазин проводит распродажу «Двойного 11», на страницу деталей товара внезапно хлынул миллионный трафик, и сервер просто «лёг». Не хватает полосы пропускания? Или проблема в проектировании архитектуры?

Ответы на эти вопросы кроются в «золотой паре» — **объектном хранилище** и **CDN**.

## 1. Объектное хранилище: ваш «умный облачный склад»

### 1.1 Что такое объектное хранилище?

Традиционная файловая система — как ваш домашний шкаф: одежда разложена по слоям «верх/брюки/юбки», и чтобы найти рубашку, нужно сначала открыть шкаф → секция верха → отделение рубашек. Эта модель «иерархической вложенности» при взрывном росте числа файлов становится крайне громоздкой.

Объектное хранилище же похоже на современную складскую логистику: у каждой посылки есть уникальный «трек-номер» (ключ объекта), нужно лишь назвать номер, и складской робот точно достанет её из массы посылок.

<ObjectStorageDemo />

**Ключевые различия одним взглядом**:

| Параметр         | Традиционная файловая система           | Объектное хранилище                |
| :----------- | :--------------------- | :---------------------- |
| **Способ организации** | Иерархическое дерево каталогов             | Плоские пары ключ-значение              |
| **Протокол доступа** | POSIX (локальные файловые операции)  | HTTP/REST API           |
| **Масштабируемость**   | Ограниченная ёмкость одной машины           | Почти безграничное горизонтальное масштабирование        |
| **Метаданные**   | Базовые атрибуты (размер, время) | Богатые пользовательские метаданные      |
| **Типичные сценарии** | Локальные офисные документы           | Картинки/видео/резервные копии/статические ресурсы |

### 1.2 Ключевые концепции объектного хранилища

#### Bucket (контейнер): ваша «секция склада»

Bucket — это контейнер верхнего уровня объектного хранилища, эквивалентный отдельному пространству имён. Все объекты должны храниться в каком-либо bucket.

**Правила именования** (на примере Alibaba Cloud OSS):

- Глобальная уникальность: не может повторяться среди всех пользователей всего облачного провайдера
- Может содержать только строчные буквы, цифры и дефисы
- Должно начинаться и заканчиваться строчной буквой или цифрой
- Длина от 3 до 63 символов

**Практическая ловушка**: однажды команда создала несколько десятков bucket по бизнес-направлениям, а в конце месяца обомлела от счёта — у каждого bucket есть минимальная плата за хранение и плата за запросы. Совет: планируйте bucket по комбинации «среда + назначение», например `prod-static-assets`, `dev-backup-archive`.

#### Объект (Object): ваша «посылка данных»

Объект — базовая единица хранения, состоящая из трёх частей:

1. **Ключ (Key)**: уникальный идентификатор объекта, эквивалент «трек-номера»
   - Пример: `images/avatar/2024/user123.jpg`
   - Хотя выглядит как путь, по сути это просто строка

2. **Данные (Data)**: само содержимое объекта
   - Может быть любыми двоичными данными
   - Ограничение размера зависит от облачного провайдера (обычно один объект до 5 ТБ)

3. **Метаданные (Metadata)**: дополнительная информация, описывающая объект
   - Системные метаданные: Content-Type, ETag, Last-Modified и др.
   - Пользовательские метаданные: например, `x-oss-meta-owner`, `x-oss-meta-project`

#### Контроль доступа: кто может трогать мой «склад»?

Объектное хранилище предоставляет многоуровневый контроль прав:

| Уровень         | Способ контроля                  | Типичный сценарий                        |
| :----------- | :------------------------ | :------------------------------ |
| **Уровень bucket**   | Bucket Policy (политика ресурса) | Запретить весь внешний доступ, разрешить только определённые IP |
| **Уровень объекта** | ACL (список контроля доступа)       | Публичные картинки, приватные документы              |
| **Временная авторизация** | STS (сервис токенов безопасности)       | Прямая загрузка с фронтенда, загрузка с мобильных            |

**Красная линия безопасности**: никогда не пишите AccessKey ID и AccessKey Secret в коде фронтенда! Правильный подход: фронтенд запрашивает у вашего бэкенда временные STS-данные, бэкенд после проверки личности возвращает временные данные с временем истечения.

## 2. CDN: ваша «глобальная курьерская сеть»

### 2.1 Зачем нужен CDN?

Представьте, что вы открыли интернет-магазин, сервер которого размещён в Шэньчжэне. Теперь пользователь в Пекине обращается к вашей картинке:

- **Без CDN**: запрос идёт из Пекина → Хэбэй → Хэнань → Хубэй → Хунань → Гуандун → Шэньчжэнь, преодолевая более 2000 км, а туда и обратно — более 4000 км. Только сетевая передача занимает десятки миллисекунд, а при сетевых заторах ещё хуже.

- **С CDN**: запрос идёт из Пекина прямо к CDN-узлу в Пекине (возможно, прямо в пекинском дата-центре China Unicom), расстояние сокращается с 2000 км до 20 км, задержка с 50 мс до 5 мс.

В этом и заключается ключевая ценность CDN: **приблизить контент к пользователю**.

<CdnAccelerationDemo />

### 2.2 Ключевая архитектура CDN

#### Граничный узел: ближайший к пользователю «пункт выдачи»

Граничный узел — это уровень CDN-сети, наиболее близкий к пользователю, обычно развёртывается:

- В дата-центрах операторов (China Unicom/China Telecom/China Mobile)
- В точках обмена интернет-трафиком крупных городов
- В важных транспортных узлах

**Распределение основных CDN-узлов в Китае**:

- Города первого эшелона: Пекин, Шанхай, Гуанчжоу, Шэньчжэнь
- Города второго эшелона: Ханчжоу, Нанкин, Чэнду, Ухань, Сиань
- За рубежом: Гонконг, Сингапур, Токио, Кремниевая долина, Франкфурт

<EdgeNodeDistributionDemo />

#### Источник (Origin): «главный склад» контента

Источник — это место, откуда CDN получает контент при обращении к источнику, может быть:

- Объектное хранилище (OSS/COS/S3)
- Собственный сервер (ECS/физическая машина)
- Балансировщик нагрузки (SLB/CLB)

**Ключевые настройки**:

- **HOST источника**: доменное имя/IP, используемые CDN-узлом при обращении к источнику
- **Протокол обращения к источнику**: HTTP или HTTPS
- **Порт обращения к источнику**: 80, 443 или пользовательский порт

#### Узлы промежуточного слоя: «региональные распределительные центры»

Между граничными узлами и источником у CDN обычно есть ещё один или несколько слоёв промежуточных узлов:

- **Агрегирующие узлы**: агрегируют запросы к источнику от нескольких граничных узлов, снижая нагрузку на источник
- **Региональные центры**: отвечают за распространение и диспетчеризацию контента большого региона

Плюсы такой многоуровневой архитектуры:

1. **Снижение нагрузки на источник**: запросы 1000 граничных узлов могут потребовать обращения к источнику лишь 10 раз
2. **Повышение коэффициента попаданий**: популярный контент перехватывается уже на промежуточном слое, не требуя обращения к источнику
3. **Изоляция сбоев**: если на каком-то маршруте проблема, можно автоматически переключиться на другой путь

### 2.3 Полный процесс ускорения через CDN

Проследим один реальный запрос пользователя:

<CachePolicyDemo />

**Шаг 1: разрешение DNS** (умная диспетчеризация)

```
用户输入：cdn.example.com/image.jpg
↓
DNS 服务器返回：北京联通 CDN 节点 IP（1.2.3.4）
```

Ключевое здесь — **умный DNS**: исходя из оператора, географического положения, нагрузки узлов пользователя, возвращается IP оптимального CDN-узла.

**Шаг 2: поиск на граничном узле** (попадание в кэш?)

```
请求到达北京联通 CDN 节点（1.2.3.4）
↓
节点检查本地缓存：
├─ 命中？直接返回内容 ✓
└─ 未命中？继续下一步
```

**Шаг 3: обращение к источнику** (слой за слоем вверх)

```
边缘节点未命中
↓
向父节点（如：华北区域中心）请求
├─ 父节点命中？返回内容
└─ 父节点未命中？继续向上
    ↓
    向源站请求
    ↓
    源站返回内容
```

**Шаг 4: кэширование и возврат** (в следующий раз быстрее)

```
内容沿链路返回
↓
每层节点都缓存一份
↓
最终到达用户
```

Таким образом, когда в следующий раз пользователь запросит тот же файл, можно будет вернуть его прямо с граничного узла, обеспечив «мгновенное открытие».

## 3. От загрузки до доступа: разбор полной цепочки

### 3.1 Три способа загрузки файлов

<UploadProcessDemo />

#### Способ первый: клиент → сервер → объектное хранилище (традиционная модель)

```
浏览器 → 你的后端服务器 → 对象存储
```

**Процесс**:

1. Пользователь выбирает файл, нажимает загрузку
2. Файл сначала загружается на ваш бэкенд-сервер
3. Бэкенд, получив файл целиком, перезагружает его в объектное хранилище
4. Возвращает результат загрузки пользователю

**Преимущества**:

- Простая реализация, легко контролировать и фронтенд, и бэкенд
- Можно на бэкенде проверять файл, преобразовывать формат
- Чувствительные операции можно логировать, проверять права

**Недостатки**:

- **Двойной расход полосы**: загрузка пользователя занимает полосу один раз, перезагрузка сервером занимает ещё раз
- **Большая нагрузка на сервер**: большие файлы занимают много памяти и CPU
- **Медленная загрузка**: фактически добавляется посредник, ощущаемое пользователем время загрузки больше

**Сценарий применения**: небольшие файлы (<10 МБ), необходимость обработки на бэкенде (например, сжатие картинок, добавление водяных знаков), внутренние системы управления.

#### Способ второй: прямая загрузка клиента в объектное хранилище (современный рекомендуемый)

```
浏览器 ──────→ 对象存储
        ↑
        后端只签发临时凭证
```

**Процесс**:

1. Пользователь выбирает файл, фронтенд сначала запрашивает у бэкенда «учётные данные для загрузки»
2. Бэкенд проверяет личность пользователя, запрашивает у сервиса объектного хранилища **временные STS-данные** (с временем истечения)
3. Бэкенд возвращает временные данные фронтенду
4. Фронтенд с этими данными **напрямую загружает файл в объектное хранилище**
5. Объектное хранилище возвращает результат загрузки, фронтенд уведомляет бэкенд «загрузка завершена»

**Преимущества**:

- **Быстрая загрузка**: меньше промежуточных звеньев, ощущаемая пользователем скорость максимальна
- **Малая нагрузка на сервер**: только выдача учётных данных, без обработки потока файла
- **Экономия полосы**: трафик загрузки идёт лишь раз
- **Высокая безопасность**: у временных данных есть срок истечения, даже при утечке вред ограничен

**Недостатки**:

- Реализация чуть сложнее, нужно понимать STS, механизм подписи
- Фронтенду нужно реализовывать логику многочастной загрузки, докачки и т.п.
- Нужно настраивать кросс-доменность (CORS)

**Сценарий применения**: загрузка больших файлов, пользовательский контент (UGC), бизнес с высокой конкурентностью загрузок.

#### Способ третий: многочастная загрузка + докачка (необходимо для больших файлов)

```
10GB 视频文件
↓
切分成 1000 个 10MB 的分片
↓
并行上传（同时传 5 个分片）
↓
断网了！已传 600 个
↓
恢复网络，从第 601 个继续传
↓
所有分片传完，发起"合并"请求
```

**Зачем нужна многочастность?**

| Сценарий         | Без многочастности                  | С многочастностью                 |
| :----------- | :---------------------- | :------------------- |
| **Сетевые колебания** | Загрузил 99%, обрыв сети — полная перезагрузка | Перезагружаются только неудавшиеся части     |
| **Скорость загрузки** | Один поток, медленно          | Многопоточная параллельность, быстро   |
| **Использование памяти** | Нужно кэшировать весь файл        | Нужно кэшировать лишь текущую часть     |
| **Отображение прогресса** | Только 0% и 100%         | Точность до прогресса каждой части |

**Спецификации многочастности основных облачных провайдеров**:

| Провайдер           | Ограничение размера части | Макс. число частей | Мин. размер части |
| :------------- | :----------- | :--------- | :----------- |
| **Alibaba Cloud OSS** | 100 МБ        | 10000      | 100 КБ        |
| **Tencent Cloud COS** | 5 ГБ          | 10000      | 1 МБ           |
| **AWS S3**     | 5 ГБ          | 10000      | 5 МБ (рекомендуется)  |
| **Qiniu Cloud**     | 100 МБ        | 10000      | 4 МБ           |

### 3.2 Подробно о стратегии обращения CDN к источнику

<CachePolicyDemo />

#### Что такое «обращение к источнику»?

Граничный узел CDN кэширует контент источника, но когда:

- Контент, запрошенный пользователем, **запрашивается впервые**
- Кэшированный контент **истёк (истёк TTL)**
- Кэш **вручную обновлён/прогрет**

CDN-узлу нужно запросить свежий контент у **источника**, этот процесс и называется «обращением к источнику».

#### Три режима обращения к источнику

| Режим                  | Принцип                     | Сценарий применения                  | Плюсы и минусы                   |
| :-------------------- | :----------------------- | :------------------------ | :----------------------- |
| **Прямое обращение к источнику**          | CDN-узел → источник          | У источника есть публичный IP и небольшой трафик | Просто и прямо, но большая нагрузка на источник   |
| **Обращение через промежуточный источник**        | CDN-узел → промежуточный слой → источник | Крупный сайт, многоуровневая архитектура кэша    | Распределяет нагрузку на источник, сложная архитектура   |
| **OSS/COS как источник** | CDN-узел → объектное хранилище      | Статические ресурсы, картинки, видео      | Лучшая практика, низкая стоимость, хорошая производительность |

#### Практика настройки обращения к источнику

**Сценарий 1: объектное хранилище как источник (рекомендуется)**

```
用户访问：cdn.example.com/images/photo.jpg
                    ↓
            CDN 边缘节点（北京）
                    ↓
            未命中，回源到源站
                    ↓
            源站：bucket-name.oss-cn-beijing.aliyuncs.com
                    ↓
            返回图片，CDN 缓存并响应用户
```

Ключевые пункты настройки:

- **Тип источника**: домен OSS/COS или пользовательский источник
- **Протокол обращения к источнику**: HTTP или HTTPS (рекомендуется HTTPS)
- **HOST источника**: заголовок Host, используемый при обращении к источнику
- **SNI источника**: указание имени сервера при обращении к источнику по HTTPS

**Сценарий 2: балансировка нагрузки между несколькими источниками**

Когда один источник не справляется с нагрузкой от обращений, можно настроить несколько источников:

```
CDN 边缘节点
    ├─ 源站 A (权重 50%)
    ├─ 源站 B (权重 30%)
    └─ 源站 C (权重 20%)
```

Режим «основной-резервный»:

```
CDN 边缘节点
    ├─ 主源站 A (健康时全部流量)
    └─ 备源站 B (主源故障时切换)
```

#### Полоса обращения к источнику vs полоса CDN

Здесь есть легко путаемое понятие:

| Метрика             | Определение                    | Связь с тарификацией                     |
| :--------------- | :---------------------- | :--------------------------- |
| **Исходящая полоса CDN** | Трафик от CDN-узла к пользователю | Обычно плата за CDN по трафику    |
| **Полоса обращения к источнику**     | Трафик от источника к CDN-узлу | Обычно плата за исходящий трафик объектного хранилища или источника |

**Способы сэкономить**:

- Повысить коэффициент попаданий CDN (чтобы больше запросов попадало в кэш, уменьшая обращения к источнику)
- Установить разумное время кэширования (TTL)
- Использовать прогрев, чтобы закэшировать горячий контент до обращения пользователей
- Включить «следование за 301/302», чтобы избежать ненужных перенаправлений с обращением к источнику

### 3.3 Настройка стратегии кэширования

<CachePolicyDemo />

#### Ключ кэша (Cache Key): определяет, что считается «одним файлом»

Как CDN определяет, должны ли два запроса вернуть одну и ту же кэшированную копию? Именно через **ключ кэша**.

**Ключ кэша по умолчанию обычно включает**:

- Путь URL (без параметров запроса)
- Например: `/images/photo.jpg`

**Проблемный сценарий**:

```
用户 A 请求：/images/photo.jpg?w=100&h=100  (100x100 缩略图)
用户 B 请求：/images/photo.jpg?w=800&h=600  (800x600 大图)
```

Если ключ кэша включает только путь, две картинки разного размера будут считаться одним файлом, что приведёт к путанице.

**Решение: пользовательские правила ключа кэша**

| Правило                 | Пример                      | Эффект                      |
| :------------------- | :------------------------ | :------------------------ |
| **Сохранять указанные параметры запроса** | Сохранять `w`, `h`             | Разные размеры кэшируются отдельно          |
| **Сохранять все параметры запроса** | Сохранять все                  | Полностью точное совпадение              |
| **Игнорировать определённые параметры запроса** | Игнорировать `token`, `timestamp` | URL с временной меткой попадают в кэш |
| **Включать заголовки запроса**       | Включать `Accept-Language`    | Разные языки возвращают разный контент              |

**Пример практической настройки** (Alibaba Cloud CDN):

```
缓存键规则：
- URL 路径：/images/*
- 保留查询参数：w, h, format
- 忽略查询参数：token, timestamp, utm_source
```

#### Время кэширования (TTL): баланс «свежести» контента

TTL (Time To Live) определяет, как долго контент кэшируется на CDN-узле. Слишком короткое — много обращений к источнику, высокая стоимость; слишком длинное — после обновления контента пользователь видит старое.

**Рекомендации по установке TTL по типам файлов**:

| Тип файла    | Рекомендуемый TTL                | Причина                           |
| :---------- | :---------------------- | :----------------------------- |
| HTML-страница   | 0-5 минут                | Контент часто обновляется, нужна актуальность         |
| JS/CSS-файлы | 1 год (в сочетании с хешем в имени) | Контент не меняется, изменение имени файла означает инвалидацию кэша |
| Картинки/видео   | 7-30 дней                 | Низкая частота обновления, можно кэшировать надолго         |
| Файлы шрифтов    | 1 год                    | Почти не меняются                       |
| Ответ API    | 0-5 минут (по бизнесу)      | Высокие требования к актуальности данных               |

**Лучшая практика сочетания фронтенд-инженерии с CDN**:

```javascript
// webpack/vite 配置
output: {
  filename: 'js/[name]-[contenthash:8].js',
  chunkFilename: 'js/[name]-[contenthash:8].chunk.js',
}
```

Сгенерированное имя файла: `app-a3f2b1c9.js`

- Содержимое файла меняется → меняется хеш → новый URL → естественная инвалидация кэша
- Содержимое файла не меняется → хеш не меняется → URL не меняется → длительное попадание в кэш

#### Обновление и прогрев кэша

**Ручное обновление (экстренный сценарий)**:

Когда вы обновили контент источника, но кэш CDN ещё не истёк, и пользователь видит всё ещё старый контент:

| Тип обновления     | Эффект                   | Время        | Сценарий применения     |
| :----------- | :--------------------- | :---------- | :----------- |
| **Обновление URL** | Инвалидация кэша указанного URL    | 5-10 минут   | Обновление одного файла |
| **Обновление каталога** | Инвалидация всего контента указанного каталога | 10-30 минут  | Массовое обновление     |
| **Обновление всего сайта** | Инвалидация всего кэша всего домена | 30 минут и более | Экстренный откат     |

**Важное напоминание**: обновление лишь инвалидирует кэш, следующий запрос обратится к источнику за новым контентом. Не обновляйте массово в часы пик, иначе можно перегрузить источник.

**Прогрев (проактивная оптимизация)**:

Обновление пассивно (контент уже обновлён), прогрев активен (кэширование заранее).

```
场景：明天上午 10 点要发一篇爆款文章

今晚就提交预热请求：
- URL: https://cdn.example.com/articles/爆款文章.html
- 预热范围：全国所有边缘节点

效果：
明天 10 点用户访问时，内容已经在边缘节点等着了
→ 零回源延迟，秒开体验
```

### 4.1 Умная диспетчеризация DNS

Традиционное разрешение DNS:

```
用户问：cdn.example.com 的 IP 是什么？
DNS 答：1.2.3.4（固定的）
```

Умное разрешение DNS:

```
用户（北京联通）问：cdn.example.com 的 IP 是什么？
智能 DNS：让我查查... 北京联通的 CDN 节点是 1.2.3.4

用户（上海电信）问：cdn.example.com 的 IP 是什么？
智能 DNS：上海电信的 CDN 节点是 5.6.7.8
```

**Измерения диспетчеризации**:
| Измерение | Пояснение | Эффект |
| :--- | :--- | :--- |
| **Географическое положение** | Распределение по провинциям/городам/странам | Доступ к ближайшему, снижение задержки |
| **Оператор** | China Unicom/China Telecom/China Mobile/BGP | Передача в пределах одного оператора, избегание межсетевого трафика |
| **Нагрузка узла** | CPU/полоса/QPS в реальном времени | Обход перегруженных узлов |
| **Здоровье узла** | Зондирование доступности | Автоисключение неисправных узлов |
| **Фактор стоимости** | Разница цен на полосу | Баланс производительности и стоимости |

### 4.2 HTTP DNS и прямое подключение по IP

У традиционного DNS есть проблема: **перехват DNS и задержка разрешения**.

**Решение HTTP DNS**:

```
客户端 → 绕过系统 DNS → 直接问 HTTP DNS 服务（如 223.5.5.5:80）
         ↓
    返回最优 IP 列表（带权重）
         ↓
    客户端根据网络质量探测，选择最优 IP
```

Преимущества:

- Защита от перехвата: не идёт через DNS оператора
- Точнее: можно выбирать IP по качеству сети клиента
- Актуальность: переключение при сбое быстрее

**Практические рекомендации**:

- Для мобильных приложений настоятельно рекомендуется подключать HTTP DNS
- На веб-стороне можно использовать диспетчеризацию через CNAME, предоставляемую CDN
- Для критичного бизнеса можно сделать резервирование на нескольких IP (один домен возвращает несколько IP)

## 5. Оптимизация HTTPS: баланс безопасности и производительности

<HttpsOptimizationDemo />

### 5.1 Почему HTTPS на CDN так важен?

**Сравнение сценариев**:

```
无 HTTPS：
用户访问 http://cdn.example.com/image.jpg
↓
浏览器地址栏显示"不安全"
↓
某些浏览器/APP 直接拦截访问
↓
SEO 排名降低
```

```
有 HTTPS：
用户访问 https://cdn.example.com/image.jpg
↓
浏览器显示绿色锁标志
↓
HTTP/2 多路复用生效
↓
性能 + 安全双提升
```

### 5.2 Ключевые пункты настройки HTTPS на CDN

#### Управление сертификатами

| Решение                   | Пояснение                  | Стоимость           | Сценарий применения         |
| :--------------------- | :-------------------- | :------------- | :--------------- |
| **Бесплатный сертификат облачного провайдера**     | Предоставляют Alibaba Cloud/Tencent Cloud и др.   | Бесплатно           | Один домен, быстрый старт |
| **Let's Encrypt**      | Бесплатный сертификат сообщества          | Бесплатно           | Автоматизированное развёртывание       |
| **Коммерческий сертификат DV/OV/EV** | Symantec, GeoTrust и др. | ¥ от сотен до десятков тысяч/год | Корпоративный уровень, нужна зелёная строка |
| **Wildcard-сертификат**         | \*.example.com        | ¥ несколько тысяч/год      | Множество поддоменов         |

**Практические рекомендации**:

- Тестовая среда: Let's Encrypt или бесплатный сертификат облачного провайдера
- Продакшен-среда: wildcard-сертификат (удобно) или однодоменный OV-сертификат (экономно)
- Следите за сроком истечения сертификата, настройте напоминание об автопродлении

#### Настройка оптимизации HTTPS

**Выбор версии TLS**:

```
推荐配置：仅 TLS 1.2 和 TLS 1.3
兼容配置：TLS 1.1 + TLS 1.2 + TLS 1.3（兼容老旧浏览器）
```

**Наборы шифров**:

```
推荐：ECDHE 密钥交换 + AES-GCM 加密
禁用：DES、RC4、MD5、SHA1
```

**OCSP Stapling**:

```
功能：CDN 节点预获取证书吊销状态
效果：减少客户端验证时间 200-500ms
建议：务必开启
```

**Повторное использование сессии TLS**:

```
Session ID 复用：客户端带着上次 Session ID，服务端恢复会话
Session Ticket 复用：服务端把会话状态加密发给客户端，下次带来
效果：避免完整 TLS 握手，减少 1-RTT
```

### 5.3 Применение HTTP/2 и HTTP/3 на CDN

**Мультиплексирование HTTP/2**:

```
HTTP/1.1：
请求 1 (index.html) ────────────────→
响应 1 ←──────────────────────────────
请求 2 (style.css) ─────────────────→
响应 2 ←──────────────────────────────
请求 3 (script.js) ─────────────────→
响应 3 ←──────────────────────────────
（串行，一个完了下一个）

HTTP/2：
请求 1 ──→
请求 2 ──→   合并在一个 TCP 连接上，帧交错传输
请求 3 ──→
响应 1 ←──   按优先级流式返回
响应 2 ←──
响应 3 ←──
（并行，一个连接多路复用）
```

**Серверный push HTTP/2**:

```
场景：用户请求 index.html，里面引用了 style.css 和 script.js

传统方式：
1. 用户下载 index.html
2. 解析发现需要 style.css 和 script.js
3. 再发两个请求获取

HTTP/2 推送：
1. 用户请求 index.html
2. CDN 节点返回 index.html 的同时，主动推送 style.css 和 script.js
3. 用户解析 html 时，资源已经在缓存里了

注意：推送要谨慎，推多了浪费带宽，推少了没效果
```

**HTTP/3 (QUIC)**:

```
HTTP/2 的问题：基于 TCP，队头阻塞
→ 一个 TCP 包丢失，整个连接等待重传

HTTP/3 的解决：基于 QUIC（UDP 之上实现可靠传输）
→ 每个流独立，一个流阻塞不影响其他流
→ 连接迁移：WiFi 切 4G，连接不中断
→ 0-RTT 握手：第一次访问也能快速建立连接

现状：2024 年主流 CDN 已支持 HTTP/3，建议开启
```

## 6. Анализ доступа: разбираемся в отчётах CDN

<AccessAnalyticsDemo />

### 6.1 Расшифровка ключевых метрик

#### Полоса пропускания (Bandwidth)

```
定义：单位时间内传输的数据量
单位：bps（比特每秒）、Mbps、Gbps

CDN 带宽 = 所有边缘节点的出流量总和

注意区分：
- 计费带宽：通常按 95 峰值或日峰值计费
- 实际带宽：实时传输速率
```

**Связь полосы и трафика**:

```
1 Mbps 带宽持续跑 1 小时 = 450 MB 流量
（计算：1,000,000 bps × 3600s ÷ 8 ÷ 1024 ÷ 1024 ≈ 429 MB）
```

#### QPS (Queries Per Second)

```
定义：每秒查询/请求数

CDN QPS = 所有边缘节点每秒处理的 HTTP 请求总数

注意：QPS 高不代表带宽高
- 小文件场景：QPS 很高，带宽不高
- 大文件场景：QPS 不高，带宽很高
```

#### Коэффициент попаданий (Hit Ratio)

```
定义：在 CDN 边缘节点命中的请求占总请求的比例

计算公式：
命中率 = (命中数 / 总请求数) × 100%
或
命中率 = (1 - 回源流量 / 总出流量) × 100%

行业标准：
- 图片/视频/JS/CSS：> 95%
- HTML 页面：50-80%（视更新频率）
- API 接口：通常不缓存或极低
```

**Частые причины низкого коэффициента попаданий**:

| Причина           | Симптом               | Решение                 |
| :------------- | :----------------- | :----------------------- |
| Слишком короткое время кэша   | TTL всего несколько минут     | Скорректировать TTL по типу файла     |
| Изменяющиеся параметры запроса   | URL со случайным числом       | Настроить игнорирование определённых параметров         |
| Неправильная установка ключа кэша | Различается то, что не должно   | Оптимизировать правила ключа кэша           |
| Частое обновление контента   | Файл часто перезаписывается     | Использовать номер версии или хеш в имени файла |
| Много первых обращений     | Новый контент или новый узел     | Прогреть заранее                 |

### 6.2 Анализ логов и диагностика проблем

#### Разбор полей лога CDN

Типичный лог доступа CDN содержит следующие поля:

```
时间 | 客户端 IP | 请求方法 | URL | HTTP 状态码 | 响应大小 | 缓存状态 | 响应时间 | Referer | User-Agent

示例：
2024-01-15 14:32:01 | 114.114.114.114 | GET | https://cdn.example.com/images/photo.jpg | 200 | 153600 | HIT | 23 | https://example.com/ | Mozilla/5.0...
```

Пояснение ключевых полей:

| Поле            | Пояснение           | Аналитическая ценность                                     |
| :-------------- | :------------- | :------------------------------------------- |
| `cache_status`  | Статус кэша       | HIT (попадание), MISS (промах), EXPIRED (истёк) |
| `response_time` | Время отклика (мс) | Оценка пользовательского опыта, >500 мс требует оптимизации                  |
| `http_status`   | HTTP-код статуса    | Диагностика ошибок 404/500                             |
| `bytes_sent`    | Число отправленных байт     | Статистика полосы                                     |

#### Диагностика частых проблем

**Проблема 1: пользователи жалуются на медленный доступ**

Шаги диагностики:

```
1. 看日志 response_time
   - 如果很大（>500ms）：检查是缓存 MISS 还是源站慢

2. 检查 cache_status
   - HIT：缓存命中，慢可能是文件太大或节点问题
   - MISS：未命中，需优化缓存策略或命中率

3. 检查客户端 IP 分布
   - 某些地区慢：可能是该节点负载高或覆盖不足
```

**Проблема 2: кэш не действует, каждый раз обращение к источнику**

Чек-лист диагностики:

```
□ 源站响应头是否有 Cache-Control: no-cache / private？
□ URL 是否带随机参数（如 ?_=123456）？
□ 缓存键配置是否正确？
□ TTL 设置是否过短？
□ 是否命中浏览器本地缓存而非 CDN？
```

**Проблема 3: резкий рост расходов**

Направления диагностики:

```
1. 看账单明细
   - CDN 流量费高：检查是否有大文件被频繁访问，或被盗链
   - 回源流量费高：检查命中率是否骤降
   - 请求数费用高：检查是否有 CC 攻击或爬虫

2. 看访问日志
   - 是否有大量 404 请求（可能是扫描或配置错误）
   - Referer 是否异常（判断是否被盗链）

3. 安全设置
   - 开启防盗链（Referer 白名单）
   - 开启 IP 黑名单/白名单
   - 配置 CC 防护
```

- [ ] Не устанавливать приватные файлы на публичное чтение
- [ ] AccessKey не писать в коде фронтенда, использовать временные STS-данные

```javascript
/**
 * 对象存储直传工具类
 * 支持：阿里云 OSS、腾讯云 COS、AWS S3
 */
class DirectUploader {
  constructor(config) {
    this.provider = config.provider // 'oss' | 'cos' | 's3'
    this.region = config.region
    this.bucket = config.bucket
    this.getCredentials = config.getCredentials // 获取临时凭证的函数
  }

  /**
   * 获取 STS 临时凭证
   */
  async fetchCredentials() {
    // 向后端申请临时凭证
    const credentials = await this.getCredentials()
    return {
      accessKeyId: credentials.accessKeyId,
      accessKeySecret: credentials.accessKeySecret,
      sessionToken: credentials.securityToken || credentials.sessionToken,
      expiration: credentials.expiration
    }
  }

  /**
   * 生成上传签名（适用于前端计算签名）
   */
  generateSignature(credentials, fileKey, fileType, options = {}) {
    const timestamp = new Date().toISOString()
    const date = timestamp.slice(0, 10).replace(/-/g, '')

    // 不同厂商的签名算法略有差异
    switch (this.provider) {
      case 'oss':
        return this._ossSignature(credentials, fileKey, date, options)
      case 'cos':
        return this._cosSignature(credentials, fileKey, date, options)
      case 's3':
        return this._s3Signature(credentials, fileKey, date, options)
      default:
        throw new Error('Unknown provider')
    }
  }

  /**
   * 单文件上传（小文件 < 100MB）
   */
  async upload(file, options = {}) {
    const credentials = await this.fetchCredentials()
    const fileKey = this._generateFileKey(file, options.directory)

    const formData = new FormData()

    // 构建表单字段（不同厂商字段名不同）
    const formFields = this._buildFormFields(
      credentials,
      fileKey,
      file.type,
      options
    )
    Object.entries(formFields).forEach(([key, value]) => {
      formData.append(key, value)
    })

    formData.append('file', file)

    // 发送上传请求
    const uploadUrl = this._getUploadUrl()
    const response = await fetch(uploadUrl, {
      method: 'POST',
      body: formData,
      // 如果上传大文件，可能需要设置更长的超时
      signal: options.signal // 支持 AbortController 取消上传
    })

    if (!response.ok) {
      const errorText = await response.text()
      throw new Error(`Upload failed: ${response.status} ${errorText}`)
    }

    return {
      url: this._getFileUrl(fileKey),
      key: fileKey,
      etag: response.headers.get('ETag'),
      size: file.size
    }
  }

  /**
   * 分片上传（大文件 > 100MB）
   */
  async multipartUpload(file, options = {}) {
    const partSize = options.partSize || 10 * 1024 * 1024 // 默认 10MB/片
    const parallel = options.parallel || 3 // 默认 3 个并发

    const credentials = await this.fetchCredentials()
    const fileKey = this._generateFileKey(file, options.directory)

    // 1. 初始化分片上传
    const uploadId = await this._initMultipartUpload(
      credentials,
      fileKey,
      file.type
    )

    // 2. 计算分片
    const parts = []
    const totalParts = Math.ceil(file.size / partSize)
    for (let i = 0; i < totalParts; i++) {
      const start = i * partSize
      const end = Math.min(start + partSize, file.size)
      parts.push({
        number: i + 1,
        start,
        end,
        blob: file.slice(start, end)
      })
    }

    // 3. 上传分片（带并发控制和断点续传）
    const uploadedParts = []
    const failedParts = []

    // 支持断点续传：检查哪些分片已上传
    if (options.resume) {
      const existingParts = await this._listParts(
        credentials,
        fileKey,
        uploadId
      )
      for (const part of existingParts) {
        uploadedParts.push(part)
      }
    }

    // 过滤出未上传的分片
    const pendingParts = parts.filter(
      (p) => !uploadedParts.some((up) => up.partNumber === p.number)
    )

    // 并发上传
    const uploadPart = async (part) => {
      try {
        const etag = await this._uploadPart(
          credentials,
          fileKey,
          uploadId,
          part
        )
        return { partNumber: part.number, etag }
      } catch (error) {
        failedParts.push({ part, error })
        throw error
      }
    }

    // 使用 Promise.all 控制并发
    const chunks = []
    for (let i = 0; i < pendingParts.length; i += parallel) {
      chunks.push(pendingParts.slice(i, i + parallel))
    }

    for (const chunk of chunks) {
      const results = await Promise.allSettled(chunk.map(uploadPart))
      for (const result of results) {
        if (result.status === 'fulfilled') {
          uploadedParts.push(result.value)
        }
      }
    }

    // 检查是否所有分片都上传成功
    if (uploadedParts.length !== totalParts) {
      throw new Error(
        `Upload incomplete: ${uploadedParts.length}/${totalParts} parts uploaded`
      )
    }

    // 4. 完成分片上传（合并分片）
    await this._completeMultipartUpload(
      credentials,
      fileKey,
      uploadId,
      uploadedParts
    )

    return {
      url: this._getFileUrl(fileKey),
      key: fileKey,
      size: file.size,
      parts: totalParts
    }
  }

  /**
   * 生成文件存储路径
   */
  _generateFileKey(file, directory = '') {
    const date = new Date()
    const datePath = `${date.getFullYear()}/${String(date.getMonth() + 1).padStart(2, '0')}/${String(date.getDate()).padStart(2, '0')}`
    const random = Math.random().toString(36).substring(2, 10)
    const ext = file.name.split('.').pop() || 'bin'
    const key = directory
      ? `${directory}/${datePath}/${random}.${ext}`
      : `${datePath}/${random}.${ext}`
    return key
  }

  // ============ 各厂商特定方法 ============

  _getUploadUrl() {
    switch (this.provider) {
      case 'oss':
        return `https://${this.bucket}.oss-${this.region}.aliyuncs.com`
      case 'cos':
        return `https://${this.bucket}.cos.${this.region}.myqcloud.com`
      case 's3':
        return `https://${this.bucket}.s3.${this.region}.amazonaws.com`
      default:
        throw new Error('Unknown provider')
    }
  }

  _getFileUrl(key) {
    return `https://${this.bucket}.${this.provider === 'oss' ? 'oss' : 'cos'}-${this.region}.${
      this.provider === 'oss'
        ? 'aliyuncs.com'
        : this.provider === 'cos'
          ? 'myqcloud.com'
          : 'amazonaws.com'
    }/${key}`
  }

  // 各厂商的签名、分片上传等方法...（根据实际需求实现）
  _buildFormFields(credentials, fileKey, fileType, options) {
    // 各厂商表单字段构建逻辑
    // 这里需要根据具体厂商的文档实现
    return {}
  }

  async _initMultipartUpload(credentials, fileKey, fileType) {
    // 各厂商初始化分片上传逻辑
    return 'upload-id'
  }

  async _uploadPart(credentials, fileKey, uploadId, part) {
    // 各厂商分片上传逻辑
    return 'etag'
  }

  async _completeMultipartUpload(credentials, fileKey, uploadId, parts) {

  }

  async _listParts(credentials, fileKey, uploadId) {

  }
}
```

```javascript
/**
 * CDN 防盗链与安全配置示例
 */

// 1. Referer 防盗链（防止其他网站直接引用你的资源）
const refererConfig = {

  ],

  blockList: [

  allowEmptyReferer: false // 生产环境建议 false，测试环境可 true
}

// 2. URL 鉴权（更安全的防盗链，带时间戳和签名）
class URLAuth {
  constructor(config) {
    this.key = config.key // 鉴权密钥，只在服务端保存
    this.expireTime = config.expireTime || 3600 // 默认 1 小时有效期
  }

  /**
   * 生成带鉴权的 URL
   * @param {string} url - 原始 URL，如 https://cdn.example.com/images/photo.jpg
   * @param {number} expireIn - 有效期（秒）
   * @returns {string} 带鉴权参数的 URL
   */
  sign(url, expireIn = this.expireTime) {
    const urlObj = new URL(url)
    const pathname = urlObj.pathname
    const timestamp = Math.floor(Date.now() / 1000) + expireIn

    // 构造签名字符串（不同厂商格式不同，这里是通用示例）
    const signStr = `${pathname}-${timestamp}-${this.key}`
    const signature = this._md5(signStr)

    // 添加鉴权参数
    urlObj.searchParams.set('sign', signature)
    urlObj.searchParams.set('t', timestamp.toString())

    return urlObj.toString()
  }

  /**
   * 验证 URL 签名（在 CDN 边缘或源站使用）
   */
  verify(url) {
    const urlObj = new URL(url)
    const signature = urlObj.searchParams.get('sign')
    const timestamp = parseInt(urlObj.searchParams.get('t'))
    const pathname = urlObj.pathname

    // 检查是否过期
    if (timestamp < Math.floor(Date.now() / 1000)) {
      return { valid: false, error: 'URL expired' }
    }

    // 验证签名
    const signStr = `${pathname}-${timestamp}-${this.key}`
    const expectedSign = this._md5(signStr)

    if (signature !== expectedSign) {
      return { valid: false, error: 'Invalid signature' }
    }

    return { valid: true }
  }

  _md5(str) {
    // 实际项目中使用 crypto-js 或其他 MD5 库
    // 这里仅作示例
    return require('crypto').createHash('md5').update(str).digest('hex')
  }
}

// 使用示例
const auth = new URLAuth({
  key: 'your-secret-key-only-known-by-server',
  expireTime: 3600 // 1 小时有效期
})

// 服务端生成带签名的 URL
const signedUrl = auth.sign(
  'https://cdn.example.com/private/document.pdf',
  7200
)
// 结果：https://cdn.example.com/private/document.pdf?sign=xxxxx&t=1699123456

// CDN 边缘或源站验证
const result = auth.verify(signedUrl)
if (!result.valid) {
  // 返回 403 Forbidden
}
```

| **Origin**                 | Источник              | Сервер, у которого CDN получает контент при обращении к источнику, может быть объектным хранилищем, ECS или собственным сервером.                                         |
| **Cache Hit**              | Попадание в кэш          | Контент, запрошенный пользователем, уже есть на граничном узле CDN, возвращается напрямую без обращения к источнику.                                            |
| **Cache Miss**             | Промах кэша        | На граничном узле нет запрошенного контента, нужно обратиться к источнику.                                                               |
| **Hit Ratio**              | Коэффициент попаданий            | Доля числа попаданий в кэш от общего числа запросов. Чем выше коэффициент попаданий, тем меньше обращений к источнику и ниже стоимость.                                     |
| **TTL**                    | Время жизни/время кэширования | Time To Live, срок действия кэша контента на CDN-узле. После истечения нужно повторно обратиться к источнику.                                    |
| **Back to Source**         | Обращение к источнику              | Процесс запроса контента граничным узлом CDN у источника.                                                                   |
| **Purge/Refresh**          | Обновление кэша          | Принудительная инвалидация кэша CDN, следующий запрос обращается к источнику за свежим контентом.                                                      |
| **Preheat**                | Прогрев              | До официального выпуска активное проталкивание контента на CDN-узлы, чтобы пользователь при первом обращении попал в кэш.                              |
| **CORS**                   | Совместное использование ресурсов между источниками      | Cross-Origin Resource Sharing, механизм безопасности браузера, контролирующий доступ к ресурсам между разными доменами.                          |
| **Referer**                | Страница-источник          | Поле заголовка HTTP-запроса, указывающее, с какой страницы пришёл запрос. Используется для защиты от хотлинкинга.                                        |
| **STS**                    | Сервис токенов безопасности      | Security Token Service, сервис выдачи временных учётных данных доступа, используется в сценариях прямой загрузки фронтендом и др.                                 |
| **Multipart Upload**       | Многочастная загрузка          | Разбиение большого файла на несколько мелких частей и их параллельная загрузка, с поддержкой докачки, для повышения эффективности и надёжности загрузки.                               |
| **ETag**                   | Тег сущности          | Заголовок HTTP-ответа, идентифицирующий определённую версию ресурса, часто используется для валидации кэша.                                                |
| **S3 API**                 | S3-совместимый интерфейс       | Спецификация API объектного хранилища AWS S3, с которой совместимо объектное хранилище большинства облачных провайдеров.                                       |
| **Canonical Query String** | Канонизированная строка запроса    | Часть строки подписи, используемая для вычисления подписи запроса, гарантирующая, что запрос не был подменён.                                             |

## Заключение: золотое правило объектного хранилища + CDN

1. **Загрузка через прямую загрузку**: большие файлы — через многочастность, безопасность — через STS
2. **Кэширование многоуровневое**: браузер -> CDN -> источник, слой за слоем кэш
3. **Обслуживание пользователя поблизости**: умный DNS + глобальное покрытие узлами
4. **Безопасность без послаблений**: HTTPS + защита от хотлинкинга + контроль доступа
5. **Затраты нужно мониторить**: коэффициент попаданий, полоса, уровневое хранилище, постоянная оптимизация

Эта архитектура держит на себе подавляющую часть доступа к статическим ресурсам в интернете, поняв её, вы поймёте краеугольный камень оптимизации производительности современного веба.
