## 0. Введение: вывод системы в онлайн — это только начало

Многие новички считают: «Код развёрнут и выведен в онлайн — задача выполнена.»

**Большая ошибка!**

Вывод системы в онлайн — лишь **отправная точка работы по эксплуатации**. Как с покупкой новой машины — последующее обслуживание, ремонт, заправка и есть норма.

У эксплуатации три цели:

1. **Стабильность (Stability)**: система не падает, сервис постоянно доступен
2. **Производительность (Performance)**: быстрый отклик, хороший пользовательский опыт
3. **Безопасность (Security)**: данные не утекают, защита от атак

## 1. Система мониторинга (Monitoring)

Мониторинг — это «глаза» эксплуатации. Система без мониторинга похожа на слепого за рулём — даже когда возникает проблема, об этом неизвестно.

### 1.1 Три уровня мониторинга

<MonitoringDashboardDemo />

**Мониторинг инфраструктуры**: внимание к аппаратным ресурсам сервера

- Загрузка CPU
- Использование памяти
- Дисковое пространство и I/O
- Сетевая полоса пропускания

**Мониторинг приложения**: внимание к состоянию работы ПО

- QPS (число запросов в секунду)
- Время отклика (задержка)
- Частота ошибок
- Состояние вызовов зависимых сервисов

**Мониторинг бизнеса**: внимание к здоровью бизнеса

- DAU/MAU (дневная/месячная активность)
- Число заказов
- Доля успешных платежей
- Удержание пользователей

### 1.2 Стек инструментов мониторинга

| Инструмент           | Назначение           | Особенности                     |
| :------------- | :------------- | :----------------------- |
| **Prometheus** | Сбор и хранение метрик | База данных временных рядов, подходит для данных мониторинга |
| **Grafana**    | Панели визуализации     | Мощные графики и dashboard   |
| **Zabbix**     | Комплексный мониторинг       | Проверенный временем инструмент, всесторонний функционал       |
| **Datadog**    | SaaS-платформа мониторинга  | Универсальное решение, платное     |

**Ключевой момент**: мониторинг должен быть многоуровневым, всесторонне покрывая всё от инфраструктуры до бизнеса, избегая «слепых зон».

## 2. Система оповещений (Alerting)

После того как мониторинг обнаружил проблему, нужно своевременно уведомить персонал эксплуатации — это и есть **оповещение**.

### 2.1 Процесс оповещения

<AlertFlowDemo />

### 2.2 Проектирование уровней оповещений

Разумная классификация оповещений позволяет избежать «усталости от оповещений»:

| Уровень   | Время реагирования        | Типичный сценарий                   | Канал уведомления           |
| :----- | :-------------- | :------------------------- | :----------------- |
| **P0** | Немедленно (в течение 5 минут) | Отказ ключевого сервиса, сбой оплаты     | Звонок + SMS + DingTalk |
| **P1** | В течение 30 минут        | Сбой части функций, серьёзное падение производительности | SMS + DingTalk + email |
| **P2** | В тот же день        | Повышенная загрузка ресурсов, единичные ошибки   | DingTalk + email        |
| **P3** | В течение недели        | Неключевые проблемы, рекомендации по оптимизации       | Email               |

### 2.3 Свёртка оповещений и снижение шума

**Боль**: одна мелкая проблема может вызвать сотни и тысячи оповещений, из-за чего дежурный теряет чувствительность.

**Решение**:

1. **Группировка оповещений**: объединение похожих оповещений (например, несколько проблем одного сервера объединяются в одно)
2. **Подавление оповещений**: если родительская проблема уже сработала, по дочерним проблемам оповещение не дублируется
3. **Правила тишины**: автоматическая приостановка оповещений во время обслуживания
4. **Ограничение частоты**: одно и то же оповещение не дублируется за короткий промежуток времени

**Ключевой момент**: оповещений должно быть «мало, но по делу», каждое должно быть достойно обработки.

## 3. Управление логами (Logging)

Логи — это «чёрный ящик» для диагностики проблем.

### 3.1 Уровни логов

```javascript
console.debug('详细调试信息') // 开发时使用
console.info('一般信息') // 正常流程记录
console.warn('警告信息') // 潜在问题
console.error('错误信息') // 需要关注的错误
```

### 3.2 Структурированные логи

Традиционный лог (плохо):

```
2024-01-15 10:23:45 ERROR User john failed to login, attempts=3, ip=192.168.1.100
```

Структурированный лог (рекомендуется):

```json
{
  "timestamp": "2024-01-15T10:23:45Z",
  "level": "ERROR",
  "message": "User login failed",
  "user": "john",
  "attempts": 3,
  "ip": "192.168.1.100",
  "service": "auth-service"
}
```

### 3.3 Стек логов ELK

**ELK = Elasticsearch + Logstash + Kibana**

- **Logstash**: сбор и фильтрация логов
- **Elasticsearch**: хранение и поиск логов
- **Kibana**: визуальный запрос логов

**Лучшие практики**:

- ✅ Чувствительную информацию (пароли, token) не записывать в логи
- ✅ Ключевые операции (вход, оплата, изменение прав) обязательно фиксировать
- ✅ Логи должны содержать контекст (ID пользователя, ID запроса, временную метку)
- ✅ Регулярно очищать устаревшие логи во избежание переполнения диска

## 4. Трассировка (Tracing)

В микросервисной архитектуре один запрос может пройти через десяток сервисов — как отследить его полный путь?

**Trace ID и Span ID**

- **Trace ID**: уникальный идентификатор всей цепочки запроса (как номер посылки)
- **Span ID**: идентификатор отдельного вызова сервиса (как каждый перевалочный пункт)

### 4.1 Демонстрация распределённой трассировки

<TraceVisualizationDemo />

### 4.2 Стандарт OpenTelemetry

OpenTelemetry (OTel) — **отраслевой стандарт** трассировки, предоставляющий единый API и SDK.

```javascript
// 示例：使用 OpenTelemetry 记录 Span
import { trace } from '@opentelemetry/api'

const tracer = trace.getTracer('my-service')

async function processOrder(orderId) {
  // 创建一个 Span
  const span = tracer.startSpan('processOrder')

  try {
    // 设置属性
    span.setAttribute('order.id', orderId)

    // 业务逻辑...
    await validateOrder(orderId)
    await saveToDatabase(orderId)

    span.setStatus({ code: SpanStatusCode.OK })
  } catch (error) {
    span.recordException(error)
    span.setStatus({ code: SpanStatusCode.ERROR, message: error.message })
  } finally {
    span.end() // 结束 Span
  }
}
```

**Ключевой момент**: трассировка позволяет быстро локализовать узкие места производительности и точки сбоев, это обязательный инструмент микросервисов.

## 5. Процесс диагностики неполадок

Сбои на продакшене неизбежны, главное — **быстро реагировать, быстро восстанавливаться**.

### 5.1 Процесс обработки сбоя

<IncidentResponseDemo />

### 5.2 Часто используемые инструменты диагностики

| Инструмент         | Назначение         | Типичный сценарий                 |
| :----------- | :----------- | :----------------------- |
| **tcpdump**  | Анализ захвата пакетов     | Нет связи в сети, потеря пакетов     |
| **strace**   | Трассировка системных вызовов | Зависание процесса, проблема прав файла   |
| **Arthas**   | Диагностика Java    | Скачок CPU, утечка памяти, взаимоблокировка |
| **top/htop** | Мониторинг системных ресурсов | Высокая загрузка CPU/памяти           |
| **netstat**  | Просмотр сетевых соединений | Занятость порта, аномальное число соединений     |
| **lsof**     | Просмотр открытых файлов | Файл занят, диск полон       |

**Пример Arthas** (open-source инструмент диагностики Java от Alibaba):

```bash
# 查看某个方法的调用耗时
$ trace com.example.OrderService createOrder

# 查看类的静态字段
$ getstatic com.example.Config MAX_CONNECTIONS

# 热更新代码（无需重启）
$ mc /tmp/Test.java
$ redefine /tmp/Test.class
```

### 5.3 Разбор сбоя (Post-mortem)

**Разбор — это не собрание для поиска виноватых!**

Цели разбора:

1. Восстановить таймлайн сбоя
2. Найти первопричину (Root Cause Analysis)
3. Подытожить извлечённые уроки
4. Разработать меры по улучшению

**Метод анализа 5 Why**:

Спрашивайте «почему» минимум 5 раз, чтобы найти первопричину:

- Почему сервис упал?
  - Потому что переполнение памяти
- Почему переполнение памяти?
  - Потому что слишком много данных в кэше
- Почему слишком много данных в кэше?
  - Потому что не задано время истечения
- Почему не задано время истечения?
  - Потому что упустили при разработке
- **Первопричина**: отсутствие ревью кода и тестовых сценариев

**Ключевой момент**: формируйте культуру blameless, уделяйте внимание улучшению процессов, а не персональной ответственности.

## 6. Оптимизация производительности

### 6.1 Анализ узких мест производительности

**Подход к оптимизации сверху вниз**:

```
Восприятие пользователя
  ↓
Оптимизация фронтенда (сокращение запросов, CDN, ленивая загрузка)
  ↓
Оптимизация сети (HTTP/2, сжатие, долгие соединения)
  ↓
Оптимизация бэкенда (кэш, асинхронность, пакетная обработка)
  ↓
Оптимизация базы данных (индексы, оптимизация запросов, шардирование)
  ↓
Оптимизация системы (параметры ядра, тюнинг JVM)
```

### 6.2 Оптимизация базы данных

**Оптимизация индексов**:

```sql
-- 查询慢（无索引）
SELECT * FROM orders WHERE user_id = 12345;

-- 创建索引后快 100 倍
CREATE INDEX idx_user_id ON orders(user_id);
```

**Оптимизация запросов**:

```sql
-- ❌ 避免 SELECT *
SELECT * FROM users WHERE id = 123;

-- ✅ 只查需要的字段
SELECT id, name, email FROM users WHERE id = 123;

-- ❌ 避免 IN 子句太多
SELECT * FROM orders WHERE user_id IN (1, 2, 3, ..., 10000);

-- ✅ 使用 JOIN 或批量查询
SELECT * FROM orders o JOIN user_ids u ON o.user_id = u.id;
```

### 6.3 Оптимизация кэширования

**Архитектура многоуровневого кэша**:

```
Кэш браузера (CDN)
  ↓
Локальный кэш (память/Guava)
  ↓
Распределённый кэш (Redis/Memcached)
  ↓
База данных (MySQL/PostgreSQL)
```

**Стратегии обновления кэша**:

| Стратегия              | Преимущества         | Недостатки         | Сценарий применения                 |
| :---------------- | :----------- | :----------- | :----------------------- |
| **Cache-Aside**   | Просто, надёжно   | Медленный первый запрос   | Много чтения, мало записи                 |
| **Write-Through** | Хорошая согласованность данных | Медленная запись       | Сбалансированные чтение/запись                 |
| **Write-Behind**  | Очень быстрая запись     | Возможна потеря данных | Много записи, мало чтения, допустимо кратковременное рассогласование |

**Ключевой момент**: кэш — не серебряная пуля, нужно учитывать вопросы согласованности, лавины, пробоя и др. (см. главу «Проектирование системного кэша»).

```yaml
kind: HorizontalPodAutoscaler

  name: my-app-hpa
```

## 8. Эксплуатация с точки зрения безопасности

### 8.1 Контроль доступа

**Принцип минимальных привилегий**:

- Разработчики могут обращаться только к среде разработки
- Персонал эксплуатации может обращаться только к продакшен-среде, и требуется согласование
- Чувствительные операции с базой данных требуют повторного подтверждения

**Бастион-хост (Jump Server)**:

Все операции эксплуатации выполняются через бастион-хост с полной записью журнала операций.

### 8.2 Резервное копирование данных

**Принцип резервирования 3-2-1**:

- **3** копии данных (1 оригинал + 2 резервных)
- **2** разных носителя хранения (локальный диск + облачное хранилище)
- **1** удалённая резервная копия (защита от катастрофы в единой точке)

**Стратегия резервного копирования**:

| Тип         | Частота | Срок хранения | RTO    | RPO     |
| :----------- | :--- | :------- | :----- | :------ |
| **Полное резервное копирование** | Еженедельно | 1 месяц   | 4 часа | 24 часа |
| **Инкрементальное резервное копирование** | Ежедневно | 1 неделя     | 2 часа | 1 час  |
| **Резервное копирование в реальном времени** | Посекундно | 7 дней     | Минуты | Секунды    |

**RTO (Recovery Time Objective)**: целевое время восстановления (как долго сервис может быть прерван максимум)
**RPO (Recovery Point Objective)**: целевая точка восстановления (сколько данных можно потерять максимум)

### 8.3 Сканирование уязвимостей

**Регулярное сканирование**:

- **Сканирование кода**: SonarQube, ESLint (обнаружение потенциальных уязвимостей)
- **Сканирование зависимостей**: npm audit, Snyk (обнаружение уязвимостей сторонних библиотек)
- **Сканирование контейнеров**: Trivy, Clair (обнаружение уязвимостей образов)

```bash

$ npm audit

lodash          high      <4.17.21
express         moderate  4.0.0 - 4.18.2

# 自动修复

```

## 9. Автоматизация эксплуатации (DevOps)

### 9.1 Пайплайн CI/CD

```yaml
# .gitlab-ci.yml 示例
stages:
  - test
  - build
  - deploy

test:
  stage: test
  script:
    - npm install
    - npm test
  tags:
    - docker

build:
  stage: build
  script:
    - docker build -t myapp:$CI_COMMIT_SHA .
    - docker push registry.example.com/myapp:$CI_COMMIT_SHA
  only:
    - main

deploy:
  stage: deploy
  script:
    - kubectl set image deployment/myapp myapp=registry.example.com/myapp:$CI_COMMIT_SHA
  environment:
    name: production
  when: manual # 手动触发部署
```

### 9.2 Инфраструктура как код (IaC)

**Пример Terraform** (управление облачными ресурсами):

```hcl
# main.tf
resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"

  tags = {
    Name = "WebServer"
    Env  = "production"
  }
}

resource "aws_security_group" "web" {
  name = "web-sg"

  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
```

**Преимущества**:

- ✅ Версионирование: вся конфигурация в Git
- ✅ Воспроизводимость: согласованность сред
- ✅ Аудируемость: ясная история изменений
- ✅ Возможность отката: быстрое восстановление к предыдущей версии

### 9.3 Практика GitOps

**GitOps = Git + IaC + Automation**

Ключевая идея: **Git-репозиторий — единственный источник истины об инфраструктуре**

Рабочий процесс:

```
1. Изменить файл конфигурации (push в Git)
   ↓
2. Изменение в Git-репозитории запускает CI/CD
   ↓
3. Автоматическое выполнение terraform apply/kubectl apply
   ↓
4. Инфраструктура автоматически обновляется
   ↓
5. Мониторинг сравнивает фактическое состояние с желаемым
```

**Инструменты**: ArgoCD, Flux (развёртывание в Kubernetes)

## 10. Заключение и лучшие практики

Эксплуатация — это обширная система, но её суть можно резюмировать так:

### 10.1 Модель зрелости эксплуатации

| Уровень     | Характеристика               | Практики                           |
| :------- | :----------------- | :----------------------------- |
| **Начальный** | Пассивное реагирование, ручные операции | Реакция только при проблеме, ручное развёртывание         |
| **Средний** | Автоматизация, стандартизация     | CI/CD, мониторинг и оповещения, документирование        |
| **Высокий** | Упор на предотвращение, самовосстановление     | Планирование ёмкости, учения по сбоям, автомасштабирование |
| **Экспертный** | Интеллектуализация, без дежурного   | AIOps, хаос-инжиниринг, Serverless    |

### 10.2 Один день инженера эксплуатации

```
09:00 - Просмотр ночных оповещений, проверка состояния системы
10:00 - Обработка проблем из обратной связи пользователей
11:00 - Участие в еженедельном собрании разработки, оценка эксплуатационных рисков нового решения
14:00 - Оптимизация медленных запросов, повышение производительности
15:00 - Ревью кода (Code Review)
16:00 - Написание документации по развёртыванию, обновление правил мониторинга
17:00 - Учения по сбоям (Chaos Engineering)
18:00 - Передача дежурства
```

### 10.3 Путь обучения

**Начальный этап** (1-3 месяца):

- Освоить часто используемые команды Linux
- Познакомиться с системой мониторинга (Prometheus + Grafana)
- Освоить запросы логов (ELK)

**Продвинутый этап** (3-6 месяцев):

- Глубоко понять технологию контейнеров (Docker + K8s)
- Освоить один инструмент диагностики (Arthas, tcpdump)
- Практиковать пайплайн CI/CD

**Высокий этап** (6-12 месяцев):

- Тюнинг производительности (база данных, JVM, сеть)
- Планирование ёмкости и оптимизация расходов
- Разбор сбоев и улучшение процессов

**Экспертный этап** (более 1 года):

- Проектирование архитектуры (высокая доступность, аварийное восстановление)
- Хаос-инжиниринг (активное внедрение сбоев)
- AIOps (интеллектуальная эксплуатация)

## 11. Краткий справочник терминов (Glossary)

| Термин            | Полное название                              | Пояснение                                           |
| :-------------- | :-------------------------------- | :--------------------------------------------- |
| **Monitoring**  | -                                 | Мониторинг, наблюдение за состоянием работы системы в реальном времени.                   |
| **Alerting**    | -                                 | Оповещение, уведомление соответствующего персонала при аномалии.                     |
| **Logging**     | -                                 | Логирование, запись событий в процессе работы системы.               |
| **Tracing**     | -                                 | Трассировка, отслеживание полного пути запроса в распределённой системе.   |
| **QPS**         | Queries Per Second                | Число запросов в секунду, мера пропускной способности системы.                   |
| **Latency**     | -                                 | Задержка, время от отправки запроса до отклика.                 |
| **RTO**         | Recovery Time Objective           | Целевое время восстановления, как долго сервис может быть прерван максимум.               |
| **RPO**         | Recovery Point Objective          | Целевая точка восстановления, сколько данных можно потерять максимум.                 |
| **Post-mortem** | -                                 | Разбор сбоя, анализ причин сбоя и мер по улучшению.             |
| **CI/CD**       | Continuous Integration/Delivery   | Непрерывная интеграция и непрерывная поставка, автоматизация тестирования и развёртывания.         |
| **IaC**         | Infrastructure as Code            | Инфраструктура как код, управление серверами, сетью и другими ресурсами через код. |
| **GitOps**      | -                                 | Git-эксплуатация, Git-репозиторий — единственный источник истины об инфраструктуре.   |
| **ELK**         | Elasticsearch + Logstash + Kibana | Тройка для сбора, хранения, визуализации логов.                 |
| **SLA**         | Service Level Agreement           | Соглашение об уровне обслуживания, обещанная доступность сервиса (например, 99,9%).   |
| **Blameless**   | -                                 | Культура без обвинений, разбор уделяет внимание улучшению процессов, а не персональной ответственности.     |
