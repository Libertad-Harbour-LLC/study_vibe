# Оркестрация Kubernetes

::: tip Предисловие
**Docker решил проблему «упаковки», Kubernetes решает проблему «управления».** Когда у вас есть десятки или сотни контейнеров, которые нужно разворачивать, масштабировать и восстанавливать после сбоев, управлять ими вручную нереально. Kubernetes (K8s) — это «операционная система» для контейнеров, она автоматизирует развёртывание, масштабирование и эксплуатацию контейнеризированных приложений.
:::

**Чему вас научит эта статья?**

- **Декларативное управление**: поймёте идею «объявить желаемое состояние — система сама к нему сходится»

## 1. Зачем нужен Kubernetes?

Docker упростил упаковку и запуск отдельного контейнера, но когда вы сталкиваетесь со следующими сценариями, ручное управление становится непосильным:

| Вызов | Описание | Решение K8s |
|------|------|---------------|
| Развёртывание множества экземпляров | Одному сервису нужно запустить 10 реплик | Deployment автоматически управляет числом реплик |
| Восстановление после сбоев | Упавший контейнер нужно автоматически перезапустить | Контроллер автоматически обнаруживает и пересоздаёт Pod |
| Обнаружение сервисов | IP контейнеров меняются, как найти друг друга? | Service предоставляет стабильные DNS и IP |
| Плавающее обновление | При обновлении версии нельзя останавливать сервис | Постепенная замена старых Pod, без простоя |
| Эластичное масштабирование | Автоматическое расширение при пиках трафика | HPA автоматически корректирует число реплик по CPU/памяти |
| Планирование ресурсов | Разместить контейнеры на самых подходящих машинах | Scheduler выполняет интеллектуальное планирование |

::: tip Ключевая идея K8s: декларативность
Вам не нужно говорить K8s «запусти 3 контейнера» (императивно), вы говорите ему «я хочу, чтобы работало 3 реплики» (декларативно). K8s непрерывно ведёт мониторинг, гарантируя, что фактическое состояние совпадает с объявленным желаемым. Если Pod упадёт, он автоматически создаст новый на замену.
:::

## 4. Декларативное управление и kubectl

### Цикл управления (Reconciliation Loop)

Основной механизм работы K8s — цикл управления:

```
Наблюдение (Observe) → Сравнение (Diff) → Действие (Act) → Наблюдение...
     ↓                ↓              ↓
  Чтение факт. сост.  Сравнение с желаемым  Выполнение коррекции
```

Вы объявляете `replicas: 3`, контроллер обнаруживает, что работают только 2 Pod, и создаёт 1 новый. Этот цикл выполняется каждые несколько секунд, гарантируя, что система всегда сходится к желаемому состоянию.

### Часто используемые команды kubectl

| Команда | Действие | Пример |
|------|------|------|
| `kubectl apply -f` | Применить YAML-конфигурацию | `kubectl apply -f deployment.yaml` |
| `kubectl get` | Просмотреть список ресурсов | `kubectl get pods -o wide` |
| `kubectl describe` | Просмотреть детали ресурса | `kubectl describe pod my-app-xxx` |
| `kubectl logs` | Просмотреть логи Pod | `kubectl logs -f my-app-xxx` |
| `kubectl exec` | Войти в терминал Pod | `kubectl exec -it my-app-xxx -- sh` |
| `kubectl delete` | Удалить ресурс | `kubectl delete -f deployment.yaml` |
| `kubectl scale` | Ручное масштабирование | `kubectl scale deploy my-app --replicas=5` |

::: tip apply vs create
`kubectl create` — императивная команда: «создай этот ресурс», и если он уже существует — будет ошибка. `kubectl apply` — декларативная: «обеспечь, чтобы ресурс был в этом состоянии», если его нет — создаст, если есть — обновит. В продакшене всегда следует использовать `apply`.
:::

## 5. Практика эксплуатации

### 5.1 Плавающие обновления и откат

Deployment по умолчанию использует стратегию плавающего обновления: постепенно создаёт Pod новой версии, одновременно постепенно завершая Pod старой версии.

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # максимум создать на 1 Pod больше
      maxUnavailable: 0   # не допускать недоступных Pod
```

| Операция | Команда |
|------|------|
| Обновить образ | `kubectl set image deploy/my-app app=my-app:2.0` |
| Просмотреть статус обновления | `kubectl rollout status deploy/my-app` |
| Просмотреть историю версий | `kubectl rollout history deploy/my-app` |
| Откатиться к предыдущей версии | `kubectl rollout undo deploy/my-app` |

### 5.2 Автомасштабирование (HPA)

HPA (Horizontal Pod Autoscaler) автоматически корректирует число реплик Pod на основе CPU, памяти или пользовательских метрик.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: my-app-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

### 5.3 Проверки здоровья (Probe)

K8s контролирует состояние здоровья Pod через три вида проб:

| Проба | Действие | Последствие сбоя |
|------|------|---------|
| livenessProbe | Проверяет, жив ли контейнер | Перезапуск контейнера |
| readinessProbe | Проверяет, готов ли контейнер | Исключается из Service, трафик не принимает |
| startupProbe | Проверяет, завершился ли запуск контейнера | Во время запуска другие пробы не выполняются |

::: tip Важность проб
Для Pod без настроенных проверок здоровья K8s может судить о состоянии только по наличию процесса. Но часто процесс ещё работает, а сервис уже не отвечает (например, взаимоблокировка, грань OOM). Настройка livenessProbe позволяет K8s автоматически перезапускать такие «зависшие» контейнеры.
:::

## Заключение

Kubernetes — де-факто стандарт оркестрации контейнеров, и понимание его ключевых концепций является основой облачно-нативной разработки.

Вспомним ключевые моменты этой главы:

1. **Декларативное управление**: сообщайте K8s «что мне нужно», а не «как это сделать», цикл управления сходится автоматически
2. **Слоистая архитектура**: плоскость управления принимает решения, рабочие узлы выполняют, etcd хранит состояние
3. **Ключевые ресурсы**: Pod (минимальная единица), Deployment (управление репликами), Service (обнаружение сервисов), Ingress (внешний вход)
4. **Автоматизация эксплуатации**: плавающие обновления без простоя, эластичное масштабирование HPA, автоматическое восстановление после сбоев через пробы
5. **Разделение конфигурации**: ConfigMap и Secret отделяют конфигурацию от образа
