# Балансировка нагрузки и шлюз
::: tip 🎯 Ключевой вопрос
**Когда один сервер не справляется, как «умно» распределить трафик на несколько экземпляров серверов?** Балансировка нагрузки — это «распределитель» современных распределённых систем. В этой статье через реальные примеры (касса в чайной, сортировка посылок, регулирование дорожного движения) глубоко разбираются философия проектирования балансировки нагрузки и инженерная практика.
:::

---

## 1. Зачем нужна «балансировка нагрузки»?

### 1.1 Начнём с реального примера: эволюция архитектуры одного сайта

Один стартап при быстром росте числа пользователей столкнулся с серьёзными проблемами производительности:

**Восстановление сценария:**

```
Этап 1: один сервер
Пользователь → сервер (1 ядро, 2 ГБ)
       ↓
  DAU 1000 → в часы активности: 1000 человек обращаются одновременно
       ↓
Проблема: CPU 100%, медленный отклик, частые падения
```

::: warning ⚠️ Фатальные проблемы одного сервера

- **Узкое место производительности**: CPU 100%, время отклика > 5 секунд
- **Единая точка отказа**: упал сервер — весь сайт недоступен
- **Сложность расширения**: только вертикальное обновление (добавить CPU, память), дорого и ограниченно
  :::

**Архитектура после улучшения (внедрение балансировки нагрузки):**

```
Этап 2: несколько серверов + балансировка нагрузки
Пользователь → балансировщик нагрузки (Nginx)
       ↓
     ├→ сервер 1 (1 ядро, 2 ГБ)
     ├→ сервер 2 (1 ядро, 2 ГБ)
     └→ сервер 3 (1 ядро, 2 ГБ)
```

::: tip ✨ Эффект после улучшения

- **Рост производительности**: 3 сервера обрабатывают параллельно, время отклика < 1 секунды
- **Высокая доступность**: упал 1 сервер — остальные продолжают обслуживать
- **Горизонтальное масштабирование**: нужно больше производительности? Просто добавить сервер
  :::

### 1.2 Бытовая аналогия балансировки нагрузки

**Касса в чайной**

Представьте, что вы открыли популярную чайную:

- **1 касса**: посетители стоят в очереди, задние не дожидаются — плохой отзыв
- **3 кассы**: сотрудники распределяют посетителей по разным кассам, эффективность выросла в 3 раза

**Балансировка нагрузки — это «распределитель по кассам»**:

- **Пользователь** (посетитель) → запрашивает услугу
- **Балансировщик нагрузки** (распределитель) → распределяет запросы по разным серверам
- **Сервер** (касса) → обрабатывает запрос

## 2. Что такое балансировка нагрузки?

### 2.1 Балансировка нагрузки уровня L4: смотрит только на номер дома

**Работает на транспортном уровне (TCP/UDP)** — как курьер, который смотрит только на **номер дома (IP-адрес + номер порта)**, не интересуясь, что у вас происходит дома.

**Особенности:**

- **Сверхвысокая скорость**: выполняет только простое перенаправление адреса, не разбирая содержимое пакетов
- **Сценарии применения**: подключения к базам данных, кэш Redis, игровые серверы с долгими соединениями
- **Представители**: LVS (Linux Virtual Server), AWS NLB, Azure Load Balancer

::: details Принцип работы

```
Запрос клиента → балансировщик L4 → бэкенд-сервер
              ↓
         смотрит только IP + Port
              ↓
         быстрое перенаправление (без разбора содержимого)
```

:::

### 2.2 Балансировка нагрузки уровня L7: проверяет содержимое посылки

**Работает на прикладном уровне (HTTP/HTTPS)** — как курьер, который не только смотрит на номер дома, но и **вскрывает посылку, чтобы проверить содержимое**, и по содержимому решает, как доставить.

**Особенности:**

- **Умная маршрутизация**: можно выполнять тонкую маршрутизацию по пути URL, HTTP-заголовкам, Cookie и т.п.
- **Продвинутые функции**: разгрузка SSL, кэширование контента, сжатие, безопасность WAF
- **Сценарии применения**: веб-приложения, API-шлюзы, микросервисная архитектура
- **Представители**: Nginx, HAProxy, AWS ALB, Envoy

::: details Принцип работы

```
Запрос клиента → балансировщик L7 → разбор содержимого HTTP
              ↓
         проверка URL, Header, Cookie
              ↓
         умная маршрутизация на конкретный сервер
```

:::

### 2.3 Сравнение L4 vs L7 одним взглядом

| Параметр           | Балансировка L4     | Балансировка L7          |
| :------------- | :------------------- | :------------------------ |
| **Уровень работы**   | Транспортный (TCP/UDP)      | Прикладной (HTTP/HTTPS)        |
| **Основа решения**   | IP-адрес + порт      | URL, Header, Cookie, Body |
| **Скорость обработки**   | Очень высокая (обработка в режиме ядра)     | Высокая (разбор в пользовательском режиме)          |
| **Богатство функций** | Базовое перенаправление             | Разгрузка SSL, кэш, сжатие, WAF  |
| **Типичные сценарии**   | БД, игры, долгие соединения | Веб-приложения, API-шлюз, микросервисы  |
| **Представители**   | LVS, AWS NLB         | Nginx, HAProxy, AWS ALB   |

## 3. Ключевой вопрос первый: как не дать «сломанному» серверу продолжать принимать клиентов?

### 3.1 Проверка здоровья: не позволяйте «больному» серверу тормозить систему

Представьте, что одна из ваших касс внезапно сломалась, но распределитель этого не знает и продолжает непрерывно направлять туда посетителей. В итоге очередь всё длиннее, посетители недовольны.

**Проверка здоровья (Health Check) — это «часовой», предотвращающий такую ситуацию**. Она периодически «обследует» каждый сервер, при обнаружении «больного» немедленно убирает его из очереди, а после «выздоровления» возвращает обратно.

### 3.2 Активная проверка здоровья vs пассивная проверка здоровья

**Активная проверка здоровья (Active Health Check)**: балансировщик нагрузки сам «стучится» к серверу с вопросом «ты ещё на месте?»

- Периодически отправляет зондирующие запросы (например, HTTP /health, TCP ping)
- При таймауте отклика или возврате кода ошибки считает сервер нездоровым
- **Преимущество**: точный и надёжный результат проверки
- **Недостаток**: создаёт дополнительный зондирующий трафик

**Пассивная проверка здоровья (Passive Health Check)**: балансировщик «наблюдает» за откликом на реальный бизнес-трафик

- Подсчитывает время отклика и частоту ошибок реальных запросов
- При нескольких подряд неудачах считает сервер нездоровым
- **Преимущество**: не создаёт дополнительного трафика
- **Недостаток**: требует достаточной выборки трафика для вынесения решения

::: details Таблица установки пороговых значений
| Метрика | Здоровый порог | Нездоровый порог | Пояснение |
|:---|:---|:---|:---|
| **HTTP-код статуса** | 200-399 | 400+ или таймаут | 4xx/5xx считаются неудачей |
| **TCP-соединение** | Успешно установлено | Таймаут соединения | Проверка доступности порта |
| **Время отклика** | < 500 мс | > 2000 мс | Таймаут обычно устанавливается в 2-5 секунд |
| **Число подряд неудач** | - | 3 раза | Избегание ошибочного решения из-за единичного дребезга |
| **Интервал проверки** | - | 5 с | Слишком частая проверка увеличивает нагрузку |

::: tip 💡 Частая ловушка: слишком «чувствительная» установка порога
Одна команда установила порог времени отклика проверки здоровья в 100 мс, тогда как среднее время отклика их приложения колебалось в пределах 80-120 мс. В результате серверы часто помечались как «нездоровые», из-за чего трафик постоянно метался между здоровым и нездоровым состоянием, а общая доступность системы наоборот падала.

**Правильный подход**: порог следует устанавливать в **2-3 раза больше времени отклика P99**, оставляя достаточный запас для нормальных колебаний.
:::

## 4. Ключевой вопрос второй: как гарантировать, что «постоянный клиент» всегда попадает к одному «кассиру»?

### 4.1 Привязка к сессии: пусть «постоянный клиент» всегда попадает к одному «кассиру»

Представьте, что вы постоянный клиент чайной, и каждый раз вас обслуживает один и тот же сотрудник. Он знает ваши вкусовые предпочтения (половина сахара, без льда) и обслуживает быстро и заботливо. Но если каждый раз будет новый человек, вам придётся снова и снова повторять одни и те же требования, эффективность сильно падает.

**Привязка к сессии (Session Persistence/Sticky Session)** — это метод решения этой проблемы: гарантировать, что запросы одного пользователя всегда маршрутизируются на один бэкенд-сервер.

<SessionPersistenceDemo />

### 4.2 Сравнение трёх механизмов привязки к сессии

| Механизм           | Принцип реализации                                  | Преимущества                            | Недостатки                          | Сценарий применения                |
| :------------- | :---------------------------------------- | :------------------------------ | :---------------------------- | :---------------------- |
| **Вставка Cookie** | LB вставляет Cookie в ответ, последующие запросы несут этот Cookie | Не зависит от смены IP, привязка с первого запроса | Клиент должен поддерживать Cookie, может быть отключён | Корзина e-commerce, сохранение состояния входа  |
| **IP-hash**     | Вычисление хеша по IP клиента, отображение на конкретный сервер     | Не требует поддержки клиента, без состояния           | При смене IP сессия теряется, сложно равномерно распределить | Среда без Cookie, WebSocket |
| **Таблица липких сессий** | LB поддерживает таблицу отображения сессии на сервер                | Поддержка репликации сессий и отказоустойчивости          | Занимает память LB, требует дополнительной синхронизации       | Сценарии со строгими требованиями к высокой доступности    |

::: tip 💡 Рекомендации по применению

- **Вставка Cookie**: рекомендуется в первую очередь, хорошая совместимость
- **IP-hash**: использовать только в особых сценариях, таких как WebSocket
- **Таблица липких сессий**: в сочетании с Cookie обеспечивает отказоустойчивость
  :::

## 5. Ключевой вопрос третий: как реализовать развёртывание без простоя?

### 5.1 Сине-зелёное развёртывание: выкат без простоя с «переключением в один клик»

**Ключевая идея**: одновременно поддерживать две полностью идентичные продакшен-среды (синюю и зелёную), но обслуживание наружу ведёт только одна среда.

<BlueGreenDeploymentDemo />

**Рабочий процесс:**

1. **Начальное состояние**: синяя среда работает на v1.0 (продакшен), зелёная среда в резерве.
2. **Развёртывание новой версии**: в зелёной среде разворачивается v1.1, проводится внутреннее дымовое тестирование.
3. **Переключение трафика**: балансировщик направляется на зелёную среду, трафик мгновенно переключается на v1.1.
4. **Мониторинг и наблюдение**: наблюдение за состоянием зелёной среды, подтверждение отсутствия аномалий.
5. **Сохранение старой версии**: синяя среда какое-то время (например, 24 часа) остаётся на v1.0 как страховка для быстрого отката.

::: tip ✨ Анализ преимуществ и недостатков
| Преимущества | Недостатки |
|:---|:---|
| ✅ Нулевой простой, переключение происходит за миллисекунды | ❌ Высокая стоимость ресурсов, нужно одновременно поддерживать две среды |
| ✅ Быстрый откат, при обнаружении проблемы немедленный возврат в исходную среду | ❌ При изменении схемы БД нужна особая обработка совместимости |
| ✅ Новую среду можно полностью протестировать перед приёмом трафика | ❌ Не подходит для сервисов с состоянием (например, долгие соединения WebSocket) |

:::

### 5.2 Канареечный выкат: стратегия «маленькими шагами быстрого бега»

Канареечный выкат получил название от исторической «шахтной канарейки» — шахтёры брали с собой в шахту канарейку, и если канарейка проявляла признаки недомогания, значит, происходила утечка ядовитого газа, и шахтёры немедленно эвакуировались. В выпуске ПО канареечный выкат — это когда сначала новой версией пользуется небольшая часть пользователей, и только после подтверждения отсутствия проблем масштаб постепенно расширяется.

<CanaryReleaseDemo />

**Ключевая идея:**

1. **Малый трафик идёт первым**: сначала 1% трафика направляется на серверы новой версии.
2. **Наблюдение за метриками**: непрерывный мониторинг частоты ошибок, задержки, ключевых бизнес-метрик.
3. **Постепенное увеличение объёма**: если всё нормально, доля постепенно повышается до 5%, 10%, 25%, 50%, 100%.
4. **Быстрый откат**: при обнаружении аномалии весь трафик немедленно возвращается на старую версию.

::: tip 💡 Преимущества канареечного выката
| Преимущество | Пояснение |
|:---|:---|
| 🎯 **Контролируемый риск** | Даже при серьёзном баге в новой версии затронуто лишь небольшое число пользователей |
| 📊 **Реальная проверка** | Проверка в реальной продакшен-среде надёжнее тестовой среды |
| 🚀 **Быстрая итерация** | Команда может увереннее часто выпускать новые функции |
| 💰 **Бережно к ресурсам** | Не нужно готовить две полные среды, как при сине-зелёном развёртывании |

:::

## 6. Ключевой вопрос четвёртый: как заставить систему «дышать» самой?

### 6.1 Автомасштабирование: пусть система составляет «гибкий график» как ресторан

Представьте, что вы открыли ресторан:

- **Пик обеда**: нужно 10 официантов, но в затишье в 3 часа дня хватает 2
- Если постоянно держать 10\*\*: расходы на персонал взрываются
- Если постоянно держать только 2: в пик посетители не дожидаются и все разбегаются

**Автомасштабирование (Auto Scaling)** — это когда система составляет «гибкий график» как ресторан: в загруженное время автоматически добавляет серверы, в затишье автоматически убавляет.

### 6.2 Выбор метрик масштабирования

Суть автомасштабирования — ответить на один вопрос: \*\* **когда добавлять машины? когда убавлять машины?**

Распространённые метрики для принятия решения:

| Метрика                | Порог расширения   | Порог сжатия   | Сценарий применения         |
| :------------------ | :--------- | :--------- | :--------------- |
| **Загрузка CPU**       | > 70%      | < 30%      | Вычислительно ёмкие приложения   |
| **Использование памяти**      | > 75%      | < 40%      | Приложения, ёмкие по памяти   |
| **QPS (запросов в секунду)** | > 1000/с   | < 400/с    | API-шлюз, веб-сервис |
| **Число соединений**          | > 5000     | < 1000     | БД, очередь сообщений |
| **Пользовательская бизнес-метрика**  | По ситуации | По ситуации | Специфические бизнес-сценарии     |

::: tip 💡 «Ловушки» и «решения» стратегии масштабирования

**Ловушка 1: слишком медленная реакция расширения, пик трафика уже снёс систему**

Во время крупной распродажи e-commerce было установлено срабатывание расширения при CPU > 80%, но сбор метрик мониторинга имел задержку в 1 минуту, а запуск нового экземпляра занимал 3 минуты. В итоге трафик пришёл слишком быстро, расширение ещё не завершилось, а серверы уже снесло.

**Решение:**

- **Заблаговременное расширение**: прогнозируя пик трафика по историческим данным, начинать расширение за 30 минут
- **Многоуровневые пороги**: установить предупреждение при 60% (начало прогрева новых экземпляров), официальное расширение при 70%, экстренное расширение при 80%
- **Быстрое расширение**: использовать контейнерное развёртывание, новый экземпляр запускается за 30 секунд (по сравнению с 3-5 минутами у виртуальной машины)

**Ловушка 2: слишком агрессивное расширение, расходы взрываются**

Один стартап установил агрессивную стратегию автомасштабирования: расширение уже при CPU > 50%. В итоге обычное бизнес-колебание вызвало расширение, число серверов раздулось с 5 до 30, а в конце месяца облачный счёт довёл CTO до слёз.

**Решение:**

- **Установить время охлаждения расширения**: после одного расширения подождать минимум 5 минут перед следующим
- **Установить максимальное число экземпляров**: max = текущее число экземпляров × 2, чтобы предотвратить бесконечное раздувание
- **Различать всплеск и тренд**: расширять только при превышении порога в течение 3 циклов подряд, избегая срабатывания от единичного всплеска

**Ловушка 3: слишком быстрое сжатие, только что добавленные машины сразу убираются**

Одна команда установила сжатие при CPU < 30%. После расширения трафик ещё переваривался, CPU кратковременно упал до 25% и вызвал сжатие. Только сжали — CPU снова взлетел до 80% и снова вызвал расширение — система бешено колеблется в режиме «расширение-сжатие-расширение».

**Решение:**

- **Более консервативное сжатие**: порог расширения 70%, порог сжатия 25%, между ними достаточный буфер
- **Более долгое время охлаждения сжатия**: после расширения подождать минимум 10 минут перед сжатием
- **Постепенное сжатие**: убирать по 1 машине за раз, после наблюдения решать, продолжать ли сжатие
  :::

## 7. Практика: как выбрать балансировщик нагрузки?

### 7.1 Сравнение основных балансировщиков нагрузки

| Характеристика           | Nginx                           | HAProxy               | Envoy          | Балансировщик облачного провайдера |
| -------------- | ------------------------------- | --------------------- | -------------- | -------------- |
| **Позиционирование**       | Высокопроизводительный обратный прокси/балансировщик         | Open-source балансировщик          | Cloud-native прокси     | Управляемый балансировщик   |
| **Производительность**       | Очень высокая (язык C, событийная модель)            | Высокая (событийная модель)          | Высокая (C++/Rust)   | Очень высокая           |
| **Богатство функций** | Базовая балансировка, статические файлы, кэш    | Богатый набор алгоритмов балансировки    | Продвинутая маршрутизация, наблюдаемость | Полнофункциональный |
| **Конфигурация**       | Файл конфигурации (nginx.conf)            | Файл конфигурации (haproxy.cfg) | API/файл конфигурации   | UI-консоль   |
| **Расширение**       | C-модули/Lua-скрипты                   | Lua-скрипты               | WASM/Filter    | Плагины           |
| **Сценарий применения**   | Статические ресурсы, балансировка L7, SSL-терминация | Балансировка L7, высокая доступность  | Service mesh, мульти-облако | Быстрый старт   |

::: tip 💡 Рекомендации по выбору
**Дерево решений:**

```
Выбор балансировщика нагрузки:
│
├─ Нужна только базовая балансировка L4?
│  ├─ Да → LVS (open-source, бесплатно) или NLB облачного провайдера
│  └─ Нет → продолжить
│
├─ Нужны service mesh, мульти-облачное развёртывание?
│  ├─ Да → Envoy
│  └─ Нет → продолжить
│
├─ Нужна чрезвычайно сложная конфигурация и плагины?
│  ├─ Да → HAProxy
│  └─ Нет → продолжить
│
├─ Нужна высокая производительность + простая конфигурация?
│  ├─ Да → Nginx (предпочтительно)
│  └─ продолжить
│
├─ Хотите управляемую эксплуатацию?
│  ├─ Да → балансировщик облачного провайдера (AWS ALB, Alibaba SLB)
│  └─ Nginx своими силами
```

:::

## 8. Заключение: ключевое мышление балансировки нагрузки

### 8.1 Обзор ключевых принципов

| Принцип     | Смысл                       | Ключевые моменты практики                              |
| -------- | -------------------------- | ------------------------------------- |
| **Многоуровневость** | L4 обрабатывает «сортировку посылок» (быстро, но просто) | L4 обрабатывает БД, игры; L7 обрабатывает Web, API     |
| **Избыточность** | Единая точка отказа — враг архитектуры       | Повышение доступности через несколько экземпляров и регионов      |
| **Постепенность** | Не выпускать новую версию «одним махом»     | Сине-зелёное развёртывание даёт нулевой простой; канареечный — контролируемый риск |
| **Эластичность** | Система должна «дышать» как живой организм | В загрузку автоматически расширяться, в затишье сжиматься             |

### 8.2 Чек-лист проектирования

Перед внедрением балансировки нагрузки задайте себе следующие вопросы:

- [ ] Действительно ли нужна балансировка нагрузки? (Действительно ли не хватает производительности одной машины)
- [ ] Выбрать L4 или L7? (По бизнес-сценарию)
- [ ] Как обрабатывать привязку к сессии? (Cookie, IP-hash, таблица сессий)
- [ ] Как реализовать проверку здоровья? (Активная, пассивная, установка порога)
- [ ] Как реализовать нулевой простой? (Сине-зелёное развёртывание, канареечный выкат)
- [ ] Как реализовать эластичность? (Метрики масштабирования, время охлаждения, максимальное число экземпляров)

## 9. Краткий справочник терминов

| Термин             | По-английски                                      | Пояснение                                                                 |
| ---------------- | ----------------------------------------- | -------------------------------------------------------------------- |
| **Балансировщик нагрузки**   | Load Balancer                             | Устройство или ПО, распределяющее трафик на несколько бэкенд-серверов                               |
| **Балансировка L4** | L4 Load Balancing                         | Балансировка нагрузки на транспортном уровне (TCP/UDP)                                        |
| **Балансировка L7** | L7 Load Balancing                         | Балансировка нагрузки на прикладном уровне (HTTP/HTTPS)                                     |
| **Проверка здоровья**     | Health Check                              | Механизм периодической проверки состояния здоровья бэкенд-серверов                                   |
| **Привязка к сессии**     | Session Persistence                       | Гарантия, что запросы одного пользователя всегда маршрутизируются на один сервер                             |
| **Липкая сессия**     | Sticky Session                            | Другое название, то же, что Session Persistence                                    |
| **Сине-зелёное развёртывание**     | Blue-Green Deployment                     | Стратегия выката без простоя с переключением двух сред                                         |
| **Канареечный выкат**   | Canary Release                            | Стратегия постепенного выката с предварительной проверкой на малом трафике                                         |
| **Автомасштабирование**   | Auto Scaling                              | Автоматическое увеличение или уменьшение числа серверов в зависимости от нагрузки                                     |
| **Горизонтальное масштабирование**     | Horizontal Scaling                        | Увеличение числа серверов для повышения обрабатывающей способности                                         |
| **Вертикальное масштабирование**     | Vertical Scaling                          | Повышение конфигурации одной машины (CPU, память) для повышения обрабатывающей способности                                |
| **Несколько регионов**       | Multi-Region                              | Развёртывание сервиса в нескольких географических регионах                                               |
| **Active-Active**         | Active-Active                             | Несколько регионов одновременно обслуживают наружу                                             |
| **Active-Standby**         | Active-Standby                            | Обслуживает только один регион, остальные в резерве                                       |
| **Синхронизация данных**     | Data Replication                          | Механизм репликации данных между регионами                                                 |
| **RTO**          | Recovery Time Objective (RTO)             | Целевое время восстановления — за какое время система должна восстановиться после сбоя                         |
| **RPO**          | Recovery Point Objective (RPO)            | Целевая точка восстановления — допустимый объём потери данных после сбоя системы                           |
