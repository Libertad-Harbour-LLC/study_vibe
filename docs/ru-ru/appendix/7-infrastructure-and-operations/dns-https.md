# Доменные имена, DNS и HTTPS

::: tip Предисловие
**Когда вы вводите в браузере `www.google.com` и нажимаете Enter, что происходит за кулисами?** За этим, казалось бы, простым действием стоит целая серия точно скоординированных процессов: разрешение доменного имени, DNS-запрос, TLS-рукопожатие с шифрованием. Понимание этих механизмов — обязательный предмет для каждого разработчика, ведь от них напрямую зависит, будет ли доступен ваш сайт и не будут ли украдены данные.
:::

- **Механизм HTTPS**: поймёте, как TLS-рукопожатие устанавливает защищённое соединение
- **Система сертификатов**: узнаете о цепочке доверия цифровых сертификатов и механизме проверки
- **Осознание безопасности**: уясните, почему HTTPS — минимальное требование современного веба

## 0. Общая картина: от доменного имени к защищённому соединению

Связь в интернете основана на IP-адресах (например, 142.250.80.46), но люди не могут запомнить эти числа. Поэтому мы изобрели **систему доменных имён (DNS)** — «телефонную книгу» интернета, переводящую читаемые человеком доменные имена в читаемые машиной IP-адреса.

Но одного лишь нахождения сервера недостаточно. Если содержимое связи передаётся открытым текстом, любой посредник может подслушать и подменить ваши данные. **HTTPS** и решает эту проблему — он добавляет поверх HTTP слой TLS-шифрования, обеспечивая конфиденциальность и целостность данных в процессе передачи.

::: tip Полный визит на веб-страницу
1. **Разрешение доменного имени**: браузер спрашивает у DNS «какой IP у www.google.com?», DNS отвечает «142.250.80.46»
2. **TCP-соединение**: браузер и сервер устанавливают тройное TCP-рукопожатие
3. **TLS-рукопожатие**: стороны согласуют алгоритм шифрования, проверяют сертификат, обмениваются ключами
4. **Шифрованная связь**: все данные HTTP передаются через шифрованный канал
:::

## 1. Разрешение DNS: «телефонная книга» интернета

Принцип работы DNS (Domain Name System) похож на поиск в телефонной книге: вы знаете имя собеседника (доменное имя) и вам нужно найти его номер телефона (IP-адрес). Но «телефонная книга» интернета — это не одна книга, а иерархическая распределённая система.

<DnsResolutionDemo />

::: tip Четыре шага разрешения DNS
1. **Кэш браузера**: сначала проверяется локальный кэш, и если этот домен посещался ранее, напрямую используется кэшированный IP
2. **Рекурсивный резолвер**: при промахе кэша запрос отправляется рекурсивному резолверу ISP (например, 8.8.8.8)
3. **Пошаговый запрос**: рекурсивный резолвер последовательно опрашивает корневой DNS-сервер → сервер домена верхнего уровня (.com) → авторитетный DNS-сервер (google.com)
4. **Возврат результата**: авторитетный сервер возвращает итоговый IP, рекурсивный резолвер кэширует результат и возвращает браузеру
:::

| Уровень | Сервер | Ответственность | Количество |
|------|-------|------|------|
| Корневой домен | Root Server | Знает адреса всех доменов верхнего уровня | 13 групп по миру |
| Домен верхнего уровня | TLD Server | Управляет .com, .cn, .org и т.п. | По одной группе на суффикс |
| Авторитетный домен | Authoritative | Хранит DNS-записи конкретного домена | Минимум 2 на домен |
| Рекурсивный резолвер | Resolver | Выполняет весь процесс запроса вместо пользователя | ISP или публичный DNS |

## 2. Типы DNS-записей: «таблица настроек» за доменным именем

DNS не только переводит доменное имя в IP. С помощью разных типов DNS-записей вы можете управлять доставкой почты, переадресацией домена, обнаружением сервисов и другими действиями. Понимание этих типов записей — основа настройки доменов и диагностики сетевых проблем.

<DnsRecordTypeDemo />

| Тип записи | Назначение | Пример |
|---------|------|------|
| A | Домен → IPv4-адрес | `example.com → 93.184.216.34` |
| AAAA | Домен → IPv6-адрес | `example.com → 2606:2800:220:1:...` |
| CNAME | Домен → другой домен (псевдоним) | `www.example.com → example.com` |
| MX | Указание почтового сервера | `example.com → mail.example.com` |
| TXT | Хранение текстовой информации | SPF-проверка, подтверждение владения доменом |
| NS | Указание авторитетного DNS-сервера | `example.com → ns1.example.com` |

::: tip Настройка DNS в реальных сценариях
- **Развёртывание сайта**: добавить запись A, указывающую на IP сервера, или CNAME, указывающую на домен CDN
- **Настройка почты**: добавить запись MX, указывающую на почтовый сервер, запись TXT для настройки SPF/DKIM против спама
- **Подтверждение владения доменом**: облачный провайдер требует добавить определённую запись TXT, чтобы доказать, что вы владеете доменом
- **Балансировка нагрузки**: для одного домена настроить несколько записей A, DNS распределяет трафик по кругу
:::

## 3. HTTPS и TLS: облачаем данные в «бронежилет»

Данные протокола HTTP передаются открытым текстом — как открытка, содержимое которой почтальон (посредник) может свободно прочитать. HTTPS добавляет поверх HTTP слой TLS-шифрования (Transport Layer Security), что равносильно тому, чтобы вложить открытку в запечатанный конверт.

TLS-рукопожатие — ключевой шаг установления защищённого соединения, оно выполняет аутентификацию и согласование ключей перед собственно передачей данных.

<HttpsHandshakeDemo />

::: tip Ключевые шаги рукопожатия TLS 1.3
1. **Client Hello**: клиент отправляет список поддерживаемых алгоритмов шифрования и случайное число
2. **Server Hello**: сервер выбирает алгоритм шифрования, возвращает цифровой сертификат и случайное число
3. **Проверка сертификата**: клиент проверяет, можно ли доверять сертификату сервера (проверка подписи CA, срока действия, соответствия домена)
4. **Обмен ключами**: стороны согласуют общий ключ через алгоритм ECDHE (сам ключ по сети не передаётся)
5. **Шифрованная связь**: все последующие данные передаются зашифрованными согласованным симметричным ключом
:::

| Характеристика | TLS 1.2 | TLS 1.3 |
|------|---------|---------|
| Число циклов рукопожатия | 2-RTT | 1-RTT (первый раз) / 0-RTT (возобновление) |
| Обмен ключами | RSA или ECDHE | Только ECDHE (прямая секретность) |
| Алгоритмы шифрования | Поддержка многих старых алгоритмов | Только безопасные алгоритмы |
| Производительность | Медленнее | Быстрее |

## 4. Цепочка доверия сертификатов: почему вообще доверять этому сайту?

Самый важный шаг в TLS-рукопожатии — «проверка сертификата». Как браузер определяет, что сертификат сайта настоящий, а не подделан злоумышленником? Ответ — **цепочка доверия сертификатов**, система доверия с послойным поручительством.

<CertificateChainDemo />

::: tip Трёхуровневая структура цепочки доверия сертификатов
1. **Корневой сертификат (Root CA)**: выдан доверенным центром сертификации, предустановлен в операционной системе и браузере. Это «якорь» доверия.
2. **Промежуточный сертификат (Intermediate CA)**: выдан корневым CA, используется для выдачи конечных сертификатов. Корневой CA не выдаёт сертификаты сайтов напрямую — это сделано для изоляции в целях безопасности.
3. **Конечный сертификат (Leaf Certificate)**: сертификат, фактически используемый вашим сайтом, выдан промежуточным CA, содержит доменное имя, публичный ключ, срок действия и другую информацию.
:::

| Тип сертификата | Уровень проверки | Скорость выдачи | Сценарий применения |
|---------|---------|---------|---------|
| DV (проверка домена) | Только проверка владения доменом | Минуты | Личный сайт, блог |
| OV (проверка организации) | Проверка личности организации | Несколько дней | Корпоративный сайт |
| EV (расширенная проверка) | Строгая проверка организации | Несколько недель | Банки, финансовые учреждения |
| Wildcard-сертификат | Покрывает все поддомены | Зависит от типа | Сценарии с множеством поддоменов |

## 5. HTTP vs HTTPS: почему шифрование — минимальный порог?

В 2024 году более 95% веб-трафика в мире уже передаётся через HTTPS. Браузер Chrome помечает HTTP-сайты предупреждением «небезопасно», поисковые системы также понижают рейтинг HTTP-сайтов. HTTPS уже не «опция», а минимальное требование современного веба.

<DnsHttpsComparisonDemo />

| Параметр | HTTP | HTTPS |
|------|------|-------|
| Передача данных | Открытый текст, можно подслушать | Шифрование, подслушать невозможно |
| Аутентификация | Нет, невозможно подтвердить личность сервера | Есть, проверка сервера через сертификат |
| Целостность данных | Без защиты, можно подменить | С защитой, подмена будет обнаружена |
| Порт | 80 | 443 |
| Влияние на SEO | Понижение в поиске | Бонус к рейтингу в поиске |
| Поведение браузера | Показывает предупреждение «небезопасно» | Показывает иконку замка |

::: tip Бесплатное получение HTTPS-сертификата
**Let's Encrypt** — бесплатный автоматизированный центр сертификации, позволяющий любому сайту включить HTTPS с нулевыми затратами. В сочетании с инструментом Certbot можно в один клик запросить и автоматически продлевать сертификат. Большинство облачных платформ и CDN-провайдеров также предоставляют бесплатные SSL-сертификаты.
:::

## Заключение

Доменные имена, DNS и HTTPS — три главных столпа инфраструктуры интернета. DNS позволяет нам обращаться к сайтам по читаемым человеком именам, HTTPS обеспечивает безопасность и доверие в процессе связи.

Вспомним ключевые моменты этой главы:

1. **DNS — иерархическая система**: корневой домен → домен верхнего уровня → авторитетный домен, пошаговый запрос, кэш для ускорения
2. **У каждого типа записей своё назначение**: запись A указывает на IP, CNAME делает псевдоним, MX управляет почтой, TXT — проверкой
3. **TLS-рукопожатие устанавливает доверие**: проверка сертификата + согласование ключей, TLS 1.3 требует лишь 1-RTT
4. **Цепочка доверия сертификатов**: корневой CA → промежуточный CA → конечный сертификат, послойное поручительство
5. **HTTPS — минимальный порог**: бесплатные сертификаты (Let's Encrypt) делают шифрование без барьеров
