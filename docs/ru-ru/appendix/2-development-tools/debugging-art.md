# Искусство отладки

::: tip Предисловие
**Код написан, при запуске возникает ошибка — а дальше что?** Многие новички застревают именно на этом шаге, тупо глядя в экран и не зная, что делать. Отладка (Debug) — один из важнейших навыков в программировании, возможно, даже более важный, чем само написание кода. Ведь написание кода занимает лишь 30% времени разработки, а остальные 70% уходят на понимание проблемы, локализацию багов и проверку исправлений.
:::

**Чему научит вас эта статья?**

После этой главы вы получите:

- **Мышление отладчика**: выстроите системный метод локализации проблем и перестанете «гадать»
- **Умение читать ошибки**: научитесь понимать сообщения об ошибках и быстро находить проблему по стеку ошибок
- **Распространённые методы отладки**: освоите классические приёмы — метод деления пополам, «резиновая уточка», минимальное воспроизведение
- **Умение пользоваться инструментами**: познакомитесь со сценариями применения точек останова, логирования, сетевой отладки
- **Отладка с помощью AI**: научитесь ускорять отладку с помощью AI, но не зависеть от него

| Глава | Содержание | Ключевые понятия |
|-----|------|---------|
| **Глава 1** | Читаем сообщения об ошибках | Типы ошибок, трассировка стека |
| **Глава 2** | Классические методы отладки | Деление пополам, резиновая уточка, минимальное воспроизведение |
| **Глава 3** | Набор инструментов для отладки | Точки останова, логи, перехват сетевого трафика |
| **Глава 4** | Отладка в эпоху AI | AI-помощь + человеческое суждение |
| **Глава 5** | Настрой и привычки отладки | Защитное программирование, журналы отладки |

## 0. Общая картина: отладка — это научный метод

Отладка — это не «полагаться на удачу», а строгий научный процесс. Методология, по которой физики ставят эксперименты, полностью применима к отладке:

1. **Наблюдение явления**: что пошло не так в программе? Какая ошибка возникла?
2. **Выдвижение гипотезы**: какая причина могла к этому привести?
3. **Проектирование эксперимента**: как проверить эту гипотезу?
4. **Проверка вывода**: гипотеза верна — исправляем, неверна — выдвигаем другую гипотезу

::: tip Золотые правила отладки
- **Сначала воспроизведи, потом исправляй**: если баг не воспроизводится стабильно, то даже исправив его, вы не узнаете, действительно ли он исправлен
- **Меняй только одну переменную за раз**: если менять несколько мест одновременно, непонятно, какое именно изменение решило проблему
- **Верь доказательствам, а не интуиции**: то, что вы считаете «здесь точно не может быть проблемы», часто и оказывается проблемой
- **Что меняли в последнее время?**: 80% багов вносятся последними изменениями
:::

## 1. Читаем сообщения об ошибках: ошибка — не враг, а подсказка

Самая частая ошибка новичков: увидев ошибку, паникуют и сразу закрывают или игнорируют её. На самом деле **сообщение об ошибке — это программа, рассказывающая вам, где что-то пошло не так** — это ваш лучший друг.

### 1.1 Три основных типа ошибок

| Тип | Когда возникает | Пример | Степень тяжести |
|-----|------------|------|---------|
| **Синтаксическая ошибка** | Код выдаёт ошибку ещё до запуска | Пропущена скобка, опечатка в ключевом слове | Легче всего исправить |
| **Ошибка времени выполнения** | Код падает на какой-то строке | Обращение к несуществующей переменной, деление на ноль | Средняя сложность |
| **Логическая ошибка** | Код работает, но результат неверный | Неправильная формула расчёта, перепутано условие | Сложнее всего обнаружить |

### 1.2 Как читать стек ошибок

На примере JavaScript — типичное сообщение об ошибке:

```
TypeError: Cannot read properties of undefined (reading 'name')
    at getUserName (app.js:15:23)
    at handleClick (app.js:42:10)
    at HTMLButtonElement.<anonymous> (app.js:58:5)
```

**Читаем сверху вниз**:

1. **Первая строка**: тип ошибки + описание → `TypeError`, попытка прочитать свойство `name` у `undefined`
2. **Вторая строка**: функция и место ошибки → функция `getUserName`, `app.js`, строка 15, столбец 23
3. **Последующие строки**: цепочка вызовов → кто вызвал эту функцию? `handleClick` → событие клика по кнопке

::: tip Шпаргалка по чтению стека
**Сверху вниз ищем причину, снизу вверх ищем источник.** Первая строка говорит вам, «что за ошибка», последняя строка — «откуда всё началось».
:::

### 1.3 Шпаргалка по распространённым типам ошибок

| Название ошибки | Значение | Частые причины |
|---------|------|---------|
| `SyntaxError` | Синтаксическая ошибка | Несоответствие скобок, пропущена запятая |
| `TypeError` | Ошибка типа | Операция над `undefined`/`null` |
| `ReferenceError` | Ошибка ссылки | Использование необъявленной переменной |
| `RangeError` | Ошибка диапазона | Выход за границы массива, слишком глубокая рекурсия |
| `NetworkError` | Сетевая ошибка | Сбой запроса к API, проблема кросс-домена |
| `404 Not Found` | Ресурс не существует | Ошибка в URL, файл удалён |
| `500 Internal Server Error` | Внутренняя ошибка сервера | Падение кода бэкенда |

### 1.4 Сравнение с сообщениями об ошибках в Python

Стек Python устроен наоборот по сравнению с JavaScript — **читается снизу вверх**:

```python
Traceback (most recent call last):
  File "main.py", line 10, in <module>
    result = calculate(data)
  File "main.py", line 5, in calculate
    return data["price"] * data["quantity"]
KeyError: 'quantity'
```

**Именно последняя строка** содержит причину ошибки: `KeyError: 'quantity'` — в словаре нет ключа `quantity`.

::: tip Разные языки — одна идея
Независимо от языка, сообщение об ошибке содержит три ключевые вещи: **что за ошибка** (тип), **где ошибка** (файл и номер строки) и **почему ошибка** (описание). Научившись извлекать эти три вещи, вы сможете понять сообщения об ошибках на любом языке.
:::

## 2. Классические методы отладки: мудрость, накопленная предшественниками

Эти методы не требуют никаких инструментов — только вашего мозга. Они являются основой всех продвинутых приёмов отладки.

### 2.1 Отладка делением пополам

**Основная идея**: сужать область проблемы вдвое, затем ещё вдвое, пока не найдёте источник.

**Сценарий**: код очень длинный, и непонятно, какой его участок сломан.

**Шаги**:

1. Добавьте `console.log` (или `print`) в середину кода
2. Если ошибка произошла до этой точки → проблема в верхней половине
3. Если ошибка произошла после неё → проблема в нижней половине
4. Для сломанной половины повторите шаги выше

```
В 100 строках кода есть баг
    ↓ добавляем log на строку 50
Проблема в строках 50-100
    ↓ добавляем log на строку 75
Проблема в строках 50-75
    ↓ добавляем log на строку 62
Проблема в строках 60-62!
```

::: tip Сила деления пополам
В 100 строках кода достаточно максимум 7 итераций (log₂100 ≈ 7), чтобы найти конкретную строку. Для 1000 строк нужно всего 10 итераций.
:::

### 2.2 Метод «резиновой уточки»

**Основная идея**: «рассказать» проблему построчно кому-то другому (или резиновой уточке) — и пока вы рассказываете, вы сами обнаруживаете проблему.

**Почему это работает?** Потому что «написание кода» и «объяснение кода» задействуют разные области мозга. Когда вы вынуждены словами описать каждый шаг логики, те предположения, которые вы «считали верными», всплывают наружу.

**Как применять**:

1. Откройте проблемный код
2. Объясняйте построчно: «Что делает эта строка? Зачем это нужно?»
3. Когда вы произносите «Хм, тут должно быть... подождите-ка», баг обычно где-то рядом

### 2.3 Минимальное воспроизведение

**Основная идея**: упростить сложную проблему до минимума, оставив лишь минимальный код, способный вызвать баг.

**Почему это важно?**

- В сложной системе баг может быть «замаскирован» другим кодом
- Минимальное воспроизведение устраняет помехи и делает проблему очевидной
- Это также облегчает обращение за помощью — никто не захочет смотреть на ваши 500 строк кода

**Шаги**:

1. Создайте новый пустой файл
2. Скопируйте только код, связанный с проблемой
3. Постепенно удаляйте, пока баг не исчезнет при удалении любой строки
4. То, что осталось, — и есть источник бага

### 2.4 Метод отката (Git Bisect)

**Основная идея**: если код «раньше работал, а теперь сломался», нужно найти, какой коммит внёс проблему.

```bash
# Встроенный в Git инструмент бинарного поиска
git bisect start
git bisect bad          # отмечаем, что в текущей версии есть баг
git bisect good abc123  # отмечаем какую-то рабочую старую версию
# Git автоматически переключится на коммит посередине; протестировав, вы говорите ему good или bad
# Повторив несколько раз, вы найдёте коммит, внёсший баг
```

::: tip Гид по выбору метода отладки
| Ситуация | Рекомендуемый метод |
|-----|---------|
| Непонятно, какой участок кода сломан | Деление пополам |
| Логика выглядит верной, но результат неверный | Резиновая уточка |
| Баг в сложной системе | Минимальное воспроизведение |
| «Только что работало и вдруг сломалось» | Метод отката / Git Bisect |
:::

## 3. Набор инструментов для отладки: правильный инструмент удваивает эффективность

Методология — это основа, но хорошие инструменты удваивают эффективность отладки.

### 3.1 console.log / print: самый простой и самый практичный

**Сценарий применения**: быстро посмотреть значение переменной, убедиться, до какого места дошёл код.

```javascript
// JavaScript
console.log('函数被调用了，参数是：', data)
console.log('计算结果：', result)
console.table(arrayData)  // 表格形式展示数组/对象
```

```python
# Python
print(f"当前值: {value}")
print(f"类型: {type(data)}")  # 检查数据类型
```

**Продвинутые приёмы**:

| Метод | Назначение |
|-----|------|
| `console.log()` | Обычный вывод |
| `console.warn()` | Жёлтое предупреждение, легко найти среди множества логов |
| `console.error()` | Красная ошибка |
| `console.table()` | Табличное отображение массивов и объектов |
| `console.time()` / `console.timeEnd()` | Измерение времени выполнения кода |
| `console.trace()` | Вывод стека вызовов |

### 3.2 Отладка по точкам останова: пошаговое выполнение, видим каждый шаг

**Сценарий применения**: сложная логика, нужно пошагово отследить выполнение кода.

**В браузере** (Chrome DevTools):

1. Откройте инструменты разработчика (F12) → панель Sources
2. Найдите файл исходного кода, кликните по номеру строки, чтобы поставить точку останова
3. Запустите соответствующее действие — код приостановится в точке останова
4. Выполняйте пошагово с помощью кнопок управления:
   - **Продолжить** (F8): выполнить до следующей точки останова
   - **Шаг с обходом** (F10): выполнить текущую строку, не заходя внутрь функции
   - **Шаг с заходом** (F11): зайти внутрь функции
   - **Шаг с выходом** (Shift+F11): выйти из текущей функции

**В VS Code**:

1. Кликните слева от номера строки, чтобы поставить точку останова (красная точка)
2. Нажмите F5, чтобы запустить отладку
3. В панели «Переменные» смотрите текущие значения всех переменных
4. В панели «Контрольные значения» добавьте интересующие вас выражения

::: tip Точки останова vs console.log
**console.log** подходит для быстрой проверки, использовали — удалили. **Отладка по точкам останова** подходит для глубокого анализа сложной логики. Это не взаимозаменяемые, а взаимодополняющие подходы.
:::

### 3.3 Сетевая отладка: проблемы между фронтендом и бэкендом

**Сценарий применения**: страница отображается неправильно, но непонятно, проблема во фронтенде или в данных, возвращаемых бэкендом.

**Chrome DevTools → панель Network**:

| Что смотреть | Какую проблему можно обнаружить |
|---------|--------------|
| **Код состояния** | 404 (неверный адрес), 500 (сервер упал), 403 (нет прав) |
| **Параметры запроса** | Верны ли данные, отправленные фронтендом |
| **Данные ответа** | Верен ли формат данных, возвращённых бэкендом |
| **Время запроса** | Какой запрос слишком медленный и тормозит страницу |
| **Заголовки запроса** | Передан ли Token, верен ли Content-Type |

**Шпаргалка по отладке**: сначала смотрим код состояния, затем параметры запроса, и в последнюю очередь — данные ответа.

### 3.4 Шпаргалка по выбору инструмента отладки

| Тип проблемы | Рекомендуемый инструмент |
|---------|---------|
| Неверное значение переменной | console.log / точка останова |
| Неверный порядок выполнения логики | Отладка по точкам останова |
| Сбой запроса к API | Панель Network |
| Неверные стили страницы | Панель Elements (проверка CSS) |
| Проблема производительности | Панель Performance / console.time |
| Утечка памяти | Панель Memory |

## 4. Отладка в эпоху AI: пусть AI станет вашим помощником

AI-инструменты (ChatGPT, Claude, Cursor и др.) способны существенно ускорить процесс отладки, но при условии, что вы знаете, как ими пользоваться.

### 4.1 В чём AI силён?

| AI силён в | AI слаб в |
|--------|----------|
| Объяснении смысла сообщений об ошибках | Понимании вашей бизнес-логики |
| Предоставлении решений распространённых проблем | Определении, какое решение лучше подходит вашему проекту |
| Генерации фрагментов отладочного кода | Воспроизведении багов, возникающих только в определённом окружении |
| Анализе потенциальных проблем в коде | Понимании сложного системного контекста |

### 4.2 Как правильно задавать вопросы AI

**Плохой вопрос**:
> «У меня код выдаёт ошибку, помоги разобраться»

**Хороший вопрос**:
> «Я пишу на React компонент-форму, при отправке возникает ошибка `TypeError: Cannot read properties of undefined (reading 'email')`. Вот соответствующий код: [вставить код]. Я уже убедился, что формат данных, возвращаемых API, правильный — проблема, вероятно, в обработке данных на фронтенде.»

**Шаблон вопроса**:

```
1. Что я делаю: [контекст]
2. Ожидаемое поведение: [как должно быть]
3. Фактическое поведение: [как есть на самом деле]
4. Сообщение об ошибке: [полный текст ошибки]
5. Соответствующий код: [вставить код]
6. Что я уже пробовал: [что исключил]
```

### 4.3 Ловушки отладки с AI

::: warning Три ловушки отладки с AI
1. **AI может «уверенно нести чушь»**: предложенное AI решение выглядит очень логичным, но может быть совершенно неверным. Всегда проверяйте сами.
2. **AI не знает вашего контекста**: он не знает структуру вашего проекта, версии зависимостей, среду выполнения. Вам нужно предоставить достаточный контекст.
3. **Чрезмерная зависимость от AI деградирует навыки отладки**: если каждую ошибку сразу скидывать AI, вы никогда не научитесь отлаживать сами. Рекомендуется сначала самостоятельно анализировать 5 минут, и только потом обращаться к AI.
:::

### 4.4 Лучшая комбинация AI + человека

```
Встретили баг
  ↓
Шаг 1: сами читаем сообщение об ошибке (1 минута)
  ↓
Шаг 2: сами выдвигаем гипотезу (2 минуты)
  ↓
Шаг 3: быстро проверяем гипотезу (2 минуты)
  ↓
Застряли? → отправляем AI сообщение об ошибке + код + ваш анализ
  ↓
AI даёт совет → вы оцениваете, разумен ли он → проверяете
```

## 5. Настрой и привычки отладки: от «тушения пожаров» к «противопожарной профилактике»

Лучшая отладка — та, которая не нужна. Выработайте хорошие привычки, и вы сократите число багов у источника.

### 5.1 Защитное программирование

**Основная идея**: при написании кода исходите из того, что «всё может пойти не так», и заранее ставьте защиту.

```javascript
// 差：假设 data 一定存在
const name = data.user.name

// 好：防御性写法
const name = data?.user?.name ?? '未知用户'
```

```python
# 差：假设文件一定能打开
content = open('config.json').read()

# 好：防御性写法
try:
    content = open('config.json').read()
except FileNotFoundError:
    print("配置文件不存在，使用默认配置")
    content = '{}'
```

### 5.2 Пишите хорошие логи

Логи — ключ к «отладке постфактум». В продакшен-окружении нельзя ставить точки останова, можно полагаться только на логи.

| Уровень лога | Назначение | Пример |
|---------|------|------|
| **DEBUG** | Подробная информация при разработке | Значения переменных, параметры функций |
| **INFO** | Нормальный бизнес-процесс | «Пользователь успешно вошёл», «Заказ создан» |
| **WARN** | Не влияет на работу, но требует внимания | «Промах кэша», «Повтор попытки №2» |
| **ERROR** | Произошла ошибка, требуется обработка | «Сбой подключения к БД», «Таймаут API» |

::: tip Критерий хорошего лога
Хороший лог должен отвечать на вопросы: **когда**, **где**, **что произошло**, **какие ключевые данные**.
```
[2025-01-15 14:30:22] [ERROR] [OrderService] 创建订单失败
  用户ID: 12345, 商品ID: 67890, 原因: 库存不足
```
:::

### 5.3 Чек-лист отладки

При встрече с багом проверяйте в таком порядке:

1. **Прочитать сообщение об ошибке**: тип ошибки, файл, номер строки
2. **Что меняли в последнее время?**: посмотрите последние изменения через `git diff`
3. **Воспроизводится ли?**: найдите стабильные шаги воспроизведения
4. **Сузить область**: локализуйте методом деления пополам или минимальным воспроизведением
5. **Выдвинуть гипотезу и проверить**: меняйте только одну переменную за раз
6. **Регрессионное тестирование после исправления**: убедитесь, что исправление не внесло новых проблем

### 5.4 Ловушки отладки, в которые часто попадают новички

| Ловушка | Правильный подход |
|-----|---------|
| Начинать менять код, не прочитав ошибку | Сначала полностью прочитать сообщение об ошибке |
| Менять несколько мест одновременно | Менять одно место за раз, проверять и только потом менять следующее |
| Коммитить без тестирования | После каждого изменения запускать тесты |
| Тестировать только на своём компьютере | Учитывать разные окружения (браузер, система, сеть) |
| Не убирать console.log после отладки | Перед коммитом удалить весь отладочный код |
| Перезапускать/переустанавливать при любой проблеме | Сначала понять причину проблемы; перезапуск — лишь временное решение |

## 6. Итог

Отладка — это ремесло, требующее осознанной практики. Вспомним ключевые моменты этой главы:

1. **Отладка — научный метод**: наблюдение → гипотеза → эксперимент → проверка, а не игра в угадайку
2. **Сообщение об ошибке — друг**: научитесь извлекать из ошибки «что за ошибка, где ошибка, почему ошибка»
3. **Классические методы не устаревают**: деление пополам, резиновая уточка, минимальное воспроизведение — основа любой отладки
4. **Инструменты под свой сценарий**: console.log для быстрой проверки, точки останова для глубокого анализа, Network для разбора запросов
5. **AI — помощник, а не костыль**: сначала проанализируйте сами, потом подключите AI, и в конце проверьте сами
6. **Профилактика лучше тушения**: защитное программирование и привычка вести хорошие логи сокращают число багов у источника

::: tip Запомните эту фразу
**Каждый баг — это возможность чему-то научиться.** Каждый исправленный вами баг помогает вам выработать способность «распознавать паттерны» — в следующий раз при похожей проблеме вы быстрее найдёте причину.
:::
