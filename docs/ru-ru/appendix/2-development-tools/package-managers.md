# Менеджеры пакетов

> 💡 **Руководство по обучению**: писать код вовсе не обязательно с нуля изобретая велосипед — 99% функциональности уже написано кем-то и опубликовано в интернете. **Менеджер пакетов** — это инструмент, который помогает вам находить, скачивать и управлять этими «готовыми деталями». Эта глава строится вокруг одного ключевого вопроса: **как сделать зависимости кода воспроизводимыми, пригодными для совместной работы и поддерживаемыми?**

---

## 0. Почему вы обязательно столкнётесь с менеджером пакетов?

Представьте, что вам нужно написать программу на Node.js, умеющую делать HTTP-запросы. Есть два пути:

- **Способ A (вручную)**: самостоятельно реализовать TCP-соединение, разбор HTTP-протокола, обработку редиректов, механизм таймаутов… вероятно, придётся написать несколько тысяч строк кода и отлаживать несколько месяцев.
- **Способ B (менеджер пакетов)**: `npm install axios`, десять секунд, одна строка кода — и готово.

Менеджер пакетов по своей сути — это «магазин приложений» для кода. Он помогает вам:

1. Найти опубликованные другими библиотеки в центральном репозитории (Registry)
2. Автоматически скачать и установить их в ваш проект
3. Обработать другие библиотеки, от которых зависит эта библиотека (зависимости зависимостей)
4. Запомнить, какую именно версию вы используете, чтобы командная работа проходила без проблем

### 1.1 Откуда скачиваются пакеты? — Registry (реестр)

За каждой экосистемой стоит центральный репозиторий, где хранятся все доступные для скачивания пакеты:

| Экосистема | Реестр | Количество пакетов |
| :--- | :--- | :--- |
| JavaScript | [npmjs.com](https://npmjs.com) | 2 млн+ |
| Python | [pypi.org](https://pypi.org) | 500 тыс.+ |
| Rust | [crates.io](https://crates.io) | 150 тыс.+ |
| Go | [pkg.go.dev](https://pkg.go.dev) | 500 тыс.+ |
| Инструменты macOS/Linux | [formulae.brew.sh](https://formulae.brew.sh) | 7000+ |
| ПО для Windows | [winget.run](https://winget.run) / [chocolatey.org](https://chocolatey.org) | десятки тысяч |

### 1.2 Сравнение трёх лидеров JavaScript: npm vs yarn vs pnpm

Функциональность схожа, различия проявляются в основном в **скорости и занимаемом месте на диске**:

```text
Место на диске: pnpm (общие жёсткие ссылки) < yarn PnP (без node_modules) < npm (полная копия)
Скорость установки: pnpm ≈ yarn > npm
Привычность: npm (самый универсальный) > pnpm (рекомендуется для новых проектов) > yarn (часть команд)
```

**Рекомендация**: для новых проектов используйте `pnpm`, для существующих проектов сохраняйте прежний инструмент, не переключайтесь произвольно.

### 1.3 Сравнение трёх лидеров Windows: winget vs Chocolatey vs Scoop

| | winget | Chocolatey | Scoop |
| :--- | :--- | :--- | :--- |
| **Официальная поддержка** | Официальный от Microsoft | Сторонний | Сторонний |
| **Требуются права администратора** | Иногда требуются | Да | **Не требуются** |
| **Подходящий сценарий** | Повседневная установка ПО | Массовое развёртывание в компании | Управление инструментами разработки |
| **Количество пакетов** | Много и быстро растёт | Больше всего (10000+) | Сфокусирован на инструментах разработки |

**Рекомендация**: для повседневных задач — `winget`, для инструментов разработки — `scoop`, для корпоративной автоматизации — `Chocolatey`.

## 2. Установка пакета — что происходит за кулисами?

После ввода `npm install axios` командная строка пару секунд молчит, а потом всё готово. Что же на самом деле происходит за эти секунды?

👇 **Попробуйте сами**: выберите пакет, нажмите «Запустить» и понаблюдайте за всем процессом установки.

<PackageInstallDemo />

### 2.1 Подробный разбор четырёх этапов

**① Разрешение зависимостей (Resolve)**

Менеджер пакетов сначала «понимает», что вы хотите установить. На примере `axios`: он сам зависит от пакетов `follow-redirects`, `form-data` и др., которые тоже нужно установить. Этот процесс называется **построением дерева зависимостей**.

**② Загрузка (Fetch)**

Загрузка из реестра всех необходимых пакетов (архивов в формате `.tgz`). Умный менеджер пакетов:
- Загружает несколько пакетов параллельно, а не ждёт по одному
- Сначала проверяет локальный кэш — при попадании не обращается к сети

**③ Связывание (Link)**

Распаковка загруженных пакетов в каталог `node_modules/` и настройка ссылочных связей.

**④ Запись lock-файла (Lockfile)**

Запись **точных номеров версий** этой установки в `package-lock.json` (или `yarn.lock` / `pnpm-lock.yaml`).

### 2.2 Шпаргалка по самым частым командам

```bash
# ── JavaScript (npm) ──────────────────────────────────
npm install              # Установить все зависимости по package.json
npm install axios        # Установить новый пакет (продакшен-зависимость)
npm install -D jest      # Установить зависимость разработки (нужна только при разработке)
npm install -g tsx       # Глобальная установка (доступна из любого каталога)
npm uninstall axios      # Удалить пакет
npm update               # Обновить все пакеты до совместимых последних версий
npm run build            # Запустить скрипт из scripts в package.json
npx create-react-app .   # Временный запуск, без установки в проект

# ── Python (pip) ──────────────────────────────────────
pip install requests           # Установить пакет
pip install requests==2.28.0   # Установить указанную версию
pip freeze > requirements.txt  # Экспортировать текущий список зависимостей
pip install -r requirements.txt # Установить по списку

# ── Rust (cargo) ──────────────────────────────────────
cargo add serde    # Добавить зависимость (автоматически обновит Cargo.toml)
cargo build        # Собрать проект
cargo test         # Запустить тесты
cargo run          # Запустить проект

# ── Go (go mod) ───────────────────────────────────────
go get github.com/gin-gonic/gin  # Добавить зависимость
go mod tidy                      # Упорядочить зависимости (удалить лишние, добавить недостающие)
go build ./...                   # Собрать

# ── Windows (winget) ──────────────────────────────────
winget install Git.Git           # Установить ПО
winget upgrade --all             # Обновить всё установленное ПО
```

### 2.3 Что такое npm scripts?

В `package.json` есть поле `scripts` — это встроенный в npm **исполнитель задач**:

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "test": "jest",
    "lint": "eslint src/"
  }
}
```

Способ запуска: `npm run dev`, `npm run build`. Преимущества такого подхода:
- **Единая точка входа**: членам команды не нужно запоминать конкретные команды низкоуровневых инструментов
- **Автоматическая настройка окружения**: при запуске `node_modules/.bin` автоматически добавляется в PATH, что позволяет напрямую использовать локально установленные инструменты

## 3. Глобальная установка vs локальная установка

Это одно из понятий, которое чаще всего путает новичков.

### 3.1 В чём разница

```bash
npm install axios        # Локальная установка: в ./node_modules/, доступна только текущему проекту
npm install -g typescript  # Глобальная установка: в системный каталог, доступна любому проекту/каталогу
```

| | Локальная установка | Глобальная установка |
| :--- | :--- | :--- |
| **Место хранения** | `./node_modules/` | Системный каталог (например, `/usr/local/lib/`) |
| **Подходит для** | Библиотек-зависимостей проекта (axios, vue, react) | Инструментов командной строки (tsc, eslint, create-react-app) |
| **Изоляция версий** | У каждого проекта своя версия ✅ | Одна версия на всю машину ⚠️ |
| **Согласованность в команде** | Lock-файл гарантирует согласованность ✅ | У каждого версия может отличаться ⚠️ |

### 3.2 Золотое правило

> **Библиотечные зависимости (axios, lodash, vue) всегда устанавливайте локально;
> инструменты командной строки (tsc, eslint) предпочтительно устанавливайте локально и вызывайте через `npx`.**

**Почему инструменты командной строки тоже рекомендуется устанавливать локально?**

Допустим, вы глобально установили `eslint@8`, но проекту A нужны новые правила `eslint@9` — вам придётся постоянно переключаться между глобальной и проектной версиями. Установите `eslint` локально и вызывайте через `npx eslint .` — тогда каждый проект сможет независимо настраивать свою версию.

### 3.3 npx — временный запуск без загрязнения окружения

`npx` — это встроенный в npm исполнитель инструментов, позволяющий **запускать пакет без установки**:

```bash
# Не устанавливая create-vue, сразу запускаем его для инициализации проекта
npx create-vue my-project

# Не устанавливая prettier, сразу форматируем файлы
npx prettier --write src/

# Принудительно используем указанную версию (игнорируя установленную)
npx typescript@5.4 tsc --version
```

`uvx` в Python и `cargo run` в Rust также предоставляют аналогичную возможность «временного запуска»:

```bash
uvx ruff check .       # Python: временный запуск линтера ruff
cargo install ripgrep  # Rust: глобальная установка, становится системной командой rg
```

## 4. Секрет номеров версий — семантическое версионирование

В `package.json` вы увидите примерно такое содержимое:

```json
{
  "dependencies": {
    "axios": "^1.6.8",
    "typescript": "~5.4.0"
  }
}
```

Что здесь означают `^` и `~`?

👇 **Попробуйте сами**: наведите мышь на разные части номера версии, чтобы понять их значение; кликните по символу диапазона, чтобы увидеть, какие версии будут приняты.

<DependencyTreeDemo />

### 4.1 Почему не фиксируют версию намертво?

| Подход | Преимущества | Недостатки |
| :--- | :--- | :--- |
| `"axios": "1.6.8"` (точная фиксация) | Полностью предсказуемо | Патчи безопасности не обновляются автоматически |
| `"axios": "^1.6.8"` (диапазон совместимости, рекомендуется) | Автоматически получает исправления багов и новые функции | В очень редких случаях вносит мелкую несовместимость |
| `"axios": "*"` (любая версия) | Всегда самая свежая | Обновление мажорной версии полностью сломает код |

**Лучшая практика**: объявляйте диапазон через `^` + фиксируйте реальную версию lock-файлом, используя их вместе.

### 4.2 Что такое ад зависимостей?

Когда вы зависите от 50 пакетов, каждый из которых зависит ещё от нескольких, «дерево зависимостей» может содержать сотни узлов. Если два пакета, от которых вы зависите, требуют **несовместимых версий одной библиотеки**, возникает «конфликт зависимостей».

Решения в разных экосистемах:
- **npm v3+**: одинаковые мажорные версии поднимаются на верхний уровень для общего использования, разные мажорные версии устанавливаются каждая отдельно
- **pnpm**: жёсткие ссылки + строгая изоляция, что в корне предотвращает «фантомные зависимости» (пакеты, которые можно использовать, не объявив их)
- **cargo (Rust)**: на уровне языка вынуждает каждый пакет зависеть только от одной версии, полностью исключая конфликты
- **go mod (Go)**: стратегия выбора минимальной версии (MVS) — выбирается наименьшая версия, удовлетворяющая всем ограничениям

## 5. Lock-файл — фундамент командной работы

### 5.1 Зачем нужен lock-файл?

Допустим, в `package.json` записано `"axios": "^1.6.0"`:

- Вы устанавливаете сегодня → ставится `1.6.8`
- Коллега устанавливает завтра → может поставиться `1.7.0` (вышла прошлой ночью)
- CI-сервер на следующей неделе → может поставиться `1.7.1`

Один и тот же код, но три человека получают разный результат. **Lock-файл** записывает точную версию каждого пакета, и все устанавливают по нему, получая полностью идентичный результат.

| Сценарий | Команда | Поведение |
| :--- | :--- | :--- |
| Синхронизация среды разработки | `npm install` | Устанавливает с опорой на lock-файл, не обновляя версии |
| CI / продакшен-развёртывание | `npm ci` | **Строго** устанавливает по lock-файлу, при расхождении сразу выдаёт ошибку |
| Активное обновление версий | `npm update` | Обновляет в допустимом диапазоне и обновляет lock-файл |

### 5.2 Нужно ли коммитить lock-файл в Git?

**Приложения обязательно коммитят, библиотеки, публикуемые в npm, могут не коммитить.**

- ✅ **Веб-приложения, бэкенд-сервисы**: обязательно коммитить, чтобы среда развёртывания полностью совпадала со средой разработки
- ❌ **Библиотеки, публикуемые в npm**: обычно не коммитят, у пользователей библиотеки есть свой lock-файл
- ✅ **Python-проекты**: `requirements.txt` сам по себе играет роль lock-файла, его следует коммитить
- ✅ **Go-проекты**: `go.sum` обязательно коммитить, он используется для проверки целостности

## 6. Виртуальные окружения Python

В Python есть понятие, на которое стоит обратить особое внимание: **виртуальное окружение (venv)**.

**Зачем оно нужно?**

Python по умолчанию устанавливает пакеты **глобально**. Вашему проекту A нужен `requests==2.28`, проекту B — `requests==2.31`, и они конфликтуют друг с другом.

**Решение**: создавать для каждого проекта отдельное виртуальное окружение, чтобы они не мешали друг другу.

```bash
# 1. Создаём виртуальное окружение (запускаем в корне проекта)
python -m venv .venv

# 2. Активируем виртуальное окружение
source .venv/bin/activate        # macOS / Linux
.venv\Scripts\activate           # Windows (командная строка CMD)
.venv\Scripts\Activate.ps1       # Windows (PowerShell)

# 3. После активации pip install влияет только на текущее окружение, не загрязняя глобальное
pip install requests

# 4. Выходим из виртуального окружения
deactivate
```

> ⚠️ **Частая проблема в Windows**: PowerShell по умолчанию запрещает запуск скриптов, нужно сначала выполнить:
> ```powershell
> Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
> ```

**Современные альтернативы**:
- `conda create -n myproject python=3.11` — управляет даже версией самого Python
- `uv venv && source .venv/bin/activate` — написан на Rust, создаётся молниеносно

**Нужно ли коммитить `.venv` в Git?**

Не нужно! `.venv` генерируется на локальной машине, его следует добавить в `.gitignore`. Для описания зависимостей используйте `requirements.txt` или `pyproject.toml`.

## 7. Шпаргалка по частым вопросам

**В: Нужно ли коммитить `node_modules` в Git?**

Не нужно! Обычно он весит несколько сотен МБ, его следует добавить в `.gitignore`. С `package-lock.json` любой сможет быстро пересобрать всё через `npm install`.

**В: Что делать, если установка не удалась / возникают странные ошибки?**

```bash
# Очищаем кэш, удаляем старую установку, начинаем заново
npm cache clean --force
rm -rf node_modules package-lock.json   # macOS/Linux
rmdir /s /q node_modules && del package-lock.json  # Windows CMD
npm install
```

**В: Установка слишком медленная?**

```bash
# Переключаемся на китайское зеркало (рекомендуется записать в файл .npmrc, не загрязняя глобальное)
echo "registry=https://registry.npmmirror.com" > .npmrc

# Для pip тоже можно настроить зеркало
pip install requests -i https://pypi.tuna.tsinghua.edu.cn/simple
```

**В: Что делать, если в пакете есть уязвимость безопасности?**

```bash
npm audit          # Сканирование известных уязвимостей
npm audit fix      # Автоматическое исправление совместимых уязвимостей
npm audit fix --force  # Принудительное обновление (может всё сломать, используйте осторожно)
```

**В: Как понять, заслуживает ли пакет доверия?**

Посмотрите на [npmjs.com](https://npmjs.com) или [bundlephobia.com](https://bundlephobia.com):
- Количество загрузок в неделю (чем выше, тем надёжнее)
- Время последнего обновления (если не обновлялся более 2 лет, будьте осторожны)
- Количество зависимостей (чем больше зависимостей, тем выше вероятность проблем)
- Активность по GitHub Stars и Issues

**В: Где находится ПО, установленное через winget на Windows?**

winget по умолчанию устанавливает в системный каталог (нужны права администратора) или в `%LOCALAPPDATA%\Microsoft\WindowsApps`. ПО, установленное через Scoop, целиком лежит в `%USERPROFILE%\scoop\apps\`, что удобно для управления и переноса.

## 8. Таблица соответствия терминов

| Английский термин | Русское соответствие | Пояснение |
| :--- | :--- | :--- |
| **Package** | Пакет / библиотека | Написанный и опубликованный кем-то модуль кода |
| **Registry** | Реестр / репозиторий | Центральный сервер хранения всех пакетов (например, npmjs.com) |
| **Dependency** | Зависимость | Другие пакеты, необходимые для работы вашего проекта |
| **devDependency** | Зависимость разработки | Пакеты, нужные только на этапе разработки (тестовые фреймворки, инструменты сборки и т. д.) |
| **Lockfile** | Lock-файл | Записывает точные номера версий, гарантируя согласованность окружения |
| **SemVer** | Семантическое версионирование | Соглашение об именовании версий MAJOR.MINOR.PATCH |
| **node_modules** | Каталог модулей | Каталог, в котором реально хранятся установленные npm пакеты |
| **venv** | Виртуальное окружение | Отдельная песочница изоляции пакетов для Python-проекта |
| **tarball** | Архив | Формат распространения пакета, обычно файл `.tgz` |
| **Hoisting** | Поднятие | npm поднимает подзависимости на верхний уровень во избежание дублирующей установки |
| **Phantom Dependency** | Фантомная зависимость | Пакет, который можно использовать, не объявив его в конфигурации (pnpm это предотвращает) |
| **npx** | — | Встроенный в npm исполнитель пакетов, запускает пакет временно без установки |
| **go.sum** | — | Файл хеш-проверки модулей Go, защищающий зависимости от подмены |
| **Crate** | — | Название единицы «пакета» в экосистеме Rust |
| **winget** | — | Официальный менеджер пакетов Windows (встроен в Windows 10/11) |

## Итог: суть менеджеров пакетов

Запомните суть в четырёх фразах:

1. **Менеджер пакетов = магазин приложений**: помогает находить, устанавливать и управлять деталями кода, чтобы не изобретать велосипед заново.
2. **Lock-файл = договор команды**: фиксирует точные версии, делая «у меня на машине всё работало» историей.
3. **Семантическое версионирование = язык общения**: `^` безопасно получает обновления, а при изменении MAJOR нужно быть осторожным.
4. **Локально > глобально**: зависимости проекта по возможности устанавливайте локально, инструменты запускайте временно через `npx` / `uvx`, сохраняя окружение чистым.
