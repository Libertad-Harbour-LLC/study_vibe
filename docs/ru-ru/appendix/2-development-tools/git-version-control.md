# Git: машина времени для кода

> 💡 **Руководство по обучению**: эта глава написана специально для тех, кто никогда не пользовался Git. Мы не будем сразу заставлять вас зубрить команды, а сначала разберёмся, «какую проблему Git вообще помогает вам решить», а затем шаг за шагом свяжем команды и понятия воедино. Прочитав её, вы сможете самостоятельно: сделать локальный коммит, создать ветку, отправить на GitHub.

---

## 0. Сначала зададим вопрос: переживали ли вы такие кошмары?

**Сценарий первый: версионный ад**

Вы пишете статью или код, дописали до середины и обнаружили, что ошиблись, хотите вернуться к версии трёхдневной давности — но не можете её найти.

```
проект_v1.zip
проект_v2_исправленный.zip
проект_v3_финальный.zip
проект_v3_финальный_реально_финальный.zip
проект_v3_финальный_больше_не_трогаю.zip
```

Каждый раз сохраняется новая копия, диск всё больше захламляется, и вы вообще не помните, какая версия что меняла.

**Сценарий второй: кошмар совместной работы**

Вы и коллега одновременно правите один и тот же файл:
- Вы изменили строку 10, добавив функцию входа
- Коллега изменил строку 10, исправив баг
- Вы пересылаете код по почте, и при слиянии изменения одного человека затираются изменениями другого
- Никто не знает, какой кусок кода в итоге правильный

**Сценарий третий: нет «таблетки от сожалений»**

Вы развернули новый код на продакшене, и вылез баг, нужно срочно откатиться к предыдущей стабильной версии — но вы не знаете, как откатиться, и в панике ищете резервную копию.

---

**Git был создан именно для решения этих трёх проблем.**

Git — это **система контроля версий** (Version Control System). Его суть в том, чтобы **записывать каждую вашу операцию «сохранения», формируя полную историческую временную линию, позволяющую в любой момент вернуться к любому историческому узлу.**

Без преувеличения, Git — один из важнейших инструментов современной разработки ПО. Его используют почти все компании и все open-source проекты.

## 1. Git и GitHub — это одно и то же?

Многие новички путают эти два понятия, давайте сначала проясним:

| | Git | GitHub |
| :--- | :--- | :--- |
| **Что это** | Инструмент контроля версий, работающий на вашем компьютере | Сайт (облако), где хранятся Git-репозитории |
| **Где находится** | Ваш локальный компьютер | В интернете |
| **Можно ли использовать самостоятельно** | ✅ Да, управляет только локальной историей | ❌ Нужно использовать вместе с Git |
| **Аналогия** | Ваш локальный дневник | Облако для хранения дневников |

Проще говоря: **Git — это инструмент, GitHub — сервис хостинга.** Как Word — это инструмент, а OneDrive — облако: они используются вместе, но это не одно и то же.

Помимо GitHub, есть и похожие сервисы: GitLab, Gitee (в Китае) и др.

## 2. Ключевое понятие: три области

Это самая важная конструкция всего Git. Поняв эти три области, вы поймёте душу Git.

Git делит состояние ваших файлов на три уровня:

**Рабочая область (Working Directory)**
Это ваша **обычная папка** — все файлы, которые вы сейчас видите и редактируете, находятся здесь. Вы правите как угодно, Git замечает, что вы изменили, но ничего не записывает.

**Область подготовки (Staging Area / Index)**
Это **«перевалочный пункт» для подготовки к коммиту**. Вы можете «положить» нужные для сохранения файлы из рабочей области в область подготовки — как положить посылку в коробку: ещё не отправили, но уже выбрали, что отправлять.

**Репозиторий (Repository)**
Это **хранилище постоянной истории**, спрятанное в папке `.git`. Каждый раз, когда вы выполняете `git commit`, содержимое области подготовки запечатывается в репозиторий, формируя неизменяемую историческую запись.

👇 **Попробуйте сами**: по очереди нажимайте кнопки команд и наблюдайте, как файлы перемещаются между тремя областями.

### Почему нужно «два шага» (add + commit)?

Многие новички спрашивают: почему нельзя сохранить одним нажатием, а нужно сначала `add`, потом `commit`?

**Потому что в реальной разработке вы часто не хотите коммитить все изменения сразу.**

Например: сегодня вы изменили 5 файлов:
- `login.js`: завершили функцию входа (хотите закоммитить)
- `style.css`: подправили стили страницы входа (хотите закоммитить)
- `debug.log`: временный отладочный вывод (**не хотите** коммитить)
- `experiment.js`: новая функция, которую вы тестируете, ещё не завершена (**не хотите** коммитить)
- `todo.txt`: ваша личная заметка (**не хотите** коммитить)

Без области подготовки вам пришлось бы либо закоммитить все 5 файлов разом (история коммитов будет хаотичной), либо не коммитить ни одного.

С областью подготовки вы можете точно контролировать: `git add login.js style.css` — кладёте в коробку только эти два файла, затем `commit`, и этот коммит чётко фиксирует «функция входа завершена».

## 3. Первое использование Git: инициализация и базовый рабочий процесс

### 3.1 Установка и инициализация

После установки Git (в macOS он встроен, в Windows скачайте с git-scm.com) откройте терминал и зайдите в папку проекта:

```bash
# Инициализируем Git-репозиторий в текущей папке
git init

# Git создаст скрытую папку .git, в которой будет храниться вся история
# Вывод: Initialized empty Git repository in .../your-project/.git/
```

При первом использовании также нужно сообщить Git, кто вы (эта информация будет прикрепляться к каждому коммиту):

```bash
git config --global user.name "Ваше имя"
git config --global user.email "Ваша почта"
```

### 3.2 Повседневный рабочий процесс: сохранение в три шага

После инициализации 90% повседневной разработки — это многократное повторение этих трёх шагов:

**Шаг первый: проверить статус**

```bash
git status
```

Это команда, которую вы используете чаще всего, без исключений. Она сообщает вам:
- На какой ветке вы находитесь
- Какие файлы изменены (красный = не подготовлены)
- Какие файлы в области подготовки (зелёный = подготовлены, ждут коммита)

**Шаг второй: положить файлы в область подготовки**

```bash
# Добавить один файл
git add login.js

# Добавить несколько файлов
git add login.js style.css

# Добавить все изменённые файлы в текущей папке (точка означает "все")
git add .
```

> ⚠️ Частое заблуждение новичков: `git add .` очень удобен, но добавит все изменения, включая временные файлы, которые вы не хотите коммитить. Выработайте привычку точно делать add или используйте `.gitignore`, чтобы исключить файлы, которые не нужно отслеживать (об этом позже).

**Шаг третий: закоммитить, написав описание**

```bash
git commit -m "feat: добавить функцию входа пользователя"
```

Содержимое в кавычках после `-m` называется **commit message** (описание коммита). Оно пишется для будущего вас и для коллег, поэтому должно быть осмысленным.

### 3.3 Как писать commit message профессионально?

```bash
# ❌ Бесполезная запись — посмотрев, не понять, что сделано
git commit -m "update"
git commit -m "fix"
git commit -m "поменял кое-что"

# ✅ Хорошая запись: тип + двоеточие + описание одной фразой
git commit -m "feat: добавить функцию входа пользователя"
git commit -m "fix: исправить белый экран главной страницы в iOS Safari"
git commit -m "docs: обновить инструкцию по развёртыванию в README"
git commit -m "refactor: вынести UserService в отдельный модуль"
git commit -m "style: привести отступы кода к 2 пробелам"
```

**Значение распространённых префиксов:**

| Префикс | Значение |
| :--- | :--- |
| `feat:` | Новая функция (feature) |
| `fix:` | Исправление бага |
| `docs:` | Изменения в документации |
| `style:` | Корректировка форматирования кода (не влияет на функциональность) |
| `refactor:` | Рефакторинг кода (функциональность не меняется, структура улучшается) |
| `chore:` | Связанное со сборкой, инструментами, зависимостями |
| `test:` | Связанное с тестами |

Выработайте эту привычку — и через несколько месяцев, листая историю, вы с одного взгляда поймёте, что делал каждый коммит. Это особенно важно в командной работе.

### 3.4 Просмотр истории

```bash
# Подробный формат (полная информация о каждом коммите)
git log

# Краткий формат (по одной строке на коммит, рекомендуется для повседневного использования)
git log --oneline

# Пример вывода:
# a1b2c3d (HEAD -> main) feat: добавить функцию входа пользователя
# 9f3e1b2 init: инициализация проекта
```

## 4. Параллельные вселенные: ветки (Branch)

**Ветки** — самая мощная и одновременно самая запутанная для новичков функция Git. Но поняв её, вы обнаружите, что эта конструкция очень элегантна.

### 4.1 Что такое ветка? Понять через «параллельные вселенные»

Представьте, что вы играете в ролевую игру, в которой есть ключевой выбор:
- Выбор A: пойти сражаться с боссом (разработать новую функцию)
- Выбор B: сохранять текущую стабильную ситуацию (основную линию не трогать)

Если вы сделаете выбор A прямо на основном сохранении, то в случае провала весь прогресс игры будет уничтожен.

Но если вы **скопируете сохранение** и в копии пойдёте сражаться с боссом:
- Выиграли? Слейте достижения копии обратно в основное сохранение
- Проиграли? Основное сохранение никак не затронуто, удалите копию и начните заново

**Ветка Git — это и есть механизм «копии сохранения».**

В Git ветка `main` (или `master`) — это ваше «основное сохранение», всегда стабильное и пригодное к использованию. Когда вам нужно разработать новую функцию, вы создаёте новую ветку от main, разрабатываете и тестируете там, а по завершении сливаете обратно в main.

### 4.2 Визуальная демонстрация веток

👇 **Попробуйте сами**: по очереди нажимайте кнопки команд и наблюдайте, как граф веток внизу разветвляется, продлевается и в итоге сливается. Особое внимание уделите изменению положения метки HEAD — она всегда указывает на то, «где вы сейчас находитесь».

### 4.3 Подробный разбор операций с ветками

**Создать новую ветку и переключиться на неё:**

```bash
# Способ первый: сначала создать, потом переключиться (два шага)
git branch feature-login      # создать ветку
git checkout feature-login    # переключиться на неё

# Способ второй: за один шаг (рекомендуется)
git checkout -b feature-login

# Вывод: Switched to a new branch 'feature-login'
```

После создания ветки в приглашении командной строки будет отображаться имя текущей ветки, например:
```
user@mac ~/project (feature-login) $
```

**Просмотреть все ветки:**

```bash
git branch

# Вывод (* означает текущую ветку):
# * feature-login
#   main
```

**Обычная разработка в ветке:**

```bash
# В ветке feature-login правим код, add, commit — точно так же, как обычно
git add login.js
git commit -m "feat: добавить HTML-структуру формы входа"

git add login.js api.js
git commit -m "feat: завершить подключение к API входа"
```

Эти коммиты находятся только в ветке `feature-login`, а ветка `main` совершенно не знает, что вы делали.

**Переключиться обратно на главную ветку и слить:**

```bash
# Переключаемся обратно на main
git checkout main

# Сливаем все изменения feature-login сюда
git merge feature-login

# После слияния можно удалить эту ветку (необязательно)
git branch -d feature-login
```

### 4.4 Когда стоит создавать ветку?

| Сценарий | Рекомендация | Обоснование |
| :--- | :--- | :--- |
| Разработка новой функции | ✅ Создать ветку | До завершения функции основная линия не затрагивается, можно в любой момент отказаться |
| Исправление срочного бага на продакшене | ✅ Создать ветку `hotfix-xxx` от main | После исправления сразу слить и выкатить, не принося незавершённые функции |
| Параллельная разработка с коллегой | ✅ Каждый создаёт свою ветку | Не мешают друг другу, по завершении единообразно сливают через Pull Request |
| Исправить одну опечатку | ❌ Править прямо в main | Риск крайне низкий, нет смысла создавать отдельную ветку |

### 4.5 Распространённые в командах стратегии ветвления

В реальных проектах команды обычно договариваются об именовании и назначении веток:

| Имя ветки | Назначение | Особенности |
| :--- | :--- | :--- |
| `main` / `master` | Стабильный код продакшен-окружения | Сюда попадает только прошедший тесты код, нельзя пушить напрямую |
| `dev` / `develop` | Повседневная ветка интеграции | Все функциональные ветки сначала сливаются сюда, после тестов попадают в main |
| `feature/xxx` | Разработка конкретной функции | Например, `feature/user-login`, по завершении сливается в dev |
| `hotfix/xxx` | Срочное исправление | Создаётся от main, после исправления сразу сливается обратно в main и dev |

## 5. Совместная работа с коллегами: удалённый репозиторий

До сих пор вы изучали **локальные** операции Git — вся история хранится на вашем собственном компьютере. Чтобы делиться кодом с коллегами, вам нужен **удалённый репозиторий**, то есть облачное хранилище вроде GitHub или GitLab.

### 5.1 Принцип работы удалённого репозитория

Удалённый репозиторий можно понимать как **«общее хранилище» команды**:

- Каждый пишет код локально и коммитит
- После написания делает `push` (выгружает) в удалённый репозиторий
- Коллега делает `pull` (скачивает) последнее содержимое удалённого репозитория к себе локально
- Так код у всех остаётся синхронизированным

👇 **Попробуйте сами**: по очереди нажимайте команды, чтобы пройти весь процесс — от связывания удалённого репозитория и отправки до получения обновлений коллеги.

<GitSyncDemo />

### 5.2 Первая отправка проекта на GitHub

**Шаг первый**: создайте на GitHub новый репозиторий (нажмите + в правом верхнем углу → New repository), не отмечайте опции инициализации.

**Шаг второй**: вернитесь в локальный терминал и свяжите удалённый репозиторий:

```bash
# Связываем локальный репозиторий с репозиторием на GitHub
# "origin" — псевдоним удалённого репозитория, общепринятое имя (можно изменить, но не нужно)
git remote add origin https://github.com/ваш-логин/имя-репозитория.git

# Проверяем, что связь установлена
git remote -v
# Вывод:
# origin  https://github.com/ваш-логин/имя-репозитория.git (fetch)
# origin  https://github.com/ваш-логин/имя-репозитория.git (push)
```

**Шаг третий**: отправьте локальное содержимое на удалённый:

```bash
# Первая отправка, -u означает "в дальнейшем git push по умолчанию пушит в ветку main репозитория origin"
git push -u origin main

# В дальнейшем для каждой отправки достаточно:
git push
```

### 5.3 Команды повседневной совместной работы

**Push (вы что-то изменили и хотите, чтобы коллеги это увидели):**
```bash
git push
```

**Pull (коллега что-то изменил, вам нужно синхронизироваться):**
```bash
git pull
```

`git pull` на самом деле является комбинацией двух команд:
1. `git fetch`: сначала скачивает с удалённого репозитория последние коммиты
2. `git merge`: сливает скачанное содержимое в вашу текущую ветку

**Первое получение чужого проекта с GitHub:**
```bash
# Копируем весь удалённый репозиторий локально (нужно сделать только один раз)
git clone https://github.com/некто/некий-проект.git

# clone автоматически устанавливает связь с удалённым, дальше просто push/pull
```

### 5.4 Направление push и pull

```
Ваш компьютер (локальный репозиторий)  ←→  GitHub (удалённый репозиторий)

git push:  локальный → удалённый   (вы что-то изменили, выгружаете коллегам)
git pull:  удалённый → локальный   (коллега что-то изменил, скачиваете к себе)
git clone: удалённый → локальный   (первое полное копирование всего репозитория)
```

> **Лучшая практика**: каждый день перед началом работы сначала делайте `git pull`, чтобы получить свежий код; в конце дня или по завершении функции делайте `git push`, чтобы вовремя создать резервную копию и показать коллегам ваш прогресс.

## 6. Продвинутое: разрешение конфликтов

Конфликты неизбежны при совместной работе, но они не так уж страшны.

### 6.1 Как возникает конфликт?

Когда вы и коллега **одновременно изменили одну и ту же строку одного и того же файла**, при слиянии Git не знает, чью версию использовать, и возникает конфликт.

Например:
- Вы в `login.js` на строке 5 написали: `const timeout = 3000`
- Коллега одновременно на той же строке написал: `const timeout = 5000`
- Когда вы делаете `git pull` или `git merge`, Git обнаруживает это противоречие, «приостанавливается» и говорит вам: я не знаю, какую использовать, решай ты.

### 6.2 Как выглядит файл с конфликтом?

Git вставляет в место конфликта специальные маркеры:

```javascript
function login() {
  const url = '/api/login'

<<<<<<< HEAD
  const timeout = 3000   // ваша версия
=======
  const timeout = 5000   // версия коллеги
>>>>>>> feature/update-timeout

  return fetch(url, { timeout })
}
```

- Между `<<<<<<< HEAD` и `=======`: содержимое вашей текущей ветки
- Между `=======` и `>>>>>>> xxx`: содержимое, пришедшее при слиянии

### 6.3 Как разрешить конфликт?

**Шаг первый**: откройте файл с конфликтом, найдите все маркеры `<<<<<<<` (обычно редакторы вроде VS Code автоматически их подсвечивают)

**Шаг второй**: решите, какой кусок кода оставить, затем вручную отредактируйте файл, удалив все символы-маркеры (`<<<<<<<`, `=======`, `>>>>>>>`).

Например, решили использовать 5000 (версию коллеги):
```javascript
function login() {
  const url = '/api/login'
  const timeout = 5000   // принимаем изменение коллеги
  return fetch(url, { timeout })
}
```

**Шаг третий**: закоммитьте заново

```bash
# Отмечаем, что конфликт разрешён
git add login.js

# Завершаем коммит слияния (Git автоматически сгенерирует сообщение коммита слияния)
git commit
```

### 6.4 Хорошие привычки для уменьшения конфликтов

- **Часто делайте pull**: синхронизируйте свежий код перед началом работы, чтобы уменьшить ситуации «вы слишком сильно отстали»
- **Коммитьте маленькими шагами**: не пишите код неделю, чтобы потом закоммитить всё разом; частые маленькие коммиты легче обнаруживать и разрешать конфликты
- **Изоляция через ветки**: разные функции — в разных ветках, чтобы уменьшить конкуренцию за одну и ту же строку кода
- **Общение**: прежде чем менять общий файл (например, `config.js`), предупредите коллег

## 8. Практика: полный процесс присоединения к командному проекту

Это стандартный порядок действий при присоединении к новой команде или новому проекту, его можно прямо переписать:

```bash
# ① Первый день: клонируем проект локально (делается один раз)
git clone https://github.com/team/project.git
cd project

# ② Каждый день в начале работы: сначала забираем свежий код, чтобы ваш код был актуальным
git pull origin main

# ③ Создаём свою функциональную ветку (не правим прямо в main)
git checkout -b feature/user-profile

# ④ Обычная разработка... пишем код...

# ⑤ Завершив маленькую функцию, сразу коммитим (не накапливаем)
git add src/UserProfile.vue
git commit -m "feat: завершить загрузку аватара пользователя"

git add src/UserProfile.vue src/api/user.js
git commit -m "feat: завершить API редактирования профиля пользователя"

# ⑥ Пушим свою ветку на удалённый, чтобы коллеги её видели
git push origin feature/user-profile

# ⑦ Создаём на GitHub Pull Request (PR) с запросом на слияние в main
# (этот шаг выполняется на веб-странице GitHub)

# ⑧ Ждём Code Review коллег, правим по замечаниям, продолжаем commit + push

# ⑨ После слияния PR возвращаемся на main, обновляем локально, удаляем функциональную ветку
git checkout main
git pull
git branch -d feature/user-profile
```

## 9. .gitignore: какие файлы не должны отслеживаться?

Некоторые файлы вы **не хотите** коммитить в Git-репозиторий, например:
- `node_modules/`: пакеты-зависимости, огромного размера, можно заново сгенерировать через `npm install`
- `.env`: файл переменных окружения, в нём могут быть пароль БД, API Key, **категорически нельзя выгружать в публичный репозиторий**
- `*.log`: файлы логов
- `.DS_Store`: скрытый файл, автоматически генерируемый macOS
- `dist/`, `build/`: продукты компиляции, можно пересобрать

Создайте в корне проекта файл `.gitignore` и впишите правила для файлов, которые не нужно отслеживать:

```gitignore
# Пакеты-зависимости
node_modules/

# Переменные окружения (важно! пароли коммитить нельзя)
.env
.env.local

# Продукты сборки
dist/
build/

# Системные файлы
.DS_Store
Thumbs.db

# Логи
*.log
```

На GitHub есть шаблоны .gitignore для разных языков и фреймворков: [github.com/github/gitignore](https://github.com/github/gitignore)

## Шпаргалка по терминам

| Термин | Английский | Пояснение |
| :--- | :--- | :--- |
| **Репозиторий** | Repository (Repo) | База данных, хранящая всю историю версий проекта, в папке `.git` |
| **Коммит** | Commit | Полная запись версии, как точка сохранения в игре, с описанием и временной меткой |
| **Ветка** | Branch | Независимая линия разработки, как параллельная временная линия, не влияют друг на друга |
| **Слияние** | Merge | Интеграция изменений одной ветки в другую |
| **Конфликт** | Conflict | Одну строку кода изменили несколько человек, Git не знает, какую использовать, нужно разрешить вручную |
| **Подготовка** | Stage / Index | Операция помещения изменений в список «готовых к коммиту» |
| **Удалённый** | Remote | Облачная копия репозитория (GitHub / GitLab / Gitee) |
| **Клонирование** | Clone | Полное копирование всего удалённого репозитория локально |
| **Push** | Push | Выгрузка локальных коммитов в удалённый репозиторий |
| **Pull** | Pull | Скачивание и слияние последнего содержимого с удалённого репозитория локально |
| **HEAD** | HEAD | Указатель на текущую ветку/коммит, означает «где вы сейчас находитесь» |
| **origin** | origin | Псевдоним удалённого репозитория по умолчанию (общепринятое имя) |
| **stash** | Stash | Временное сохранение ещё не закоммиченных изменений, используется при переключении задач |
| **PR / MR** | Pull Request / Merge Request | Запрос на слияние вашей ветки в основную, обычно требует review коллеги |
