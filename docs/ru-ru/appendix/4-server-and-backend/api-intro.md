# Введение в API: понимаем «диалог между программами» с нуля

::: tip 🎯 Ключевой вопрос
**Что такое API?** Это как спросить: как составить меню в ресторане, чтобы гость сразу всё понял? Как официанту принять заказ, не допустив ошибки? API решает именно проблему «как программы общаются друг с другом». Вы используете API с первого дня написания кода, просто, возможно, не осознаёте этого.
:::

## 0. Три распространённых заблуждения новичков

**Заблуждение первое: API — это что-то очень сложное?**

Многие, услышав про API, думают, что это концепция, доступная только опытным инженерам. На самом деле вы давно уже использовали API:

```python
len("hello")        # Это API, предоставляемый Python
open("file.txt")    # Это тоже API
requests.get(url)   # И это тоже API
```

**Заблуждение второе: чем Web API отличается от обычного API?**

| Тип | Объект вызова | Способ связи | Типичный сценарий |
| :--- | :--- | :--- | :--- |
| **Функциональный API** | Локальный код | Вызов функции | `len()`, `open()` |
| **API операционной системы** | Операционная система | Системный вызов | Чтение/запись файлов, создание процессов |
| **Web API** | Удалённый сервер | HTTP-запрос | Вызов AI-модели, получение погоды |

**Заблуждение третье: мне использовать HTTP или SDK?**

```python
# Способ через HTTP: вы обрабатываете все детали сами
import requests
response = requests.post(
    "https://api.deepseek.com/v1/chat/completions",
    headers={"Authorization": "Bearer sk-xxx"},
    json={"model": "deepseek-chat", "messages": [...]}
)
result = response.json()["choices"][0]["message"]["content"]

# Способ через SDK: «дворецкий» делает всё за вас
from openai import OpenAI
client = OpenAI(api_key="sk-xxx")
response = client.chat.completions.create(
    model="deepseek-chat",
    messages=[...]
)
result = response.choices[0].message.content
```

## 1. Суть API: вилка и розетка

**API** (Application Programming Interface, программный интерфейс приложения) — это «договорённость о диалоге между программами».

### 1.1 Аналогия с электроприборами

| Понятие | Аналогия с электроприбором | Соответствие в API |
| :--- | :--- | :--- |

| **Вход** | Подача тока | Параметры функции / тело запроса |
| **Выход** | Работа прибора | Возвращаемое значение / тело ответа |

### 2.1 Четыре этапа вызова API

| Этап | Что происходит | Аналогия с электроприбором |
| :--- | :--- | :--- |
| **Запрос** | Клиент отправляет запрос на сервер | Нажатие выключателя |

| Роль в ресторане | Соответствие в API | Пояснение |

| **Кухня** | Сервер | Обрабатывает запрос по «заказу» |
| **Подача блюд** | Ответ | Возвращает результат «гостю» |

## 3. HTTP-методы: вы «спрашиваете» или «делаете»?

При вызове Web API вам нужно сообщить серверу, что вы хотите сделать. Отсюда и появились HTTP-методы.

### 3.1 Понимаем через заказ блюд в ресторане

| Сценарий | Как бы вы сказали в реальности? | Соответствующий HTTP-метод |
| :--- | :--- | :--- |
| Вы хотите узнать, какие блюда есть сегодня | «Официант, покажите мне меню» | **GET** — чистый «вопрос», не меняет данные |
| Вы хотите заказать порцию курицы гунбао | «Принесите мне порцию курицы гунбао» | **POST** — «делаете» что-то, создаёте данные |
| Вы хотите заменить блюдо | «Замените курицу гунбао на свинину в кисло-сладком соусе» | **PUT** — заменяете данные |
| Вы хотите изменить вкус | «В курицу гунбао не кладите арахис» | **PATCH** — частичное изменение |
| Вы передумали | «Ладно, это блюдо не нужно» | **DELETE** — удаляете данные |

<HttpMethodsDemo />

::: warning Об идемпотентности
**Идемпотентность**: одинаков ли результат при многократном выполнении?

- **Идемпотентные операции** (GET/PUT/DELETE): нажать 10 раз и нажать 1 раз — результат одинаков
- **Неидемпотентные операции** (POST): нажав 10 раз, можно создать 10 заказов

**Решение**: для POST-операций использовать проверку по уникальному ID, чтобы избежать повторной обработки.
:::

### 3.2 Шпаргалка по HTTP-методам

| Метод | Назначение | Идемпотентность | Безопасность | Типичный сценарий |
| :--- | :--- | :--- | :--- | :--- |
| **GET** | Получение ресурса | Да | Да | Запрос списка, просмотр деталей |
| **POST** | Создание ресурса | Нет | Нет | Добавление пользователя, отправка заказа |
| **PUT** | Полное обновление | Да | Нет | Замена всего профиля пользователя |
| **PATCH** | Частичное обновление | Нет | Нет | Изменение только никнейма |
| **DELETE** | Удаление ресурса | Да | Нет | Удаление пользователя, отмена заказа |

Отвечая, сервер сначала возвращает статус-код, который говорит, успешен ли запрос.

### 4.1 Классификация статус-кодов

<StatusCodeCategories />

### 4.2 Подробно о распространённых статус-кодах

| Статус-код | Значение | Типичный сценарий | Обработка на клиенте |
| :--- | :--- | :--- | :--- |
| **200 OK** | Успех | Запрос обработан нормально | Отобразить данные |
| **201 Created** | Создано успешно | POST-запрос успешно создал ресурс | Перейти к новому ресурсу |
| **400 Bad Request** | Ошибка формата запроса | Параметр отсутствует или неверного формата | Проверить параметры |
| **401 Unauthorized** | Не аутентифицирован | Не предоставлен действительный API Key | Направить пользователя на вход |
| **403 Forbidden** | Нет прав | У API Key нет прав доступа к этому ресурсу | Сообщить о недостатке прав |
| **404 Not Found** | Не существует | Запрошенный адрес или ресурс не существует | Проверить URL |
| **429 Too Many Requests** | Слишком много запросов | Превышено ограничение частоты | Повторить позже |
| **500 Internal Server Error** | Ошибка сервера | Проблема на стороне сервера | Предложить пользователю повторить позже |

## 5. HTTP vs SDK: бегать самому или поручить дворецкому?

### 5.1 Сравнение двух способов вызова

| | 🏃 **HTTP API** | 🤵 **SDK** |
| :--- | :--- | :--- |
| **Метафора** | Бегаете сами | Дворецкий делает за вас |
| **Плюсы** | ✓ Работает на любом языке<br>✓ Полный контроль над деталями запроса<br>✓ Не нужны дополнительные зависимости | ✓ Код лаконичен и читаем<br>✓ Автоматическая обработка аутентификации<br>✓ Встроенные повторы при ошибках |
| **Минусы** | ✗ Нужно обрабатывать все детали<br>✗ Код длинный и подвержен ошибкам | ✗ Нужно устанавливать зависимости<br>✗ Возможны проблемы с версиями |
| **Пример кода** | `requests.post(url, json=..., headers={...})` | `client.chat.completions.create(...)` |

### 5.2 Как выбрать?

| Сценарий | Рекомендуемый способ | Причина |
| :--- | :--- | :--- |
| **Быстрая разработка** | SDK | Автоматическая обработка аутентификации, ошибок, повторов |
| **Изучение принципов** | HTTP | Понимание низкоуровневого механизма |
| **Неподдерживаемый язык** | HTTP | Работает на любом языке |
| **Нужна кастомизация** | HTTP | Гибкий контроль над каждой деталью |

::: tip 💡 Рекомендация
**Если можно использовать SDK — используйте SDK**, отдайте хлопоты библиотеке, а время оставьте себе.
:::

## 6. Как читать документацию API?

Документация API — это нечто среднее между инструкцией и меню. Вам не нужно читать её от начала до конца, нужно лишь научиться «искать в словаре».

### 6.1 Чек-лист чтения документации

Открыв любую документацию API (например, OpenAI или DeepSeek), вам нужно найти лишь несколько вещей:

<ApiDocumentDemo />

| Пункт | Пояснение | Пример |
| :--- | :--- | :--- |
| **Base URL** | Корневой адрес API | `https://api.deepseek.com` |
| **Authentication** | Как подтвердить личность | `Authorization: Bearer sk-xxx` |
| **Endpoints** | Список конкретных эндпоинтов | `/v1/chat/completions` |
| **Parameters** | Обязательные/опциональные параметры | `model` (обязательный), `temperature` (опциональный) |
| **Response** | Структура возвращаемых данных | `{"choices": [...]}` |

### 6.2 Шаги чтения документации

1. **Найдите Base URL** — это префикс всех запросов
2. **Разберитесь в способе аутентификации** — API Key помещается в Header или Query?
3. **Найдите нужный Endpoint** — конкретный эндпоинт, который вы хотите вызвать
4. **Посмотрите параметры запроса** — какие обязательны? какие опциональны?
5. **Поймите формат ответа** — как организованы данные?

## 8. Заключение

::: info Ключевые моменты
1. **API — это переговорная трубка**, которая помогает передать ваши слова другому фрагменту кода или удалённому серверу
2. **Вы давно уже использовали API**: от `len()` до `open()` — всё это API
3. **Web API — это суперспособность**, позволяющая вызывать суперкомпьютер за тысячи километров
4. **SDK — хороший дворецкий**: если можно использовать SDK, не бегайте сами
5. **В документации ищите три вещи**: адрес, аутентификацию, параметры
:::

В эпоху AI-программирования вам нужно лишь запомнить эти ключевые понятия. Остальные детали возьмут на себя IDE и AI-ассистент.

## Шпаргалка по терминам

| Термин | Полное название | Объяснение |
| :--- | :--- | :--- |
| **API** | Application Programming Interface | Программный интерфейс приложения, определяет, как взаимодействует программное обеспечение |
| **Web API** | - | API на основе протокола HTTP, для сетевого взаимодействия |
| **Endpoint** | - | Эндпоинт, конкретный адрес API |
| **HTTP** | HyperText Transfer Protocol | Протокол связи, используемый Web API |
| **GET** | - | Метод получения ресурса |
| **POST** | - | Метод отправки данных |
| **SDK** | Software Development Kit | Набор инструментов разработки, инкапсулирующий низкоуровневые вызовы API |
| **URL** | Uniform Resource Locator | Сетевой адрес API |
| **JSON** | JavaScript Object Notation | Распространённый формат данных |
| **Authentication** | - | Процесс проверки личности |
| **Status Code** | - | Статус-код в HTTP-ответе |
| **Request** | - | Запрос |
| **Response** | - | Ответ |
| **Header** | - | HTTP-заголовок, содержит метаинформацию |
| **Payload** | - | Фактические данные запроса или ответа |
| **Rate Limit** | - | Ограничение частоты |
| **Idempotent** | - | Идемпотентность, многократное выполнение даёт одинаковый результат |
| **REST** | Representational State Transfer | Архитектурный стиль API |
| **RPC** | Remote Procedure Call | Удалённый вызов процедур |
| **GraphQL** | - | API в виде языка запросов |
| **gRPC** | - | Высокопроизводительный RPC-фреймворк, разработанный Google |
