## 0. Введение: почему ваш сервис «зависает» в час пик?

<ProcessThreadCoroutineDemo />

Многие в реальной разработке сталкиваются с похожими ситуациями:

- При локальном тестировании сервис отвечает молниеносно, а после выкладки «тормозит как PPT-презентация»;
- Хотя куплена очень мощная конфигурация сервера, загрузка CPU никак не поднимается;
- В пик распродаж сервис «лавинообразно падает», приходится прибегать к деградации или размыканию цепи.

Интуитивно мы думаем, что дело в: **«сервер недостаточно мощный»**.
Но в большинстве случаев проблема не в том, что железо «недостаточно быстрое», а в том, что мы **плохо спроектировали модель конкурентности**.

**Ключевое противоречие**:
- Если не обрабатывать конкурентно: запросы пользователей выстраиваются в очередь, опыт ужасен;
- Если бездумно использовать многопоточность: конкуренция за блокировки, накладные расходы на переключение контекста, производительность наоборот падает.

Перед лицом этих вызовов простое «добавление машин» уже не справляется. Нам нужен системный метод проектирования конкурентности, который в сценариях высокой конкурентности обеспечивает и производительность, и стабильность. Именно эту проблему и пытается решить данная глава.

## 1. Ключевые понятия: процесс, поток, корутина — в чём же разница?

### 1.1 Аналогия с рестораном

Представьте, что вы открыли ресторан и должны обслуживать множество гостей одновременно:

| Понятие | Аналогия с рестораном | Технический смысл |
| :--- | :--- | :--- |
| **Процесс (Process)** | **Независимый филиал ресторана** | Обладает независимым пространством памяти и распределением ресурсов, является базовой единицей распределения ресурсов ОС. Падение одного процесса не влияет на другие. |
| **Поток (Thread)** | **Повар внутри филиала** | Базовая единица планирования CPU, разделяет пространство памяти внутри процесса. Потоки одного процесса могут разделять данные, но падение одного потока может уронить весь процесс. |
| **Корутина (Coroutine)** | **«Раздвоение» повара** | Лёгкий поток в пространстве пользователя, планируемый самой программой, а не операционной системой. Накладные расходы на переключение крайне малы, можно создать миллионы. |

### 1.2 Глубокое сравнение: сущностные различия трёх

<ProcessIsolationDemo />

#### Процесс: «контейнер» изоляции ресурсов

**Ключевые особенности**:
- **Сильная изоляция**: у каждого процесса независимое виртуальное адресное пространство
- **Большие накладные расходы**: создание/переключение требуют вмешательства ОС, занимают около 1-10 мс
- **Сложная коммуникация**: межпроцессное взаимодействие (IPC) требует специальных механизмов (каналы, очереди сообщений, разделяемая память и т. д.)

**Сценарии применения**:
- Сервисы, требующие сильной изоляции (вкладки браузера, программы-песочницы)
- Сервисы со смешанным развёртыванием на нескольких языках
- Сервисные единицы, требующие независимого перезапуска/обновления

#### Поток: «лёгкая кавалерия» разделяемой памяти

<ThreadSchedulingDemo />

**Ключевые особенности**:
- **Разделяемая память**: потоки одного процесса разделяют сегмент кода, сегмент данных, кучу
- **Независимое пространство стека**: у каждого потока свой стек (обычно около 1 МБ)
- **Относительно быстрое переключение**: переключение потоков около 1-10 мкс, в 1000 раз быстрее процессов
- **Требуется синхронизация**: разделяемые данные нужно защищать блокировками

**Сценарии применения**:
- CPU-интенсивные задачи (вычисления, обработка изображений)
- Конкурентные задачи, требующие разделения большого объёма данных
- Фоновые задачи, чувствительные к задержке

#### Корутина: «зелёный поток» в пространстве пользователя

<CoroutineLightweightDemo />

**Ключевые особенности**:
- **Планирование в пространстве пользователя**: планируется программой/библиотекой времени выполнения, минуя ОС
- **Крайняя лёгкость**: стек корутины обычно всего несколько КБ, можно создать миллионы
- **Крайне быстрое переключение**: переключение корутин около 100 нс, в 100 раз быстрее потоков
- **Невытесняющее**: корутина добровольно уступает CPU (кооперативная многозадачность)

**Сценарии применения**:
- I/O-интенсивные высококонкурентные сервисы (Web-серверы, шлюзы)
- Сценарии с большим количеством долгих соединений (IM, игровые серверы)
- Потоковая обработка данных, конвейерные работы

## 2. Разбор кейса: «боль конкурентности» в крупной распродаже электронной коммерции

### 2.1 Урок кровью и слезами: эволюция от «одной машины» к «распределённому»

Рассмотрим реальную историю эволюции системы электронной коммерции:

#### Этап первый: эра одной машины (DAU 1000)

```python
# Простое приложение Flask
from flask import Flask

app = Flask(__name__)

@app.route('/order')
def create_order():
    # Запрос наличия на складе
    stock = db.query("SELECT stock FROM products WHERE id=1")
    if stock > 0:
        # Списание со склада
        db.execute("UPDATE products SET stock = stock - 1 WHERE id=1")
        # Создание заказа
        db.execute("INSERT INTO orders ...")
        return "Order created!"
    return "Out of stock!"

# Запуск: flask run
```

**Проблемы**:
- Один процесс, один поток, может обрабатывать только один запрос за раз
- Списание со склада без блокировки, при конкурентности возникает оверселл (продажа больше, чем есть)
- Число соединений с базой данных ограничено, пул соединений быстро исчерпывается

#### Этап второй: эра многопроцессности (DAU 10 тыс.)

```python
# Многопроцессное развёртывание с помощью Gunicorn
gunicorn -w 4 -k sync app:app

# 4 worker-процесса, каждый процесс независимо обрабатывает запросы
```

**Новые проблемы**:
- 4 процесса одновременно запрашивают наличие, все видят stock=1, все успешно списывают, оверселл на 3 единицы!
- Нужно внедрить распределённую блокировку

```python
import redis

# Распределённая блокировка с помощью Redis
lock = redis_client.lock("stock_lock", timeout=10)
if lock.acquire():
    try:
        stock = db.query("SELECT stock FROM products WHERE id=1")
        if stock > 0:
            db.execute("UPDATE products SET stock = stock - 1 WHERE id=1")
    finally:
        lock.release()
```

#### Этап третий: эра корутин (DAU 100 тыс.)

```python
# Использование FastAPI + asyncio
from fastapi import FastAPI
import asyncio

app = FastAPI()

async def check_stock(product_id: int) -> int:
    # Асинхронный запрос к базе данных, без блокировки
    result = await db.fetch_one(
        "SELECT stock FROM products WHERE id = :id",
        {"id": product_id}
    )
    return result["stock"]

@app.get("/order")
async def create_order(product_id: int):
    # Конкурентная проверка наличия и информации о пользователе
    stock_task = check_stock(product_id)
    user_task = get_user_info(request.user_id)

    stock, user = await asyncio.gather(stock_task, user_task)

    if stock > 0:
        # Асинхронное списание со склада
        await db.execute(
            "UPDATE products SET stock = stock - 1 WHERE id = :id",
            {"id": product_id}
        )
        return {"status": "success"}

    return {"status": "out_of_stock"}

# Запуск: uvicorn main:app --workers 4
# Внутри каждого worker можно обрабатывать тысячи конкурентных корутин
```

**Преимущества**:
- Внутри одного потока можно обрабатывать тысячи конкурентных соединений
- При I/O-операциях добровольно уступает CPU, не блокируя другие запросы
- Крайне низкое потребление памяти, подходит для сценариев высокой конкурентности с долгими соединениями

| :--- | :--- | :--- | :--- |

### 3.2 Модель потоков: планирование и синхронизация

#### Принцип планирования потоков

<ThreadSchedulingDemo />

Базовая работа планировщика потоков операционной системы:

```
Очередь готовых              В работе               Очередь ожидания
+--------+                +--------+               +--------+
|Поток B |  <-- квант    |Поток A |  <-- I/O-запрос|Поток C |
|Поток D |  истёк        |(работа)|               |Поток E |
|Поток F |                +--------+               |(блок.) |
+--------+                                          +--------+
    |                                                  |
    v                                                  v
Планировщик выбирает следующий по приоритету   При завершении I/O возврат в очередь готовых
```

#### Распространённые механизмы синхронизации потоков

| Механизм | Принцип | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **Мьютекс (Mutex)** | Двоичное состояние, эксклюзивный доступ | Простая реализация | Плохая производительность при сильной конкуренции |
| **Блокировка чтения-записи (RWLock)** | Чтение разделяемое, запись эксклюзивная | Эффективна при «много чтения, мало записи» | Сложная реализация, риск голодания записи |
| **Спин-блокировка (Spinlock)** | Активное ожидание, не освобождает CPU | Эффективна при коротком ожидании | Тратит CPU при долгом ожидании |
| **Условная переменная** | Ожидание выполнения определённого условия | Избегает активного ожидания | Требует использования совместно с блокировкой |
| **Семафор (Semaphore)** | Счётчик контролирует число доступов | Может контролировать число параллельных | Легко ошибиться при неправильном использовании |
| **Атомарная операция** | Атомарность на уровне инструкций CPU | Без блокировок, высочайшая производительность | Может работать только с простыми типами данных |
| **Очередь без блокировок** | Реализация через CAS-операции | Отличная производительность при высокой конкуренции | Сложная реализация, проблема ABA |

#### Механизм работы async/await

<AsyncAwaitDemo />

```python
import asyncio

async def fetch_data(url):
    # При встрече await корутина приостанавливается, уступает CPU
    response = await aiohttp.get(url)
    # После завершения I/O цикл событий пробуждает корутину, продолжаем отсюда
    return response.json()

async def main():
    # Создаём 3 задачи-корутины
    tasks = [
        fetch_data("https://api1.example.com"),
        fetch_data("https://api2.example.com"),
        fetch_data("https://api3.example.com")
    ]
    # Конкурентное выполнение, общее время ≈ самый медленный запрос
    results = await asyncio.gather(*tasks)
    return results

# Запуск цикла событий
asyncio.run(main())
```

**Процесс выполнения**:

```
Временная линия ----------------------------------------------------------->

Корутина A: [подготовка запроса]--[await приостановка]=======[получен ответ]--[обработка данных]
                     |
Корутина B:          [подготовка запроса]--[await приостановка]=======[получен ответ]--[обработка данных]
                                  |
Корутина C:                       [подготовка запроса]--[await приостановка]=======[получен ответ]
                                               |
                                               ↓
                                         Весь I/O завершён

Пояснение: [ ] обозначает выполнение CPU, === обозначает ожидание I/O, | обозначает переключение корутины
```

### 3.4 Цикл событий: «сердце» корутин

<EventLoopDemo />

Цикл событий — это основной механизм планирования корутин:

```python
import selectors
import heapq

class EventLoop:
    def __init__(self):
        self.selector = selectors.DefaultSelector()
        self.ready = []  # очередь готовых
        self.scheduled = []  # очередь задач по таймеру
        self.current = None

    def run(self):
        while True:
            # 1. Обрабатываем задачи по таймеру
            now = time.time()
            while self.scheduled and self.scheduled[0][0] <= now:
                _, callback = heapq.heappop(self.scheduled)
                self.ready.append(callback)

            # 2. Ожидаем I/O-события
            timeout = 0 if self.ready else 0.1
            events = self.selector.select(timeout)

            for key, mask in events:
                callback = key.data
                self.ready.append(callback)

            # 3. Выполняем готовые колбэки
            while self.ready:
                callback = self.ready.popleft()
                callback()
```

### 3.5 Конкурентность vs параллелизм: это не одно и то же

<ConcurrentVsParallelDemo />

| Понятие | Английский | Смысл | Аналогия | Необходимые условия |
| :--- | :--- | :--- | :--- | :--- |
| **Конкурентность** | Concurrency | Несколько задач выполняются попеременно, на макроуровне продвигаясь одновременно | Один человек по очереди готовит несколько блюд | Достаточно одноядерного CPU |
| **Параллелизм** | Parallelism | Несколько задач выполняются по-настоящему одновременно | Несколько человек одновременно готовят разные блюда | Многоядерный CPU или несколько машин |

**Схематическое пояснение**:

```
Одноядерный CPU — конкурентность (Concurrent)
Время →  1    2    3    4    5    6    7    8
Задача A: [выпол][выпол]      [выпол][выпол]
Задача B:      [выпол][выпол]      [выпол][выпол]

Две задачи выполняются попеременно, на макроуровне продвигаясь «одновременно»

========================================

Многоядерный CPU — параллелизм (Parallel)
Время →  1    2    3    4    5    6    7    8
Ядро 1: [задачаA][задачаA][задачаA][задачаA]
Ядро 2: [задачаB][задачаB][задачаB][задачаB]

Две задачи выполняются по-настоящему «одновременно»

========================================

В реальности часто бывает: конкурентность + параллелизм
Время →  1    2    3    4    5    6    7    8
Ядро 1: [A1][A1][B1][B1][C1][C1][D1][D1]
Ядро 2: [A2][A2][B2][B2][C2][C2][D2][D2]

Несколько задач сначала конкурентно распределяются по разным ядрам, затем параллельно выполняются на ядрах
```

## 4. Практика: корутины Go и зелёные потоки

### 4.1 Философия конкурентности Go

<GoroutineGreenThreadDemo />

Философия проектирования конкурентности языка Go: **не общайтесь через разделяемую память, а разделяйте память через общение**.

```go
package main

import (
    "fmt"
    "time"
)

// Производитель
func producer(ch chan<- int, id int) {
    for i := 0; i < 5; i++ {
        fmt.Printf("Producer %d sending: %d\n", id, i)
        ch <- i  // отправка данных в channel
        time.Sleep(100 * time.Millisecond)
    }
}

// Потребитель
func consumer(ch <-chan int, id int) {
    for val := range ch {  // получение данных из channel
        fmt.Printf("Consumer %d received: %d\n", id, val)
    }
}

func main() {
    // Создаём channel с буфером
    ch := make(chan int, 10)

    // Запускаем 2 goroutine-производителя
    for i := 0; i < 2; i++ {
        go producer(ch, i)
    }

    // Запускаем 2 goroutine-потребителя
    for i := 0; i < 2; i++ {
        go consumer(ch, i)
    }

    // Ждём некоторое время
    time.Sleep(3 * time.Second)
    close(ch)
}
```

### 4.2 Планировщик Goroutine: модель GMP

Планировщик Go использует модель GMP:

| Компонент | Смысл | Роль |
| :--- | :--- | :--- |
| **G (Goroutine)** | Корутина | Задача к выполнению, лёгкая (стек 2КБ, может динамически расширяться) |
| **M (Machine)** | Системный поток | Носитель, фактически выполняющий G, соответствует потоку ядра 1:1 |
| **P (Processor)** | Логический процессор | Контекст планирования, содержит очередь выполнимых G, число по умолчанию равно числу ядер CPU |

**Процесс планирования**:

```
Глобальная очередь
+----------------+
|  G1  |  G2  |  G3  |
+----------------+

Локальная очередь P0  Локальная очередь P1  Локальная очередь P2  Локальная очередь P3
+----------+       +----------+       +----------+       +----------+
| G4 | G5  |       | G6 | G7  |       | G8 | G9  |       | G10| G11 |
+----------+       +----------+       +----------+       +----------+
    |                     |                     |                     |
    v                     v                     v                     v
+----------+       +----------+       +----------+       +----------+
|    M0    |       |    M1    |       |    M2    |       |    M3    |
| (ОС-поток)|      | (ОС-поток)|      | (ОС-поток)|      | (ОС-поток)|
+----------+       +----------+       +----------+       +----------+

Стратегия планирования:
1. Каждый P поддерживает локальную очередь G, снижая конкуренцию за блокировки
2. P берёт G из локальной очереди и передаёт M на выполнение
3. Когда локальная очередь пуста, «крадёт» половину G у других P (Work Stealing)
4. Глобальная очередь служит подстраховкой, проверяется через определённые интервалы
```

### 5.1 Шаблон высокой конкурентности Python asyncio

```python
import asyncio
import aiohttp
from typing import List, Dict
import time

class AsyncHTTPClient:
    """Высокопроизводительный HTTP-клиент на основе asyncio"""

    def __init__(self, max_connections: int = 100, timeout: int = 30):
        self.timeout = aiohttp.ClientTimeout(total=timeout)
        # Ограничиваем число конкурентных соединений, чтобы не уронить чужой сервис
        connector = aiohttp.TCPConnector(
            limit=max_connections,
            limit_per_host=10,  # ограничение соединений на один домен
            enable_cleanup_closed=True,
            force_close=True,
        )
        self.session = aiohttp.ClientSession(
            connector=connector,
            timeout=self.timeout,
        )

    async def fetch(self, url: str, method: str = 'GET', **kwargs) -> Dict:
        """Отправка одного запроса"""
        try:
            async with self.session.request(method, url, **kwargs) as response:
                return {
                    'url': url,
                    'status': response.status,
                    'data': await response.text(),
                    'error': None
                }
        except asyncio.TimeoutError:
            return {'url': url, 'status': None, 'data': None, 'error': 'Timeout'}
        except Exception as e:
            return {'url': url, 'status': None, 'data': None, 'error': str(e)}

    async def fetch_many(self, urls: List[str], concurrency: int = 10) -> List[Dict]:
        """Конкурентное получение нескольких URL с ограничением числа параллельных"""
        semaphore = asyncio.Semaphore(concurrency)

        async def fetch_with_limit(url):
            async with semaphore:
                return await self.fetch(url)

        # Конкурентное выполнение всех запросов
        tasks = [fetch_with_limit(url) for url in urls]
        return await asyncio.gather(*tasks, return_exceptions=True)

    async def close(self):
        await self.session.close()


# Пример использования
async def main():
    client = AsyncHTTPClient(max_connections=50)

    # Список URL для скачивания
    urls = [
        "https://api.github.com/users/github",
        "https://api.github.com/users/google",
        "https://api.github.com/users/microsoft",
        # ... больше URL
    ] * 10  # имитируем 300 запросов

    start = time.time()
    results = await client.fetch_many(urls, concurrency=20)
    elapsed = time.time() - start

    # Подсчёт результатов
    success = sum(1 for r in results if r.get('status') == 200)
    failed = len(results) - success

    print(f"Всего запросов: {len(results)}")
    print(f"Успешно: {success}, неудачно: {failed}")
    print(f"Время: {elapsed:.2f}s")
    print(f"QPS: {len(results)/elapsed:.1f}")

    await client.close()

if __name__ == "__main__":
    asyncio.run(main())
```

### 5.2 Шаблон высококонкурентного сервиса Go

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"log"
	"net/http"
	"runtime"
	"time"

	"golang.org/x/sync/errgroup"
)

// Структуры Request/Response
type OrderRequest struct {
	UserID    int64   `json:"user_id"`
	ProductID int64   `json:"product_id"`
	Quantity  int     `json:"quantity"`
	Price     float64 `json:"price"`
}

type OrderResponse struct {
	OrderID   int64   `json:"order_id"`
	Status    string  `json:"status"`
	Total     float64 `json:"total"`
	CreatedAt string  `json:"created_at"`
}

// Имитация операций с базой данных
type Database struct {
	orders map[int64]*OrderResponse
	mutex  chan struct{}
}

func NewDatabase() *Database {
	db := &Database{
		orders: make(map[int64]*OrderResponse),
		mutex:  make(chan struct{}, 1), // имитация мьютекса
	}
	return db
}

func (db *Database) CreateOrder(ctx context.Context, req *OrderRequest) (*OrderResponse, error) {
	// Получаем блокировку
	select {
	case db.mutex <- struct{}{}:
		defer func() { <-db.mutex }()
	case <-ctx.Done():
		return nil, ctx.Err()
	}

	// Имитация задержки операции с базой данных
	select {
	case <-time.After(50 * time.Millisecond):
	case <-ctx.Done():
		return nil, ctx.Err()
	}

	order := &OrderResponse{
		OrderID:   time.Now().UnixNano(),
		Status:    "created",
		Total:     req.Price * float64(req.Quantity),
		CreatedAt: time.Now().Format(time.RFC3339),
	}
	db.orders[order.OrderID] = order
	return order, nil
}

// HTTP-обработчик
type Handler struct {
	db *Database
}

func NewHandler(db *Database) *Handler {
	return &Handler{db: db}
}

func (h *Handler) CreateOrder(w http.ResponseWriter, r *http.Request) {
	// Устанавливаем таймаут запроса
	ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
	defer cancel()

	var req OrderRequest
	if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
		http.Error(w, err.Error(), http.StatusBadRequest)
		return
	}

	order, err := h.db.CreateOrder(ctx, &req)
	if err != nil {
		if err == context.DeadlineExceeded {
			http.Error(w, "Request timeout", http.StatusGatewayTimeout)
			return
		}
		http.Error(w, err.Error(), http.StatusInternalServerError)
		return
	}

	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(order)
}

func (h *Handler) Health(w http.ResponseWriter, r *http.Request) {
	info := map[string]interface{}{
		"status":    "ok",
		"goroutine": runtime.NumGoroutine(),
		"cpu":       runtime.NumCPU(),
		"version":   runtime.Version(),
	}
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(info)
}

// Пример пакетной обработки
func BatchProcess(ctx context.Context, items []int) ([]int, error) {
	g, ctx := errgroup.WithContext(ctx)
	g.SetLimit(10) // ограничиваем число параллельных до 10

	results := make([]int, len(items))

	for i, item := range items {
		i, item := i, item // избегаем ловушки замыкания
		g.Go(func() error {
			select {
			case <-ctx.Done():
				return ctx.Err()
			default:
				// Имитация обработки
				time.Sleep(100 * time.Millisecond)
				results[i] = item * 2
				return nil
			}
		})
	}

	if err := g.Wait(); err != nil {
		return nil, err
	}
	return results, nil
}

func main() {
	// Инициализация базы данных
	db := NewDatabase()

	// Создаём обработчик
	handler := NewHandler(db)

	// Настраиваем маршрутизацию
	mux := http.NewServeMux()
	mux.HandleFunc("/order", handler.CreateOrder)
	mux.HandleFunc("/health", handler.Health)

	// Создаём сервер
	server := &http.Server{
		Addr:         ":8080",
		Handler:      mux,
		ReadTimeout:  5 * time.Second,
		WriteTimeout: 10 * time.Second,
		IdleTimeout:  120 * time.Second,
	}

	fmt.Println("Server starting on :8080")
	fmt.Printf("Go version: %s\n", runtime.Version())
	fmt.Printf("CPU cores: %d\n", runtime.NumCPU())

	if err := server.ListenAndServe(); err != nil {
		log.Fatal(err)
	}
}
```

### 6.1 Сравнение ключевых понятий

| Характеристика | Процесс | Поток | Корутина |
| :--- | :--- | :--- | :--- |

| **Накладные расходы на переключение** | ~1-10 мс | ~1-10 мкс | ~100 нс |

| **Способ коммуникации** | IPC | Разделяемая память | Разделяемая память/Channel |
| **Потребность в синхронизации** | Не нужна | Нужны блокировки | Нужны блокировки/кооперативность |
| **Влияние падения** | Только текущий процесс | Весь процесс | Контролируемо |

| **Типичные языки** | Все языки | Все языки | Go, Python, JS, Rust |

### 6.2 Руководство по выбору модели конкурентности

| Сценарий | Рекомендуемая модель | Обоснование |
| :--- | :--- | :--- |
| Шлюз веб-сервисов | Корутины + асинхронный I/O | Высокая конкурентность соединений, низкое потребление памяти |
| Сервис связи в реальном времени | Корутины + долгие соединения | Поддержание большого числа WebSocket-соединений |
| Конвейер обработки данных | Многопроцессность + корутины | Использование многоядерности, I/O не блокирует |
| Научные вычисления | Многопоточность/многопроцессность | CPU-интенсивные, нужны параллельные вычисления |
| Микросервисная архитектура | Многопроцессность + корутины | Изоляция между сервисами, высокая конкурентность внутри |
| Встраиваемые системы | Корутины/один поток | Ограниченность ресурсов, детерминированное планирование |

### 6.3 Таблица соответствия терминов

| Английский термин | Русский эквивалент | Объяснение |
| :--- | :--- | :--- |
| **Process** | Процесс | Базовая единица распределения ресурсов ОС, обладает независимым пространством памяти |
| **Thread** | Поток | Базовая единица планирования CPU, разделяет пространство памяти процесса |
| **Coroutine** | Корутина | Лёгкий поток в пространстве пользователя, планируемый самой программой |
| **Concurrency** | Конкурентность | Несколько задач выполняются попеременно, на макроуровне продвигаясь одновременно |
| **Parallelism** | Параллелизм | Несколько задач выполняются по-настоящему одновременно, нужна многоядерность |
| **Context Switch** | Переключение контекста | Процесс переключения CPU с одной задачи на другую |
| **Blocking I/O** | Блокирующий I/O | После I/O-запроса ожидание завершения, на это время поток приостановлен |
| **Non-blocking I/O** | Неблокирующий I/O | После I/O-запроса немедленный возврат, без ожидания результата |
| **Async I/O** | Асинхронный I/O | По завершении I/O вызывающий уведомляется через колбэк или механизм уведомления |
| **Event Loop** | Цикл событий | Механизм планирования корутин, непрерывно отслеживает события и распределяет их обработку |
| **Goroutine** | Корутина Go | Реализация лёгкого потока в языке Go |
| **Channel** | Канал | Механизм связи между корутинами в языке Go |
| **Mutex** | Мьютекс | Примитив синхронизации для защиты разделяемых ресурсов |
| **Semaphore** | Семафор | Контролирует число потоков, одновременно обращающихся к ресурсу |
| **Deadlock** | Взаимоблокировка | Несколько потоков взаимно ждут освобождения ресурсов друг друга, что приводит к вечной блокировке |
| **Race Condition** | Гонка данных | Несколько потоков одновременно обращаются к разделяемым данным, приводя к неопределённому результату |
| **Thread Pool** | Пул потоков | Заранее создаётся группа потоков, переиспользуется для снижения накладных расходов на создание/уничтожение |
| **Work Stealing** | Кража работы | Простаивающий поток «крадёт» задачи из очереди занятого потока для выполнения |
| **Zero-copy** | Нулевое копирование | Данные при передаче между пространством ядра и пользователя не проходят через копирование CPU |
| **C10K Problem** | Проблема C10K | Вызов одновременной обработки 10 тысяч соединений на одной машине |
| **C10M Problem** | Проблема C10M | Предельный вызов одновременной обработки 10 млн соединений на одной машине |

## 7. В заключение

### 7.1 Золотые правила конкурентного программирования

1. **Не оптимизируйте преждевременно**: сначала добейтесь правильной работы кода, затем думайте об оптимизации производительности
2. **Избегайте разделяемого состояния**: «не общайтесь через разделяемую память, а разделяйте память через общение»
3. **Выявляйте ошибки как можно раньше**: баги конкурентности часто трудно воспроизвести, нужно максимально выявлять их на этапе тестирования
4. **Ограничивайте число параллельных**: бесконечная конкурентность равносильна отсутствию защиты, нужно ограничивать семафорами или пулами соединений
5. **Мониторинг и наблюдаемость**: конкурентная система обязательно должна иметь полноценный мониторинг, чтобы быстро локализовать проблемы

### 7.2 Учебная дорожная карта

```
Этап 1: базовое понимание
    ├── Понять базовые понятия процесса/потока
    ├── Изучить примитивы синхронизации (блокировки, семафоры, условные переменные)
    └── Написать простые многопоточные программы

Этап 2: углубление в принципы
    ├── Понять модель памяти и видимость
    ├── Изучить программирование без блокировок и атомарные операции
    ├── Понять пулы потоков и кражу работы
    └── Анализировать взаимоблокировки и гонки данных

Этап 3: продвинутое применение
    ├── Освоить корутины и асинхронное программирование
    ├── Изучить модели конкурентности Go/Python/Rust
    ├── Понять конкурентность в распределённых системах
    └── Оптимизация производительности и планирование ёмкости

Этап 4: уровень эксперта
    ├── Проектировать архитектуру высококонкурентных систем
    ├── Решать сложные баги конкурентности
    ├── Разрабатывать фреймворки конкурентного программирования
    └── Делиться и распространять знания о конкурентности
```

Надеюсь, это руководство поможет вам сформировать системное понимание конкурентного программирования. Помните: **конкурентность — это не цель, а средство** — настоящая цель в том, чтобы строить высокопроизводительные и высокодоступные сервисы. Понимайте принципы, выбирайте правильную модель, пишите хороший код — и вы сможете всё дальше продвигаться на пути конкурентности.
