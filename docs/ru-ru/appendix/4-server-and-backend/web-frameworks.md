# Сущность веб-фреймворков
::: tip 🎯 Ключевой вопрос
**Код написан — как сделать так, чтобы к нему могли обращаться люди со всего мира?** Это всё равно что спросить: вы хотите открыть уличный лоток или управлять международной сетью ресторанов? Выбор бэкенд-архитектуры определяет, сколько клиентов сможет обслужить ваш «ресторан».
:::

## 1. Зачем разбираться в эволюции архитектуры?

Представьте, что вы планируете дальнее путешествие. Вы можете поехать на велосипеде, на личном автомобиле, на скоростном поезде или полететь на самолёте. У каждого способа есть свой подходящий сценарий: велосипед подходит для коротких дистанций и желания размяться, а самолёт — для дальних путешествий через континенты.

**С выбором бэкенд-архитектуры всё так же.**

С момента зарождения интернета до сегодняшнего дня бэкенд-архитектура пережила множество крупных преобразований. Каждое преобразование было не ради «погони за модой», а ради решения конкретной проблемы того времени:

| Эпоха | Ключевая проблема | Эволюция архитектуры |
| ----- | ------------------------ | ------------------- |
| 1990-е | Как запустить сайт | Физический сервер |
| 2000-е | Как поддерживать всё более запутанный код | Монолитная архитектура + MVC |
| 2010-е | Как масштабировать и сотрудничать, когда система слишком велика | Микросервисы + контейнеризация |
| 2020-е | Как снизить затраты на эксплуатацию и сложность | Serverless + облачная нативность |

::: tip 📊 Что можно увидеть из таблицы?
Разберём эту таблицу построчно:

**1990-е → 2000-е**: от «лишь бы работало» к «нужно поддерживать». Сайты превратились из статических страниц в динамические приложения, объём кода резко вырос, потребовался лучший способ организации.

**2000-е → 2010-е**: от «одной машины» к «распределённости». Число пользователей росло взрывообразно, один сервер не выдерживал, понадобилось разбивать систему и горизонтально масштабировать.

**2010-е → 2020-е**: от «собственной эксплуатации» к «облачным сервисам». Контейнеры и микросервисы хоть и мощны, но затраты на эксплуатацию слишком высоки, и Serverless позволяет разработчику сосредоточиться только на бизнес-логике.

**Ключевой вывод**: эволюция архитектуры — это не игра в выбор технологий, а процесс **решения реальных проблем**. У каждого этапа есть свой подходящий сценарий, нет «лучшей архитектуры», есть лишь «наиболее подходящая архитектура».
:::

**Смысл понимания эволюции архитектуры в том, чтобы:**

1. **Не изобретать велосипед заново**: многие «новые» концепции на самом деле зародились десятилетия назад, понимание истории позволяет встать на плечи гигантов
2. **Делать обоснованный выбор технологий**: нет лучшей архитектуры, есть лишь наиболее подходящая текущему этапу
3. **Понимать компромиссы за технологиями**: каждое преобразование архитектуры — это компромисс между **эффективностью разработки**, **производительностью системы** и **сложностью эксплуатации**
4. **Предугадывать технологические тренды**: история всегда рифмуется, понимание закономерностей прошлой эволюции помогает уловить будущее направление

## 2. Эпоха физических серверов (1990-е)

### 2.1 Что такое физический сервер?

На заре интернета бэкендом был **физический сервер** (реальный компьютер), стоящий в серверной.

::: tip 💡 Простое объяснение
**Физический сервер** — это как настольный ПК у вас дома, но он:

- Работает 7×24, не выключаясь
- Стоит в специализированном дата-центре (с кондиционером, ИБП, системой пожаротушения)
- Имеет более широкий сетевой канал (корпоративная оптоволоконная связь)
- Имеет фиксированный публичный IP-адрес (доступен из любой точки мира)

Это как ваш дом vs ресторан: дома вы готовите лишь изредка, а ресторан — профессиональная кухня, работает круглосуточно, оборудование профессиональнее.
:::

### 2.2 Ключевые особенности

- **Развёртывание на одной машине**: все приложения работают на одном физическом сервере
- **Ручная эксплуатация**: нужно вручную монтировать, прокладывать кабели, устанавливать систему
- **Вертикальное масштабирование**: при нехватке производительности можно лишь купить более мощную машину

::: details 🔧 Вертикальное масштабирование vs горизонтальное масштабирование
**Вертикальное масштабирование** (Scale Up): улучшение конфигурации одного сервера (больше CPU, больше памяти, быстрее диск).

**Горизонтальное масштабирование** (Scale Out): добавление новых серверов, чтобы они работали вместе.

**Аналогия**:

- Вертикальное масштабирование: превратить маленький ресторан в большой, отделка роскошнее, но повар по-прежнему один
- Горизонтальное масштабирование: открыть сеть, каждое заведение небольшое, но всего 100 филиалов

**Достоинства и недостатки**:

- Вертикальное масштабирование простое, но имеет предел (топовые серверы очень дороги и ограничены)
- Горизонтальное масштабирование теоретически безгранично, но требует решения проблемы согласованности данных
  :::

### 2.3 Болевые точки

- **Медленно**: при каждом изменении кода нужно вручную загружать его, а затем перезапускать сервер
- **Дорого**: масштабирование возможно лишь покупкой более мощной машины (вертикальное масштабирование)
- **Трудно масштабируется**: одна машина держит все запросы, при полной загрузке CPU остаётся лишь стоять в очереди

### 2.4 Достоинства и недостатки эпохи физических серверов

| Измерение | Оценка |
| ------------ | ------------------------------------------------------------ |
| **Достоинства** | Полный контроль над оборудованием, предсказуемая производительность; нет накладных расходов виртуализации; физическая изоляция данных, высокая безопасность |
| **Недостатки** | Долгий цикл закупки (недели); большие начальные вложения (CapEx); низкая утилизация ресурсов; сложность масштабирования |
| **Сценарии применения** | Ключевые финансовые системы, государственные секретные системы, сценарии со строгими требованиями к суверенитету данных |

::: tip 💡 CapEx vs OpEx
**CapEx** (Capital Expenditure): капитальные затраты, единовременное вложение крупной суммы на покупку оборудования.

**OpEx** (Operating Expenditure): операционные затраты, оплата по объёму использования (например, облачный сервер).

**Аналогия**:

- CapEx: купить квартиру, единовременно заплатить несколько миллионов, затем ежемесячно платить только за обслуживание
- OpEx: снять квартиру, платить аренду ежемесячно, не выкладывая крупную сумму сразу

**Вывод эпохи облаков**: Serverless и облачные сервисы позволяют большему числу компаний перейти от CapEx к OpEx, снижая порог входа для стартапов.
:::

## 3. Эпоха монолитной архитектуры (2000-е)

### 3.1 Что такое монолитная архитектура?

С появлением фреймворков (Rails / Django / Spring) все стали запихивать весь функционал в одно приложение.

::: tip 💡 Простое объяснение
**Монолитная архитектура** (Monolith) — это как огромный торговый центр:

- Отдел одежды, отдел продуктов, отдел электроники — всё в одном здании
- Все сотрудники работают в одной системе управления
- Если во всём здании отключат электричество, все отделы прекратят работу

Для сравнения, микросервисы — это как торговая улица: каждый магазин работает независимо, закрытие одного не влияет на остальные.
:::

<MonolithDemo />

### 3.2 Ключевые особенности

- **Единый кодовый репозиторий**: все функциональные модули в одном проекте
- **Общая база данных**: все модули используют одну базу данных
- **Единое развёртывание**: всё приложение упаковывается и развёртывается как единое целое

### 3.3 Достоинства

- **Простота разработки**: один проект решает весь функционал
- **Удобство развёртывания**: достаточно закинуть один большой пакет на сервер
- **Лёгкость отладки**: запуск локально позволяет отлаживать весь функционал

### 3.4 Болевая точка: эффект лавины

Представьте, что повар, нарезающий овощи, случайно порезал руку (в коде возник баг), и вся кухня вынуждена остановиться, чтобы обработать рану, в результате чего все гости остаются без еды.

Это и есть самый большой риск монолитной архитектуры: **плохая изоляция**.

::: details 🚨 Реальный кейс лавины
Некая e-commerce-компания во время распродажи 11 ноября:

- Сервис заказов из-за ошибки расчёта цены некоторого товара выбросил исключение
- Исключение не было корректно перехвачено, что привело к исчерпанию пула потоков
- Все последующие запросы (включая просмотр товаров, поиск, вход пользователей) были заблокированы
- Весь сайт полностью парализовало на 1 час

**Если бы использовались микросервисы**:

- Сервис заказов упал бы, но просмотр товаров, поиск, вход пользователей оставались бы доступны
- Пользователи могли бы хотя бы продолжать просматривать товары, потери минимальны
  :::

### 3.5 Достоинства, недостатки и сценарии применения монолитной архитектуры

| Измерение | Оценка |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **Достоинства** | Простота разработки, не нужно думать о сложности распределённости; удобство отладки, локальный запуск позволяет отлаживать весь функционал; простота развёртывания, достаточно одного пакета; лёгкость управления транзакциями, одна база данных обеспечивает ACID |
| **Недостатки** | Высокая связанность кода, с ростом бизнеса код разбухает; единый технологический стек, трудно частично обновлять; сложность масштабирования, можно лишь масштабировать целиком; плохая изоляция сбоев, сбой одного модуля влияет на всё; низкая эффективность командной работы, много людей правят один и тот же код |
| **Сценарии применения** | Проверка MVP стартапов, малые команды (<10 человек), относительно простой бизнес, сценарии, где скорость поставки важнее масштабируемости |
| **Неподходящие сценарии** | Параллельная разработка большими командами, частые релизы разных модулей, сценарии, где некоторые модули нужно масштабировать независимо |

::: tip 🎯 Рекомендации новичкам
Если вы изучаете бэкенд-разработку, **настоятельно рекомендуется начать с монолитной архитектуры**:

1. **Сначала научитесь ходить**: разберитесь в HTTP, базах данных, базовой архитектуре MVC
2. **Затем подумайте о беге**: когда проект действительно столкнётся с проблемой масштабируемости, тогда подумайте о микросервисах
3. **Избегайте чрезмерного проектирования**: «микросервисы» многих компаний на самом деле являются «распределённым монолитом», который сложнее поддерживать

**Путь обучения**:

- Этап 1: написать полноценное монолитное приложение на Spring Boot / Django / Rails
- Этап 2: при столкновении с узким местом производительности попробовать выделить 1–2 сервиса
- Этап 3: когда команда вырастет до >50 человек, а система действительно усложнится, перейти к полноценным микросервисам
  :::

### 3.6 Технологический стек монолитной архитектуры

| Язык/фреймворк | Особенности | Представительные компании |
| -------------------------- | ---------------------------- | --------------------- |
| **Java + Spring** | Первый выбор для корпоративной разработки, развитая экосистема | Alibaba, JD |
| **PHP + Laravel/ThinkPHP** | Быстрая разработка, подходит для малых и средних проектов | Ранний Facebook, Weibo |

| **Node.js + Express** | Единый язык фронтенда и бэкенда, сценарии с интенсивным I/O | Netflix, Uber |

## 4. Контейнеризация и микросервисы (2010-е)

### 4.1 Зачем нужны микросервисы?

Болевые точки монолитной архитектуры массово проявились в 2010-х:

- **Слишком большой код**: один проект на несколько миллионов строк, новичку нужен месяц, чтобы разобраться
- **Слишком медленное развёртывание**: одна сборка занимает 30 минут, релиз приходится делать с предельной осторожностью
- **Слишком сложное сотрудничество**: 100 разработчиков правят один проект, конфликты кода случаются ежедневно
- **Слишком дорогое масштабирование**: нужно масштабировать лишь «сервис чата», а приходится копировать всё приложение

**Ключевая идея микросервисов**: разбить большое приложение на несколько маленьких сервисов, каждый из которых:

- Разрабатывается и развёртывается независимо
- Имеет собственную базу данных
- Общается через API

<ContainerDockerDemo />

::: tip 💡 Что такое Docker?
**Docker** — это как «контейнер»:

- В каждом контейнере находится независимый груз (код + библиотеки зависимостей + среда выполнения)
- Куда бы его ни доставили (на какой бы сервер), открыв контейнер, можно сразу приступать к работе
- Не нужно беспокоиться: «на этой машине нет Python 3.9», «на той машине отсутствует какая-то библиотека»

**Аналогия**:

- Без Docker: при каждом переезде нужно по одной выносить на грузовик мебель, технику, одежду, а в новом доме по одной расставлять
- С Docker: всё упаковано в контейнер, грузовик просто увозит его, в новом доме поставил — и можно пользоваться

**Ключевая ценность**: «собрать один раз — запускать везде».
:::

### 4.4 Оркестрация Kubernetes

Когда число контейнеров достигает сотен и тысяч, нужна «система портовой диспетчеризации»:

- **Kubernetes (K8s)**: отвечает за размещение контейнеров на подходящих машинах (планирование, масштабирование, плавающие обновления)
- **Service Mesh**: отвечает за «правила дорожного движения» между сервисами (разрыв цепи, ограничение трафика, повторы, наблюдаемость)

<KubernetesDemo />

::: tip 💡 Что такое «оркестрация»?
**Оркестрация** (Orchestration) — это система автоматического управления большим числом контейнеров.

**Аналогия**:

- Без K8s: вы вручную управляете 100 контейнерами, какой упал — вручную перезапускаете, где трафик вырос — вручную добавляете машины
- С K8s: вы говорите ему «хочу, чтобы у этого сервиса всегда работало 10 экземпляров», и он автоматически:
  - Где сервер с достаточными ресурсами — туда и размещает контейнер
  - Контейнер упал — автоматически перезапускает
  - Трафик вырос — автоматически масштабирует до 20 экземпляров
  - При обновлении кода — плавающее обновление (сначала останавливает 1 старый экземпляр, запускает 1 новый, заменяет по одному)

**Ключевой момент**: микросервисы — это не «разбил и хорошо», настоящая сложность в **управлении и эксплуатации**.
:::

### 4.5 Достоинства и недостатки микросервисов и контейнеризации

| Измерение | Оценка |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Достоинства** | Независимое развёртывание сервисов, гетерогенный технологический стек; изоляция сбоев, крах одного сервиса не влияет на всё; масштабирование по требованию, горячие сервисы масштабируются отдельно; удобство командной работы, разные команды отвечают за разные сервисы; меньший кодовый репозиторий, проще понимать и поддерживать |
| **Недостатки** | Высокая сложность распределённости (сетевые задержки, распределённые транзакции, обнаружение сервисов); высокие затраты на эксплуатацию, нужна профессиональная DevOps-команда; сложность отладки, проблему, возможно, придётся отслеживать через несколько сервисов; трудно обеспечить согласованность данных; сложные требования к инфраструктуре развёртывания и мониторинга |
| **Сценарии применения** | Большие команды (>50 человек), сложный бизнес с независимой эволюцией по модулям, некоторые модули нужно масштабировать независимо, нужен многоязычный технологический стек, системы с высокими требованиями к доступности |
| **Неподходящие сценарии** | Малые команды, простой бизнес, малый и стабильный трафик, отсутствие профессиональной команды эксплуатации |

::: details ⚠️ Ловушки микросервисов
**Ловушка 1: распределённый монолит**

Разбили на 10 микросервисов, но они тесно связаны между собой:

- Сервис A вызывает сервис B, сервис B вызывает сервис C, а сервис C снова вызывает сервис A
- Чтобы изменить одну функцию, нужно одновременно менять 5 сервисов
- При развёртывании приходится развёртывать строго по порядку, иначе система выдаёт ошибку

**Это хуже монолита**: вы получили сложность монолита, но не воспользовались преимуществом независимого развёртывания микросервисов.

**Ловушка 2: чрезмерное дробление**

Даже функцию всего из 100 строк кода выделяют в отдельный сервис:

- 10 сервисов, в каждом всего по 100 строк кода
- Накладные расходы на связь между сервисами (сетевая сериализация/десериализация) тяжелее, чем сама бизнес-логика
- Затраты на эксплуатацию взрываются: нужно развёртывать, мониторить, собирать логи 10 сервисов

**Правильный подход**: дробить с точки зрения функциональной связности, один микросервис должен быть целостной бизнес-способностью (например, «сервис заказов», а не «сервис создания заказов», «сервис запроса заказов»).
:::

### 4.6 Технологический стек микросервисов

| Категория | Технология/инструмент | Назначение |
| ------------ | ---------------------------------- | -------------------- |
| **Контейнеризация** | Docker, containerd | Упаковка и изоляция приложений |
| **Оркестрация и планирование** | Kubernetes, Docker Swarm | Управление контейнерами и автоматическое масштабирование |
| **Обнаружение сервисов** | Consul, etcd, ZooKeeper | Регистрация и обнаружение сервисов |
| **API-шлюз** | Kong, Zuul, Envoy | Единая точка входа, маршрутизация, ограничение трафика |
| **Центр конфигурации** | Apollo, Nacos, Spring Cloud Config | Централизованное управление конфигурацией |
| **Мониторинг и оповещения** | Prometheus, Grafana, ELK | Мониторинг метрик и анализ логов |
| **Трассировка** | Jaeger, Zipkin, SkyWalking | Распределённая трассировка запросов |
| **Service Mesh** | Istio, Linkerd | Управление трафиком и безопасность |

## 5. Эпоха Serverless и облачной нативности (2020-е+)

### 5.1 Зачем нужен Serverless?

Микросервисы хороши, но обслуживать десятки маленьких кухонь всё равно утомительно. Вам приходится беспокоиться:

- Достаточно ли велика кухня? (масштабирование серверов)
- Что делать при отключении электричества? (высокая доступность)
- Как управлять, когда контейнеров слишком много? (затраты на эксплуатацию)

<ServerlessDemo />

::: tip 💡 Serverless — это не «совсем без серверов»
**Serverless** означает «вам не нужно управлять серверами», а не то, что серверов действительно нет.

**Аналогия**:

- **Эпоха физических серверов**: вы покупаете землю, строите здание, делаете ремонт, нанимаете повара, покупаете продукты… всё сами
- **Эпоха облачных серверов**: вы арендуете уже отремонтированный ресторан, но сами нанимаете повара и управляете
- **Эпоха Serverless**: вам нужно лишь составить меню, в облаке есть общая кухня и профессиональные повара, вы делаете заказ — они готовят, оплата по факту

**Ключевые изменения**:

- Раньше: купить сервер → настроить среду → развернуть код → мониторить → масштабировать → поддерживать
- Сейчас: написать код → загрузить → платить по объёму использования

**Как доставка еды**: вам не нужна кухня, нужно лишь составить меню, кто-то приготовит за вас.
:::

### 5.2 Что такое Serverless?

**Serverless = FaaS + BaaS**

**FaaS** (Function as a Service, функция как сервис):

- Вы пишете только функцию (например, «при регистрации пользователя отправить приветственное письмо»)
- Облачный провайдер отвечает за запуск этой функции, автоматическое масштабирование
- Типичные представители: AWS Lambda, Alibaba Cloud Function Compute

**BaaS** (Backend as a Service, бэкенд как сервис):

- Вход → Auth0 / Supabase Auth
- Оплата → Stripe
- База данных → Supabase / Firebase / DynamoDB
- Сообщения → Kafka / SQS

::: tip 🎯 Сценарии применения Serverless
**Лучшие сценарии**:

1. **Приливный трафик**: приложение доставки еды, днём трафик большой, ночью никого. Serverless автоматически выделит днём 1000 машин, а ночью сократит до 0
2. **Событийно-ориентированность**: «после загрузки пользователем изображения автоматически сжать его»
3. **Быстрая проверка**: малые команды, MVP, хакатонные проекты

**Неподходящие сценарии**:

1. **Долго выполняющиеся задачи**: транскодирование видео (может занять 1 час, а максимальное время выполнения функции обычно всего 15 минут)
2. **Приложения с требованием низкой задержки**: высокочастотная торговля (задержка холодного старта может быть от десятков миллисекунд до нескольких секунд)
3. **Нужен тонкий контроль низкого уровня**: тюнинг ядра ОС, прямой доступ к GPU
   :::

### 5.3 Достоинства и недостатки Serverless и облачной нативности

| Измерение | Оценка |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Достоинства** | Нулевые затраты на эксплуатацию, разработчику нужен лишь бизнес-код; автоматическое масштабирование, идеально справляется с пиками трафика; оплата по требованию, при отсутствии трафика затраты близки к нулю; быстрый запуск, за несколько минут развёртывание по всему миру; встроенная высокая доступность, облачный сервис автоматически обрабатывает переключение при отказе |
| **Недостатки** | Задержка холодного старта (от сотен миллисекунд до нескольких секунд); ограничение времени выполнения (обычно 5–15 минут); сложность отладки, локально трудно полностью эмулировать облачную среду; риск привязки к вендору; не подходит для долго выполняющихся или вычислительно-интенсивных задач; при высокочастотном постоянном трафике затраты могут превысить традиционные решения |
| **Сценарии применения** | Событийно-ориентированная обработка (обработка изображений, уведомления о сообщениях); приложения с приливным трафиком (страницы акций, распродажи); быстрая проверка прототипов и MVP; низкочастотные API или фоновые задачи; малые команды без штатной команды эксплуатации |
| **Неподходящие сценарии** | Приложения, требующие постоянно низкой задержки; долгие вычислительные задачи; сценарии, чувствительные к холодному старту (высокочастотная торговля); сценарии, требующие тонкого контроля низкоуровневой инфраструктуры |

::: details 💰 Сравнение затрат: когда Serverless дороже?
**Сценарий 1: низкочастотный доступ**

- Традиционный сервер: $20 в месяц (независимо от того, есть ли посетители)
- Serverless: 1 млн запросов × $0.0002/запрос = $20 (оплата только при наличии трафика)
- **Вывод**: в низкочастотных сценариях Serverless экономнее

**Сценарий 2: высокочастотный постоянный доступ**

- Традиционный сервер: $20 в месяц
- Serverless: 100 млн запросов × $0.0002/запрос = $20 000
- **Вывод**: в высокочастотных постоянных сценариях традиционный сервер экономнее

**Сценарий 3: приливный трафик**

- Традиционный сервер: чтобы справиться с пиком, нужен сервер за $100/месяц (в обычное время утилизация ресурсов всего 10%)
- Serverless: на пике $20, в обычное время почти $0
- **Вывод**: в сценариях приливного трафика Serverless экономит затраты

**Вывод**: не переходите на Serverless вслепую, делайте расчёт затрат на основе реальных характеристик трафика.
:::

| Категория | Технология/платформа | Особенности |
| ------------ | ------------------------ | ---------------------------- |

## 6. Сравнение этапов архитектуры и руководство по выбору

### 6.1 Общее сравнение эволюции архитектуры

<ArchitectureComparisonDemo />

| Измерение | Физический сервер | Монолитная архитектура | Микросервисы+контейнеры | Serverless |
| ---------------- | ---------------------- | ------------------ | ------------------------ | ------------------ |
| **Размер команды** | 1–5 человек | 5–50 человек | 50–500 человек | 1–20 человек |
| **Сложность развёртывания** | Крайне высокая | Низкая | Крайне высокая | Крайне низкая |
| **Затраты на эксплуатацию** | Высокие | Средние | Очень высокие | Низкие |
| **Масштабируемость** | Плохая | Ограниченное вертикальное масштабирование | Отличное горизонтальное масштабирование | Автоматическое масштабирование |
| **Гибкость технологического стека** | Нет | Единый | Разнообразный | Ограниченный |
| **Холодный старт** | Нет | Нет | Время запуска контейнера | Есть задержка |
| **Сценарии применения** | Устаревшие системы, особые требования соответствия | Стартапы, простой бизнес | Крупные интернет-компании, сложный бизнес | Быстрая проверка, событийно-ориентированность |

### 6.2 Дерево принятия решений по выбору технологий

```
Начало выбора
    │
    ├─ Есть ли в команде профессиональные специалисты по эксплуатации?
    │   ├─ Да → рассмотреть микросервисы или физические машины
    │   └─ Нет → продолжить
    │
    ├─ Нужно быстро запустить и проверить идею?
    │   ├─ Да → Serverless или монолит
    │   └─ Нет → продолжить
    │
    ├─ Размер команды > 50 человек?
    │   ├─ Да → рассмотреть микросервисы
    │   └─ Нет → продолжить
    │
    ├─ Есть ли у трафика выраженные пики и провалы?
    │   ├─ Да → Serverless
    │   └─ Нет → монолитная архитектура (рекомендуется стартапам)
    │
    └─ Особые требования (соответствие, устаревшие системы)?
        └─ Да → физический сервер
```

::: tip 🎯 Рекомендации новичкам по выбору
**Если вы разработчик или малая команда:**

1. **Этап 0 (обучение)**: локально запускать монолитное приложение, разобраться в HTTP, базах данных, базовой архитектуре
2. **Этап 1 (MVP)**: развернуть монолитное приложение на облачный сервер (например, Alibaba Cloud ECS, AWS EC2)
3. **Этап 2 (рост)**: когда команда >10 человек, а бизнес усложняется, рассмотреть выделение 1–2 микросервисов
4. **Этап 3 (зрелость)**: когда команда >50 человек, а трафик достигает миллионов, перейти к полноценным микросервисам

**Ключевой принцип**: не переходите на микросервисы с самого начала — это «преждевременная оптимизация». Пусть архитектура эволюционирует вместе с ростом бизнеса.
:::

### 6.3 Рекомендуемые архитектуры для разных сценариев

#### Сценарий первый: независимый разработчик/проект на полставки

- **Рекомендуемая архитектура**: Serverless (Vercel/Netlify) или монолитное приложение
- **Обоснование**: почти нулевые затраты на эксплуатацию, оплата по требованию, быстрый запуск
- **Пример технологического стека**: Next.js + Vercel + Supabase

#### Сценарий второй: проверка MVP стартапа

- **Рекомендуемая архитектура**: монолитная архитектура + облачный сервер
- **Обоснование**: высокая скорость разработки, команда может сосредоточиться на бизнес-логике, а не на инфраструктуре
- **Пример технологического стека**: Spring Boot / Django / Rails + RDS + ECS

#### Сценарий третий: растущая компания (команда 10–50 человек)

- **Рекомендуемая архитектура**: модульный монолит или лёгкие микросервисы
- **Обоснование**: начинают возникать проблемы связанности кода, но полная сложность микросервисов ещё не нужна
- **Пример технологического стека**: Spring Cloud / Go Micro + Kubernetes

#### Сценарий четвёртый: крупная интернет-компания

- **Рекомендуемая архитектура**: микросервисы + Service Mesh + платформенная архитектура (middle platform)
- **Обоснование**: большой размер команды, сложный бизнес, нужны независимый ритм релизов и технологические стеки
- **Пример технологического стека**: собственный RPC-фреймворк + Istio + собственная PaaS-платформа

#### Сценарий пятый: событийно-ориентированные приложения/приложения с приливным трафиком

- **Рекомендуемая архитектура**: Serverless + шина событий
- **Обоснование**: большие колебания трафика, нужна предельная оптимизация затрат и автоматическое масштабирование
- **Пример технологического стека**: AWS Lambda + API Gateway + EventBridge

## 7. Заключение и путь обучения

### 7.1 Ключевые моменты

Эволюция бэкенд-архитектуры по сути является **сложением** и **вычитанием**:

| Эпоха | Архитектура | Что делает разработчик | Что делает эксплуатация |
| :------------- | :----- | :--------------- | :----------------- |
| **Эпоха физических серверов** | Одна машина | Писать скрипты, вручную развёртывать | Обслуживать серверную и оборудование |
| **Эпоха монолита** | Единый блок | Писать всю бизнес-логику | Обслуживать несколько больших серверов |
| **Эпоха микросервисов** | Дробление | Сосредоточиться на одном бизнесе | Обслуживать кластер K8s (очень утомительно!) |
| **Serverless** | Функции | Писать только ключевые функции | Пить чай (облачный провайдер всё берёт на себя) |

**Ключевое прозрение**:

- Эволюция архитектуры — это не «новая технология заменяет старую», а **изменение подходящих сценариев**
- Серебряной пули нет, у каждой архитектуры есть свои границы применимости
- При выборе архитектуры нужно учитывать: размер команды, сложность бизнеса, характеристики трафика, возможности эксплуатации

### 7.2 Рекомендации по пути обучения

В зависимости от вашего профессионального этапа рекомендуются следующие пути обучения:

#### Этап первый: заложить основу (0–1 год)

**Цель**: понять ключевые понятия бэкенда, уметь самостоятельно разрабатывать монолитные приложения

- Освоить один бэкенд-язык (Java/Python/Go на выбор)
- Изучить протокол HTTP и проектирование RESTful API
- Освоить реляционные базы данных (MySQL/PostgreSQL)
- Познакомиться с основами кеширования (Redis)
- Изучить Git и базовые команды Linux
- **Практический проект**: реализовать CRUD-приложение в монолитной архитектуре (например, блог, список дел)

#### Этап второй: расширить возможности (1–3 года)

**Цель**: понять распределённые системы, уметь участвовать в разработке микросервисов

- Глубоко изучить микросервисную архитектуру и стратегии дробления
- Освоить основы Docker и Kubernetes
- Изучить очереди сообщений (Kafka/RabbitMQ)
- Познакомиться с распределёнными транзакциями и согласованностью
- Освоить мониторинг и логирование (Prometheus/ELK)
- **Практический проект**: разбить монолитное приложение на 3–5 микросервисов, развернуть с помощью Docker

#### Этап третий: профессиональное углубление (3–5 лет)

**Цель**: уметь проектировать крупные системы, обладать способностью выбора технологий

- Глубоко понять облачно-нативную архитектуру (Service Mesh, Serverless)
- Освоить планирование ёмкости и тюнинг производительности
- Познакомиться с архитектурой active-active и проектированием аварийного восстановления
- Изучить DDD (предметно-ориентированное проектирование)
- Развивать техническое суждение и архитектурное мышление
- **Практический проект**: спроектировать архитектуру системы, поддерживающей миллионы пользователей, включая высокую доступность, эластичное масштабирование и др.

## 8. Краткий справочник терминов (Glossary)

| Термин | Полное название | Объяснение |
| :---------------- | :-------------------------------- | :------------------------------------------------ |
| **Backend** | - | Серверная система, отвечающая за бизнес-логику, хранение данных и внешние интерфейсы |
| **CGI** | Common Gateway Interface | Ранняя технология динамических веб-страниц, обрабатывает запросы скриптом и возвращает результат |
| **Monolith** | - | Монолитная архитектура, упаковывает всю бизнес-логику в одно приложение |
| **Microservices** | - | Микросервисная архитектура, разбивает бизнес на несколько независимых сервисов |
| **Container** | - | Технология контейнеризации, упаковывает приложение и зависимости в переносимую единицу |
| **K8s** | Kubernetes | Платформа оркестрации контейнеров для планирования, масштабирования и управления контейнерами |
| **Service Mesh** | - | Service Mesh, отвечает за управление, наблюдаемость и безопасность связи между микросервисами |
| **Serverless** | - | Бессерверные вычисления, разработчик пишет лишь функции, платформа автоматически запускает и масштабирует |
| **BaaS** | Backend as a Service | Готовые к использованию облачные бэкенд-сервисы (аутентификация, база данных, оплата и др.) |
| **CI/CD** | Continuous Integration / Delivery | Непрерывная интеграция и непрерывная поставка, автоматизация тестирования и развёртывания |
| **Observability** | - | Наблюдаемость, использование логов/метрик/трассировки для понимания состояния работы системы |
