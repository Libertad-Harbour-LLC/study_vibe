# Слоистая архитектура бэкенда

> **Ключевой вопрос**: код становится всё запутаннее — как его организовать, чтобы было ясно и понятно?

Когда проект разрастается с нескольких десятков строк кода до десятков тысяч, от разработки в одиночку до командной работы, от простого CRUD до сложной бизнес-логики, способ организации кода напрямую определяет жизнь или смерть проекта. Слоистая архитектура нужна не ради демонстрации мастерства или следования догмам, а для решения фундаментального противоречия программной инженерии: конфликта между **естественным ростом сложности бизнеса** и **ограниченностью человеческих познавательных способностей**.

---

## 1. Зачем нужно деление на слои?

### 1.1 Корень проблемы

**Начальная версия** (100 строк кода):
```java
@PostMapping("/register")
public Result register(@RequestBody User user) {
    // 1. Проверяем, не дублируется ли имя пользователя
    if (userRepository.findByUsername(user.getUsername()) != null) {
        return Result.error("Имя пользователя уже существует");
    }
    // 2. Шифруем пароль
    user.setPassword(encrypt(user.getPassword()));
    // 3. Сохраняем пользователя
    userRepository.save(user);
    // 4. Отправляем приветственное письмо
    emailService.sendWelcome(user.getEmail());
    // 5. Записываем лог
    log.info("User registered: {}", user.getUsername());
    return Result.success();
}
```

**Спустя 6 месяцев** (500 строк кода):
- Добавлена верификация номера телефона
- Добавлена идентификация по реальному имени
- Добавлено вознаграждение за приглашение
- Добавлена проверка контроля рисков
- ...

Теперь этот метод занимает 500 строк, и каждое изменение пугает, потому что:
- Логика смешана воедино, изменение в одном месте может затронуть другие функции
- Трудно тестировать: для каждого теста нужно имитировать полный HTTP-запрос
- Новички не понимают, потому что вся логика свалена в кучу

**Суть проблемы**: у кода нет «границ», все обязанности перемешаны.

**Кумулятивный эффект технического долга**:
- ❌ **Высокая связанность**: бизнес-логика связана с доступом к данным и протоколом HTTP, изменение одного тянет за собой всё
- ❌ **Низкая сцепленность**: один метод несёт несколько обязанностей, нарушая принцип единственной ответственности
- ❌ **Трудно тестировать**: невозможно тестировать бизнес-логику изолированно, нужно запускать полный HTTP-контейнер
- ❌ **Трудно переиспользовать**: бизнес-логика привязана к HTTP-запросу, периодические задачи и очереди сообщений не могут её переиспользовать
- ❌ **Когнитивная нагрузка**: разработчику нужно одновременно понимать детали всех слоёв, невозможно сфокусироваться

### 1.2 Ключевая идея деления на слои

Слоистая архитектура — это проведение чётких границ в коде:

```
┌─────────────────────────────────────┐
│  Приём запроса ← Controller         │  Только «принимает заказ»
├─────────────────────────────────────┤
│  Оркестрация бизнеса ← Service      │  Только «готовит блюдо»
├─────────────────────────────────────┤
│  Доступ к данным ← Repository       │  Только «берёт ингредиенты»
├─────────────────────────────────────┤
│  Определение бизнеса ← Domain       │  Только «стандарт рецепта»
└─────────────────────────────────────┘
```

**Ключевые принципы**:
- Каждый слой делает только своё дело
- Слои общаются друг с другом через чёткие интерфейсы
- Бизнес-логика сосредоточена в Service и Domain
- Логика доступа к данным сосредоточена в Repository

**Инженерная ценность слоистой архитектуры**:

1. **Снижение когнитивной нагрузки**: разработчик может сосредоточиться на обязанностях текущего слоя, не понимая глобальных деталей
2. **Повышение тестируемости**: каждый слой можно тестировать модульно независимо, достаточно сделать Mock зависимостей
3. **Усиление поддерживаемости**: при изменении требований область изменений локализуется чётко, снижая риски
4. **Содействие переиспользованию кода**: бизнес-логика не зависит от HTTP, её можно переиспользовать в периодических задачах и очередях сообщений
5. **Поддержка командной работы**: разные разработчики могут параллельно разрабатывать разные слои, снижая количество конфликтов
6. **Продление жизни кода**: чёткие границы делают код проще для рефакторинга и эволюции

## 2. Подробно о четырёхслойной архитектуре

### 2.1 Общая структура

Суть слоистой архитектуры — это **разделение ответственности** (Separation of Concerns) и **контроль направления зависимостей**:

```
┌─────────────────────────────────────────────────────┐
│  Запрос с фронтенда                                  │
└────────────────────┬────────────────────────────────┘
                     │ HTTP Request
                     ▼
┌─────────────────────────────────────────────────────┐
│  Controller (слой контроллеров)                      │
│  - Приём запроса, валидация параметров                │
│  - Преобразование DTO                                │
│  - Вызов Service                                     │
│  - Возврат ответа                                    │
└────────────────────┬────────────────────────────────┘
                     │ Бизнес-вызов
                     ▼
┌─────────────────────────────────────────────────────┐
│  Service (слой бизнес-логики)                        │
│  - Оркестрация бизнес-логики                          │
│  - Управление транзакциями                            │
│  - Координация нескольких Repository                  │
│  - Межмодульная координация                           │
└────────────────────┬────────────────────────────────┘
                     │ Доступ к данным
                     ▼
┌─────────────────────────────────────────────────────┐
│  Repository (слой доступа к данным)                  │
│  - CRUD базы данных                                  │
│  - Инкапсуляция запросов                              │
│  - ORM-маппинг                                       │
└────────────────────┬────────────────────────────────┘
                     │ Доменные объекты
                     ▼
┌─────────────────────────────────────────────────────┐
│  Domain (слой доменной модели)                       │
│  - Сущность (Entity)                                 │
│  - Объект-значение (Value Object)                    │
│  - Бизнес-правила                                    │
└─────────────────────────────────────────────────────┘
```

**Направление зависимостей**: зависимости кода должны указывать в сторону **более стабильного и абстрактного**
- Controller зависит от интерфейса Service (абстракция)
- Service зависит от интерфейса Repository (абстракция)
- Все слои зависят от Domain (ядро бизнеса, самое стабильное)
- **Обратные зависимости не допускаются** (например, Repository зависит от Service)

### 2.2 Слой Controller

**Обязанность**: «администратор» приёма запросов

- Приём HTTP-запроса, парсинг параметров
- Валидация параметров (формат, обязательность и т. д.)
- Преобразование DTO (Request → Param)
- Вызов Service для выполнения бизнес-логики
- Преобразование DTO (Result → Response)
- Возврат HTTP-ответа

**Чего делать не следует**:
- Писать бизнес-логику напрямую
- Напрямую работать с базой данных
- Обрабатывать транзакции

**Философия проектирования**:
Controller — это «фасад» системы, он несёт роль адаптера: адаптирует внешний протокол HTTP под внутренние бизнес-вызовы. Он не должен содержать никаких бизнес-решений, потому что бизнес-решения — это воплощение доменных знаний и должны быть развязаны с транспортным протоколом.

**Пример**:
```java
@RestController
@RequestMapping("/api/users")
public class UserController {

    private final UserService userService;

    @PostMapping
    public UserResponse createUser(
            @RequestBody @Valid UserRequest request) {
        
        // 1. Request DTO → Param DTO
        UserParam param = UserParam.builder()
                .username(request.getUsername())
                .password(encrypt(request.getPassword()))
                .email(request.getEmail())
                .build();

        // 2. Вызов Service
        User user = userService.createUser(param);

        // 3. Entity → Response DTO
        return UserResponse.from(user);
    }
}
```

**Ключевые моменты**:
- Автоматическая валидация параметров через `@Valid`
- Изоляция структур данных фронтенда и бэкенда через DTO
- Только «перевод» и «диспетчеризация», без бизнес-логики

### 2.3 Слой Service

**Обязанность**: «повар» бизнеса

- Реализация основной бизнес-логики
- Оркестрация операций нескольких Repository
- Управление границами транзакций
- Обработка межмодульной координации

**Чего делать не следует**:
- Писать SQL напрямую (это задача Repository)
- Обрабатывать вещи, связанные с HTTP
- Возвращать сущности базы данных в Controller

**Философия проектирования**:
Слой Service — это носитель бизнес-логики, он должен сохранять чистоту. Он не зависит ни от какого фреймворка или транспортного протокола, что позволяет:
- Тестировать модульно независимо от веб-слоя
- Переиспользовать в периодических задачах и потребителях очередей сообщений
- Избежать влияния смены технологического стека на бизнес-логику

**Пример**:
```java
@Service
@RequiredArgsConstructor
public class UserService {

    private final UserRepository userRepository;
    private final EmailService emailService;

    @Transactional
    public User createUser(UserParam param) {
        // 1. Бизнес-правило: проверяем, не дублируется ли имя пользователя
        if (userRepository.existsByUsername(param.getUsername())) {
            throw new UserAlreadyExistsException();
        }

        // 2. Создаём сущность пользователя
        User user = new User();
        user.setUsername(param.getUsername());
        user.setPassword(param.getPassword());
        user.setEmail(param.getEmail());

        // 3. Сохраняем в базу данных
        userRepository.save(user);

        // 4. Отправляем приветственное письмо (межмодульная координация)
        emailService.sendWelcomeEmail(user);

        return user;
    }
}
```

**Ключевые моменты**:
- Гарантия согласованности транзакций через Transactional
- Выбрасывание бизнес-исключений, чтобы Controller обрабатывал их единообразно
- Не зависит от понятий HTTP, может переиспользоваться

### 2.4 Слой Repository

**Обязанность**: «кладовщик» данных

- Инкапсуляция всей логики доступа к данным
- Выполнение CRUD-операций
- Обработка ORM-маппинга
- Инкапсуляция условий запроса

**Чего делать не следует**:
- Писать бизнес-логику
- Обрабатывать транзакции (этим управляет слой Service)
- Зависеть от вышестоящих модулей

**Философия проектирования**:
Repository — это абстрактный слой доступа к данным, скрывающий детали нижележащей базы данных. Ценность этой абстракции в том, что:
- При смене базы данных нужно изменить только реализацию Repository, бизнес-логику менять не требуется
- Удобно делать Mock для модульного тестирования
- Логика запросов управляется централизованно, избегая дублирования кода

**Пример**:
```java
@Repository
public interface UserRepository extends JpaRepository<User, Long> {

    // Spring Data JPA реализует автоматически
    Optional<User> findByUsername(String username);
    boolean existsByUsername(String username);

    // Пользовательский сложный запрос
    @Query("SELECT u FROM User u WHERE u.email = :email AND u.deleted = false")
    Optional<User> findActiveByEmail(@Param("email") String email);
}
```

**Ключевые моменты**:
- Repository — это интерфейс, он не содержит бизнес-логики
- Намерение запроса выражается именем метода
- Сложные запросы можно задать с помощью Query

### 2.5 Слой Domain

**Обязанность**: «стандарт рецептов» бизнеса

- Определение бизнес-сущностей (Entity)
- Определение объектов-значений (Value Object)
- Инкапсуляция бизнес-правил
- Служит общей зависимостью всех слоёв

**Важные особенности**:
- Слой Domain не зависит ни от какого другого слоя
- Все слои зависят от слоя Domain
- Является основой слоистой архитектуры

**Философия проектирования**:
Слой Domain — это бизнес-ядро всей системы, он выражает доменные знания и бизнес-правила. Его чистота критически важна:
- Независимость от фреймворка означает, что бизнес-логика не захвачена технологическим стеком
- Зависимость всех слоёв от него гарантирует единообразие бизнес-правил
- Удобство для долгосрочной эволюции: технологический стек можно заменить, а бизнес-правила относительно стабильны

**Пример**:
```java
@Entity
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(unique = true, nullable = false)
    private String username;

    @Column(nullable = false)
    private String password;

    // ✅ Бизнес-метод: инкапсулирует бизнес-правило
    public boolean isPasswordCorrect(String rawPassword) {
        return BCrypt.checkpw(rawPassword, this.password);
    }

    public void changePassword(String oldPassword, String newPassword) {
        if (!isPasswordCorrect(oldPassword)) {
            throw new IncorrectPasswordException();
        }
        this.password = BCrypt.hashpw(newPassword);
    }
}
```

**Ключевые моменты**:
- У Entity есть уникальный идентификатор
- Бизнес-правила инкапсулированы в объектах Domain
- Слой Domain — это чистая бизнес-логика, не зависящая от фреймворка

## 3. DTO: «переводчик» между слоями

### 3.1 Зачем нужен DTO?

**Проблема**: если напрямую возвращать сущность базы данных на фронтенд:

```java
// ❌ Неправильно: напрямую возвращаем Entity
@Entity
public class User {
    private Long id;
    private String username;
    private String password;        // Чувствительная информация!
    private Boolean isDeleted;      // Внутреннее поле!
}
```

Фронтенд получит поля, которые не должны раскрываться, что создаёт угрозу безопасности.

**Решение**: использовать DTO для «перевода»

```
Entity базы данных → Service Param/Result → Controller Request/Response → фронтенд
```

### 3.2 Типы DTO

| Тип | Назначение | Пример |
|------|------|------|
| Request DTO | Controller принимает параметры | UserCreateRequest |
| Response DTO | Controller возвращает данные | UserResponse |
| Param DTO | Параметры метода Service | UserParam |
| Result DTO | Результат, возвращаемый Service | UserResult |
| Entity | Маппинг базы данных | User |

**Ключевой принцип**:
Каждый слой использует свой собственный DTO, не передавайте Entity напрямую; DTO содержит только необходимые поля. Это позволяет избежать раскрытия внутренних деталей реализации и гарантирует независимость каждого слоя.

## 4. Направление зависимостей: железное правило слоистой архитектуры

### 4.1 Принцип инверсии зависимостей

**Неправильный подход**:
```
Controller → UserServiceImpl → UserDaoImpl → UserEntity
```

**Правильный подход**:
```
Controller → UserService(интерфейс) → UserRepository(интерфейс) → UserEntity
```

**Направление зависимостей**:

Правильное направление зависимостей — это когда все слои зависят от более абстрактного и стабильного слоя. Конкретно: Controller зависит от интерфейса Service, Service зависит от интерфейса Repository, все слои зависят от слоя Domain, а слой Domain не зависит ни от какого другого слоя. Такое направление зависимостей обеспечивает независимость и тестируемость бизнес-логики.

К неправильным подходам относятся: прямая зависимость Service от класса реализации Repository, прямая работа Controller с базой данных или зависимость слоя Domain от других слоёв — всё это повышает связанность и снижает поддерживаемость системы.

### 4.2 Пример кода

```java
// ✅ Правильно: зависим от интерфейса
@Service
public class OrderService {
    private final OrderRepository orderRepository;  // интерфейс
    private final PaymentService paymentService;    // интерфейс
}

// ✅ Класс реализации внедряется Spring автоматически
@Repository
public class OrderRepositoryImpl implements OrderRepository {
    // Детали реализации
}
```

## 5. Практический пример: система заказов электронной коммерции

### 5.1 Требования

Создание заказа:
1. Пользователь выбирает товар
2. Проверка наличия на складе
3. Расчёт суммы
4. Создание заказа
5. Списание со склада

### 5.2 Реализация кода

**Слой Domain**:
```java
@Entity
public class Order {
    @Id
    private Long id;
    private Long userId;
    private List<OrderItem> items;
    private Money totalAmount;
    private OrderStatus status;

    public void calculateTotal() {
        Money total = Money.zero();
        for (OrderItem item : items) {
            total = total.add(item.getSubTotal());
        }
        this.totalAmount = total;
    }

    public void cancel() {
        if (this.status != OrderStatus.PENDING_PAYMENT) {
            throw new IllegalStateException("Отменить можно только заказ, ожидающий оплаты");
        }
        this.status = OrderStatus.CANCELLED;
    }
}
```

**Слой Repository**:
```java
@Repository
public interface OrderRepository extends JpaRepository<Order, Long> {
    List<Order> findByUserIdOrderByCreatedAtDesc(Long userId);
}
```

**Слой Service**:
```java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orderRepository;
    private final InventoryService inventoryService;

    @Transactional
    public OrderDTO createOrder(OrderParam param) {
        // 1. Проверяем товары и списываем со склада
        for (OrderItemParam item : param.getItems()) {
            inventoryService.reserveStock(item.getProductId(), item.getQuantity());
        }

        // 2. Создаём заказ
        Order order = new Order();
        order.setUserId(param.getUserId());
        order.calculateTotal();

        // 3. Сохраняем заказ
        orderRepository.save(order);

        return OrderDTO.from(order);
    }
}
```

**Слой Controller**:
```java
@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final OrderService orderService;

    @PostMapping
    public OrderResponse createOrder(@RequestBody @Valid OrderRequest request) {
        OrderParam param = OrderParam.builder()
                .userId(request.getUserId())
                .items(request.getItems())
                .build();

        OrderDTO order = orderService.createOrder(param);

        return OrderResponse.from(order);
    }
}
```

## 6. Частые вопросы

### 6.1 Можно ли писать бизнес-логику в Controller?

Controller не должен писать бизнес-логику, он отвечает только за приём запроса и возврат ответа. Бизнес-логика должна быть инкапсулирована в слое Service, и преимущество такого подхода в том, что код можно переиспользовать — например, периодическая задача или потребитель очереди сообщений могут напрямую вызывать Service, не проходя через HTTP-запрос. Кроме того, когда бизнес-логика сосредоточена в одном месте, её проще тестировать и поддерживать, что позволяет избежать несогласованности из-за разбросанной логики.

### 6.2 Что такое анемичная и насыщенная модель?

Анемичная модель — это когда класс-сущность содержит только атрибуты и соответствующие методы getter/setter, без какой-либо бизнес-логики, а все бизнес-правила реализуются в слое Service. Такая модель проста по структуре и легка для понимания, её применяет большинство проектов.

Насыщенная модель — это когда класс-сущность содержит не только атрибуты, но и бизнес-методы, связанные с этой сущностью, инкапсулируя бизнес-правила внутри сущности. Этот подход более соответствует идеям объектно-ориентированного проектирования, объединяя данные и поведение и повышая сцепленность кода.

Рекомендуется выбирать подходящую модель в зависимости от технического опыта команды и сложности проекта, но какую бы вы ни выбрали, следует сохранять согласованность; при этом слой Domain должен содержать хотя бы базовые методы бизнес-поведения, а не быть полностью пустой оболочкой.

### 6.3 Как обрабатывать транзакции, охватывающие несколько Service?

Когда одна бизнес-операция должна охватывать несколько Service, следует использовать аннотацию транзакции в вышестоящем Service, последовательно вызывая в этом методе несколько нижестоящих Service. Это гарантирует, что все операции выполняются в одном транзакционном контексте — либо все успешно, либо все откатываются, обеспечивая согласованность данных. Следует учитывать, что границы транзакции должны быть как можно меньше и включать только необходимые операции, чтобы не удерживать блокировку базы данных слишком долго и не снижать производительность при конкурентном доступе.

## 7. Заключение

| Слой | Обязанность | Ключевое слово |
|------|------|--------|
| Controller | Приём запроса, валидация параметров, вызов Service, возврат ответа | Администратор |
| Service | Оркестрация бизнес-логики, управление транзакциями, координация Repository | Повар |
| Repository | Доступ к данным, ORM-маппинг, инкапсуляция запросов | Кладовщик |
| Domain | Определение сущностей, бизнес-правила, объекты-значения | Стандарт рецептов |

**Ключевые принципы**:
1. Каждый слой делает только своё дело
2. Слои общаются друг с другом через интерфейсы
3. Бизнес-логика сосредоточена в Service и Domain
4. Логика доступа к данным сосредоточена в Repository
5. Изоляция структур данных слоёв через DTO

## 8. Больше архитектурных паттернов

В этой статье описана **слоистая архитектура** (Layered Architecture) — самый распространённый и простой для освоения паттерн бэкенд-архитектуры. Но бэкенд-архитектура далеко не ограничивается им; в зависимости от бизнес-сценария существуют и другие паттерны, которые стоит знать:

### 8.1 Другие распространённые архитектурные паттерны

| Архитектурный паттерн | Сценарий применения | Особенности |
|----------|----------|------|
| **Монолитная архитектура** | Небольшие проекты, MVP | Все функции в одном приложении, простое развёртывание |
| **Микросервисная архитектура** | Крупные сложные системы | Разбиение на несколько независимых сервисов, каждый развёртывается отдельно |
| **Событийно-ориентированная архитектура** | Высокая нагрузка, асинхронная обработка | Процессы запускаются событиями, высокая степень развязки |
| **Чистая архитектура** | Сложные бизнес-системы | Бизнес-логика в центре, зависимости направлены только внутрь, фреймворк на самом внешнем уровне |
| **Гексагональная архитектура** | Необходимость множества внешних адаптеров | Изоляция ядра от внешних систем через порты и адаптеры |
| **Луковичная архитектура** | Предметно-ориентированное проектирование | Концентрические слои, доменная модель в самом центре, инфраструктура снаружи |

Рассмотрим каждый из них подробнее:

#### Монолитная архитектура (Monolithic)

Все функции упакованы в одно приложение, разделяющее одну базу данных и процесс.

```
┌──────────────────────────────┐
│        Монолитное приложение  │
│  ┌────┐ ┌────┐ ┌────┐       │
│  │Польз│ │Заказ│ │Оплата│ ...│
│  └──┬─┘ └──┬─┘ └──┬─┘       │
│     └──────┼──────┘          │
│       Общая база данных       │
└──────────────────────────────┘
```

- **Плюсы**: простая разработка, удобное развёртывание, лёгкая локальная отладка
- **Минусы**: высокая связанность кода, сложное масштабирование, проблема в одном модуле может уронить всю систему
- **Применение**: ранние стартап-проекты, разработка одной командой, быстрая проверка прототипа

#### Микросервисная архитектура (Microservices)

Разбиение системы на несколько независимых сервисов, каждый из которых имеет свои данные и бизнес-логику и может развёртываться и масштабироваться отдельно.

```
┌────────┐  ┌────────┐  ┌────────┐
│Сервис   │  │Сервис   │  │Сервис   │
│пользоват│  │заказов  │  │оплаты   │
│  DB-1  │  │  DB-2  │  │  DB-3  │
└───┬────┘  └───┬────┘  └───┬────┘
    └───────────┼───────────┘
          API Gateway
```

- **Плюсы**: независимое развёртывание и масштабирование, гибкость технологического стека, изоляция сбоев
- **Минусы**: сложность связи между сервисами, трудности с согласованностью распределённых данных, необходимость зрелых DevOps-возможностей
- **Применение**: крупные сложные системы, работа нескольких команд, сценарии, требующие независимого масштабирования

#### Событийно-ориентированная архитектура (Event-Driven)

Связь через асинхронные события: производитель издаёт событие, потребитель реагирует на него, а компоненты высоко развязаны.

```
Производитель ──→ [Шина событий/Очередь сообщений] ──→ Потребитель A
                                                   ──→ Потребитель B
                                                   ──→ Потребитель C
```

- **Плюсы**: высокая степень развязки, естественная поддержка масштабирования, подходит для обработки в реальном времени
- **Минусы**: сложность отладки, порядок событий и идемпотентность требуют дополнительной обработки
- **Применение**: анализ данных в реальном времени, IoT-системы, асинхронная связь между микросервисами

#### Чистая архитектура (Clean Architecture)

Предложена Робертом Мартином (Robert C. Martin); делит систему на четыре концентрических слоя, зависимости направлены только снаружи внутрь:

```
┌─────────────────────────────────────┐
│  Frameworks & Drivers (фреймворки и драйверы) │
│  ┌─────────────────────────────┐    │
│  │  Interface Adapters (адаптеры) │    │
│  │  ┌─────────────────────┐    │    │
│  │  │  Use Cases (сценарии)│    │    │
│  │  │  ┌─────────────┐    │    │    │
│  │  │  │  Entities    │    │    │    │
│  │  │  │  (сущности/домен) │    │    │    │
│  │  │  └─────────────┘    │    │    │
│  │  └─────────────────────┘    │    │
│  └─────────────────────────────┘    │
└─────────────────────────────────────┘
         Направление зависимостей: снаружи → внутрь
```

- **Ключевое правило**: внутренний слой не знает о существовании внешнего, бизнес-логика полностью независима от фреймворка и базы данных
- **Плюсы**: высокая тестируемость, заменяемость технологического стека, ясная бизнес-логика
- **Минусы**: высокая начальная стоимость разработки, много кода для маппинга между слоями, в маленьких проектах легко переусложнить
- **Применение**: сложные бизнес-системы, проекты, требующие долгосрочной поддержки

#### Гексагональная архитектура (Hexagonal / Ports & Adapters)

Через «порты» определяются интерфейсы ввода-вывода ядра бизнеса, а через «адаптеры» подключаются внешние системы:

```
        ┌─────────────┐
  HTTP ──→ Port      │
  CLI  ──→ (вх. порт) │  Ядро бизнес-логики  │  (исх. порт) ──→ База данных
  MQ   ──→           │               │  Port    ──→ Внешний API
        └─────────────┘
```

- **Ключевая идея**: бизнес-логика не зависит ни от какой внешней технологии, внешние системы подключаются через адаптеры
- **Плюсы**: внешние системы можно свободно заменять, при тестировании достаточно Mock-адаптера
- **Применение**: сценарии с необходимостью подключения множества внешних систем

#### Луковичная архитектура (Onion Architecture)

Похожа на чистую архитектуру, подчёркивает, что доменная модель находится в самом центре, а инфраструктура — снаружи, зависимости направлены только внутрь:

```
┌──────────────────────────────┐
│  Infrastructure (инфраструктура) │
│  ┌────────────────────────┐  │
│  │  Application Services  │  │
│  │  ┌──────────────────┐  │  │
│  │  │  Domain Services  │  │  │
│  │  │  ┌────────────┐   │  │  │
│  │  │  │Domain Model│   │  │  │
│  │  │  └────────────┘   │  │  │
│  │  └──────────────────┘  │  │
│  └────────────────────────┘  │
└──────────────────────────────┘
```

- **Ключевая идея**: доменная модель — это ядро системы, все зависимости указывают на неё
- **Отличие от чистой архитектуры**: луковичная архитектура больше подчёркивает слой доменных сервисов, а чистая архитектура — слой сценариев (use cases)
- **Применение**: проекты, использующие предметно-ориентированное проектирование (DDD)

### 8.2 Маршрут эволюции архитектуры

Эти архитектуры не заменяют друг друга, а постепенно эволюционируют:

```text
Традиционная слоистая архитектура (N-Layered)
  │  Проблема: связанность слоёв, трудно заменять внешние зависимости
  ▼
Гексагональная архитектура (Ports & Adapters)
  │  Улучшение: изоляция внешних систем через порты и адаптеры
  ▼
Луковичная архитектура (Onion)
  │  Улучшение: чёткое концентрическое деление, доменная модель в центре
  ▼
Чистая архитектура (Clean Architecture)
  │  Улучшение: единые правила зависимостей, чёткие обязанности четырёх слоёв
  ▼
Выбор подходящей архитектуры в зависимости от потребностей бизнеса
```

### 8.3 Руководство по выбору архитектурного паттерна

```text
Пользователей < 1k, строк кода < 5000
    ↓
Монолитная архитектура + простое деление на слои
    ↓
Пользователей 1k-100k, нужна работа нескольких команд
    ↓
Слоистая архитектура (описана в этой статье)
    ↓
Пользователей > 100k, высокая сложность бизнеса
    ↓
Микросервисная / событийно-ориентированная архитектура
```

Более детальные критерии выбора:

| Фактор | Простое деление на слои | Чистая/гексагональная архитектура | Микросервисы |
|----------|---------|----------------|--------|
| Размер команды | 1-5 чел. | 5-20 чел. | 20+ чел. |
| Сложность бизнеса | Низкая | Средне-высокая | Высокая |
| Частота развёртывания | Низкая | Средняя | Высокая (независимое развёртывание) |
| Разнообразие технологического стека | Единый | Единый | Может быть разнообразным |
| Стоимость эксплуатации | Низкая | Средняя | Высокая |

- **Монолитная архитектура**: смотрите родственную статью [`backend-project-architecture.md`](./backend-project-architecture.md), чтобы узнать об эволюции от скрипта к монолиту
- **Микросервисная архитектура**: смотрите [Эволюция от монолита к микросервисам](/ru-ru/appendix/6-architecture-and-system-design/monolith-to-microservices)
- **Чистая архитектура**: «Clean Architecture» Роберта Мартина — классический труд, предложивший правило зависимостей и модель из четырёх концентрических слоёв
- **Паттерны корпоративной архитектуры**: «Patterns of Enterprise Application Architecture» Мартина Фаулера — авторитетный справочник по слоистой архитектуре и организации бизнес-логики

### 8.5 Как выбрать?

**Запомните этот принцип**: **архитектура служит бизнесу, а не наоборот**.

- В маленьких проектах используйте простую архитектуру, быстро выходите в продакшен для проверки
- В крупных проектах уже стоит подумать о сложной архитектуре, избегая переусложнения
- Знакомство команды тоже важно: выбирайте решение, понятное всем

## 9. Заключение

| Слой | Обязанность | Ключевое слово |
|------|------|--------|
| Controller | Приём запроса, валидация параметров, вызов Service, возврат ответа | Администратор |
| Service | Оркестрация бизнес-логики, управление транзакциями, координация Repository | Повар |
| Repository | Доступ к данным, ORM-маппинг, инкапсуляция запросов | Кладовщик |
| Domain | Определение сущностей, бизнес-правила, объекты-значения | Стандарт рецептов |

**Ключевые принципы**:

Суть слоистой архитектуры — в чётком разделении обязанностей и контроле направления зависимостей. Каждый слой заботится только о своих обязанностях, общается с соседними слоями через интерфейсы, бизнес-логика сосредоточена в слоях Service и Domain, логика доступа к данным — в слое Repository, а структуры данных слоёв изолированы через DTO, что предотвращает прямое раскрытие внутренней реализации. Такой дизайн делает систему проще для понимания, тестирования и поддержки и позволяет справляться с непрерывной эволюцией бизнеса.
