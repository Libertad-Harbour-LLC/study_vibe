# Полное путешествие одного запроса

::: tip Предисловие
**Когда вы вводите адрес в браузере и нажимаете Enter, что именно происходит до того, как страница отобразится?** Этот вопрос — классика собеседований, а главное — ключ к пониманию всей веб-архитектуры. Разобравшись в этом пути, вы поймёте, как взаимодействуют фронтенд, бэкенд, сеть и база данных.
:::

**Чему вас научит эта статья?**

После изучения этой главы вы получите:

- **Взгляд на весь путь**: поймёте полный процесс HTTP-запроса от отправки до возврата

- **Способность локализовать проблему**: когда запрос медленный или провалился, будете знать, с какого слоя начать диагностику
- **Подходы к оптимизации производительности**: на каждом слое есть пространство для оптимизации, будете знать, где точки оптимизации

## 0. Общая картина: что переживает один запрос?

Поймём через аналогию: вы заказываете книгу онлайн, и этот процесс поразительно похож на HTTP-запрос.

| Этап запроса | Аналогия с покупкой книги | Техническое соответствие |
|---------|---------|---------|
| Ввод адреса | Вы говорите «хочу в такой-то книжный магазин» | Браузер разбирает URL |
| Разрешение DNS | Смотрите на карту, находите адрес магазина | Доменное имя → IP-адрес |
| TCP-соединение | Подходите к двери магазина, толкаете дверь и входите | Трёхстороннее рукопожатие устанавливает соединение |
| Отправка запроса | Говорите продавцу «хочу книгу „xxx“» | HTTP-запрос |
| Обработка на сервере | Продавец идёт на склад искать книгу, проверяет наличие, считает цену | Логика приложения + запрос к базе данных |
| Возврат ответа | Продавец вручает вам книгу | HTTP-ответ |
| Отрисовка в браузере | Вы открываете книгу и начинаете читать | Разбор и отрисовка HTML/CSS/JS |

## 1. Браузер инициирует запрос

### 1.1 Разбор URL

Когда вы вводите `https://api.example.com/books?id=123`, браузер разбивает его на несколько частей:

| Часть | Значение | Смысл |
|-----|-----|------|
| Протокол | `https` | Связь зашифрованным способом |
| Доменное имя | `api.example.com` | «Имя» сервера |
| Путь | `/books` | Ресурс, к которому идёт обращение |
| Параметры запроса | `id=123` | Дополнительные условия |

### 1.2 Разрешение DNS: доменное имя → IP-адрес

Компьютер не понимает доменные имена, он понимает только IP-адреса (например, `93.184.216.34`). DNS — это «телефонная книга» интернета.

```
Кеш браузера → Кеш системы → Кеш роутера → DNS провайдера → Корневой DNS-сервер
     ↓ Если попадание — используем сразу, если нет — запрашиваем дальше
```

::: tip Смысл кеширования DNS
Если каждый запрос начинать с корневого DNS-сервера, глобальный интернет был бы раздавлен DNS-запросами. Поэтому на каждом уровне есть кеш, и большинство запросов разрешается уже на уровне браузера или системы.
:::

### 1.3 Трёхстороннее рукопожатие TCP

Найдя IP-адрес, браузеру нужно «установить соединение» с сервером. TCP с помощью трёхстороннего рукопожатия убеждается, что обе стороны готовы:

```
Клиент → Сервер: привет, хочу соединиться (SYN)
Сервер → Клиент: хорошо, я готов (SYN + ACK)
Клиент → Сервер: получил, начинаем связь (ACK)
```

Если это HTTPS, дополнительно требуется рукопожатие TLS для согласования способа шифрования.

### 1.4 Отправка HTTP-запроса

После установления соединения браузер отправляет HTTP-запрос:

```http
GET /books?id=123 HTTP/1.1
Host: api.example.com
Accept: application/json
Authorization: Bearer eyJhbGci...
User-Agent: Chrome/120.0
```

| Составляющая | Содержание |
|---------|------|
| Строка запроса | Метод (GET) + путь + версия протокола |
| Заголовки запроса | Метаинформация: аутентификация, ожидаемый формат данных и т. д. |
| Тело запроса | Есть только у запросов POST/PUT, несёт отправляемые данные |

## 2. Сетевая передача: запрос в пути

### 2.1 Маршрутизация и пересылка

После выхода из вашего компьютера запрос проходит через несколько роутеров, как посылка через несколько транзитных пунктов:

```
Ваш компьютер → Домашний роутер → Сеть оператора → Магистральная сеть → Целевой ЦОД
```

Каждый роутер на основе IP-адреса решает, куда переслать «следующий переход». Команда `traceroute` позволяет увидеть, через какие узлы прошёл запрос.

### 2.2 Ускорение CDN

Если целевой сайт использует CDN (сеть доставки контента), запросу может быть необязательно достигать сервера-источника:

| Сценарий | Направление |
|-----|------|
| Запрос статического ресурса (изображения, CSS, JS) | Граничный узел CDN возвращает напрямую |
| Запрос динамических данных (API) | Проходит сквозь CDN, достигает сервера-источника |

Суть CDN — «заранее разместить контент как можно ближе к пользователю».

### 2.3 Балансировка нагрузки

У крупных сайтов не один сервер. Балансировщик нагрузки распределяет запросы между несколькими серверами:

```
Запрос пользователя → Балансировщик нагрузки → Сервер A (30% трафика)
                      → Сервер B (30% трафика)
                      → Сервер C (40% трафика)
```

Распространённые стратегии распределения:

| Стратегия | Принцип | Сценарий применения |
|-----|------|---------|
| Round-robin | Распределение по очереди | Серверы одинаковой конфигурации |
| Взвешенный round-robin | Распределение по весу | Серверы разной конфигурации |
| IP-хеш | Один пользователь закреплён за одним сервером | Нужна привязка сессии |
| Наименьшее число соединений | Отдаётся тому, у кого сейчас меньше всего соединений | Большой разброс времени обработки запросов |

## 3. Обработка на сервере: что происходит на кухне

После того как запрос достигает сервера, он проходит несколько слоёв обработки.

### 3.1 Веб-сервер (Nginx / Apache)

Первым запрос обычно принимает веб-сервер, который отвечает за:

| Обязанность | Пояснение |
|-----|------|
| Обслуживание статических файлов | Прямой возврат HTML, CSS, JS, изображений |
| Обратное проксирование | Пересылка API-запросов бэкенд-приложению |
| Терминация SSL | Обработка шифрования/расшифровки HTTPS |
| Фильтрация запросов | Перехват вредоносных запросов, ограничение трафика |

### 3.2 Обработка сервером приложений

Веб-сервер пересылает запрос серверу приложений (Node.js, Spring, Django и т. д.), процесс обработки:

```
Запрос входит → Цепочка middleware → Сопоставление маршрута → Контроллер → Сервисный слой → Слой доступа к данным
```

Что делает **middleware**:

1. Разбирает тело запроса (JSON, данные формы)
2. Проверяет подлинность (проверка Token)
3. Проверяет права (может ли этот пользователь обращаться к этому интерфейсу?)
4. Записывает логи (кто, когда и к чему обращался)

### 3.3 Запрос к базе данных

Большинство запросов в итоге так или иначе работают с базой данных:

```
Код приложения: SELECT * FROM books WHERE id = 123
    ↓
Движок базы данных: разбор SQL → оптимизация запроса → план выполнения → чтение данных
    ↓
Возврат результата: { id: 123, title: "xxx", price: 59.9 }
```

::: tip База данных — самое частое узкое место производительности
Сетевая передача обычно измеряется миллисекундами, логика приложения тоже быстрая, но запрос к базе данных без индекса может занять несколько секунд или даже десятки секунд. Поэтому «медленный запрос» с большой вероятностью означает медленный запрос к базе данных.
:::

## 4. Возврат ответа: путь данных домой

### 4.1 Формирование HTTP-ответа

После обработки сервер формирует ответ:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Encoding: gzip
Cache-Control: max-age=3600

{"id": 123, "title": "xxx", "price": 59.9}
```

| Составляющая | Содержание |
|---------|------|
| Строка статуса | Версия протокола + код статуса (200 успех, 404 не найдено, 500 ошибка сервера) |
| Заголовки ответа | Формат данных, стратегия кеширования, способ сжатия и т. д. |
| Тело ответа | Фактическое содержимое данных (JSON, HTML и т. д.) |

### 4.2 Сжатие данных

Сервер обычно сжимает тело ответа с помощью gzip или brotli, чтобы уменьшить объём передачи:

| Алгоритм сжатия | Степень сжатия | Скорость |
|---------|--------|------|
| gzip | около 70% | Быстро |
| brotli | около 80% | Медленнее, но сжатие лучше |

JSON размером 100 КБ после сжатия может занимать всего 20–30 КБ.

### 4.3 Отрисовка в браузере

После получения ответа браузер:

1. **Разбирает HTML** → строит DOM-дерево
2. **Разбирает CSS** → строит дерево стилей
3. **Объединяет** → формирует дерево отрисовки
4. **Раскладка** → вычисляет позицию и размер каждого элемента
5. **Отрисовка** → рисует пиксели на экране

## 5. Оптимизация всего пути: каждый слой может быть быстрее

### 5.1 Способы оптимизации по слоям

| Уровень | Способ оптимизации | Эффект |
|-----|---------|------|
| DNS | Предварительное разрешение DNS, использование быстрого DNS-сервиса | Уменьшение времени DNS-запроса |
| Сеть | CDN, HTTP/2, переиспользование соединений | Уменьшение задержки передачи |
| Сервер | Кеширование (Redis), асинхронная обработка | Уменьшение времени обработки |
| База данных | Индексы, оптимизация запросов, разделение чтения и записи | Уменьшение времени запроса |
| Фронтенд | Ленивая загрузка, разделение кода, сжатие ресурсов | Уменьшение времени отрисовки |

### 5.2 Кеширование: самая эффективная оптимизация

Кеш существует на каждом слое пути запроса:

```
Кеш браузера → Кеш CDN → Кеш обратного прокси → Кеш приложения (Redis) → Кеш базы данных
```

::: tip Суть кеширования
Обмен пространства на время. Сохранить уже вычисленный результат и использовать его в следующий раз напрямую, не пересчитывая. Каждое повышение коэффициента попадания в кеш на 10% может увеличить производительность системы в несколько раз.
:::

### 5.3 Подход к диагностике при сбое запроса

| Симптом | Возможный проблемный слой | Метод диагностики |
|-----|------------|---------|
| Полное отсутствие отклика | DNS / сеть | ping, nslookup |
| Тайм-аут соединения | Сеть / отказ сервера | telnet, curl |
| Возврат 4xx | Ошибка в запросе клиента | Проверить URL, параметры, Token |
| Возврат 5xx | Внутренняя ошибка сервера | Посмотреть логи сервера |
| Очень медленный ответ | База данных / логика приложения | Посмотреть лог медленных запросов, инструменты APM |

## 6. Заключение

Полное путешествие одного HTTP-запроса:

1. **Браузер**: разбор URL → DNS-запрос → TCP-соединение → отправка запроса
2. **Сеть**: маршрутизация → решение по CDN → распределение балансировщиком нагрузки
3. **Сервер**: приём веб-сервером → обработка middleware → бизнес-логика → запрос к базе данных
4. **Возврат**: формирование ответа → сжатие → сетевая передача → отрисовка в браузере

::: tip Ценность понимания всего пути
Когда вы можете мысленно нарисовать полный путь запроса, при любой проблеме вы быстро локализуете, на каком слое она возникла. Это ключевой переход от «младшего разработчика» к «способному самостоятельно диагностировать проблемы».
:::
