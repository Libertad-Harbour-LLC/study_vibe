## 1. Общий обзор DSL: ещё один мир за пределами универсальных языков

### 1.1 Что такое DSL?

**DSL (Domain-Specific Language, предметно-ориентированный язык)** — это язык, разработанный для конкретной предметной области или конкретной задачи. Ему противопоставляется **GPL (General-Purpose Language, универсальный язык программирования)**, такой как Python, Java, Go, C++ и др. — они спроектированы так, чтобы решать любые вычислительные задачи.

Ключевые различия между ними:

| Измерение | GPL (универсальный язык программирования) | DSL (предметно-ориентированный язык) |
|------|-------------------|-------------------|
| **Цель проектирования** | Решение любых вычислительных задач | Решение задач конкретной предметной области |
| **Диапазон выразительности** | Полнота по Тьюрингу, теоретически может вычислить что угодно | Обычно намеренно ограничивает диапазон выразительности |
| **Стоимость обучения** | Выше, нужно понять полную систему языка | Ниже, нужно лишь понять понятия данной области |
| **Типичные представители** | Python, Java, Go, C++, JavaScript | SQL, HTML/CSS, регулярные выражения, YAML, HCL |

На самом деле вы уже давно используете DSL:

- **SQL** — это DSL области запросов к базам данных: вы пишете `SELECT * FROM users WHERE age > 18` для выборки данных, а не вручную пишете логику обхода на Python
- **HTML/CSS** — это DSL области структуры и стилей веб-страниц: вы описываете страницу тегами и атрибутами, а не управляете пикселями на C++
- **Регулярные выражения** — это DSL области сопоставления текстовых шаблонов: вы используете `\d{3}-\d{4}` для сопоставления номера телефона, а не пишете вручную цикл сравнения символов

### 1.2 Классификация DSL

DSL можно разделить на две большие категории по признаку «обладает ли полнотой по Тьюрингу»:

**Внешние DSL (External DSL)**

Имеют независимый синтаксис и парсер, не привязаны ни к какому универсальному языку программирования. Написанный пользователем код обрабатывается специализированным интерпретатором или компилятором.

- Чисто описательные данные: JSON, YAML, XML, TOML, CSV, Protobuf (не содержат никакой логики)
- Запрос/манипуляция: SQL, GraphQL, регулярные выражения (ограниченные логические возможности)
- Доменное моделирование: HCL (Terraform), Dockerfile, синтаксис конфигурации Nginx (декларативное описание состояния конкретной области)

**Внутренние DSL (Internal DSL / Embedded DSL)**

Паразитируют внутри какого-либо универсального языка программирования, используя синтаксис языка-хоста для построения предметно-специфичного способа выражения. Сам код является допустимым кодом языка-хоста, но читается как специализированный язык.

- Pulumi (пишется на TypeScript/Python/Go, но API спроектирован как декларативная конфигурация)
- Определение маршрутов в Ruby on Rails (`get '/users', to: 'users#index'` — допустимый код Ruby, но читается как конфигурация)
- Синтаксис утверждений в тестовых фреймворках (`expect(value).toBe(42)` — допустимый JavaScript, но читается как естественный язык)

### 1.3 Общая картина DSL в бэкенд-проектах

В типичном бэкенд-проекте вы столкнётесь со следующими категориями DSL:

```
DSL в бэкенд-проекте
├── Форматы сериализации данных (описывают структуру данных)
│   ├── Текстовые форматы: JSON, YAML, XML, TOML, CSV, INI
│   └── Бинарные форматы: Protobuf, MessagePack, Avro, BSON
├── Встраиваемые скриптовые языки (программируемый слой конфигурации)
│   ├── Lua (игровые движки, Nginx, Redis)
│   ├── GDScript (движок Godot)
│   └── Jsonnet (генерация шаблонов конфигурации)
├── DSL инфраструктуры и эксплуатации (декларативное описание состояния системы)
│   ├── HCL (Terraform)
│   ├── Dockerfile / Docker Compose YAML
│   └── Синтаксис конфигурации Nginx / Apache
└── Языки описания интерфейсов (описывают контракт API)
    ├── OpenAPI / Swagger
    ├── Protocol Buffers (файлы .proto)
    └── GraphQL Schema
```

Поняв эту общую картину, в последующих главах мы раскроем каждую ветвь по очереди.

## 2. Форматы сериализации данных: описание структурированных данных текстом

### 2.1 Что такое сериализация данных?

**Сериализация (Serialization)** — это процесс преобразования структуры данных в памяти (объектов, словарей, массивов и т. д.) в текстовый/байтовый поток, пригодный для хранения или передачи. Обратный процесс восстановления структуры данных в памяти из текстового/байтового потока называется **десериализацией (Deserialization)**.

Форматы сериализации данных — самая базовая категория DSL: они относятся к чисто описательным внешним DSL, не обладают никакими логическими возможностями и отвечают лишь за статическое описание того, «что есть значение».

### 2.2 Зачем нужны эти форматы?

Предположим, вы разработали бэкенд-сервис, адрес базы данных которого — `localhost:5432`. Если жёстко прописать этот адрес в исходном коде, то для локальной разработки проблем нет, но при развёртывании в продакшене адрес базы данных меняется на `db.prod.company.com:5432`, и вам приходится менять исходный код и заново компилировать.

Общепринятый подход в инженерной практике таков: **выделить изменяемые параметры из кода и хранить их в отдельных конфигурационных файлах.** Программа при запуске читает конфигурационный файл и определяет своё поведение на основе значений в нём.

Помимо конфигурации, форматы сериализации данных также широко используются в таких сценариях, как: обмен данными между системами (запросы/ответы API), персистентное хранение данных, межъязыковое взаимодействие и т. д.

### 2.3 Человекочитаемые текстовые форматы

Ниже представлены самые распространённые в инженерии текстовые форматы сериализации, в историческом порядке.

**INI**

Самый ранний формат конфигурации, появившийся в системе Windows. Структура проста, состоит из секций (section) и пар «ключ-значение»:

```ini
[database]
host = localhost
port = 5432

[server]
debug = true
```

Преимущество — высокая читаемость. Ограничение в том, что он не поддерживает вложенные структуры и типы массивов и не может выразить сложные конфигурации. В настоящее время в основном встречается в устаревших системах и части конфигураций Linux (например, `php.ini`, `my.cnf`).

**CSV**

**CSV (Comma-Separated Values, значения, разделённые запятыми)** — это простейший формат табличных данных:

```csv
name,age,city
Alice,30,Beijing
Bob,25,Shanghai
```

Каждая строка — одна запись, поля разделены запятыми. CSV широко используется для импорта/экспорта данных, обмена электронными таблицами, конвейеров анализа данных. Его ограничение в том, что он может выражать только плоскую двумерную таблицу, не поддерживает вложенные структуры и не несёт информации о типах (все значения — строки).

**XML**

**XML (eXtensible Markup Language, расширяемый язык разметки)** появился в 1998 году и когда-то был основным стандартом обмена данными:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config>
  <database>
    <host>localhost</host>
    <port>5432</port>
  </database>
  <server>
    <debug>true</debug>
    <allowed_origins>
      <origin>https://example.com</origin>
      <origin>https://app.example.com</origin>
    </allowed_origins>
  </server>
</config>
```

Выразительность XML очень высока, он поддерживает вложенность, атрибуты, пространства имён, валидацию по Schema и другие продвинутые возможности. Но его синтаксис многословен — большое количество открывающих и закрывающих тегов приводит к низкому соотношению полезного сигнала, и ручное написание и чтение даётся тяжело.

XML по-прежнему широко используется в следующих областях:
- Экосистема Java (`pom.xml` в Maven, конфигурация Spring, файлы разметки Android)
- Корпоративные веб-сервисы (протокол SOAP)
- Форматы офисных документов (`.docx`, `.xlsx` по сути являются наборами XML-файлов, сжатых в ZIP)
- Ленты подписок RSS/Atom, векторная графика SVG

**JSON**

**JSON (JavaScript Object Notation)** появился в 2001 году и благодаря своей лаконичности быстро вытеснил XML, став фактическим стандартом обмена данными в Web API:

```json
{
  "database": {
    "host": "localhost",
    "port": 5432
  },
  "server": {
    "debug": true
  }
}
```

Преимущество — чёткая структура, почти все языки программирования имеют нативную поддержку парсинга. Основной недостаток — **отсутствие поддержки комментариев**, а большое количество скобок и кавычек легко приводит к ошибкам при ручном написании. JSON также является стандартным форматом конфигурации фронтенд-проектов (`package.json`, `tsconfig.json`).

**YAML**

**YAML (YAML Ain't Markup Language)** также появился в 2001 году и сейчас является самым широко используемым форматом конфигурации в области бэкенда и DevOps. Такие инструменты, как Docker Compose, Kubernetes, GitHub Actions, используют YAML:

```yaml
# Конфигурация базы данных
database:
  host: localhost
  port: 5432

# Конфигурация сервера
server:
  debug: true
  allowed_origins:
    - https://example.com
    - https://app.example.com
```

Преимущества — поддержка комментариев, лаконичный синтаксис, возможность выражать сложные вложенные структуры. Недостаток — **зависимость от отступов для обозначения уровней иерархии**: ошибка отступа приводит к сбою парсинга, и это самая частая проблема, с которой сталкиваются новички.

> Дополнение: полное название YAML — «YAML Ain't Markup Language» — это рекурсивная аббревиатура.

**TOML**

**TOML (Tom's Obvious Minimal Language)** появился в 2013 году и используется менеджером пакетов Cargo для Rust и файлом `pyproject.toml` в Python:

```toml
[database]
host = "localhost"
port = 5432

[server]
debug = true
allowed_origins = [
  "https://example.com",
  "https://app.example.com"
]
```

TOML стремится сочетать лаконичность INI с выразительностью YAML, избегая при этом проблем, связанных с чувствительностью к отступам.

### 2.4 Бинарные форматы сериализации

Все вышеперечисленные форматы — человекочитаемый текст. В сценариях с более высокими требованиями к производительности и размеру существует категория **бинарных форматов сериализации** — они жертвуют читаемостью ради меньшего размера и более быстрой скорости парсинга.

| Формат | Разработчик | Особенности | Типичные сценарии применения |
|------|-------|------|------------|
| **Protocol Buffers (Protobuf)** | Google | Требует предварительно определённого Schema-файла `.proto`, строгая типизация, крайне малый размер | Связь по gRPC, внутренние сервисы Google, высокопроизводительные микросервисы |
| **MessagePack** | Сообщество | Бинарная версия, похожая на JSON, не требует Schema | Внутреннее кодирование Redis, высокопроизводительное межъязыковое взаимодействие |
| **Avro** | Apache | Поддерживает эволюцию Schema, подходит для сценариев больших данных | Сериализация данных в экосистеме Hadoop / Kafka |
| **BSON** | MongoDB | Бинарное расширение JSON, поддерживает больше типов данных | Внутренний формат хранения базы данных MongoDB |

На примере Protocol Buffers — сначала нужно определить Schema:

```protobuf
// user.proto
syntax = "proto3";

message User {
  string name = 1;
  int32 age = 2;
  string email = 3;
}
```

Затем с помощью компилятора (`protoc`) автоматически генерируется код сериализации/десериализации для разных языков. Эта модель «сначала определить Schema, затем сгенерировать код» совпадает с идеей генерации SDK по OpenAPI, о которой будет рассказано далее.

### 2.5 Полное сравнение

| Формат | Тип | Год появления | Читаемость | Поддержка комментариев | Типичные сценарии применения |
|------|------|---------|--------|---------|------------|
| **INI** | Текст | 1980-е | Высокая | ✅ | Системная конфигурация, устаревшие проекты |
| **CSV** | Текст | 1972 | Высокая | ❌ | Импорт/экспорт данных, обмен таблицами |
| **XML** | Текст | 1998 | Средняя | ✅ | Экосистема Java, корпоративные веб-сервисы, форматы документов |
| **JSON** | Текст | 2001 | Высокая | ❌ | Обмен данными в Web API, конфигурация фронтенда |
| **YAML** | Текст | 2001 | Высокая | ✅ | Docker, K8s, CI/CD, конфигурация бэкенд-сервисов |
| **TOML** | Текст | 2013 | Высокая | ✅ | Конфигурация проектов Rust / Python |
| **Protobuf** | Бинарный | 2008 | Нет | — | gRPC, высокопроизводительное взаимодействие микросервисов |
| **MessagePack** | Бинарный | 2008 | Нет | — | Высокопроизводительное межъязыковое взаимодействие |
| **Avro** | Бинарный | 2009 | Нет | — | Конвейеры больших данных Hadoop / Kafka |
| **BSON** | Бинарный | 2009 | Нет | — | Внутреннее хранилище MongoDB |

**Ключевой момент**: сущностная функция всех этих форматов одинакова — **преобразование структурированных данных в форму, пригодную для хранения и передачи**. Текстовые форматы отдают приоритет человекочитаемости и удобству редактирования; бинарные форматы — производительности парсинга и объёму передачи. Выбор формата зависит от баланса требований конкретного сценария.

## 3. Встраиваемые скриптовые языки: программируемый слой конфигурации

### 3.1 Определение понятия

Python, JavaScript, Go и другие языки — это универсальные языки программирования (General-Purpose Language), которые могут работать самостоятельно и строить полноценные приложения.

В отличие от них, есть категория языков, **специально спроектированных для встраивания и выполнения внутри других программ-хостов**, чтобы предоставлять программе-хосту программируемые возможности расширения. Такие языки называются **встраиваемыми скриптовыми языками (Embedded Scripting Language)**.

Ключевая проблема, которую они решают: **когда выразительности статических конфигурационных файлов (YAML/JSON) недостаточно и требуется ввести условные ветвления, циклы и другую логику, как реализовать динамическое поведение, не изменяя исходный код программы-хоста.**

### 3.2 Lua: самый репрезентативный встраиваемый скриптовый язык

Lua («луна» по-португальски) — это чрезвычайно лёгкий скриптовый язык, весь интерпретатор после компиляции занимает всего несколько сотен КБ. Цель его проектирования — не самостоятельная работа, а роль встраиваемого слоя расширения.

Типичные сценарии применения Lua:

- **Игровые движки**: система плагинов World of Warcraft, игровые скрипты Roblox используют Lua. Игровой движок реализует основной рендеринг и физические вычисления на C/C++, а часто меняющиеся части — логику уровней, диалоги NPC и т. д. — отдаёт скриптам на Lua. Так геймдизайнерам не нужно перекомпилировать движок при изменении игрового контента.

- **Веб-серверы**: OpenResty встраивает Lua внутрь Nginx, позволяя инженерам эксплуатации реализовывать на Lua-скриптах логику фильтрации запросов, ограничения трафика, аутентификации и т. д., не изменяя исходный код Nginx на C.

- **Базы данных**: Redis поддерживает отправку Lua-скриптов на выполнение на стороне сервера для реализации составных операций, требующих гарантии атомарности (например, «сначала чтение, затем запись»).

Ниже — пример Lua-скрипта, встроенного в Nginx (OpenResty):

```lua
-- Функция: token-аутентификация для пути /api/secret
local uri = ngx.var.uri
local token = ngx.req.get_headers()["Authorization"]

if uri == "/api/secret" and token ~= "Bearer my-secret-token" then
    ngx.status = 403
    ngx.say("Access denied")
    return ngx.exit(403)
end
```

### 3.3 Другие встраиваемые скриптовые языки

| Язык | Среда-хост | Типичное применение |
|------|---------|---------|
| **Lua** | Игровые движки, Nginx (OpenResty), Redis | Игровая логика, политики шлюзов, операции с кешем |
| **VimScript / Lua** | Редакторы Vim / Neovim | Разработка плагинов редактора |
| **Emacs Lisp** | Редактор Emacs | Кастомизация поведения редактора |
| **GDScript** | Игровой движок Godot | Скрипты игровой логики |
| **Jsonnet** | Экосистема Kubernetes / инструменты генерации конфигурации | Шаблонная генерация большого числа похожих конфигураций JSON/YAML |

**Ключевой момент**: встраиваемые скриптовые языки в классификации DSL относятся к **пограничной зоне между внутренними и внешними DSL** — они являются самостоятельными языками (со своим синтаксисом и интерпретатором), но цель их проектирования — встраивание и выполнение в программе-хосте, а не самостоятельное построение приложений. Они заполняют пробел между «статическими конфигурационными файлами» (чисто описательными DSL) и «универсальными языками программирования» (GPL): когда конфигурации требуется выразить логику (условные ветвления, циклы, вызовы функций), встраивание лёгкого скриптового языка является стандартным инженерным решением.

## 4. Инфраструктура как код (Infrastructure as Code)

### 4.1 Что такое «инфраструктура»

В бэкенд-инженерии «инфраструктура» (Infrastructure) означает низкоуровневые ресурсы, от которых зависит работа приложения:

- Вычислительные ресурсы: серверы (виртуальные машины или контейнеры)
- Хранилище данных: экземпляры баз данных, бакеты объектного хранилища
- Сеть: правила файрвола, балансировщики нагрузки, конфигурация DNS
- Промежуточное ПО: очереди сообщений, кластеры кеша

В эпоху облачных вычислений эти ресурсы создаются и управляются через консоль облачных провайдеров (например, AWS, Alibaba Cloud, Tencent Cloud) с помощью графического интерфейса.

### 4.2 Ограничения ручного управления

Ручные операции через консоль возможны в малых проектах, но с ростом масштаба проекта проявляются следующие проблемы:

1. **Невоспроизводимость**: шаги операций не записываются, невозможно точно воссоздать ту же самую среду
2. **Неаудируемость**: невозможно отследить, «кто и когда какую конфигурацию изменил»
3. **Невозможность совместной работы**: процесс операций нельзя включить в систему контроля версий и провести code review
4. **Подверженность ошибкам**: ручные операции в продакшене несут риск ошибочных действий

Ключевая идея **«инфраструктуры как кода» (Infrastructure as Code, сокращённо IaC)** такова: **декларативно определять инфраструктурные ресурсы с помощью кода, чтобы они обладали возможностями контроля версий, автоматизированного выполнения и воспроизводимого развёртывания.**

### 4.3 Terraform

Terraform — самый широко используемый на сегодня инструмент IaC, разработанный компанией HashiCorp. Он использует специализированный язык **HCL (HashiCorp Configuration Language)**.

Terraform использует **декларативную** парадигму: пользователь описывает желаемое итоговое состояние, а Terraform автоматически вычисляет операции, необходимые для перехода из текущего состояния в целевое.

```hcl
# Определение облачного сервера
resource "aws_instance" "my_server" {
  ami           = "ami-0c55b159cbfafe1f0"  # Образ операционной системы
  instance_type = "t3.micro"               # Спецификация экземпляра

  tags = {
    Name = "my-first-server"
  }
}

# Определение экземпляра базы данных PostgreSQL
resource "aws_db_instance" "my_database" {
  engine         = "postgres"
  instance_class = "db.t3.micro"
  username       = "admin"
  password       = "please-use-secrets-manager"
}
```

Процесс выполнения:

```bash
terraform plan    # Предпросмотр изменений, которые будут выполнены
terraform apply   # Подтверждение и выполнение, автоматическое создание ресурсов на облачной платформе
```

### 4.4 Pulumi

Pulumi предлагает другой подход: **напрямую использовать универсальные языки программирования (TypeScript, Python, Go и др.) для определения инфраструктуры**, а не изучать специализированный синтаксис HCL.

То же определение сервера, выраженное на Pulumi + TypeScript:

```typescript
import * as aws from "@pulumi/aws";

const server = new aws.ec2.Instance("my-server", {
    ami: "ami-0c55b159cbfafe1f0",
    instanceType: "t3.micro",
    tags: { Name: "my-first-server" },
});

const bucket = new aws.s3.Bucket("my-bucket", {
    acl: "private",
});

export const serverIp = server.publicIp;
```

Поскольку используется универсальный язык программирования, разработчик может применять циклы, условные ветвления, абстракцию функций и другие возможности языка для обработки сложной инфраструктурной логики.

### 4.5 Сравнение Terraform и Pulumi

| Измерение | Terraform | Pulumi |
|------|-----------|--------|
| **Язык** | HCL (специализированный язык) | TypeScript / Python / Go и другие универсальные языки |
| **Стоимость обучения** | Нужно изучить синтаксис HCL | Используется уже освоенный язык программирования, стоимость обучения ниже |
| **Экосистема сообщества** | Очень зрелая, охватывает почти всех облачных провайдеров | Быстро растёт, но по масштабу меньше Terraform |
| **Сценарии применения** | Стандартизированное управление инфраструктурой под руководством команды эксплуатации | Проекты под руководством разработчиков, сценарии со сложной логикой |
| **Степень пригодности для генерации кода ИИ** | Высокая (фиксированные шаблоны) | Очень высокая (по сути это код универсального языка программирования) |

**Ключевой момент**: HCL в инструментах IaC — это типичный внешний DSL: он имеет независимый синтаксис и парсер и предназначен специально для декларативного описания состояния инфраструктуры. А Pulumi использует стратегию внутреннего DSL — выражает предметно-специфичные понятия синтаксисом универсального языка программирования. У обоих одна цель (перевести управление инфраструктурой из ручных операций в код), но разные пути (специализированный язык vs универсальный язык). Код можно включить в систему контроля версий Git, проводить командный review, автоматизированно выполнять и откатывать.

## 5. Связующий код и автоматическая генерация SDK

### 5.1 Что такое связующий код

В программной инженерии **связующий код (Glue Code)** означает код, который сам по себе не содержит бизнес-логики, а используется лишь для соединения двух систем или модулей.

Типичный связующий код включает:

- Код HTTP-запросов, который пишут при вызове фронтендом бэкенд-API (сборка URL, установка заголовков запроса, парсинг ответа)
- Код HTTP-клиента, который пишут, когда бэкенд-сервис A вызывает интерфейс сервиса B
- Код адаптации интерфейсов между разными языками программирования

Особенность такого кода: **высоко повторяющийся, с фиксированными шаблонами, но обязательный.**

### 5.2 Спецификация OpenAPI и автоматическая генерация кода

Поскольку связующий код обладает высокой степенью шаблонности, инженерное решение таково: **сначала описать интерфейс API в стандартном формате, затем с помощью инструмента автоматически сгенерировать клиентский код.**

**Спецификация OpenAPI** (ранее Swagger) — это отраслевой стандарт описания REST API. Она использует формат YAML или JSON и точно определяет пути API, параметры, тело запроса и структуру ответа:

```yaml
openapi: 3.0.0
info:
  title: API сервиса электронной почты
  version: 1.0.0

paths:
  /emails:
    post:
      summary: Отправить письмо
      requestBody:
        content:
          application/json:
            schema:
              type: object
              properties:
                to:
                  type: string
                  example: "user@example.com"
                subject:
                  type: string
                body:
                  type: string
      responses:
        '200':
          description: Отправлено успешно
```

На основе этого файла спецификации с помощью инструментов вроде `openapi-generator` можно автоматически сгенерировать клиентские SDK для разных языков:

- **Python**: `client.emails.send(to="user@example.com", subject="Hi", body="Hello")`
- **TypeScript**: `client.emails.send({ to: "user@example.com", subject: "Hi", body: "Hello" })`
- **Go**: `client.Emails.Send(ctx, &SendEmailRequest{To: "user@example.com", ...})`

Сгенерированный SDK инкапсулирует все детали HTTP-запроса, и вызывающей стороне не нужно беспокоиться о пути URL, методе запроса, формате сериализации и других низкоуровневых деталях реализации.

### 5.3 Новый взгляд на кейс Armin

Возвращаясь к кейсу из начала статьи, теперь можно точно понять каждую его составляющую:

| Составляющая | Природа | Пояснение |
|---------|------|------|
| **Go** | Код бизнес-логики | Реализация основного функционала сервиса отправки/получения почты |
| **YAML** | Конфигурационные файлы | Конфигурация сервиса, определение CI/CD-конвейера, файлы спецификации OpenAPI |
| **Pulumi** | Инфраструктурный код | Определение облачных ресурсов (серверов, баз данных, сети) на Go/TypeScript |
| **Связующий код SDK** | Автоматически сгенерированные клиентские библиотеки | SDK для Python и TypeScript, автоматически сгенерированные из спецификации OpenAPI |

Из них YAML-конфигурация, определение ресурсов Pulumi и связующий код SDK — все три категории относятся к высоко шаблонному коду с чёткими спецификационными ограничениями, и именно это та область, где способности ИИ к генерации кода сильнее всего. Поэтому утверждение «90% из 40 тысяч строк кода сгенерировано ИИ» вполне разумно.

## 6. Связь ИИ и DSL

### 6.1 Анализ применимости генерации кода ИИ

| Измерение признака | Подходит для генерации ИИ | Не подходит для генерации ИИ |
|---------|-------------|---------------|
| **Степень шаблонности** | Высокая повторяемость, есть фиксированные шаблоны | Требуется творческое проектирование, нет прецедентов |
| **Спецификационные ограничения** | Есть чёткая schema или синтаксическая спецификация | Требования размыты, границы нечёткие |
| **Зависимость от контекста** | Локально самодостаточно, отдельное определение не зависит от глобального понимания | Требуется понимание архитектурного замысла всей системы |
| **Проверяемость** | Может автоматически проверяться инструментами (например, `terraform validate`) | Можно полагаться только на ручную оценку обоснованности проектирования |

Четыре категории технологий, представленные в этой статье — конфигурационные файлы, встраиваемые скрипты, IaC-код, связующий код SDK — все обладают признаками из левого столбца. Это объясняет, почему эффект генерации кода ИИ в этих областях значительно превосходит код бизнес-логики.

### 6.2 Оценочная рамка

При определении того, подходит ли некоторый фрагмент кода для генерации ИИ, можно опираться на следующие три критерия:

1. **Есть ли готовая спецификация или schema?** — если есть, то это дружелюбно к ИИ
2. **Относится ли это к большому числу повторяющихся шаблонов?** — если да, то это дружелюбно к ИИ
3. **Можно ли автоматически проверить результат генерации инструментами?** — если можно, то это дружелюбно к ИИ

Код, удовлетворяющий всем трём пунктам (например, генерация SDK из спецификации OpenAPI, массовое определение однотипных ресурсов через Terraform), можно в высокой степени доверять генерации ИИ. Код, не удовлетворяющий ни одному из трёх пунктов (например, проектирование нового протокола распределённой согласованности), по-прежнему требует самостоятельной работы инженера.

## 7. Глоссарий

| Термин | Полное название / перевод | Определение |
|------|------------|------|
| **DSL** | Domain-Specific Language / предметно-ориентированный язык | Язык, спроектированный для конкретной области, противопоставляемый универсальному языку программирования |
| **GPL** | General-Purpose Language / универсальный язык программирования | Язык программирования, способный решать любые вычислительные задачи, например Python, Java, Go |
| **Внешний DSL** | External DSL | Предметно-ориентированный язык с независимым синтаксисом и парсером, например SQL, HCL, YAML |
| **Внутренний DSL** | Internal DSL / Embedded DSL | Предметно-специфичное выражение, паразитирующее внутри универсального языка программирования и построенное на синтаксисе хоста, например Pulumi |
| **Сериализация данных** | Data Serialization | Процесс преобразования структуры данных в памяти в формат, пригодный для хранения или передачи |
| **INI** | Initialization | Самый ранний формат конфигурации «ключ-значение», появившийся в системе Windows |
| **CSV** | Comma-Separated Values / значения, разделённые запятыми | Текстовый табличный формат с разделением полей запятыми |
| **XML** | eXtensible Markup Language / расширяемый язык разметки | Текстовый формат данных на основе тегов, выразительный, но многословный |
| **JSON** | JavaScript Object Notation | Лёгкий формат обмена данными на основе пар «ключ-значение», фактический стандарт Web API |
| **YAML** | YAML Ain't Markup Language | Формат конфигурационных файлов на основе отступов, широко используемый в бэкенде и DevOps |
| **TOML** | Tom's Obvious Minimal Language | Формат конфигурации с явным синтаксисом, часто используемый в экосистемах Rust и Python |
| **Protobuf** | Protocol Buffers | Бинарный формат сериализации от Google, требует предопределённой Schema, малый размер, высокая скорость |
| **MessagePack** | — | Бинарный формат сериализации, похожий на JSON, не требует Schema |
| **Lua** | — | Лёгкий встраиваемый скриптовый язык, часто используемый для расширения игровых движков, веб-серверов и баз данных |
| **IaC** | Infrastructure as Code / инфраструктура как код | Инженерная практика определения и управления облачными вычислительными ресурсами с помощью кода |
| **Terraform** | — | Инструмент IaC, разработанный HashiCorp, использует декларативный язык HCL |
| **HCL** | HashiCorp Configuration Language | Специализированный язык конфигурации, используемый Terraform |
| **Pulumi** | — | Инструмент IaC, поддерживающий универсальные языки программирования |
| **OpenAPI** | — | Отраслевой стандарт спецификации описания интерфейсов REST API (ранее Swagger) |
| **SDK** | Software Development Kit / комплект средств разработки ПО | Клиентская библиотека, инкапсулирующая детали вызова API |
| **Связующий код** | Glue Code | Адаптирующий код, не содержащий бизнес-логики и используемый лишь для соединения двух систем |

## Заключение

В бэкенд-инженерии существует большое количество кода, не относящегося к бизнес-логике. У него есть общее вышестоящее понятие: **DSL (предметно-ориентированный язык)** — язык, спроектированный для конкретной области и противопоставляемый универсальному языку программирования.

DSL, представленные в этой статье, можно отнести к четырём категориям:

1. **Форматы сериализации данных** (XML / JSON / YAML / TOML / CSV / Protobuf и др.) — чисто описательные внешние DSL, преобразующие структурированные данные в форму, пригодную для хранения и передачи
2. **Встраиваемые скриптовые языки** (Lua и др.) — находятся между конфигурацией и универсальными языками, предоставляют программе-хосту программируемые возможности расширения
3. **Языки определения инфраструктуры** (HCL / Dockerfile и др.) — декларативные внешние DSL, описывающие желаемое состояние системы; а Pulumi реализует ту же цель способом внутреннего DSL
4. **Языки описания интерфейсов и генерация связующего кода** (OpenAPI / .proto) — автоматическая генерация соединительного кода между системами по описанию спецификации

Поняв рамку классификации DSL, при встрече с разнообразным «кодом, не похожим на код» в бэкенд-проектах можно быстро определить его природу: к какой категории DSL он относится, какую задачу какой области решает и почему он написан не на универсальном языке программирования.

При этом, поскольку код DSL обладает признаками высокой шаблонности, управления спецификациями и автоматической проверяемости, он также является самой эффективной на сегодня областью применения технологий генерации кода ИИ.
