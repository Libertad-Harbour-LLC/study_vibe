# Ограничение трафика и контроль обратного давления

::: tip Предисловие
**В полночь на 11 ноября одновременно врываются сотни миллионов пользователей — выдержит ли сервер?** У любой системы есть верхний предел обрабатывающей способности. Когда объём запросов превышает несущую способность системы, при отсутствии контроля результат таков, что никто не сможет ею воспользоваться. Ограничение трафика и обратное давление — это два рубежа обороны, защищающие систему от «раздавливания».
:::

- **Многоуровневое ограничение трафика**: узнаете о многоуровневой архитектуре ограничения трафика от клиента к шлюзу и к сервису

## 0. Общая картина: зачем «отказывать» пользователям?

Звучит контринтуитивно — разве мы не должны хорошо обслуживать каждого пользователя? Но реальность такова: **если не отказать части запросов, то провалятся все запросы**.

Представьте ресторан, вмещающий лишь 100 человек, в который внезапно врываются 1000. Если не ограничить поток, результат не в том, что все 1000 смогут поесть, а в том, что кухня рухнет, официанты выбьются из сил, и никто из 1000 не поест. Правильный подход — ограничить поток очередью у входа: пустить сначала 100 человек, остальные ждут.

::: tip Ключевые цели ограничения трафика
- **Защита системы**: предотвращение полной недоступности сервиса из-за перегрузки
- **Справедливое распределение**: гарантия нормальной обработки уже принятых запросов
- **Плавная деградация**: ограниченные запросы получают явный код статуса 429, а не тайм-аут или ошибку 500
:::

## 1. Алгоритмы ограничения трафика: три классических решения

Ключевая проблема ограничения трафика: **сколько максимум запросов можно пропустить за единицу времени?** Разные алгоритмы по-разному балансируют точность, обработку всплесков трафика и сложность реализации.

<RateLimitAlgorithmDemo />

| Алгоритм | Принцип | Всплески трафика | Точность | Сложность реализации |
|------|------|---------|--------|-----------|
| Token bucket | С фиксированной скоростью добавляются токены, запрос расходует токен | Разрешены (при наличии запаса в ведре) | Высокая | Средняя |
| Leaky bucket | Запросы выстраиваются в очередь, обработка с фиксированной скоростью | Не разрешены (полностью сглажено) | Высокая | Средняя |
| Скользящее окно | Подсчёт числа запросов внутри окна | Частично разрешены | Довольно высокая | Низкая |
| Фиксированное окно | Подсчёт по временным окнам | На границах возможны всплески | Низкая | Минимальная |

::: tip Какой алгоритм выбрать?
- **Ограничение трафика API**: token bucket используется чаще всего, допускает разумные всплески трафика
- **Формирование трафика**: leaky bucket подходит для сценариев, требующих постоянной скорости вывода
- **Простой подсчёт**: скользящее окно просто в реализации, подходит для большинства веб-приложений
:::

## 2. Контроль обратного давления: когда вышестоящее звено быстрее нижестоящего

Ограничение трафика решает проблему «слишком много внешних запросов», а **обратное давление (Backpressure)** решает проблему «несоответствия скоростей внутренних компонентов».

Когда скорость производства данных производителем постоянно превышает скорость их обработки потребителем, промежуточный буфер непрерывно разбухает, что в итоге приводит к переполнению памяти или потере данных. Механизм обратного давления позволяет потребителю «обратно уведомить» производителя о необходимости замедлиться.

::: tip Четыре стратегии обратного давления
1. **Отбрасывание (Drop)**: при заполнении буфера отбрасываются новые или старые данные; подходит для сценариев с высокими требованиями к реальному времени, но допускающих потери
2. **Блокировка (Block)**: производитель приостанавливается и ждёт, пока потребитель обработает, затем продолжает; подходит для сценариев, где данные нельзя терять
3. **Выборка (Sample)**: обрабатывается лишь часть данных; подходит для высокочастотных потоков данных
4. **Эластичное масштабирование (Scale)**: динамическое увеличение числа потребителей; подходит для облачно-нативной среды
:::

## 3. Многоуровневая архитектура ограничения трафика

В продакшене ограничения трафика в одной точке недостаточно — нужна **многоуровневая защита**, где каждый уровень решает задачу своей гранулярности.

| Уровень | Расположение | Гранулярность ограничения | Инструменты |
|------|------|---------|------|
| Клиент | Фронтенд/App | Антидребезг кнопок, троттлинг запросов | lodash.throttle, debounce |
| CDN/WAF | Граничные узлы | Уровень IP, уровень региона | Cloudflare Rate Limiting |
| API-шлюз | Входной шлюз | Уровень маршрута, уровень пользователя | Nginx limit_req, Kong |
| Сервер | Внутри приложения | Уровень интерфейса, уровень ресурса | Sentinel, Resilience4j |
| База данных | Слой хранения | Число соединений, QPS | Конфигурация пула соединений, разрыв при медленных запросах |

::: tip HTTP-спецификация ограничения трафика
Ограниченный запрос должен возвращать код статуса `429 Too Many Requests`, а в заголовках ответа содержать:
- `Retry-After`: рекомендуемое время до повторной попытки клиента (в секундах или в виде даты)
- `X-RateLimit-Limit`: верхний предел ограничения трафика
- `X-RateLimit-Remaining`: оставшаяся квота
- `X-RateLimit-Reset`: время сброса квоты
:::

## Заключение

Ограничение трафика и обратное давление — два ключевых рубежа обороны, защищающих стабильность системы. Ограничение трафика контролирует скорость притока внешнего трафика, а обратное давление согласует скорость обработки внутренних компонентов.

Вспомним ключевые моменты этой главы:

1. **Необходимость ограничения трафика**: если не отказать части запросов, провалятся все запросы
2. **Три ключевых алгоритма**: token bucket (допускает всплески), leaky bucket (полное сглаживание), скользящее окно (просто и точно)
3. **Механизм обратного давления**: четыре стратегии — отбрасывание, блокировка, выборка, масштабирование
4. **Многоуровневая защита**: от клиента до базы данных, каждый уровень решает задачу своей гранулярности
5. **Спецификация 429**: при ограничении трафика возвращается стандартный код статуса и заголовки ограничения трафика
