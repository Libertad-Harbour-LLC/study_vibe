# Очереди асинхронных задач и модель «производитель-потребитель»

::: tip Предисловие
**Пользователь нажал кнопку «Экспортировать отчёт» и потом 30 секунд смотрел на крутящуюся анимацию загрузки — это нормально?** Когда операция занимает несколько секунд или даже минут, заставлять пользователя ждать впустую — это явно плохой опыт. Очереди асинхронных задач — это ключевой архитектурный паттерн, решающий именно эту проблему: трудоёмкие операции отправляются на обработку в фон, а пользователь сразу получает ответ.
:::

После изучения этой главы вы получите:

- **Модель «производитель-потребитель»**: освоите ключевую идею паттерна Producer-Consumer и рабочий процесс
- **Механизм пула Worker'ов**: узнаете, как задачи распределяются между несколькими Worker'ами для параллельной обработки
- **Гарантии надёжности**: освоите механизмы повторных попыток, идемпотентности, очереди мёртвых сообщений (dead-letter queue) и другие гарантии
- **Навык выбора технологий**: познакомитесь с особенностями и сценариями применения основных фреймворков асинхронных задач

## 0. Общая картина: почему нельзя заставлять пользователя «ждать впустую»?

Представьте, что вы пришли в ресторан сделать заказ. Хороший ресторан сразу после оформления заказа выдаст вам номер для получения, и вы сможете найти место, посидеть в телефоне, а когда блюдо будет готово — прийти за ним. А не заставит вас стоять у стойки и наблюдать, как повар готовит блюдо целиком.

В веб-приложениях есть много подобных операций «приготовления блюд»:

- **Отправка email/SMS**: вызов стороннего API, может занять несколько секунд
- **Генерация отчётов/PDF**: вычисления над большим объёмом данных, могут занять десятки секунд
- **Обработка изображений/видео**: сжатие, перекодирование, наложение водяного знака, могут занять несколько минут
- **Синхронизация данных**: синхронизация данных между системами, время непредсказуемо

::: tip Ключевая идея асинхронных задач
Вынести трудоёмкие операции из основного потока «запрос-ответ» и поместить их в фоновую очередь для асинхронной обработки. После отправки запроса пользователь сразу получает ответ «принято, обрабатывается», а по завершении обработки результат сообщается через уведомление, опрос (polling) или WebSocket.
:::

## 1. Синхронно vs асинхронно: история одного заказа

Когда пользователь оформляет заказ, бэкенду нужно сделать много вещей: списать товар со склада, создать запись о заказе, отправить подтверждающее письмо, обновить систему рекомендаций, записать журнал аудита…

В синхронном режиме эти операции выполняются последовательно, и пользователь должен дождаться завершения всех операций, чтобы увидеть результат. В асинхронном режиме достаточно выполнить только основные операции (списание со склада, создание заказа), а остальные отправить в очередь для фоновой обработки.

<AsyncTaskFlowDemo />

| Критерий сравнения | Синхронная обработка | Асинхронная обработка |
|---------|---------|---------|
| Время ожидания пользователя | Суммарное время всех операций | Только время основных операций |
| Пропускная способность системы | Низкая (потоки заблокированы) | Высокая (потоки быстро освобождаются) |
| Влияние сбоев | Сбой неосновной операции приводит к общему сбою | Сбой неосновной операции не влияет на основной поток |
| Сложность реализации | Простая | Нужна дополнительная инфраструктура очередей |
| Согласованность данных | Строгая согласованность | Конечная согласованность |

::: tip Когда стоит использовать асинхронность?
Три критерия оценки: **долго выполняется** (более 1-2 секунд), **не основное** (сбой не должен влиять на основной поток), **можно отложить** (результат не нужен немедленно). Если выполняются любые два из них — стоит задуматься об асинхронной обработке.
:::

## 2. Модель «производитель-потребитель»: «конвейер» задач

Ядро очереди асинхронных задач — классический **паттерн «производитель-потребитель» (Producer-Consumer Pattern)**. В этом паттерне три роли:

- **Производитель (Producer)**: сторона, порождающая задачи, обычно это веб-сервер при обработке запроса пользователя
- **Очередь (Queue)**: буфер для хранения задач, ожидающих обработки, обычно реализуется с помощью Redis, RabbitMQ и т. п.
- **Потребитель (Consumer/Worker)**: рабочий процесс, который извлекает задачи из очереди и выполняет их

<TaskWorkerDemo />

::: tip Три главные ценности очереди
1. **Развязка (decoupling)**: производителю не нужно знать, кто обрабатывает задачу, а потребителю — откуда задача пришла
2. **Сглаживание пиков нагрузки**: при всплеске трафика задачи сначала накапливаются в очереди, а потребитель обрабатывает их в своём темпе
3. **Надёжность**: задачи сохраняются в очереди, и даже при падении потребителя они не теряются
:::

| Компонент | Обязанность | Распространённые реализации |
|------|------|---------|
| Брокер сообщений | Хранение и пересылка сообщений-задач | Redis, RabbitMQ, Kafka |
| Сериализатор | Сериализация/десериализация параметров задачи | JSON, MessagePack, Pickle |
| Планировщик | Управление периодическими и отложенными задачами | Cron, APScheduler, node-cron |
| Хранилище результатов | Сохранение результатов выполнения задач | Redis, база данных, S3 |

## 3. Гарантии надёжности: задача не должна «потеряться» и не должна «повториться»

В распределённой среде в любой момент могут возникнуть проблемы: сетевые сбои, перезапуск сервисов, нехватка ресурсов. Система асинхронных задач должна обладать полноценными механизмами гарантии надёжности.

Две самые важные проблемы: **потеря задачи** (потребитель упал на середине обработки) и **повторное выполнение** (задача была доставлена дважды).

<TaskRetryDemo />

::: tip Три кита надёжности
1. **Механизм ACK**: потребитель отправляет подтверждение (ACK) только после завершения обработки задачи; неподтверждённые задачи доставляются повторно
2. **Стратегия повторов**: при сбое задача повторяется по стратегии, экспоненциальная задержка + джиттер — лучшая практика
3. **Проектирование идемпотентности**: многократное выполнение одной задачи даёт тот же эффект, что и однократное; реализуется через дедупликацию по уникальному ID
:::

| Механизм | Решаемая проблема | Способ реализации |
|------|-----------|---------|
| Подтверждение ACK | Потеря задачи | Ручное подтверждение после завершения; при отсутствии подтверждения по таймауту — повторная доставка |
| Очередь мёртвых сообщений (DLQ) | Постоянно сбоящие «ядовитые сообщения» | После превышения лимита повторов задача переводится в DLQ для ручного вмешательства |
| Идемпотентность | Повторное выполнение | Дедупликация по уникальному ID задачи, уникальное ограничение в базе данных |
| Очередь с приоритетами | Голодание задач | Высокоприоритетные задачи обрабатываются первыми, чтобы не блокироваться низкоприоритетными |
| Контроль таймаута | Зависание задачи | Установка максимального времени выполнения, автоматическое завершение по таймауту и повтор |

## 4. Выбор фреймворка: выберите подходящий инструмент

В экосистемах разных языков есть разные фреймворки асинхронных задач, и они по-разному расставляют акценты на богатстве функций, производительности и удобстве использования. При выборе фреймворка сначала учитывайте свой технологический стек, а затем принимайте решение исходя из масштаба и требований проекта.

<AsyncComparisonDemo />

::: tip Рекомендации по выбору
- **Проекты на Python**: для средних и крупных — Celery, для небольших — RQ
- **Проекты на Node.js**: предпочтительно BullMQ (следующее поколение Bull)
- **Проекты на Ruby**: Sidekiq — практически единственный выбор
- **Проекты на Java**: в экосистеме Spring — Spring Batch, для высокой пропускной способности — Kafka Streams
- **Проекты на Go**: Asynq (на основе Redis) или Machinery

Если в вашем проекте уже используется Redis, то решения на основе Redis (Celery+Redis, BullMQ, Sidekiq) — самый простой способ начать.
:::

## Заключение

Очереди асинхронных задач — незаменимая инфраструктура в бэкенд-архитектуре. Они позволяют системе изящно обрабатывать трудоёмкие операции, одновременно улучшая пользовательский опыт и повышая пропускную способность системы.

Вспомним ключевые моменты этой главы:

1. **Критерии асинхронности**: долго выполняется, не основное, можно отложить — при выполнении двух из них стоит делать асинхронным
2. **Модель «производитель-потребитель»**: Producer → Queue → Consumer, три развязанных сотрудничающих звена
3. **Пул Worker'ов**: несколько Worker'ов параллельно потребляют задачи, повышая мощность обработки
4. **Гарантии надёжности**: подтверждение ACK + стратегия повторов + идемпотентность, ни одно из трёх не должно отсутствовать
5. **Выбор фреймворка**: исходя из технологического стека и масштаба проекта; Redis — самый распространённый брокер сообщений
