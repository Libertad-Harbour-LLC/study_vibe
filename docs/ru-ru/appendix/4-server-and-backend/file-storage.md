# Файловое хранилище и объектное хранилище

::: tip Предисловие
**Пользователь загрузил аватар, а вы сохранили его в каталоге `/uploads` на сервере — и тут диск сервера переполнился, или вы добавили второй сервер, и пользователь обнаружил, что аватар то отображается, то нет.** Файловое хранилище кажется простым, но в распределённой среде это архитектурная проблема, к которой нужно отнестись серьёзно. Объектное хранилище — это стандартный ответ эпохи интернета на эту проблему.
:::

## 0. Общая картина: почему нельзя хранить файлы локально на сервере?

В начале работы над проектом хранение загруженных пользователем файлов в локальном каталоге сервера — самый интуитивный подход. Но по мере развития проекта вы столкнётесь с рядом проблем:

- **Ограниченное место на диске**: диск сервера всегда переполняется, расширение хлопотно
- **Несовместное использование при нескольких серверах**: после балансировки нагрузки запрос пользователя может попасть на разные серверы, и файл не находится
- **Нет резервных копий**: если сервер выходит из строя, файлы теряются
- **Нет CDN**: пользователи по всему миру обращаются к одному серверу, скорость низкая

::: tip Ключевая ценность объектного хранилища
Объектное хранилище (например, AWS S3, Alibaba Cloud OSS) решает все эти проблемы: **безграничная ёмкость, глобальная доступность, автоматическое резервное копирование, естественная поддержка CDN**. Оно уже стало фактическим стандартом хранения файлов для интернет-приложений.
:::

## 1. Сравнение типов хранилищ: блочное, файловое, объектное

В компьютерном мире есть три основных способа хранения, и они решают задачи разного уровня.

<FileStorageTypeDemo />

| Измерение | Блочное хранилище | Файловое хранилище | Объектное хранилище |
|------|--------|---------|---------|
| Единица данных | Блок фиксированного размера | Файл + каталог | Объект (Key-Value) |
| Протокол доступа | iSCSI/FC | NFS/SMB | HTTP REST API |
| Производительность | Наивысшая (миллисекунды) | Средняя | Ниже (но достаточная) |
| Масштабируемость | Ограниченная | Средняя | Практически безграничная |
| Стоимость | Наивысшая | Средняя | Наименьшая |
| Типичные сценарии | Базы данных | Общие файлы | Изображения/видео/резервные копии |

::: tip Простой способ запомнить
- **Блочное хранилище** как жёсткий диск — для баз данных
- **Файловое хранилище** как сетевая общая папка — для совместного использования конфигураций несколькими серверами
- **Объектное хранилище** как облачный диск — для загруженных пользователями изображений и видео
:::

## 2. Ключевые понятия объектного хранилища

Модель данных объектного хранилища очень проста: **Bucket (бакет)** — это контейнер, **Object (объект)** — это файл, и каждый объект идентифицируется уникальным **Key (ключом)**.

```
my-app-bucket/                    ← Bucket (бакет)
├── avatars/user-123.jpg          ← Object Key
├── avatars/user-456.png          ← Object Key
├── reports/2024/q1-report.pdf    ← Object Key («каталог» — это лишь префикс Key)
└── uploads/temp/file.zip         ← Object Key
```

| Понятие | Пояснение | Пример |
|------|------|------|
| Bucket | Контейнер хранения, глобально уникальное имя | `my-app-prod`, `company-assets` |
| Object | Сам хранимый файл + метаданные | Изображение, PDF |
| Key | Уникальный идентификатор объекта | `avatars/user-123.jpg` |
| Метаданные | Дополнительная информация об объекте | Content-Type, пользовательские теги |
| ACL | Список контроля доступа | public-read, private |
| Pre-signed URL | Ссылка временного авторизованного доступа | Ссылка для загрузки/скачивания со сроком действия 15 минут |

::: tip В объектном хранилище нет настоящих «каталогов»
`avatars/` в `avatars/user-123.jpg` — это не каталог, а лишь префикс Key. Объектное хранилище имеет плоскую структуру, все объекты находятся на одном уровне. «Папки», отображаемые в консоли, — это лишь визуальный эффект группировки по префиксу.
:::

## 3. Схемы загрузки файлов: кто передаёт файл?

Существует две основные схемы загрузки файлов: загрузка через сервер и прямая загрузка с клиента. Для большинства сценариев **прямая загрузка с клиента** является лучшим выбором.

<FileUploadFlowDemo />

::: tip Преимущества прямой загрузки с клиента
1. **Экономия пропускной способности сервера**: файл не проходит через ваш сервер, а попадает прямо в OSS
2. **Избежание тайм-аутов**: загрузка больших файлов не вызывает ограничения тайм-аута Nginx/шлюза
3. **Снижение нагрузки на сервер**: серверу нужно лишь выдать учётные данные, не обрабатывая поток файла
4. **Поддержка докачки**: OSS изначально поддерживает фрагментированную загрузку, фронтенд может реализовать докачку

Шаги реализации: фронтенд запрашивает у бэкенда Pre-signed URL → фронтенд по этой ссылке напрямую загружает в OSS → OSS через колбэк уведомляет бэкенд
:::

## 4. Ускорение CDN: чтобы было быстро для пользователей по всему миру

Когда ваши пользователи распределены по всему миру, скачивание файлов с единственного источника будет медленным. CDN (Content Delivery Network) благодаря развёртыванию граничных узлов по всему миру кеширует файлы на ближайших к пользователю узлах, значительно снижая задержку доступа.

<CDNAccelerationDemo />

| Понятие CDN | Пояснение |
|---------|------|
| Граничный узел | Кеширующие серверы, распределённые по всему миру |
| Обращение к источнику | Когда у граничного узла нет кеша, он запрашивает файл у источника |
| Коэффициент попадания в кеш | Доля запросов, на которые граничный узел отвечает напрямую; чем выше, тем лучше |
| TTL | Срок действия кеша, по истечении требуется повторное обращение к источнику |
| Сброс кеша | Активная очистка кеша граничных узлов для вступления в силу нового файла |

::: tip Лучшие практики CDN
- **Добавляйте hash в имя файла**: `logo.a3f2b1.png` вместо `logo.png`, тогда при обновлении файла не нужно сбрасывать кеш
- **Устанавливайте разумный TTL**: для статических ресурсов (JS/CSS/изображения) длинный TTL (1 год), для HTML короткий TTL (5 минут)
- **Включайте сжатие Gzip/Brotli**: текстовые ресурсы после сжатия уменьшаются в объёме на 60–80%
:::

## 5. Лучшие практики

| Практика | Пояснение | Пример |
|------|------|------|
| Правила именования Key | Организуйте файлы с помощью осмысленных префиксов | `{type}/{date}/{uuid}.{ext}` |
| Избегайте «горячих» Key | Не начинайте с возрастающих чисел | Используйте UUID или префикс-hash |
| Минимизация прав | Bucket по умолчанию private | Устанавливайте public-read только для файлов, требующих публичности |
| Правила жизненного цикла | Автоматическая очистка устаревших файлов | Временные файлы автоматически удаляются через 7 дней |
| Настройка CORS | Прямая загрузка с фронтенда требует настройки CORS | Разрешите PUT/POST для вашего домена |
| Шифрование на стороне сервера | Включайте SSE для конфиденциальных файлов | SSE-S3 или SSE-KMS |

## Заключение

Файловое хранилище — это базовая проблема, с которой сталкивается каждое веб-приложение. Объектное хранилище благодаря безграничной ёмкости, низкой стоимости и высокой доступности стало стандартным выбором для интернет-приложений.

Вспомним ключевые моменты этой главы:

1. **Три типа хранилищ**: блочное — для баз данных, файловое — для совместного использования, объектное — для пользовательских файлов
2. **Модель объектного хранилища**: Bucket + Key + Object, плоская структура, доступ по HTTP API
3. **Прямая загрузка с клиента**: схема Pre-signed URL, файл не проходит через сервер, эффективно и экономно
4. **Ускорение CDN**: кеширование на граничных узлах + hash в имени файла, чтобы было быстро для пользователей по всему миру
5. **Безопасность и управление**: минимизация прав, правила жизненного цикла, шифрование на стороне сервера
