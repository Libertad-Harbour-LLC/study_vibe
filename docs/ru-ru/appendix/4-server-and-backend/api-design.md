# Проектирование API: «протокол диалога» между фронтендом и бэкендом

::: tip 🎯 Ключевой вопрос
**Как фронтенду и бэкенду эффективно общаться?** Это как спросить: как составить меню в ресторане, чтобы гость сразу всё понял? Как официанту принять заказ, не допустив ошибки? Как организовать подачу блюд, чтобы гость остался доволен? Проектирование API решает именно проблему «правил диалога».
:::

---

## 0. Сначала вопрос: вы когда-нибудь сталкивались с этими кошмарами?

**Ситуация первая: имена эндпоинтов придумывают как попало**

```
GET /getUserData
GET /fetchUserInfo
GET /queryUserById
GET /users/query
```

Четыре эндпоинта, функциональность одинаковая, а стиль именования совершенно разный. Новичок в полном недоумении: какой из них использовать?

**Ситуация вторая: обработка ошибок самая разношёрстная**

```json
// Кто-то возвращает HTTP-статус-код
HTTP/1.1 404 Not Found

// Кто-то возвращает 200 + code
HTTP/1.1 200 OK
{ "code": 404, "message": "Пользователь не существует" }

// Кто-то просто выбрасывает исключение
HTTP/1.1 200 OK
{ "error": "Произошла ошибка" }
```

Фронтенд не знает, как определить, успешен ли запрос.

**Ситуация третья: структура ответа у каждого своя**

```json
// Эндпоинт A
{ "data": { ... } }

// Эндпоинт B
{ "result": { ... } }

// Эндпоинт C
{ "content": { ... } }
```

Каждый эндпоинт возвращает данные в своём формате, и фронтенду приходится обрабатывать каждый эндпоинт отдельно.

**Хорошее проектирование API похоже на систему заказа блюд в ресторане** — меню понятное, процесс отлажен, при ошибке есть подсказка.

## 1. Что такое API?

**API** (Application Programming Interface, программный интерфейс приложения) — это «договорённость о диалоге между программами».

### 1.1 Аналогия с рестораном

| Роль в ресторане | Соответствующее понятие | Пояснение |
| :--- | :--- | :--- |
| Меню | Документация API | Говорит, какие «блюда» можно заказать |
| Официант | Протокол HTTP | Стандартизированный «способ диалога» |
| Кухня | Сервер | Обрабатывает запрос по «заказу» |
| Подача блюд | Ответ | Возвращает результат «гостю» |

### 2.1 REST vs RESTful: в чём разница?

Многие путают эти два понятия:

| Понятие | Значение | Пояснение |
| :--- | :--- | :--- |
| **REST** | Архитектурный стиль | Концепция проектирования, предложенная Роем Филдингом, включающая набор ограничений |
| **RESTful** | Соответствующий стилю REST | Прилагательное, означающее, что проектирование API следует принципам REST |

**Аналогия**:
- REST — это как «минимализм», концепция проектирования
- RESTful API — это как «комната в стиле минимализм», конкретная реализация этой концепции

**Шесть ограничений REST**:

| Ограничение | Пояснение |
| :--- | :--- |
| **Разделение клиента и сервера** | Фронтенд и бэкенд разрабатываются независимо, интерфейсы развязаны |
| **Отсутствие состояния** | Каждый запрос содержит всю необходимую информацию, сервер не хранит состояние сессии |
| **Кэшируемость** | Ответ должен указывать, можно ли его кэшировать, для повышения производительности |
| **Единый интерфейс** | Использование стандартных HTTP-методов и статус-кодов |
| **Многоуровневая система** | Клиенту не нужно знать, к какому уровню сервера он подключён |
| **Код по требованию** (опционально) | Сервер может расширять функциональность клиента |

::: tip 💡 Почему REST используется чаще всего?
1. **Низкий порог входа**: сам протокол HTTP воплощает идеи REST
2. **Зрелая экосистема**: множество инструментов, фреймворков, документации
3. **Высокая универсальность**: вызывать можно из любого языка, на любой платформе
4. **Лёгкость кэширования**: GET-запросы естественно кэшируются, дружелюбны к CDN
:::

## 3. Проектирование RESTful: пусть URL говорит сам за себя

**REST** (Representational State Transfer) — это архитектурный стиль, ключевая идея которого:

- Абстрагировать сущности в сети как «ресурсы» (Resource)
- Идентифицировать ресурс с помощью URL
- Оперировать ресурсом с помощью HTTP-методов

### 3.1 Аналогия со складом

| Понятие склада | Соответствие в REST | Пример |
| :--- | :--- | :--- |
| Адрес стеллажа | URL | `/users`, `/orders` |
| Способ операции | HTTP-метод | GET (просмотр), POST (поступление на склад) |
| Товар | Ресурс | Данные пользователя, данные заказа |

**Ключевой принцип**: URL — это существительное, а не глагол.

### 3.2 Правила проектирования URL

| Правило | Неверный пример | Верный пример | Пояснение |
| :--- | :--- | :--- | :--- |
| Существительное, а не глагол | `/getUsers` | `/users` | URL обозначает ресурс, HTTP-метод обозначает операцию |
| Множественное число | `/user` | `/users` | Единообразный стиль множественного числа |
| Нижний регистр + дефис | `/UserProfiles` | `/user-profiles` | URL чувствителен к регистру |
| Избегать глубокой вложенности | `/a/b/c/d/e` | `/a/b/c` | Не более 3 уровней |
| Фильтрация через query-параметры | `/products/phone/5000` | `/products?cat=phone` | Условия фильтрации через параметры `?` |

::: tip 💡 URL чувствителен к регистру
Единообразное использование нижнего регистра + дефиса (-) — самый безопасный подход, он избегает путаницы с регистром и несогласованности стиля с подчёркиваниями.
:::

### 3.3 Выбор HTTP-метода

| Метод | Назначение | Идемпотентность | Безопасность | Типичный сценарий |
| :--- | :--- | :--- | :--- | :--- |
| **GET** | Получение ресурса | Да | Да | Запрос списка, просмотр деталей |
| **POST** | Создание ресурса | Нет | Нет | Добавление пользователя, отправка заказа |
| **PUT** | Полное обновление | Да | Нет | Замена всего профиля пользователя |
| **PATCH** | Частичное обновление | Нет | Нет | Изменение только никнейма |
| **DELETE** | Удаление ресурса | Да | Нет | Удаление пользователя, отмена заказа |

::: tip 💡 Что такое идемпотентность?
**Идемпотентность**: многократное выполнение даёт одинаковый результат.

- **Идемпотентные операции** (GET/PUT/DELETE): нажать 10 раз и нажать 1 раз — результат одинаков
- **Неидемпотентные операции** (POST): нажав 10 раз, можно создать 10 заказов

**Решение**: для POST-операций использовать проверку по уникальному ID, чтобы избежать повторной обработки.
:::

## 4. Статус-коды: пусть ошибка «говорит сама за себя»

HTTP-статус-код — это стандартный способ сервера сообщить клиенту, «что произошло».

### 4.1 Классификация статус-кодов

| Класс | Значение | Типичные статус-коды |
| :--- | :--- | :--- |
| **2xx** | Успех | 200 OK, 201 Created, 204 No Content |
| **3xx** | Перенаправление | 301 Перемещено навсегда, 304 Не изменено |
| **4xx** | Ошибка клиента | 400 Ошибка параметров, 401 Не аутентифицирован, 404 Не найдено |
| **5xx** | Ошибка сервера | 500 Внутренняя ошибка, 503 Сервис недоступен |

## 5. Обработка ошибок: как изящно «отказать»

Хорошая обработка ошибок позволяет клиенту «по статус-коду понять, в чём дело», а не гадать.

### 4.1 «Руководство по обходу ям» в обработке ошибок

**Яма 1: все ошибки возвращают 200**

```json
// ❌ Неверный подход
HTTP/1.1 200 OK
{ "error": "Произошла ошибка" }
```

Проблема: слой кэширования закэширует этот «успешный» ответ, а система мониторинга не обнаружит проблему.

**Яма 2: сообщение об ошибке слишком общее**

```json
// ❌ Неверный подход
HTTP/1.1 400 Bad Request
{ "message": "Ошибка параметров" }
```

Проблема: клиент не знает, какой параметр неверен и почему.

**Яма 3: раскрытие чувствительной информации**

```json
// ❌ Опасный подход
HTTP/1.1 500 Internal Server Error
{ "stack": "at UserService.login...", "sql": "SELECT * FROM..." }
```

Опасность: раскрыты структура кода и запросы к базе данных, злоумышленник может воспользоваться этой информацией.

## 6. Управление версиями: «обратная совместимость» API

### 6.1 Зачем нужно управление версиями?

Сценарий: у вашего приложения 1 миллион пользователей, и нужно изменить эндпоинт заказов.

**Если не управлять версиями**:
- Новое приложение вызывает новый эндпоинт → нормально
- Старое приложение вызывает новый эндпоинт → отсутствуют поля, падение!

**Правильный подход**:
- `/v1/orders` — старый эндпоинт, продолжает обслуживать старое приложение
- `/v2/orders` — новый эндпоинт, новый функционал здесь

### 6.2 Стратегии управления версиями

| Стратегия | Пример | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **Путь в URL** | `/v1/users` | Наглядно, легко кэшировать | URL удлиняется |
| **Заголовок запроса** | `Accept: vnd.api.v2+json` | URL чистый | Неудобно отлаживать |
| **Query-параметр** | `/users?version=2` | Просто | Недостаточно стандартно |

### 6.3 Пример эволюции версий

На примере пользовательского эндпоинта покажем эволюцию от v1 к v2:

| Эндпоинт | v1 (старая версия) | v2 (новая версия) | Описание изменений |
| :--- | :--- | :--- | :--- |
| **Получение пользователя** | `GET /v1/users`<br>возвращает: `name, email` | `GET /v2/users`<br>возвращает: `name, email, avatar, phone` | Добавлены поля аватара и телефона |
| **Создание заказа** | `POST /v1/orders`<br>принимает: `items[]` | `POST /v2/orders`<br>принимает: `items[], coupons[]` | Добавлена поддержка купонов |
| **Пакетные операции** | Нет | `POST /v2/orders/batch` | Добавлен эндпоинт пакетного создания |

::: tip 💡 Лучшие практики управления версиями
- **Сохраняйте обратную совместимость**: эндпоинт v1 поддерживается минимум 6-12 месяцев, чтобы дать клиентам время на обновление
- **Синхронное обновление документации**: у каждой версии своя отдельная документация API
- **Объявление об устаревании**: заранее уведомлять, когда v1 будет отключён, направляя на миграцию
- **Мониторинг использования**: подсчитывать количество вызовов v1, отключать сервис только после подтверждения, что это безопасно
:::

## 7. Проектирование структуры ответа

Структура ответа — это «контракт данных» между фронтендом и бэкендом, единый формат существенно снижает затраты на коммуникацию.

<ResponseStructureDemo />

### 7.1 Опыт крупных компаний

::: details Руководство по проектированию API от Google
Согласно [Google API Design Guide](https://cloud.google.com/apis/design/errors), Google требует, чтобы все ответы об ошибках API содержали структуру сообщения `google.rpc.Status`:

```json
{
  "error": {
    "code": 429,
    "message": "Недостаточно ресурсов, повторите попытку позже",
    "status": "RESOURCE_EXHAUSTED",
    "details": [
      {
        "@type": "type.googleapis.com/google.rpc.ErrorInfo",
        "reason": "RESOURCE_AVAILABILITY",
        "domain": "compute.googleapis.com",
        "metadata": {
          "zone": "us-east1-a",
          "service": "compute"
        }
      }
    ]
  }
}
```

**Ключевые требования**:
- Обязательно содержать `ErrorInfo` для машиночитаемого идентификатора ошибки
- `message` ориентирован на разработчика, описывает проблему и решение лаконичным языком
- Массив `details` может содержать `LocalizedMessage` (локализованное сообщение), `Help` (ссылка на справку) и т. д.
:::

::: details Руководство по REST API от Microsoft
Согласно [Microsoft REST API Guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md), Microsoft подчёркивает согласованность ответов:

**Классификация ошибок и сбоев**:
- **Ошибка (Error)**: вызвана передачей клиентом некорректных данных, возвращает 4xx, не влияет на доступность API
- **Сбой (Fault)**: сервер не может корректно ответить на валидный запрос, возвращает 5xx, влияет на доступность API

**Спецификация заголовков ответа**:
- `Date`: обязательно возвращать, в формате RFC 5322 (часовой пояс GMT)
- `Content-Type`: обязательно возвращать
- `ETag`: обязательно возвращать для ресурсов, поддерживающих оптимистичный контроль конкурентного доступа
:::

::: details Руководство по разработке на Java от Alibaba
Согласно [Руководству по разработке на Java от Alibaba](https://developer.aliyun.com/special/tech-java), у Alibaba следующие правила для ответов API:

**Единый объект ответа**:
```java
public class Result<T> {
    private Integer code;
    private String message;
    private T data;
    private String requestId;
}
```

**Сегментированное проектирование кодов ошибок**:
| Диапазон | Тип | Пример |
| :--- | :--- | :--- |
| 0 | Успех | 0 |
| 1xxxx | Ошибка параметров | 10001 Отсутствует обязательный параметр |
| 2xxxx | Бизнес-ошибка | 20001 Недостаточно средств |
| 3xxxx | Ошибка аутентификации | 30001 Не выполнен вход |
| 5xxxx | Системная ошибка | 50001 Ошибка базы данных |
:::

::: details Проектирование ответов API в Stripe
Согласно [Stripe API Documentation](https://docs.stripe.com/api/errors), проектирование ответов об ошибках у Stripe очень детальное:

```json
{
  "error": {
    "type": "card_error",
    "code": "card_declined",
    "message": "Your card was declined.",
    "param": "number",
    "decline_code": "insufficient_funds",
    "doc_url": "https://stripe.com/docs/error-codes/card-declined"
  }
}
```

**Особенности дизайна**:
- `type` различает типы ошибок: `api_error`, `card_error`, `invalid_request_error`
- `param` указывает, какой именно параметр ошибочен, фронтенд может сразу найти поле формы
- `doc_url` предоставляет ссылку на документацию, разработчик может изучить подробнее
- `decline_code` предоставляет более детальную причину ошибки
:::

::: details Спецификация JSON:API
Согласно [JSON:API Specification](https://jsonapi.org/format/) — это широко принятая в индустрии спецификация ответов JSON API:

```json
{
  "data": {
    "type": "articles",
    "id": "1",
    "attributes": {
      "title": "Подробный разбор спецификации JSON:API"
    },
    "relationships": {
      "author": {
        "data": { "type": "users", "id": "9" }
      }
    }
  },
  "included": [
    {
      "type": "users",
      "id": "9",
      "attributes": {
        "name": "Иван Иванов"
      }
    }
  ]
}
```

**Ключевые элементы дизайна**:
- `data` содержит основной ресурс, обязательно имеет `type` и `id`
- `attributes` хранит атрибуты ресурса
- `relationships` описывает связи ресурса
- `included` избегает повторных запросов, возвращая связанные данные за один раз
:::

**Особенности дизайна**:
- Ответ содержит несколько форматов URL (`html_url`, `url`) для разных сценариев
- Ответ об ошибке содержит `documentation_url`, указывающий на документацию
- Используется заголовок ответа `Link` для навигации по страницам

::: details Проектирование ответов Twitter/X API v2
Согласно [Twitter API v2 Documentation](https://developer.twitter.com/en/docs/twitter-api), Twitter API v2 использует лаконичный формат ответа:

```json
{
  "data": {
    "id": "1460323737035677698",
    "text": "Hello, Twitter!"
  },
  "includes": {
    "users": [
      {
        "id": "2244994945",
        "name": "Twitter Dev",
        "username": "TwitterDev"
      }
    ]
  }
}
```

**Особенности дизайна**:
- `data` содержит основные данные, `includes` содержит связанные данные (аналогично JSON:API)
- Поддерживается выбор полей: `?tweet.fields=created_at,public_metrics`
- Постраничная навигация использует `next_token` и `previous_token`
:::

### 7.2 Сводка лучших практик

Обобщая приведённые выше спецификации, проектирование структуры ответа должно следовать таким принципам:

1. **Приоритет согласованности**: все эндпоинты используют одинаковую структуру ответа, фронтенд может единообразно инкапсулировать слой запросов
2. **Машиночитаемость**: код ошибки + причина ошибки (reason) позволяют программе обрабатывать автоматически
3. **Дружелюбие к человеку**: message описывает чётко, содержит рекомендации по решению
4. **Трассируемость**: request_id проходит через всю цепочку запроса, облегчая локализацию проблем
5. **Поддержка интернационализации**: расширение локализованных сообщений через details

## Шпаргалка по терминам

| Термин | Английский | Объяснение |
| :--- | :--- | :--- |
| **API** | Application Programming Interface | Договорённость о диалоге между программами |
| **REST** | Representational State Transfer | Архитектурный стиль, идентифицирующий ресурс по URL |
| **Ресурс** | Resource | Ключевое понятие архитектуры REST, имеет уникальный идентификатор (URL) |
| **Идемпотентность** | Idempotency | Многократное выполнение даёт одинаковый результат |
| **Статус-код** | Status Code | Статус ответа, определённый протоколом HTTP |
| **Управление версиями** | Versioning | Позволяет сосуществовать старым и новым API, обеспечивает плавное обновление |
| **Тело запроса** | Request Body | Данные, передаваемые запросами POST/PUT/PATCH |
| **Тело ответа** | Response Body | Данные, возвращаемые сервером |
| **Header** | Header | Метаданные запроса/ответа (например, Content-Type) |
| **Аутентификация** | Authentication | Проверка, «кто ты» (вход, Token) |
| **Авторизация** | Authorization | Проверка, «что ты можешь делать» (права доступа) |
