# 1. От диалога к агенту

На предыдущем этапе мы научились использовать промпты, чтобы заставлять модели играть роли, генерировать текст или писать простой код. Но если задуматься, есть ключевая проблема: чат-бот сам по себе на самом деле не может выполнять работу.

Он может ответить на вопрос «как проверить заказ», но не может действительно запросить в вашей базе данных номер заказа. Он может описать, что должен включать еженедельный отчёт, но не может автоматически собрать данные проекта и отправить письмо. Это ограничение «может сказать, но не может сделать» затрудняет реальное встраивание чисто разговорного AI в бизнес-процессы.

Чтобы поднять AI с уровня собеседника до цифрового сотрудника, нам нужно дать ему три ключевые способности:

1. Собственные знания: позволить ему читать и понимать документацию по вашим продуктам, клиентские материалы и внутренние регламенты.
2. Вызов инструментов (или плагинов): позволить ему работать с базами данных и вызывать API.
3. Структурированное выполнение: позволить ему выполнять задачи шаг за шагом по заранее заданной логике, а не свободно импровизировать.

Это и есть прототип AI-агента: единицы автоматизации с целями, знаниями, инструментами и путём выполнения.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image1.png)

> Примечание: в текущем отраслевом употреблении «простые агенты» обычно означают расширенные приложения, построенные из LLM + инструменты + база знаний, а не полностью автономные планирующие агенты. Хотя у этих простых агентов нет настоящего долгосрочного рассуждения и планирования, их уже достаточно для многих сценариев автоматизации на предприятии. Действительно автономных агентов мы представим в последующих главах.

## 1.1 Простейший агент: чат-бот для вопросов и ответов на базе знаний

После прояснения ключевых способностей агента возникает естественный вопрос: можем ли мы построить практичного базового агента, реализовав только одну из этих способностей? Ответ — да.

Во многих реальных бизнес-сценариях пользователям не нужно, чтобы AI выполнял сложные операции (такие как оркестрация API между несколькими системами). Их основная потребность — точные, надёжные вопросы и ответы, основанные на специфических для компании материалах. Это точно соответствует первой ключевой способности: сервису собственных знаний.

Это приводит к простейшей и наиболее широко используемой форме агента: чат-боту для вопросов и ответов на базе знаний.

Хотя он пока не включает вызов инструментов или автономное планирование, ключевой прорыв в следующем: ответы модели больше не генерируются «из воздуха». Они становятся обоснованными фактами. Как это достигается? Нам нужно решить одну ключевую задачу: когда есть тысячи страниц внутренней документации, как модель может быстро найти наиболее релевантные части для каждого вопроса пользователя?

Одним из решений является генерация с дополнением через поиск (Retrieval-Augmented Generation, RAG).

Основная идея RAG такова: когда пользователь задаёт вопрос, система сначала извлекает из корпоративных знаний наиболее семантически релевантные фрагменты текста (например, один абзац из руководства по продукту, один пункт регламента из HR-документов), затем внедряет эти фрагменты в контекст модели, чтобы ответ генерировался на основе реального исходного материала.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image2.png)

Источник изображения: [https://www.datacamp.com/blog/what-is-retrieval-augmented-generation-rag](https://www.datacamp.com/blog/what-is-retrieval-augmented-generation-rag)

Это означает, что ответы больше не опираются только на обобщённые знания, полученные при обучении. Они привязаны к авторитетной для предприятия информации. Цель RAG — именно это динамическое внедрение внешних знаний, которое значительно повышает достоверность, точность и согласованность ответов. Оно даже может задавать персону/стиль ответа, например тон службы поддержки или стиль технической документации.

В реальном бизнесе это особенно важно, потому что модели могут галлюцинировать. Например, если вы попросите конкретные метрики как CFO или консультант, модель может выдумать даты и события. С RAG управляемость и надёжность значительно улучшаются.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image3.png)

Источник изображения: [https://www.databricks.com/glossary/retrieval-augmented-generation-rag](https://www.databricks.com/glossary/retrieval-augmented-generation-rag)

В практической части этого урока мы используем Dify, популярную платформу AI-рабочих процессов, чтобы построить чат-бот для вопросов и ответов на базе знаний. Вы можете легко превратить многие виды собственных материалов в базу знаний, например руководства по продуктам, документы с регламентами компании, проектную документацию, научные статьи, статьи базы знаний и даже личные заметки.

После настройки вы можете протестировать его вопросами, такими как:

- «Какие крупные обновления в последней версии Продукта A?»
- «Согласно справочнику сотрудника, как в этом году определяется политика ежегодного отпуска?»
- «В проекте XX как мы решили техническую задачу „XXX“?»
- «Каков основной метод исследования, описанный в этой статье?»

Вы напрямую почувствуете, как RAG превращает статичные, разрозненные документы в точную интеллектуальную базу знаний, которая поддерживает вопросы и ответы высокой точности в разных сценариях.

## 1.2 От разговорного агента к рабочему процессу

Однако даже «расширенных агентов» с базой знаний и вызовом инструментов всё ещё недостаточно для более сложных бизнес-процессов.

Представьте такой запрос:
«Какие новые функции были недавно выпущены в нашем только что запущенном SaaS-продукте? Можешь оформить их в краткую справку для клиентов?»

Это выглядит просто, но за кулисами требует согласованных шагов: сначала извлечь заметки о выпусках за последний месяц из внутренней документации или базы знаний Notion; затем отфильтровать ключевые функции, обращённые к клиентам; затем вызвать LLM, чтобы переписать технические описания в понятный клиентам язык; и наконец отправить сгенерированный контент на email команды маркетинга или сохранить его в шаблон Google Docs.

Если мы полагаемся только на одну LLM, свободно рассуждающую, трудно выполнить весь процесс в одном диалоге. Даже если это получится, она может упустить ключевые детали, перепутать внутренние термины с клиентским языком или не выдать результат в структурированной форме. Что ещё важнее, предприятиям нужен поддающийся аудиту, переиспользуемый, контролируемый стандартизированный путь выполнения, а не одноразовая импровизация при каждом запуске. Мониторинг и воспроизводимость критически важны для управления рисками на предприятии.

Это приводит к паттерну AI-приложений более высокого уровня: AI-рабочему процессу (AI Workflow).

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image4.png)

Рабочий процесс означает разложение сложной задачи на упорядоченные, конфигурируемые, автоматически выполняемые подшаги, а затем оркестрацию логики между шагами (условия, циклы, параллелизм) визуально или через код. Превращение возможностей AI в SOP означает закрепление того, «как AI выполняет эту задачу», в переиспользуемые шаблоны.

Это приносит множество преимуществ: нетехнические роли (такие как продакт-менеджеры или операторы) могут быстро строить AI-приложения через перетаскивание; разработчики могут инкапсулировать RAG-поиск, вызовы LLM, API-инструменты как стандартные узлы для переиспользования в разных бизнес-сценариях; а весь процесс можно отслеживать, отлаживать и непрерывно оптимизировать для удовлетворения требований предприятия к стабильности и соответствию нормам.

Круг пользователей AI-рабочих процессов широк. Продакт-менеджеры могут проектировать полные потоки взаимодействия, не написав ни строки кода; операционные команды могут быстро строить ботов поддержки, генераторы контента или системы уведомлений; разработчики и ML-инженеры могут модуляризировать возможности для интеграции с фронтендом; основатели и независимые разработчики могут с низкими затратами проверять AI-MVP и запускать прототипы с запросом + генерацией + действиями за считанные дни.

Также обратите внимание, что AI-рабочие процессы обычно описываются промежуточным представлением. Специфика платформ различается, но большинство используют структурированные файлы (JSON, YAML и т. п.) для определения типов узлов, входов/выходов и логики выполнения, как показано ниже:

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image5.png)

Короче говоря, если агенты позволяют AI перейти от «может беседовать» к «может делать», то рабочие процессы позволяют AI перейти от «изредка выполняет одну задачу» к «стабильно, надёжно и в масштабе выполняет класс задач». В дальнейшей практике мы построим полный AI-рабочий процесс на Dify и пройдём весь путь от идеи до работающего приложения.

## 1.3 Распространённые платформы агентов / рабочих процессов

По мере быстрого развития генеративного AI появилось множество low-code и no-code платформ для агентов/рабочих процессов, помогающих разработчикам и бизнес-пользователям быстро строить интеллектуальные процессы, не погружаясь в сложность низкоуровневого кодирования.

Сначала проясним, что означает low-code: инструменты разработки, которые значительно сокращают ручное кодирование за счёт визуальных компонентов «перетащи и оставь», готовых шаблонов логики и графической настройки правил. Основная идея: заменить прямое кодирование визуальной оркестрацией узлов. Это освобождает технических пользователей от повторяющейся работы и позволяет нетехническим пользователям, знакомым с бизнес-логикой, участвовать в построении приложений. По сути это мост между эффективностью и гибкостью.

Ключевая ценность low-code/no-code AI-платформ — снижение порога разработки. Работа, которая раньше занимала недели межфункционального сотрудничества (требования, кодирование, тестирование, развёртывание), теперь может проходить путь от идеи до запуска за часы для распространённых сценариев агентов, таких как боты для ответов клиентам и помощники по обработке данных.

К основным low-code платформам AI-рабочих процессов относятся:

| Платформа | Особенности | Типичные сценарии |
| --------------------------------------------- | -------------------------------------------------- | -------------------------------------- |
| Dify | Открытый исходный код; поддержка RAG на базе знаний, оркестрации LLM, вывода через API; дружественность к китайскому языку | Корпоративные вопросы и ответы на базе знаний, кастомные агенты, API-сервисы |
| Coze (ByteDance) | Доступна в Китае, интегрирована с экосистемой Doubao/Feishu, богатый набор плагинов | Социальные боты, интеграция с отечественными мини-программами |
| n8n | Универсальная платформа автоматизации с AI-узлами, сильна в оркестрации API | Синхронизация между системами, автоматизация AI + традиционного SaaS |
| Baidu Qianfan AppBuilder / Alibaba Bailian / Tencent HunYuan | Облачные стеки вендоров с собственными моделями | Корпоративное развёртывание, сценарии со строгими требованиями к соответствию нормам |

На рынке много вариантов. Хотя AWS, Azure, Alibaba Cloud и другие также предоставляют решения для рабочих процессов, Dify, Coze и n8n в настоящее время относятся к наиболее широко используемым благодаря трём главным преимуществам:

1. Предельная удобность: визуальные интерфейсы «перетащи и оставь» упрощают начало работы без глубокого понимания низкого уровня.
2. Высокая гибкость: кастомные компоненты и расширяемые API поддерживают как лёгкие демо/MVP, так и гибкую итерацию для команд малого и среднего бизнеса.
3. Зрелая экосистема: подробная документация, отзывчивая поддержка и активные сообщества с переиспользуемыми шаблонами.

Все три поддерживают публикацию построенных агентов в виде стандартизированных API, обеспечивая бесшовную интеграцию с фронтенд-веб-приложениями, корпоративными ERP-системами и мобильными приложениями, что дополнительно снижает порог развёртывания.

### 1.3.1 Dify: платформа корпоративного LLMOps и жизненного цикла приложений

Dify позиционируется как платформа разработки и эксплуатации LLM-приложений, сфокусированная на управлении полным жизненным циклом от идеи до развёртывания и оптимизации. Её основу составляет low-code платформа, помогающая разработчикам и нетехническим новаторам быстро строить production-grade AI-приложения.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image6.png)

С точки зрения функций Dify включает визуальную оркестрацию рабочих процессов, построение агентов, управление базой знаний и поддержку множества моделей. Вы можете проектировать сложные процессы, перетаскивая узлы, и создавать агентов на основе намерений. Её возможности базы знаний позволяют обрабатывать многие форматы документов и поддерживают эффективный векторный поиск. Dify поддерживает GPT, Claude и многие открытые модели и может публиковать приложения как стандартные API в один клик.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image7.png)

С архитектурной точки зрения Dify делает упор на открытый исходный код и частное развёртывание, на гибкость, расширяемость и корпоративное соответствие нормам. Типичные пользователи включают команды разработчиков и бизнес-новаторов. Типичные сценарии использования включают корпоративные вопросы и ответы на базе знаний/поддержку клиентов, автоматизацию контента, вертикальные AI-ассистенты и корпоративные AI-платформы среднего слоя.

### 1.3.2 Coze (ByteDance): популяризация zero-code построения AI-агентов

Coze — это платформа AI-агентов от ByteDance. Её основная ценность — предельная удобность, позволяющая пользователям без программистского бэкграунда создавать, отлаживать и публиковать богатые AI-чат-боты.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image8.png)

Её основное взаимодействие — «строительные блоки». Пользователи могут настраивать роли ботов и базы знаний через интерфейс и использовать богатые встроенные библиотеки плагинов для внешних возможностей, таких как новости, путешествия и генерация изображений. ![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image9.png)

Её архитектура спроектирована вокруг использования с низким порогом, интегрируя модели ByteDance за облачными сервисами и абстрагируя сложные детали потоков, с упором на мультимодальное понимание и ответы в реальном времени. Возможности частного развёртывания относительно ограничены. Типичные сценарии включают личных ассистентов и развлекательных ботов, системы вопросов и ответов для клиентов, помощников по онлайн-обучению и быстрое прототипирование.

### 1.3.2 n8n: программируемый бэкенд-движок автоматизации рабочих процессов

n8n — это универсальная программируемая платформа автоматизации рабочих процессов. Её основное позиционирование — соединение приложений, баз данных и API для автоматизации перемещения данных и выполнения задач.

Она поддерживает сотни SaaS-сервисов, баз данных и протоколов через большую экосистему узлов-интеграций и сочетает визуальное проектирование с кодом: вы можете перетаскивать узлы на холсте, внедряя при этом JavaScript/Python для кастомной логики. n8n сильна в бэкенд-рабочих процессах с интенсивной обработкой данных, таких как синхронизация, ETL и оркестрация API.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image10.png)

Её ключевая техническая характеристика — видимый исходный код и self-hosting, что позволяет полностью контролировать данные и окружение. Это особенно привлекательно для отраслей со строгими требованиями к безопасности данных. Основные пользователи — разработчики, технические операторы и аналитики данных. Самая большая сила n8n — мощная экосистема сообщества: богатые онлайн-руководства и общие шаблоны снижают стоимость обучения. Она также подключается к глобальным экосистемам, таким как YouTube и Instagram, помогая пользователям преодолевать кросс-платформенные барьеры данных/сервисов.

Помимо этих известных платформ, крупные китайские технологические вендоры также запустили интегрированные AI-платформы. Хотя позиционирование платформ и экосистемы различаются, основная логика схожа: визуально оркестрировать и соединять модули возможностей. Освоив проектирование и работу одной платформы, вы сможете быстро перейти к другим. В дальнейшей практике мы используем Dify в качестве примера.

# 2. Понимание Dify шаг за шагом

## 2.1 Что такое Dify

Базовое введение в Dify мы уже рассмотрели ранее. Для дополнительных деталей посетите [https://cloud.dify.ai/apps](https://cloud.dify.ai/apps), а для официальной информации — https://dify.ai.

Dify — это открытая платформа для разработки LLM-приложений. Она предоставляет интуитивный интерфейс, который сочетает рабочие процессы агентов, RAG-конвейеры, возможности инструментов, управление моделями и наблюдаемость, помогая вам быстро перейти от прототипа к продакшену.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image11.png)

В Dify вы можете комбинировать большие модели и множество инструментов, чтобы построить «рабочий процесс». Рабочий процесс — это цепочка бизнес-логики, которая автоматизирует операции, которые иначе вы бы делали вручную шаг за шагом, такие как поиск данных, вызовы LLM, веб-поиск, фильтрация результатов и форматирование. Без рабочих процессов вы многократно копируете/вставляете похожие промпты, что неэффективно, чревато ошибками и трудно переиспользуется в реальном бизнесе.

Построение рабочих процессов похоже на сборку блоков/частей пазла. Вы соединяете узлы LLM (понимание/генерация), узлы инструментов (конкретные действия, такие как запрос к БД, отправка email, перевод текста) и узлы данных (чтение/хранение информации). Затем они автоматически взаимодействуют по вашей заранее заданной логике без ручного повторения. Можно также думать об этом как о «low-code программировании»: посредством перетаскивания и настройки входов/выходов вы можете реализовать довольно сложную бизнес-логику.

Например, если вы держите магазин на Amazon или Douyin и хотите систему AI-поддержки клиентов, вы можете спроектировать рабочий процесс так:

1. Узел триггера (`START`): получает запрос пользователя, например «Какой гарантийный срок у этого товара?»
2. Узел классификатора вопросов (`QUESTION CLASSIFIER`): использует LLM (например GPT), чтобы классифицировать запрос как послепродажный (гарантия), руководство по использованию или другой тип.
3. Узел поиска по знаниям (`KNOWLEDGE RETRIEVAL`): автоматически запрашивает соответствующую базу знаний на основе классификации. Если запрос связан с гарантией, извлекает точное SOP-содержимое о гарантии.
4. Узел LLM: отправляет запрос пользователя + извлечённый контекст модели и генерирует понятный пользователю ответ.
5. Узел условия: проверяет, содержит ли ответ чёткие термины гарантийного срока (например «1 год» или «3 года»). Если да, продолжает; если нет, возвращает «пожалуйста, укажите модель товара».
6. Узел вывода (`ANSWER`): возвращает финальный ответ и автоматически записывает эту консультацию в таблицу.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image12.png)

В этом процессе вы не просматриваете документацию вручную, не подстраиваете выводы многократно и не записываете данные отдельно. Рабочий процесс связывает всё это автоматически. Он также гибок: если позже вы добавите новое правило, например «когда пользователь спрашивает о покрытии гарантии, запрашивать другую базу знаний», просто добавьте один узел условия вместо перестройки системы.

Это относительно простой пример рабочего процесса. Полное освоение всех возможностей может всё ещё казаться трудным на этом этапе. Поэтому на этом уроке мы начинаем с более базового агента на базе знаний и постепенно перейдём к продвинутым техникам рабочих процессов позже.

## 2.4 Создайте свою первую базу знаний в Dify

На данном этапе мы создали базового агента, но у него всё ещё нет базы знаний. Нажмите `Knowledge` в верхнем меню, чтобы перейти к созданию базы знаний.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image30.png)

Затем нажмите `Create Knowledge` слева, чтобы создать вашу первую базу знаний.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image31.png)

На этой странице вы можете загрузить множество типов файлов (PDF, TXT и т. д.), чтобы построить знания. Вы можете загрузить длинный текст или скопировать содержимое из Википедии в TXT и загрузить его. В этом примере мы загружаем TXT-файл из Википедии про Илона Маска.

После нажатия Next вы переходите к настройкам базы знаний (Knowledge Base Settings). Опций много, поэтому давайте разберём их шаг за шагом.

Сначала в настройках **General** — это область «правил чанкинга текста». Поскольку длинный текст должен быть разбит на меньшие фрагменты, мы сначала определяем стратегию чанкинга. Для начального уровня сосредоточьтесь только на **максимальной длине чанка**. Попробуйте 512, 2048 или 4096 и нажмите **Preview Chunk**, чтобы сравнить эффекты.

Вы также можете настроить **Chunk overlap**. Это управляет тем, сохраняют ли соседние чанки перекрывающееся содержимое. Правильное перекрытие помогает избежать разбиения критической информации между чанками таким образом, который вредит пониманию.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image32.png)

Есть также **Chunk using Q&A format in English**. Когда эта опция включена, система использует LLM для преобразования части знаний в формат «вопрос-ответ» перед сохранением, что в некоторых сценариях может значительно улучшить поиск.

В реальном бизнесе выбор стратегии чанкинга в зависимости от сценария сильно влияет на качество поиска и на то, соответствует ли возвращаемое содержимое ожиданиям.

Прокрутите вниз к настройкам модели Embedding.

Простое объяснение: модели Embedding преобразуют неструктурированные данные (текст, изображения и т. д.) в понятные машине числовые векторы. Это позволяет быстро вычислять схожесть и выполнять семантическое сопоставление, например извлекать документы/изображения/товары, наиболее близкие по смыслу к вводу пользователя.

Выбор Embedding существенно влияет на качество поиска (точность, задержка и т. д.). Здесь мы рекомендуем начать с Qwen 0.6B Embedding. Вы можете переключиться на 4B или 8B и сравнить влияние масштаба параметров.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image33.png)

Вы также увидите **Rerank model**, по умолчанию **Jina-rerank-m0**. (Если вы вне кампусного окружения, вы можете увидеть ошибки об отсутствии модели Rerank. В этом случае сначала настройте модель rerank в настройках провайдера моделей.)

Назначение Rerank — точная сортировка второго этапа над первоначальными кандидатами, перемещающая результаты, наиболее соответствующие намерению пользователя, на верхние позиции, улучшая релевантность и UX.

Простая интуиция: rerank решает проблему «недостаточно точного поиска первого этапа». Поисковые системы могут извлечь 1000 потенциальных страниц по простым правилам, затем выполнить rerank топ-10 для первой страницы. Рекомендательные системы работают аналогично: из 500 возможных элементов rerank продвигает наиболее вероятные конверсии.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image34.png)

После завершения настроек нажмите **Save & Process**, чтобы начать векторизацию. На этом этапе модели Embedding преобразуют разбитый на чанки текст в векторы.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image35.png)

После завершения обработки нажмите **Go to document**, чтобы изучить обработанное/сохранённое содержимое базы знаний.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image36.png)

Нажмите непосредственно на имя базы знаний, чтобы просмотреть детали каждого чанка.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image37.png)

## 2.6 Создайте своё первое приложение-рабочий процесс в Dify

После начала с агентов в стиле чат-ботов мы теперь строим более сложные бизнес-рабочие процессы. Рабочий процесс — это основной метод Dify для визуализации сложной бизнес-логики. Вы можете напрямую наблюдать поток данных между узлами, где размещена логика решений, где установлены точки вмешательства человека и как производятся финальные бизнес-результаты.

Вы можете создать с нуля или из шаблонов. Здесь мы демонстрируем создание с нуля:

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image49.png)

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image50.png)

Здесь вы увидите Chatflow и Workflow. Как выбрать? Решайте на основе того, является ли вашей основной потребностью непрерывный диалог или выполнение конвейера задач.

Chatflow спроектирован для диалога. Он имитирует разговорную сущность с памятью и непрерывностью контекста, идеально подходит для многоходовых взаимодействий и сессий с состоянием. Для поддержки клиентов он может связно обрабатывать уточняющие вопросы. Потоковый вывод также ощущается более естественным. Если вам нужен агент, который «беседует», выбирайте Chatflow.

Workflow фокусируется на автоматизированном выполнении процесса. Он действует как заранее заданный конвейер для одноразовых входов, многошаговой обработки и детерминированных выводов. Например, ежедневная генерация отчётов, пакетная обработка файлов или цепочки вызовов API. Эти задачи обычно запускаются событиями и не являются разговорными в реальном времени. Если ваша потребность — «автоматизация», выбирайте Workflow.

Чтобы избежать несоответствия архитектуры, оцените с помощью четырёх вопросов:

1. Требует ли процесс повторного ввода/корректировки от пользователя?
2. Нужно ли представлять вывод пошагово/потоково?
3. Сильно ли логика зависит от истории предыдущих взаимодействий?
4. Запускается ли задача событием и в основном одноразовая по входу/выходу?

Если первые три — «да», Chatflow идеален (поддержка клиентов, обучение, творческое сотрудничество). Если доминирует четвёртый, Workflow подходит лучше (очистка данных, генерация отчётов, пакетная обработка).

Здесь мы выбираем Chatflow для демонстрации и входим в рабочее пространство:

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image51.png)

Быстрый обзор интерфейса: центральный холст — это место, где вы визуально строите логику приложения. Базовый рабочий процесс обычно начинается с `START` (ввод), передаёт данные через связи в `LLM` и выводит через `ANSWER`. Каждый узел — это функциональный модуль; связи определяют порядок выполнения.

Вокруг холста расположены элементы управления. Верхняя область включает глобальные действия, такие как `Preview` (тест) и `Publish` (публикация). В углах холста расположены масштабирование/отмена и другие элементы управления видом.

Левая панель содержит области управления приложением. `Orchestrate` предназначена для проектирования потока. После построения используйте `API Access` для учётных данных интеграции. `Logs & Annotations` записывает трассировки выполнения для отладки. `Monitoring` обеспечивает видимость статуса выполнения/производительности.

Вы можете ввести простые инструкции-промпты в SYSTEM узла LLM в Chatflow, запустить Preview и убедиться, что поведение меняется как ожидалось.

### 2.6.1 Распространённые типы узлов

Dify предоставляет множество типов узлов. Сначала разберитесь в роли каждого узла. Для практического использования тестируйте напрямую, учитесь на шаблонах или спрашивайте модель со скриншотами о параметрах и использовании. Хорошая тактика для новичков: заменять узлы в существующих шаблонах и выводить лучшие практики из известных рабочих паттернов.

Щёлкните правой кнопкой по холсту и выберите `Add Node` или изучите все доступные узлы из боковой панели:

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image52.png)

Вы также можете открыть панель выбора инструментов, чтобы просмотреть категории вызываемых инструментов:

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image53.png)

Ниже краткое введение в распространённые узлы/инструменты. Вам не нужно осваивать всё сразу. Держите базовую ментальную карту и учитесь постепенно на практике.

1. Узлы LLM и рассуждений

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image54.png)

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image55.png)

Эти узлы — основные компоненты обработки:

- Узел LLM: основная вычислительная единица, которая вызывает LLM. Ключевой фокус — инженерия промптов и настройка параметров для отображения бизнес-задач в исполняемые инструкции для модели.
- Узел Knowledge Retrieval: извлекает релевантную информацию из настроенных баз знаний или внешних авторитетных источников для поддержки LLM и снижения риска галлюцинаций.
- Узел Answer: единица вывода, форматирующая обработанное содержимое в финальный готовый к бизнесу результат (шаблон ответа, спецификация форматирования и т. д.).
- Узел Agent: продвинутая единица принятия решений. Помимо вызова модели, он может выполнять многошаговое планирование и динамический выбор инструментов, подходит для сложных цепочек задач.
- Узел Question Classifier: классифицирует ввод пользователя по намерению/теме и направляет на подходящие нисходящие пути (разные промпты/цепочки инструментов для каждой категории).

2. Узлы логики и управления потоком

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image56.png)

Эти узлы определяют путь/правила выполнения:

- Узел условия (`IF/ELSE`): ветвление на основе булевых значений. Ключ — строгое проектирование условий, всесторонне покрывающее бизнес-кейсы.
- Узел итерации: пакетно-параллельная обработка без состояния, лучше всего когда подзадачи не имеют взаимозависимостей (пакетный перевод, параллельная проверка, генерация нескольких отчётов). Он принимает входной массив, нарезает элементы, запускает одну и ту же цепочку параллельно. Используйте `{{item}}` для текущего элемента и `{{index}}` для индекса. Выводы агрегируются обратно в массив. Настройте параллелизм для баланса скорости/нагрузки; настройте обработку повторов/сбоев для надёжности.
- Узел цикла: рекурсивный итератор с состоянием, лучше всего когда каждый раунд зависит от предыдущего вывода (циклы настройки параметров, итеративная полировка контента, цепочки зависимых вычислений). Суть — управление переменной состояния: инициализируйте перед циклом, обновляйте каждый раунд и определяйте строгие условия остановки (максимум раундов, порог качества, внешний сигнал остановки), а также таймаут и путь исключений, чтобы избежать бесконечных циклов.

3. Узлы операций с данными и интеграции

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image57.png)

- Узел Code: выполняет кастомную логику для преобразования данных, сложных вычислений и т. д. Фокус на корректности синтаксиса и совместимости среды выполнения.
- Узел Template: заполняет динамические данные в шаблоны (кастомный текст/каркас отчёта). Фокус на синтаксисе шаблонов и сопоставлении переменных.
- Узел Variable Aggregator: собирает выводы из нескольких узлов в единый набор данных. Фокус на области видимости и правилах слияния.
- Узел Doc Extractor: извлекает текст/таблицы из PDF/Word и преобразует в структурированные обрабатываемые данные.
- Узел Variable Assigner: определяет/инициализирует/обновляет переменные рабочего процесса для передачи данных.
- Узел Parameter Extractor: извлекает структурированные параметры из ввода пользователя/API (regex/JSON path и т. д.).
- Узел HTTP Request: отправляет внешние API-запросы (GET/POST и т. д.) для интеграции систем.
- Узел List Operator: фильтрует/сортирует/разбивает данные списка для соответствия нисходящей структуре.

### 2.6.3 Постройте простой рабочий процесс классификации намерений

Теперь, когда мы понимаем основы рабочих процессов/инструментов Dify, нам нужна практика. Без практики детали никогда не становятся привычными. Нам нужен реалистичный бизнес-сценарий.

Например, в реальных сценариях чата по заказу еды ввод пользователя никогда не является чистыми параметрами. Одни пользователи делают заказы, другие жалуются, третьи просто болтают, четвёртые уходят от темы. Если все эти вводы отправляются в один общий путь LLM, появляются две распространённые проблемы:

1. Нестабильный стиль ответа
   На одну и ту же жалобу в одном запуске может прийти извинение, а в другом — оправдание. На один и тот же заказ в одном запуске может последовать запрос недостающей информации, а в другом — придуманные детали заказа.
2. Неконтролируемая бизнес-логика
   Вы хотите, чтобы «жалобы начинались с извинения», но модель может не всегда этому следовать. Вы хотите, чтобы «запросы не по теме перенаправлялись», но модель может продолжить беседу вне домена.

Более инженерный подход — стандартизированная декомпозиция конвейера:
сначала классификация намерений (определить, что хочет пользователь), затем маршрутизация на основе намерений (разные промпты/роли для каждого сценария), затем единое упаковывание вывода из разветвлённых ветвей (для интеграции с фронтендом/системами).

Цель: обработать несколько типов диалога в сценарии общепита. Пройдите один раз, чтобы освоиться.

Сначала определим намерения:

- **buy_food**: пользователь демонстрирует явное намерение покупки/заказа.
  - Пример: «Дайте мне одну жареную курицу и одну колу.»
- **complain**: пользователь выражает недовольство/гнев/жалобу.
  - Пример: «Почему так медленно? Я жду уже час.»
- **chitchat**: пользователь просит открытые рекомендации без явной команды заказа.
  - Пример: «Что мне сегодня поесть? Есть рекомендации?»
- **other**: не относится к сценарию заказа еды.
  - Пример: «Помоги мне написать смешной пост в соцсети.»

Для этих четырёх намерений заранее определим четыре коммуникативные персоны через четыре выделенных узла LLM:

- **LLM_BuyFood**: профессиональный и эффективный. Подтверждает детали заказа и проактивно дополняет недостающую информацию.
- **LLM_Complain**: эмпатичный и спокойный. Сначала успокаивает пользователя и предоставляет чёткие шаги решения.
- **LLM_Chitchat**: расслабленный и дружелюбный. Даёт персонализированные рекомендации и подводит к потенциальной конверсии.
- **LLM_Other**: вежливый и понимающий границы. Перенаправляет беседы не по теме обратно к основному бизнесу.

#### Проектирование оркестрации рабочего процесса

Теперь определим архитектуру узлов. Новички часто не знают, какие узлы использовать (и даже продвинутые пользователи часто просят модели сделать первый набросок дизайна, потому что это быстро). Основная структура:

- Start: узел входа данных, принимающий сырой ввод `user_text`.
- Question Classifier: «мозг + диспетчер». Он анализирует `user_text` и выдаёт одну из четырёх меток намерения.
- Condition: «маршрутизирующий вентиль». Он направляет поток на основе метки классификатора в соответствующую ветвь обработки.
- Четыре параллельных узла LLM (`LLM_BuyFood`, `LLM_Complain`, `LLM_Chitchat`, `LLM_Other`): каждый получает исходный вопрос, но отвечает по-разному на основе персоны своего SYSTEM-промпта.
- Variable Aggregator: после обработки в ветвях агрегирует вывод одной активированной ветви в единую переменную `final_reply` для стабильной структуры вывода.
- Output: финальный структурированный вывод (например JSON), включающий намерение, исходный запрос и ответ, подходящий для нисходящей интеграции/отладки.

#### Реализация оркестрации рабочего процесса

В этом руководстве мы выбираем Workflow (а не Chatflow). Выберите User Input:

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image59.png)

Затем нажмите Start -> User Input и определите строковую переменную `user_text` как глобальный источник входа потока.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image60.png)

Сохраните и нажмите Test Run (справа вверху). Вам будет предложено предоставить тестовый текст.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image61.png)

Далее нажмите `+` после узла ввода и добавьте Question Classifier. Настройте четыре метки, каждую с чётким описанием и примерами:

- `buy_food`: пользователь явно хочет купить/заказать еду.
- `complain`: пользователь жалуется/злится, обычно с недовольством.
- `chitchat`: пользователь болтает, обсуждает, что поесть, спрашивает рекомендации.
- `other`: не относится к сценарию еды или трудно классифицировать.

Также задайте промпт в ADVANCED SETTING для поведения классификации. Пример промпта:

```text
Choose the most appropriate label from buy_food / complain / chitchat / other.
If user both complains and orders, prioritize core emotion: if dissatisfaction is primary, classify as complain.
If complaint is minor and primary intent is ordering, classify as buy_food.
If truly hard to determine, use other as fallback.
```

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image62.png)

После настройки используйте значок воспроизведения в правом верхнем углу этого узла, чтобы протестировать классификацию.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image63.png)

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image64.png)

Из OUTPUT мы видим, что классификация точна. Протестируйте несколько типов ввода, чтобы проверить стабильность классификатора.

Далее соедините классификатор с нисходящими ветвями LLM. Например, когда `label == "buy_food"`, направляйте в `LLM_BuyFood`.
Создайте четыре узла LLM и задайте разные SYSTEM-промпты:

- LLM_BuyFood (помощник по заказу):

  Вы — помощник по заказу. Требования:
  1. Подтвердите, что хочет заказать пользователь.
  2. Если информация неполная, вежливо задавайте уточняющие вопросы.
  3. Сохраняйте вежливый и лаконичный тон.

- LLM_Complain (специалист поддержки):

  Вы — специалист поддержки клиентов в общепите, обрабатывающий жалобы. Требования:
  1. Искренне извинитесь.
  2. Кратко объясните вероятные причины (без перекладывания вины).
  3. Предоставьте чёткое решение для следующего шага.

- LLM_Chitchat (собеседник):

  Вы — непринуждённый помощник по рекомендации еды. Требования:
  1. Используйте расслабленный дружелюбный тон.
  2. Дайте 1–3 простые рекомендации.
  3. Если предпочтений нет, предложите варианты разных стилей.

- LLM_Other (вежливый привратник):

  Вы — помощник по заказу еды, сфокусированный только на темах еды. Для нерелевантного ввода пользователя:
  1. Вежливо объясните границы.
  2. Верните пользователя к основному сценарию.

Важно: в каждом узле после настройки SYSTEM-промпта включите сопоставление переменной USER-промпта. Нажмите `{x}`, выберите `user_text` как переменную ввода пользователя и добавьте перед ней `user input:`, чтобы обозначить семантику источника. Во время генерации ответа модель использует как первоначальный ввод пользователя, так и системный промпт.

Как всегда, нажмите значок воспроизведения на уровне узла, чтобы протестировать с образцом ввода, например «Хочу пузырьковый молочный чай», и проверить поведение.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image65.png)

Далее обработайте выводы параллельных ветвей. В `Variable Aggregator` найдите `ASSIGN VARIABLES` и добавьте выводы ветвей один за другим.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image66.png)

Теперь агрегируйте финальный вывод, включающий ввод пользователя, намерение и ответ. Поскольку это Workflow (а не Chatflow), узла Answer для этой конкретной структуры нет, поэтому мы можем использовать узел Template для эквивалентной упаковки вывода. В области переменных укажите результат намерения, ввод пользователя и финальный ответ агрегатора. В CODE напишите финальный JSON-шаблон:

- `intent` <- `class_name`
- `original_text` <- `user_text`
- `final_reply` <- `variable_aggregator`

```text
{
  "intent": "{{ intent }}",
  "original_text": "{{ original_text }}",
  "reply": {{ final_reply }}
}
```

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image67.png)

Наконец добавьте узел Output, и вся настройка завершена.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image68.png)

#### Тестирование рабочего процесса во время выполнения

Готово. Теперь запустите этот рабочий процесс и понаблюдайте за различным поведением для разных вводов:

- Ввод (заказ): «Дайте мне один комбо с острым куриным бургером и большую колу.»
  - Путь: `buy_food` -> `LLM_BuyFood`
  - Ответ на выходе: «Конечно, один комбо с острым куриным бургером и большая кола записаны. Хотите заменить картофель фри в комбо?»
- Ввод (жалоба): «Почему вы такие медленные? Я жду уже больше часа!»
  - Путь: `complain` -> `LLM_Complain`
  - Ответ на выходе: «Нам искренне жаль за долгое ожидание. Это была наша ошибка, и она доставила вам неприятный опыт. Мы срочно проверяем статус вашей доставки и организуем компенсацию. Спасибо за ваше терпение и обратную связь.»
- Ввод (болтовня): «Что сегодня полезнее съесть?»
  - Путь: `chitchat` -> `LLM_Chitchat`
  - Ответ на выходе: «Если вы предпочитаете более здоровые варианты, можете попробовать нашу серию лёгких салатов или куриную грудку на гриле с овощами. Вы предпочитаете более лёгкий вкус или более насыщенный? Я могу порекомендовать конкретнее.»
- Ввод (не по теме): «Помоги придумать шутку для завтрашней встречи.»
  - Путь: `other` -> `LLM_Other`
  - Ответ на выходе: «Звучит весело, но я в основном специализируюсь на рекомендациях еды и заказах. Если хотите заказать что-нибудь в награду за свой труд, я всегда готов помочь.»

> Скрытый баг: если вы столкнулись со странными проблемами `aggregation group`, это, вероятно, встроенный баг Dify. Он может срабатывать при определённых последовательностях операций. Если AGGREGATION GROUP был включён, а затем выключен, остаточная конфигурация группы может сохраниться и вызвать ошибки (например, связанные с параметрами `any`), даже когда переключатель выглядит выключенным. Решение: удалите этот узел и создайте его заново.

После запуска в Test Run вы можете изучить полный путь выполнения. Он должен следовать правильной ветви и выдавать ожидаемый финальный результат. Полный поток завершён.

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image69.png)

## 3.1 Рабочие процессы для платформ соцсетей

1. Рабочий процесс распространения контента по платформам в один клик (сложный)
   1. Идея: рассматривать один основной черновик как «сырьё», автоматически создавая адаптированные под платформы варианты.
   2. Реализация: ввод статьи `Start` -> полировка `LLM` -> параллельные узлы `LLM` для экспертов по платформам (например эксперт по виральным текстам Xiaohongshu, профессиональный отвечающий Zhihu) -> `Iterator` для правил форматирования платформ -> `Variable Aggregator` слияние -> `Answer` вывод всех версий.
2. Планировщик горячих тем и генератор первого черновика (средний)
   1. Идея: автоматически улавливать тренды и быстро генерировать предложения тем и черновики.
   2. Реализация: ключевое слово `Start` -> поисковый API `Tool` для данных о трендах -> `LLM` извлечение 3–5 тем -> `LLM` генерация плана/черновика.
3. Интеллектуальная классификация комментариев и помощник ответов (сложный)
   1. Идея: классифицировать настроение/намерение комментариев и генерировать категоризированные предложения ответов.
   2. Реализация: `HTTP Request` для получения комментариев -> `Question Classifier`/`LLM` многометочная классификация (позитив/вопрос/жалоба/спам) -> `Condition` маршрутизация -> параллельное составление ответов `LLM` -> `Answer`.
4. Автогенератор сценария и раскадровки короткого видео (сложный)
   1. Идея: по трендовой теме/описанию продукта автоматически генерировать сценарий, раскадровку и рекомендуемые теги.
   2. Реализация: тема `Start` -> `LLM` генерация идеи сценария -> второй `LLM` декомпозиция сцен (визуал/диалоги/длительность) -> `Tool` генерация образца TTS -> `Variable Aggregator` слияние -> `Answer` структурированный сценарий.
5. Суммаризатор вопросов и ответов во время прямой трансляции (средний)
   1. Идея: обрабатывать комментарии трансляции почти в реальном времени и резюмировать ключевые вопросы/настроение аудитории.
   2. Реализация: `HTTP Request` потоковые комментарии -> `Iterator` оконные пакеты -> `LLM` резюме трендов по окну -> `Answer`/`Webhook` вывод ведущему.

## 3.2 Рабочие процессы для рабочих задач

1. Система интеллектуального протокола встречи и автораспределения задач (сложный)
   1. Идея: извлекать протокол из транскрипта и автоматически создавать задачи.
   2. Реализация: текст встречи `Start` -> `LLM` резюме повестки/выводов -> `Parameter Extractor` пункты действий (задача/ответственный/срок) -> `LLM` форматирование письма с протоколом -> параллельные `HTTP Request` создание задач в Jira/Trello/Feishu.
2. Помощник пакетного отбора резюме и первичной оценки (средний)
   1. Идея: парсить резюме, оценивать соответствие и генерировать вопросы для собеседования.
   2. Реализация: `Start` загрузка резюме + JD -> `Document Extractor` парсинг текста -> `LLM` HR-стиль оценки соответствия -> для высоких совпадений другой `LLM` генерирует глубокие вопросы для собеседования.
3. Перевод писем на несколько языков в один клик и черновик ответа (простой)
   1. Идея: автоперевод входящего письма и составление черновика ответа.
   2. Реализация: письмо `Start` -> `LLM` определение языка + перевод -> `LLM` тезисы ответа -> `LLM` обратный перевод и полировка.
4. Автоагрегация еженедельных/месячных отчётов и генерация инсайтов (сложный)
   1. Идея: подключить несколько источников данных и автоматически генерировать структурированный отчёт.
   2. Реализация: параллельные вызовы `HTTP Request`/`Tool` к API CRM/Git/PM -> `Code`/`LLM` очистка/расчёт данных -> `LLM` нарратив трендов/моментов/рисков -> `Answer` богатый отчёт.
5. Интеллектуальная проверка контрактов/документов и извлечение ключевых пунктов (средний)
   1. Идея: быстро проверять юридические/деловые документы, выявлять риски и извлекать ключевые пункты.
   2. Реализация: контракт PDF `Start` -> `Document Extractor` извлечение текста -> `LLM` проверка пунктов юридическим экспертом -> `Parameter Extractor` извлечение дат/сумм/сторон -> `Answer` резюме рисков + ключевая таблица.

1. Глубокий анализ научной статьи и генератор заметок (сложный)
   1. Идея: загрузить PDF статьи и автоматически генерировать структурированные заметки.

   1. Идея: автоматически планировать детальный маршрут на основе предпочтений пользователя.
   2. Реализация: `Start` направление/дни/бюджет/интересы -> `Tool` поисковые/картографические API -> `LLM` ежедневный маршрут с расписанием/активностями/оценкой бюджета.
3. Интерактивный партнёр для разговорной практики иностранного языка (простой)
   1. Идея: бот для ролевого диалога с исправлением грамматики.

5. Советник по отслеживанию фитнеса/питания и корректировке (средний)
   1. Идея: анализировать ежедневные логи питания/тренировок и выдавать рекомендации по питанию/тренировкам.
   2. Реализация: текстовый лог `Start` (например обед + запись о тренировке) -> `Parameter Extractor` структурный парсинг -> `LLM` анализ фитнес-тренера по питанию/объёму тренировок -> сравнение с долгосрочными целями -> рекомендации по микрокорректировкам.

# 6. Ограничения платформ рабочих процессов

Платформы рабочих процессов (low-code) не являются универсальными решениями. Они дружественны к бизнесу и снижают порог прямого кодирования, но с другой стороны, «low code» может также быть «high code»: пользователям всё ещё нужно понимать концепции платформы, правила и логику работы. Это само по себе является затратой на обучение.

Вы можете спросить: многие простые рабочие процессы — это просто цепочки вызовов функций вокруг API моделей. В коде несколько строк могут это решить. Зачем использовать тяжёлые визуальные обёртки и делать вызов API более громоздким?

Это справедливое замечание. С быстрым прогрессом vibe coding и AI-генерации кода прямое чтение или генерация кода иногда могут быть эффективнее. В идеале мы должны иметь возможность управлять логикой приложения напрямую на естественном языке. Но у текущих платформ рабочих процессов всё ещё есть неизбежный «средний слой» между намерением пользователя и финальной реализацией. Изучение этого среднего слоя требует времени. В идеале будущие платформы должны поддерживать полное управление через диалог с AI как для построения рабочих процессов, так и для контроля на уровне параметров.

Тем не менее, владение этими платформами всё больше становится базовым навыком, подобно офисному ПО: широко используемым и практически ценным в бизнес-контексте.

В последующих продвинутых курсах мы представим платформы разработки рабочих процессов и RAG на уровне кода, где вы сможете сравнить компромиссы сложности/гибкости между разными стилями реализации. (Также учтите, что многие простые диалоговые приложения и вложенные логики всё же просты в форме рабочего процесса.)

# [Баг] Как исправить ошибки HTTP Request

Обращайтесь к этому разделу только если вы столкнулись с проблемой, показанной ниже. В противном случае вы можете проигнорировать эту часть.

Иногда вы развёртываете Dify на собственном сервере, где публичный эндпоинт работает по HTTP (а не HTTPS). Если вы обращаетесь к сервису только по HTTP, вы можете увидеть ошибки, подобные этой (включите отладочную информацию F12 в браузере, чтобы изучить):

![](/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image98.png)

Корневая причина: Dify развёрнут на сервере, который поддерживает HTTP, но не HTTPS.
HTTPS (HyperText Transfer Protocol Secure) добавляет шифрование SSL/TLS поверх HTTP, по сути это более безопасный HTTP.

Чтобы поддержать HTTPS, распространённые варианты таковы:

- Перенаправлять запросы через другой сервис (например обратный прокси на nginx с включёнными сертификатами), или
- Привязать домен и выпустить TLS-сертификат.

Это относительно сложно, поэтому здесь мы используем Zeabur в качестве шлюза сетевого перенаправления.

Страницы Zeabur по умолчанию доступны по HTTPS. Поэтому если вы перенаправите исходный домен на домен Zeabur, проблема будет исправлена.

- Исходный URL: `http://{DIFY_API_URL}/v1/chat-messages`
- Новый URL: `https://{DIFY_NEW_API_URL}.zeabur.app/v1/chat-messages`

Вам нужно лишь заменить домен URL (публичный IP/домен) на ваш развёрнутый домен Zeabur. Перенаправление преднастроено в сервисе.

Если интересно, вы можете развернуть собственный сервис перенаправления на Zeabur. Создайте сервис на Python и используйте следующий код. После развёртывания вы получите HTTPS-эндпоинт, который работает нормально.

После развёртывания установите порт прослушивания сервиса на локальный `8080` и откройте этот порт публично.

Примечание: замените `{DIFY_API_URL}` на ваш реальный Dify API URL.

```python
from flask import Flask, request, Response
import requests

app = Flask(__name__)

TARGET_BASE_URL = "{DIFY_API_URL}"
LISTEN_PORT = 8080

@app.route('/', defaults={'path': ''}, methods=['GET', 'POST', 'PUT', 'DELETE', 'PATCH', 'OPTIONS', 'HEAD'])
@app.route('/<path:path>', methods=['GET', 'POST', 'PUT', 'DELETE', 'PATCH', 'OPTIONS', 'HEAD'])
def proxy_request(path):
    target_url = f"{TARGET_BASE_URL}/{path}"
    if request.query_string:
        target_url += f"?{request.query_string.decode('utf-8')}"

    headers = {key: value for key, value in request.headers if key.lower() not in ['host', 'connection', 'content-length', 'accept-encoding']}

    try:
        resp = requests.request(
            method=request.method,
            url=target_url,
            headers=headers,
            data=request.get_data(),
            cookies=request.cookies,
            allow_redirects=False,
            timeout=30
        )

        excluded_headers = ['content-encoding', 'content-length', 'transfer-encoding', 'connection']
        response_headers = [(name, value) for name, value in resp.raw.headers.items() if name.lower() not in excluded_headers]

        return Response(resp.content, resp.status_code, response_headers)

    except requests.exceptions.RequestException as e:
        print(f"Error forwarding request to {target_url}: {e}")
        return Response(f"Proxy Error: Could not reach target server or invalid response: {e}", status=502)
    except Exception as e:
        print(f"An unexpected error occurred: {e}")
        return Response(f"Internal Proxy Error: {e}", status=500)

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=LISTEN_PORT, debug=True)
```
